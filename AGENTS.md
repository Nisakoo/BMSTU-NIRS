# smeshariki-ai

Этот репозиторий содержит проект НИРС «Смешарики AI» со следующими логическими частями:

- `frontend/` — пользовательский интерфейс;
- `backend/` — API, runtime агента и серверная бизнес-логика;
- RAG — внутренний инструмент (tool) агента, реализуемый внутри backend;
- `docker/` — единая точка входа для контейнерного запуска backend и его инфраструктурных зависимостей.

## Именование

1. Публичное имя проекта и Python-дистрибутива — `smeshariki-ai`.
2. Имя импортируемого Python-пакета backend — `smeshariki_ai`.
3. Не использовать дефис в имени импортируемого Python-модуля.

## Архитектурные правила

1. Frontend запускается отдельно от Docker-окружения backend. Не добавлять frontend в `docker/compose.yaml`, если пользователь явно не попросил изменить это правило.
2. Агент является частью backend, а не отдельным сервисом верхнего уровня.
3. RAG подключается к агенту через интерфейс инструмента. Не оформлять RAG как самостоятельное пользовательское приложение или отдельный публичный API без явной необходимости.
4. Векторное хранилище, база данных и другие инфраструктурные зависимости RAG могут быть отдельными контейнерами, но orchestration и обращение к ним остаются ответственностью backend.
5. Все файлы контейнерного запуска — Compose-файлы, Dockerfile, примеры переменных окружения и связанные скрипты — хранить в `docker/`.
6. Команды запуска из документации должны выполняться из корня репозитория либо явно указывать путь к файлу в `docker/`.
7. Секреты не коммитить. В репозитории хранить только шаблон `docker/.env.example`; локальный `docker/.env` должен игнорироваться Git.

## Процесс разработки

1. Разработка ведётся по SDD (Spec-Driven Development) через локальный skill `.agents/skills/sdd/SKILL.md`.
2. На этапе `specify` спецификация должна фиксировать требования, ограничения, основные сценарии, проверяемые критерии приёмки и способы проверки каждого требования. Новые тесты на этом этапе не реализуются.
3. Код и тесты должны соответствовать согласованной спецификации. При изменении поведения сначала обновлять спецификацию, затем реализацию и тесты в порядке, заданном SDD skill.
4. `Makefile` является единой точкой входа для стандартных команд проекта:
   - `make run` — запуск проекта;
   - `make test` — запуск полного набора автоматических тестов продукта;
   - `make lint` — проверка Python-кода backend через Ruff;
   - `make format` — автоматическое исправление и форматирование Python-кода
     backend через Ruff.
5. Автоматические тесты должны проверять поведение Python-кода продукта. Не добавлять тесты, которые проверяют только структуру каталогов, наличие README, служебных файлов или конфигурации репозитория.
6. Пока тесты продукта не настроены, `make test` должен явно сообщать об этом и завершаться с ошибкой, а не имитировать успешную проверку.
7. Краткое состояние SDD-изменений хранится в `specs/status.yaml`. Файл содержит
   только список уникальных пар `name`/`status`, без прогресса отдельных задач.
8. Допустимые статусы спецификации: `draft`, `in-queue`, `in-progress` и `done`.
   Статус `done` устанавливается только после успешного этапа `verify`.
9. Читать `specs/status.yaml` можно напрямую. Создавать, обновлять и удалять
   записи разрешено только командами Create, Update и Delete скрипта
   `.agents/skills/sdd/scripts/spec_status.py`; ручное редактирование запрещено.

## Коммиты

1. Названия коммитов должны соответствовать Conventional Commits: `<type>(<scope>): <description>`. Scope необязателен.
2. Использовать стандартные типы: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `build`, `ci`, `perf`, `style` и `revert`.
3. Для обратно несовместимых изменений добавлять `!` после типа или scope и описывать изменение в `BREAKING CHANGE`.

## Согласованная архитектура

1. Приложение строится как модульный монолит: API, runtime агента, бизнес-логика и реализация RAG находятся в одном backend-приложении.
2. Frontend взаимодействует с backend по HTTP. Для потоковой передачи ответов используется SSE, если спецификация конкретного сценария не требует другого транспорта.
3. Агент работает через отдельный сервисный интерфейс и не должен быть связан напрямую с HTTP-слоем.
4. Интеграция с LLM скрывается за внутренней абстракцией, чтобы поставщика модели можно было заменить без изменения бизнес-логики и интерфейса RAG.
5. RAG предоставляется агенту как инструмент `search_knowledge`. Агент самостоятельно решает, когда вызвать этот инструмент.
6. Внутри RAG разделяются индексация документов и поиск. Загрузка и переиндексация запускаются командой backend, а не отдельным постоянно работающим приложением.
7. Векторное хранилище является инфраструктурной зависимостью backend и может работать в отдельном контейнере.
8. Для первой версии используется простой цикл tool calling. LangGraph добавляется только при появлении требований к сложным ветвящимся процессам, длительному состоянию, возобновлению выполнения или human-in-the-loop.
9. LLM, embeddings и внешние хранилища в модульных тестах заменяются детерминированными тестовыми реализациями. Интеграционные тесты отдельно проверяют реальные инфраструктурные адаптеры.

## Реализованный runtime агента

1. Внутренний класс `Agent` получает `LLMProvider`, `ToolRegistry` и
   неизменяемый `AgentConfig` через конструктор. Runtime не читает переменные
   окружения и не создаёт собственные инфраструктурные зависимости.
2. Асинхронный `Agent.run(history, request)` выполняет собственный цикл tool
   calling: не более одного вызова инструмента на ответ LLM и по умолчанию не
   более четырёх итераций. Пустая строка является корректным финальным ответом.
3. Интеграция с моделью определяется внутренним асинхронным контрактом
   `LLMProvider`. Текущая реализация `FakeLLMProvider` не обращается к сети и
   всегда возвращает успешный пустой ответ. SDK поставщиков LLM не входят в
   runtime.
4. Каждый инструмент наследуется от `Tool`, объявляет уникальное имя, описание,
   Pydantic-модель аргументов и асинхронное выполнение. `ToolRegistry` строит
   определения инструментов, валидирует аргументы и преобразует неизвестные
   инструменты, ошибки валидации и исполнения в безопасный `ToolResult`.
5. Runtime журналирует только стабильные события жизненного цикла, номера
   итераций, имена и статусы инструментов и типы ошибок. Текст запросов и
   истории, аргументы и результаты инструментов и текст исключений в лог не
   передаются.
6. Runtime не использует LangChain и LangGraph. Инструмент `search_knowledge`,
   реальный LLM-провайдер и потоковая передача реализуются отдельными
   согласованными изменениями.

## Реализованные диалоги и HTTP API

1. `HistoryStore` задаёт асинхронный контракт создания диалога, чтения истории
   и атомарного добавления сообщений. `InMemoryHistoryStore` создаёт UUIDv4 и
   хранит независимые истории только в памяти процесса; после рестарта данные
   теряются.
2. `AgentService` находится в application-слое, получает готовые `Agent` и
   `HistoryStore`, не зависит от FastAPI и не читает environment. Пакет
   `dialogs` отвечает за контракт и реализацию истории. Запросы одного
   `dialog_id` выполняются последовательно, а разные диалоги не блокируют друг
   друга.
3. `POST /api/v1/dialogs` создаёт диалог и возвращает `201 Created`, `Location`
   и JSON с `dialog_id`. Идентификатор является UUID, но не механизмом
   аутентификации.
4. `POST /api/v1/dialogs/{dialog_id}/messages` принимает непустой `request`,
   ставит agent loop в in-memory очередь и немедленно возвращает пустой
   `202 Accepted`. `dialog_id` обязателен в URL; cookie для выбора диалога не
   используется.
5. После успешного фонового запуска сервис атомарно сохраняет только сообщения
   пользователя и ассистента. Tool calls и tool results в историю диалога не
   попадают; при ошибке история не изменяется.
6. Фоновые задачи отслеживаются и отменяются при shutdown через FastAPI
   lifespan. События журналируются с `dialog_id` без текста запросов, истории и
   ответов.
7. Текущая версия не предоставляет получение результата или истории по HTTP,
   не использует SSE и `StreamingResponse` и не добавляет CORS middleware.
   Bootstrap собирает приложение с `FakeLLMProvider` и пустым `ToolRegistry`.

## Согласованные технологии

- Python 3.12 — runtime backend.
- `uv` — обязательный инструмент для установки Python, управления виртуальным окружением и зависимостями, синхронизации lock-файла и запуска Python-команд. Не использовать `pip`, `poetry` или `pipenv` в стандартном процессе разработки.
- FastAPI и Pydantic — HTTP API, валидация входных и выходных данных и SSE-интерфейс.
- Qdrant — векторное хранилище и поиск для RAG.
- Pytest — модульные и интеграционные тесты backend.
- Ruff — линтинг, проверка форматирования и автоформатирование Python-кода.
- Docker Compose — локальный запуск backend и его инфраструктурных зависимостей.
- Make — единый интерфейс запуска и тестирования из корня репозитория.

Конкретные структура репозитория, версии зависимостей, контракты API и Docker-конфигурация определяются и добавляются только через отдельные согласованные SDD-спецификации. Не создавать структуру будущей реализации на основании этого раздела без такой спецификации.
