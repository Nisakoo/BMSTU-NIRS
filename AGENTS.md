# smeshariki-ai

Этот репозиторий содержит проект НИРС «Смешарики AI» со следующими логическими частями:

- `frontend/` — пользовательский интерфейс;
- `backend/` — API, runtime агента и серверная бизнес-логика;
- RAG — внутренний инструмент (tool) агента, реализуемый внутри backend;
- `docker/` — единая точка входа для контейнерного запуска Caddy, frontend,
  backend и его инфраструктурных зависимостей.

## Именование

1. Публичное имя проекта и Python-дистрибутива — `smeshariki-ai`.
2. Имя импортируемого Python-пакета backend — `smeshariki_ai`.
3. Не использовать дефис в имени импортируемого Python-модуля.

## Архитектурные правила

1. Основной запуск frontend и backend выполняется одним Docker Compose проектом:
   Caddy является внешней точкой входа, Nginx раздаёт собранный frontend в
   отдельном контейнере. Vite dev server можно запускать отдельно для разработки.
2. Агент является частью backend, а не отдельным сервисом верхнего уровня.
3. RAG подключается к агенту через интерфейс инструмента. Не оформлять RAG как самостоятельное пользовательское приложение или отдельный публичный API без явной необходимости.
4. Векторное хранилище, база данных и другие инфраструктурные зависимости RAG могут быть отдельными контейнерами, но orchestration и обращение к ним остаются ответственностью backend.
5. Все файлы контейнерного запуска — Compose-файлы, Dockerfile, примеры переменных окружения и связанные скрипты — хранить в `docker/`.
6. Команды запуска из документации должны выполняться из корня репозитория либо явно указывать путь к файлу в `docker/`.
7. Секреты не коммитить. В репозитории хранить только шаблон `docker/.env.example`; локальный `docker/.env` должен игнорироваться Git.

## Процесс разработки

1. Разработка ведётся по SDD (Spec-Driven Development) через локальный skill `.agents/skills/sdd/SKILL.md`.
2. На этапе `specify` спецификация должна фиксировать требования, ограничения, основные сценарии, проверяемые критерии приёмки и способы проверки каждого требования. Новые тесты на этом этапе не реализуются.
3. Код и тесты должны соответствовать согласованной спецификации. При изменении поведения сначала обновлять спецификацию, затем реализацию и тесты в порядке, заданном SDD skill.
4. `Makefile` является единой точкой входа для стандартных команд проекта:
   - `make run` — запуск проекта;
   - `make migrate` — применение миграций базы данных через Compose-сервис
     `migrate`;
   - `make test` — запуск полного набора автоматических тестов продукта;
   - `make lint` — проверка Python-кода backend через Ruff;
   - `make format` — автоматическое исправление и форматирование Python-кода
     backend через Ruff.
5. Автоматические тесты должны проверять поведение Python-кода продукта. Не добавлять тесты, которые проверяют только структуру каталогов, наличие README, служебных файлов или конфигурации репозитория.
6. Пока тесты продукта не настроены, `make test` должен явно сообщать об этом и завершаться с ошибкой, а не имитировать успешную проверку.
7. Краткое состояние SDD-изменений хранится в `specs/status.yaml`. Файл содержит
   только список уникальных пар `name`/`status`, без прогресса отдельных задач.
8. Допустимые статусы спецификации: `draft`, `in-queue`, `in-progress` и `done`.
   Статус `done` устанавливается только после успешного этапа `verify`.
9. Читать `specs/status.yaml` можно напрямую. Создавать, обновлять и удалять
   записи разрешено только командами Create, Update и Delete скрипта
   `.agents/skills/sdd/scripts/spec_status.py`; ручное редактирование запрещено.

## Документация архитектуры и контрактов

1. `docs/README.md` является обязательным глобальным каталогом архитектуры,
   фактической реализации и контрактов проекта. Детали компонентов размещаются
   на отдельных тематических страницах в `docs/`.
2. Любое SDD-изменение, которое добавляет, удаляет или меняет компонент,
   архитектурную границу, существенную деталь реализации либо внутренний или
   внешний контракт, должно обновить соответствующую тематическую страницу и,
   если меняется глобальная карта, `docs/README.md` в рамках того же изменения.
3. Каталог содержит только архитектурные сведения, необходимые пояснения по
   реализации и краткие контракты. Не переносить в него целиком требования,
   сценарии, критерии приёмки, планы задач или verification-отчёты; вместо этого
   давать ссылки на SDD-артефакты.
4. Mermaid-диаграммы можно и нужно добавлять, когда они заметно упрощают
   понимание архитектуры, связей или последовательности взаимодействий. Не
   добавлять диаграммы формально или когда они только дублируют текст.
5. При расхождении каталога с последней согласованной спецификацией и успешным
   результатом verify источником истины являются SDD-артефакты.

## Коммиты

1. Названия коммитов должны соответствовать Conventional Commits: `<type>(<scope>): <description>`. Scope необязателен.
2. Использовать стандартные типы: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `build`, `ci`, `perf`, `style` и `revert`.
3. Для обратно несовместимых изменений добавлять `!` после типа или scope и описывать изменение в `BREAKING CHANGE`.

## Согласованная архитектура

1. Приложение строится как модульный монолит: API, runtime агента, бизнес-логика и реализация RAG находятся в одном backend-приложении.
2. Frontend взаимодействует с backend по HTTP. Для потоковой передачи ответов используется SSE, если спецификация конкретного сценария не требует другого транспорта.
3. Агент работает через отдельный сервисный интерфейс и не должен быть связан напрямую с HTTP-слоем.
4. Интеграция с LLM скрывается за внутренней абстракцией, чтобы поставщика модели можно было заменить без изменения бизнес-логики и интерфейса RAG.
5. RAG предоставляется агенту как инструмент `search_knowledge`. Агент самостоятельно решает, когда вызвать этот инструмент.
6. Внутри RAG разделяются индексация документов и поиск. Загрузка и переиндексация запускаются командой backend, а не отдельным постоянно работающим приложением.
7. Векторное хранилище является инфраструктурной зависимостью backend и может работать в отдельном контейнере.
8. Для первой версии используется простой цикл tool calling. LangGraph добавляется только при появлении требований к сложным ветвящимся процессам, длительному состоянию, возобновлению выполнения или human-in-the-loop.
9. LLM, embeddings и внешние хранилища в модульных тестах заменяются детерминированными тестовыми реализациями. Интеграционные тесты отдельно проверяют реальные инфраструктурные адаптеры.

## Реализованный runtime агента

1. Внутренний класс `Agent` получает `LLMProvider`, `ToolRegistry` и
   неизменяемый `AgentConfig` через конструктор. Runtime не читает переменные
   окружения и не создаёт собственные инфраструктурные зависимости.
2. Асинхронный поток `Agent.run(history, request)` выполняет собственный цикл
   tool calling и передаёт только фрагменты финального текста и терминальный
   ответ. Допускается не более одного вызова инструмента на ответ LLM и по
   умолчанию не более четырёх итераций; пустая строка является корректным
   финальным ответом.
3. Интеграция с моделью определяется внутренним асинхронным контрактом
   `LLMProvider`. Контракт, `FakeLLMProvider`, `LiteLLMProvider` и связанные с
   провайдерами типы находятся в отдельном подмодуле `agent.providers`; типы
   LiteLLM SDK не входят в `Agent`.
4. Каждый инструмент наследуется от `Tool`, объявляет уникальное имя, описание,
   Pydantic-модель аргументов и асинхронное выполнение. `ToolRegistry` строит
   определения инструментов, валидирует аргументы и преобразует неизвестные
   инструменты, ошибки валидации и исполнения в безопасный `ToolResult`.
5. Runtime журналирует только стабильные события жизненного цикла, номера
   итераций, имена и статусы инструментов и типы ошибок. Текст запросов и
   истории, аргументы и результаты инструментов и текст исключений в лог не
   передаются.
6. Production bootstrap использует `LiteLLMProvider`, который получает
   неизменяемый `LiteLLMProviderConfig` извне и вызывает только асинхронный
   `litellm.acompletion`. Провайдер не читает environment, не запускает
   синхронный `completion` в системном потоке и не хранит изменяемое состояние
   отдельного запроса.
7. `LiteLLMProvider` переводит доменные сообщения, function tools и tool results
   в Chat Completions format, вызывает `litellm.acompletion(..., stream=True)`,
   передаёт текстовые фрагменты и собирает фрагментированный tool call в
   доменный `LLMResponse`. Инструменты исполняются только `Agent` через
   `ToolRegistry`; LiteLLM auto-execution, Router, Proxy и callbacks не
   используются.
8. Ошибки LiteLLM и некорректные внешние ответы преобразуются в безопасную
   `LLMProviderError` без содержимого запроса, ответа, tool payload, credentials
   и текста внешнего исключения. Отмена asyncio-задачи распространяется без
   преобразования.
9. Runtime не использует LangChain и LangGraph. `FakeLLMProvider` остаётся
   детерминированной потоковой реализацией без сети для тестов. Инструмент
   `search_knowledge` реализуется отдельным согласованным изменением.

## Реализованная конфигурация backend

1. Общий модуль `smeshariki_ai.config` определяет единственный корневой
   неизменяемый `Config` с подконфигами `agent: AgentConfig`,
   `llm: LiteLLMProviderConfig` и `logging: LoggingConfig` и функцию
   `load_config`.
2. Только `load_config` читает `os.environ`. ASGI-entrypoint вызывает его один
   раз и передаёт готовый `Config` в `create_application`; bootstrap и
   внутренние компоненты environment не читают.
3. Корневой `Config` является агрегатом, а не module-level singleton. Он не
   создаётся при импорте `smeshariki_ai.config`; для тестов loader принимает
   явный `Mapping[str, str]`.
4. Модели подконфигов принадлежат настраиваемым компонентам. Composition root
   передаёт `Agent` только `config.agent`, а `LiteLLMProvider` — только
   `config.llm`; внутренние компоненты не получают и не импортируют корневой
   `Config`.
5. Python-код не загружает `.env` как файл и не использует
   `pydantic-settings`: локальный `docker/.env` читает Docker Compose, после
   чего значения поступают backend через process environment.
6. Production-системный промпт хранится в
   `smeshariki_ai/agent/prompts/system.md`, загружается `load_config` как
   package resource и передаётся агенту через `AgentConfig`. Переменная
   `AGENT_SYSTEM_PROMPT` не поддерживается; runtime агента не читает resource
   или environment самостоятельно.

## Реализованное логирование backend

1. `LOG_LEVEL` и `LOG_FORMAT` загружаются только через `load_config`; defaults —
   `INFO` и `human`, альтернативный формат — построчный `json`.
2. HTTP-запросы к API получают серверный `request_id` в `X-Request-ID`.
   Контекст принятого сообщения сохраняется в фоновой задаче; `dialog_id`,
   `call_id` вызова LLM и `tool_call_id` различают связанные операции.
3. Терминальные события HTTP, обработки сообщения, LLM и инструментов содержат
   UTC-время начала, длительность и исход. Для LLM также журналируются
   подтверждённые провайдером числа входных/выходных токенов либо явное
   отсутствие usage.
4. Журнал не содержит пользовательский текст, payload инструментов и секреты.
   Штатный Uvicorn access log отключён; подробный вывод LiteLLM отключён.

## Реализованные диалоги и HTTP API

1. `HistoryStore` задаёт асинхронный контракт хранения сохранённых диалогов:
   атомарное создание диалога вместе с первыми сообщениями, владелец, чтение
   истории и транскрипта, атомарное добавление сообщений, страница списка
   владельца с keyset-курсором и удаление. `PostgresHistoryStore` хранит их в
   PostgreSQL и переживает рестарт; `InMemoryHistoryStore` выполняет тот же
   контракт для тестов. Черновик диалога живёт только в памяти процесса
   (`DialogDrafts`), в базу не записывается и истекает через 30 минут без
   подписок и запусков.
2. `AgentService` находится в application-слое, получает готовые `Agent`,
   `HistoryStore` и `DialogEventBroker`, не зависит от FastAPI и не читает
   environment. Пакет `dialogs` отвечает за контракт и реализацию истории.
   Запросы одного `dialog_id` выполняются последовательно, а разные диалоги не
   блокируют друг друга.
3. `POST /api/v1/dialogs` создаёт черновик и возвращает `201 Created`, `Location`
   и JSON с `dialog_id`. Идентификатор является UUID, но не механизмом
   аутентификации. Диалог сохраняется в PostgreSQL после первого успешного
   ответа агента; заголовок — начало первого запроса (до 60 символов).
   `GET /api/v1/dialogs` (список с `limit` и `cursor`),
   `GET /api/v1/dialogs/{dialog_id}/messages` и
   `DELETE /api/v1/dialogs/{dialog_id}` описаны в `docs/dialogs.md`; удаление
   отменяет запуски диалога и закрывает его SSE-подписки. Спецификация:
   `specs/changes/dialog-history/`.
4. `POST /api/v1/dialogs/{dialog_id}/messages` принимает непустой `request`,
   ставит agent loop в in-memory очередь и немедленно возвращает пустой
   `202 Accepted`. `dialog_id` обязателен в URL; cookie для выбора диалога не
   используется.
5. После успешного фонового запуска сервис атомарно сохраняет (первый запуск
   создаёт диалог, следующие добавляют сообщения) только сообщения
   пользователя и ассистента. Tool calls и tool results в историю диалога не
   попадают; при ошибке история не изменяется.
6. `DialogEventBroker` задаёт асинхронный контракт subscribe, unsubscribe,
   publish и shutdown. `InMemoryDialogEventBroker` владеет подписками и их
   ограниченными очередями; `AgentService` только проверяет диалог и делегирует
   брокеру операции. Production bootstrap создаёт брокер и передаёт его сервису.
7. `GET /api/v1/dialogs/{dialog_id}/events` предоставляет SSE-события `ready`,
   `message_start`, `message_delta`, `message_end` и `message_error`, а также
   heartbeat; на каждом heartbeat сессия перепроверяется
   (`AuthService.verify_session`, без проверки `exp`), и при отзыве поток
   закрывается, а agent loop не отменяется. In-memory подписки передают только
   будущие события и не поддерживают replay через `Last-Event-ID`.
8. Отключение или переполнение подписчика не отменяет agent loop и не блокирует
   сохранение истории. Успешный `message_end` публикуется после атомарного
   сохранения полного ответа; при ошибке после частичного текста история не
   изменяется.
9. Фоновые задачи отслеживаются и отменяются при shutdown через FastAPI
   lifespan; после их завершения брокер закрывает подписки. События
   журналируются с `dialog_id` без текста запросов, фрагментов, истории и
   ответов.
10. `GET /agent_test` отдаёт один самодостаточный HTML с минимальным тестовым
   чатом на vanilla JavaScript. Страница использует существующие API и
   `EventSource`, не требует отдельной сборки и выводит сообщения как текст.
11. Текущая версия не добавляет CORS middleware, отвечает `415` на `messages` с `Content-Type`, отличным от
    `application/json`, и не использует cookie для выбора диалога. Bootstrap
    собирает приложение с настроенным `LiteLLMProvider`, пустым `ToolRegistry`
    и `InMemoryDialogEventBroker`; историю хранит `PostgresHistoryStore` на
    engine аутентификации (при переданном `auth_service` — in-memory
    хранилище); fake-провайдер применяется только как явная
    тестовая зависимость.
12. Диалог принадлежит создателю: владелец хранится в черновике и в `dialogs`,
    `AgentService.start_dialog/submit/subscribe` принимают `user_id` и проверяют
    его в application-слое. Для чужого диалога (в том числе для
    `admin`) `messages` и `events` отвечают `404 Dialog not found.`, как для
    несуществующего; в журнале остаётся `dialog.access.denied` с `dialog_id`,
    `user_id` и `outcome="foreign"` без текста запроса. Спецификация:
    `specs/changes/dialog-ownership/`.

## Реализованный frontend

1. Frontend остаётся vanilla JavaScript приложением в `frontend/src/`.
   Основной Compose запуск собирает его Vite и раздаёт отдельным Nginx
   контейнером через Caddy. Vite dev server остаётся альтернативой для разработки.
   Nginx настраивается `docker/nginx.conf`: относительные редиректы на каталог
   (`absolute_redirect off`), `no-cache` для HTML, `immutable` для `/assets/`.
2. Caddy направляет `/api` в backend без изменения пути, а остальные запросы —
   в Nginx. Браузерный код не содержит cross-origin backend URL. В dev-режиме
   Vite использует `frontend/src/` как root и проксирует `/api`; default target
   — `http://127.0.0.1:8000`, переопределение — `BACKEND_URL` процессу Vite.
3. При загрузке frontend создаёт новый диалог, открывает один `EventSource` и
   блокирует форму до `ready`. `dialog_id` не сохраняется в cookie или
   `localStorage`; перезагрузка создаёт новый in-memory диалог. При ошибке
   создания диалога frontend повторяет попытку через три секунды, сохраняя
   форму заблокированной до успешного `ready`.
4. Пользовательский запрос добавляется в чат только после `202 Accepted`.
   Быстрые `message_*` события буферизуются до завершения POST, delta
   дописываются в одну реплику ассистента, а одновременная отправка нескольких
   запросов блокируется.
5. Динамический пользовательский, модельный и error-текст вставляется только
   как текст, без `innerHTML`. Ошибки создания, отправки и SSE переводят форму
   в явное безопасное состояние; hardcoded ответ отсутствует.
6. `make run` собирает и запускает Caddy, Nginx и backend; `make frontend`
   запускает dev server. `make test` выполняет frontend
   Node-тесты сетевого контракта и состояний UI и полный backend Pytest. Vite
   build создаёт игнорируемый `frontend/dist/`.
7. `/admin/` — вторая HTML-entry того же Vite build и Nginx-контейнера в
   `frontend/src/admin/`: панель администратора. Перед показом страница
   проверяет сессию через `/users/me`: гость переходит на `/login/`, роль
   `user` — в `/`. Статистика и список пользователей загружаются из
   `GET /api/v1/admin/stats` (`docs/admin.md`); показатели агента (диалоги,
   сообщения, активность, качество) остаются demo-данными из `demo-data.js` с
   меткой «демо-данные». Активный раздел навигации синхронизируется с URL hash
   через `aria-current="location"`.
8. `/login/` — вторая HTML-entry того же Vite build и Nginx-контейнера в
   `frontend/src/login/`: страница входа и регистрации в стилистике чата.
   DOM-независимый клиент `frontend/src/auth-api.js` реализует frontend-часть
   контракта аутентификации из `docs/auth.md`: регистрацию, вход, выход и
   получение текущего пользователя на том же origin. Сессия передаётся только
   `HttpOnly` cookie; пароль и сессия не сохраняются в JavaScript-хранилищах.
   После входа страница переходит по роли: `admin` — в `/admin/`, `user` — в
   `/`.
9. Общий модуль `frontend/src/auth-session.js` проверяет сессию через
   `GET /users/me` и один `POST /auth/refresh`; только `401` означает отсутствие
   сессии, сбой backend не ведёт на `/login/`. Чат создаёт диалог лишь для
   вошедшего пользователя, при `401` у операций выполняет один `refresh` и
   повтор, при ошибке SSE проверяет сессию. Кнопка «Выйти» в шапке чата и в
   боковой панели `/admin/` вызывает `POST /auth/logout` и после `204` открывает
   `/login/`; при ошибке страница остаётся на месте с сообщением.
10. `refresh` выполняется под блокировкой Web Locks `smeshariki-auth-refresh`:
    вкладка, дождавшаяся её, сначала повторяет `GET /users/me` и вызывает
    `refresh` только при `401`; без `navigator.locks` поведение прежнее.
    `AuthApi` переводит `429` у входа и регистрации в `too_many_attempts`, а
    `/login/` показывает «Слишком много попыток. Попробуйте позже».
    Спецификация: `specs/changes/auth-rate-limit/`.

## Реализованная аутентификация backend

1. Пакет `smeshariki_ai.auth` содержит транспортно-независимый `AuthService` и
   контракты `UserStore`, `RefreshSessionStore`, `TokenBlacklist`,
   `AttemptLimiter`; сервис не
   зависит от FastAPI, SQLAlchemy и redis-py и не читает environment.
   `api/auth.py` реализует HTTP-контракт из `docs/auth.md` и зависимость
   `current_user`.
2. Access JWT (HS256, 15 минут) и одноразовый refresh-токен (30 дней, в БД
   только SHA-256) передаются только `HttpOnly` cookie. Повторное
   использование refresh-токена и `logout` отзывают всё семейство: access JWT
   содержит claim `fid`, а семейство помечается отозванным в Redis
   (`auth:revoked-family:<fid>`) с TTL не меньше времени жизни access-токена;
   `logout` также заносит `jti` в Redis. Токен без `fid` отклоняется. Сбой
   PostgreSQL или Redis даёт `503` (fail closed).
3. Пользователи и refresh-сессии хранятся в PostgreSQL (`smeshariki_ai.db`,
   SQLAlchemy Core + asyncpg); схема, включая запланированные `dialogs` и
   `messages`, описана в `docs/database.md`. Миграции Alembic применяются
   командой `python -m smeshariki_ai.db.migrate` одноразовым Compose-сервисом
   `migrate`.
4. Ручки диалогов подключают `current_user` на уровне роутера и без
   действительного access-токена отвечают `401` раньше `404`/`422`; без
   `auth_service` — `503`. Диалог принадлежит создателю
   (`docs/dialogs.md`).
   Регистрация и вход принимают только `application/json` (`415`), а
   `ForbiddenOriginMiddleware` отвечает `403` на небезопасные запросы к
   `/api/*` с `Sec-Fetch-Site: cross-site|same-site` (`Origin` с `Host` не
   сравниваются). `AUTH_JWT_SECRET` с префиксом `replace-with-` отклоняется
   `load_config`, а шаблон `docker/.env.example` оставляет его пустым.
   Спецификация: `specs/changes/auth-hardening/`.
5. Роль `admin` не выдаётся через HTTP. `make create-admin LOGIN=<login>`
   запускает `python -m smeshariki_ai.create_admin` в Compose: пароль вводится
   интерактивно, проверяется `Credentials` и хешируется через общую с
   регистрацией функцию `create_user`.
6. Пакет `smeshariki_ai.admin` содержит `AdminStatsService` и контракт
   `AdminStatsStore`; `PostgresAdminStatsStore` считает пользователей по
   `users` и `refresh_sessions`. `GET /api/v1/admin/stats` защищён зависимостью
   `current_admin` (`401`/`403`/`503` до валидации `period`).
7. Вход и регистрация ограничены по частоте счётчиками фиксированного окна в
   Redis (`RedisAttemptLimiter`, `auth:ratelimit:*`): 5 неудач за 15 минут для
   пары «логин + IP», 30 входов в минуту и 10 регистраций в час с IP; порядок
   проверок `403` → `415` → `429` → `422`, ответ `429` с `Retry-After`, при
   недоступном Redis — `503`. Пороги задаёт `load_config`
   (`AUTH_LOGIN_*`, `AUTH_REGISTER_*`). IP берётся из `request.client`;
   Uvicorn доверяет `X-Forwarded-For` только от Caddy (`FORWARDED_ALLOW_IPS`,
   фиксированный адрес в подсети Compose). `Argon2PasswordHasher`
   выполняет не более 4 операций одновременно. Спецификация:
   `specs/changes/auth-rate-limit/`.

## Согласованные технологии

- Python 3.12 — runtime backend.
- Node.js 22 и npm — runtime инструментов разработки frontend и управление
  зафиксированными frontend-зависимостями.
- Vite — dev server, production build и локальный dev proxy `/api` к backend;
  frontend-фреймворк не используется.
- Nginx — раздача production build frontend в отдельном контейнере.
- Caddy — единая локальная HTTP-точка входа и reverse proxy к Nginx и backend.
- `uv` — обязательный инструмент для установки Python, управления виртуальным окружением и зависимостями, синхронизации lock-файла и запуска Python-команд. Не использовать `pip`, `poetry` или `pipenv` в стандартном процессе разработки.
- FastAPI и Pydantic — HTTP API, валидация входных и выходных данных и SSE-интерфейс.
- LiteLLM Python SDK — асинхронная интеграция backend с LLM через внутренний
  адаптер; отдельный LiteLLM Proxy не используется.
- Qdrant — векторное хранилище и поиск для RAG.
- PostgreSQL 17, SQLAlchemy (async Core) с asyncpg и Alembic — постоянное
  хранилище пользователей, истории диалогов и его миграции.
- Redis — blacklist отозванных access-токенов и счётчики ограничения частоты входа.
- PyJWT и argon2-cffi — подпись access JWT и хеширование паролей.
- Pytest — модульные и интеграционные тесты backend.
- Ruff — линтинг, проверка форматирования и автоформатирование Python-кода.
- Docker Compose — локальный запуск всего приложения и инфраструктурных зависимостей.
- Make — единый интерфейс запуска и тестирования из корня репозитория.

Конкретные структура репозитория, версии зависимостей, контракты API и Docker-конфигурация определяются и добавляются только через отдельные согласованные SDD-спецификации. Не создавать структуру будущей реализации на основании этого раздела без такой спецификации.
