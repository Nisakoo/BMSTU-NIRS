# Настраиваемое безопасное логирование backend

## Цель

Сделать журнал backend пригодным для локальной разработки и разбора ошибок: оператор выбирает читаемый человеком либо JSON-формат и уровень подробности,
связывает HTTP-запрос, фоновую обработку диалога, вызовы модели и инструмента по идентификаторам, видит длительность и доступную статистику токенов LLM. При
этом журнал не раскрывает содержимое диалога, аргументы инструментов и секреты. Изменение опирается на действующие контракты
[`backend-config`](../backend-config/spec.md), [`agent-runtime`](../agent-runtime/spec.md), [`litellm-provider`](../litellm-provider/spec.md),
[`agent-dialog-api`](../agent-dialog-api/spec.md) и [`dialog-event-broker`](../dialog-event-broker/spec.md).

## Требования

### Общая схема записи | Поле | Значение | | --- | --- | | `timestamp` | Время события в UTC, ISO 8601 с указанием `Z`; обязательно для каждой записи | | `level`, `logger`, `event` | Уровень, имя источника и стабильное имя события;
  обязательны для каждой записи | | `request_id`, `dialog_id`, `call_id`, `tool_call_id` | Идентификаторы связи; в JSON присутствуют всегда, со значением `null`, когда неприменимы | | `started_at` | Время начала операции в UTC, ISO 8601;
  обязательно в терминальной записи HTTP-запроса, обработки сообщения, LLM-вызова и инструмента | | `duration_ms` | Неотрицательная числовая длительность той же операции от начала до терминального исхода, измеренная монотонными часами | |
  `outcome` | `completed`, `failed` или `cancelled` для терминальных событий; если событие описывает другой исход, используется явно документированное значение | `timestamp` терминальной записи обозначает время окончания операции. Пара
  `started_at`/`duration_ms` позволяет видеть и момент запроса, и его длительность; разница между двумя wall-clock timestamp не используется для расчёта `duration_ms`. В `human` выводятся те же обязательные и применимые поля, но пустые
  идентификаторы можно опускать.
- REQ-001: Корневой неизменяемый `Config` должен включать принадлежащую системе логирования типизированную конфигурацию. Только `load_config` читает `LOG_LEVEL` (`DEBUG`, `INFO`, `WARNING`, `ERROR`) и `LOG_FORMAT` (`human`, `json`) из
  переданного mapping либо process environment. Defaults — `INFO` и `human`. Недопустимые значения приводят к контролируемой ошибке конфигурации до создания приложения; регистр допустимых значений и формат ошибки документируются.
- REQ-002: Production bootstrap применяет готовую конфигурацию логирования один раз без чтения environment внутренними компонентами. Выбранный уровень реально фильтрует события приложения; повторная сборка приложения в тестах не добавляет
  дублирующие обработчики. Настройка учитывает уже созданные обработчики ASGI-сервера и не зависит от того, успел ли он настроить root logger.
- REQ-003: Оба формата пишутся в stdout/stderr контейнера по одной записи на строку и следуют общей схеме выше. `json` даёт валидный JSON-объект с типизированными числами; `human` показывает те же доступные поля в читаемом виде, без
  повторения контекста в тексте события. Имена полей и событий стабильны для обработки журналов.
- REQ-004: Backend генерирует непрогнозируемый `request_id` для каждого входящего HTTP-запроса к API и возвращает его в `X-Request-ID`, в том числе для `201`, `202`, ожидаемых `4xx` и `5xx`. В журнале безопасно отмечаются начало и
  завершение HTTP-запроса: метод, шаблон маршрута (не исходный URL), статус, `started_at`, `duration_ms` и `outcome`; тело, query string и заголовки не записываются. Идентификатор от клиента не принимается как доверенный без отдельного
  решения об аутентификации и прокси.
- REQ-005: При успешном принятии сообщения `request_id` передаётся в его фоновую задачу и сохраняется для событий сервиса, агента, LLM и инструментов до терминального результата, включая отмену и ошибку. Параллельные диалоги и
  последовательные сообщения одного диалога не смешивают контекст. Для событий, не связанных с HTTP-запросом, отсутствующий `request_id` остаётся пустым/`null`, а не наследуется от другого запроса.
- REQ-006: События жизненного цикла диалога и подписки содержат `dialog_id`. События agent loop и провайдера, относящиеся к принятому сообщению, наследуют его `dialog_id`; агент сохраняет номера итераций. Каждый вызов модели получает
  отдельный `call_id`, общий для его start/completed/failed записей. Выполнение инструмента содержит `tool_call_id`, имя инструмента и безопасный статус; `call_id` LLM не подменяет `tool_call_id`. Терминальные события обработки сообщения и
  выполнения инструмента содержат `started_at`, `duration_ms` и `outcome`, включая неуспех и отмену.
- REQ-007: Для каждого вызова LLM записываются модель, число сообщений и доступных инструментов, исход (`completed`, `failed`, `cancelled`), `started_at`, `duration_ms` и, если измеримо, `time_to_first_token_ms`. В записи завершения
  присутствуют `input_tokens`, `output_tokens`, `total_tokens`, когда провайдер сообщил соответствующие значения; при отсутствии метаданных фиксируется `usage_available=false`, а токены не выдумываются. Терминальная запись создаётся также
  при исключении во время чтения потока, а отмена asyncio-задачи не превращается в обычную ошибку.
- REQ-008: Если потоковый ответ LiteLLM содержит статистику использования, адаптер извлекает её без потери текстовых фрагментов и tool calls и без изменения внешнего HTTP/SSE-контракта. Провайдер, который не отдаёт usage, остаётся
  работоспособным. Некорректные либо отрицательные значения usage не выводятся как достоверные метрики и обрабатываются безопасно.
- REQ-009: Переполнение очереди подписчика SSE и её принудительное закрытие наблюдаемы через безопасное событие с `dialog_id` и причиной. Отключение клиента не отменяет фоновую обработку диалога и не раскрывает содержимое отправленных
  фрагментов.
- REQ-010: Политика уровней едина: штатные этапы и итог LLM — `INFO`, подробные диагностические этапы без payload — `DEBUG`, ожидаемые восстановимые отклонения (например, переполнение SSE) — `WARNING`, неуспех задачи, LLM или инструмента —
  `ERROR`. Ошибки содержат безопасный `error_type` и контекст этапа, но не текст внешнего исключения или traceback, пока для них не определена отдельная безопасная схема.
- REQ-011: Конфигурация приложения не повышает глобально подробность журналов сторонних библиотек. Вывод LiteLLM, Uvicorn и других зависимостей не должен обходить принятую политику скрытия payload и секретов; штатный access log сервера не
  должен включать query string либо дублировать события HTTP API.
- REQ-012: В журнал не попадают текст system prompt, запросов, истории и ответов, аргументы и результаты инструментов, API keys, полные URL с query, тела ответов провайдера и текст исключений, способный содержать эти данные. Это выполняется
  для обоих форматов, всех уровней и ошибок фоновой задачи.
- REQ-013: Настройки `LOG_LEVEL` и `LOG_FORMAT` доступны в `docker/.env.example` и Compose. Тематическая страница в `docs/` описывает поля, формат, уровни, границы метрик и поиск одной операции по `request_id`; `docs/README.md` отражает
  новую границу конфигурации и наблюдаемости.

Действующий контракт и архитектурные границы описаны в [каталоге](../../../docs/README.md).
