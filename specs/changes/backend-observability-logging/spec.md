# Настраиваемое безопасное логирование backend

## Цель

Сделать журнал backend пригодным для локальной разработки и разбора ошибок:
оператор выбирает читаемый человеком либо JSON-формат и уровень подробности,
связывает HTTP-запрос, фоновую обработку диалога, вызовы модели и инструмента по
идентификаторам, видит длительность и доступную статистику токенов LLM. При этом
журнал не раскрывает содержимое диалога, аргументы инструментов и секреты.

Изменение опирается на действующие контракты
[`backend-config`](../backend-config/spec.md),
[`agent-runtime`](../agent-runtime/spec.md),
[`litellm-provider`](../litellm-provider/spec.md),
[`agent-dialog-api`](../agent-dialog-api/spec.md) и
[`dialog-event-broker`](../dialog-event-broker/spec.md).

## Допущения

- Область изменения — Python backend и его штатный запуск через Compose.
  Собственные журналы Caddy и Nginx и клиентская аналитика frontend сюда не
  входят.
- `request_id` обозначает одну принятую HTTP-операцию. Для фонового запуска,
  начатого `POST /api/v1/dialogs/{dialog_id}/messages`, сохраняется `request_id`
  этого POST, даже после возврата `202`; новый HTTP-запрос к SSE имеет свой
  `request_id`.
- `call_id` обозначает один логический вызов LLM внутри agent loop. Повторные
  сетевые попытки LiteLLM внутри этого вызова отдельно не измеряются.
  `tool_call_id` обозначает идентификатор вызова инструмента из ответа LLM.
- Статистика токенов зависит от метаданных, полученных от провайдера в
  потоковом ответе. Отсутствующие числа не вычисляются по длине текста и не
  записываются как нули.
- Время вызова LLM включает ожидание первого и последнего фрагмента потока,
  а также внутренние повторы SDK, если они есть. Время измеряется монотонными
  часами.
- Для первой версии достаточно уровней `DEBUG`, `INFO`, `WARNING`, `ERROR` и
  двух форматов `human`, `json`; ротация и сбор логов остаются ответственностью
  среды запуска.

## Требования

### Общая схема записи

| Поле | Значение |
| --- | --- |
| `timestamp` | Время события в UTC, ISO 8601 с указанием `Z`; обязательно для каждой записи |
| `level`, `logger`, `event` | Уровень, имя источника и стабильное имя события; обязательны для каждой записи |
| `request_id`, `dialog_id`, `call_id`, `tool_call_id` | Идентификаторы связи; в JSON присутствуют всегда, со значением `null`, когда неприменимы |
| `started_at` | Время начала операции в UTC, ISO 8601; обязательно в терминальной записи HTTP-запроса, обработки сообщения, LLM-вызова и инструмента |
| `duration_ms` | Неотрицательная числовая длительность той же операции от начала до терминального исхода, измеренная монотонными часами |
| `outcome` | `completed`, `failed` или `cancelled` для терминальных событий; если событие описывает другой исход, используется явно документированное значение |

`timestamp` терминальной записи обозначает время окончания операции. Пара
`started_at`/`duration_ms` позволяет видеть и момент запроса, и его длительность;
разница между двумя wall-clock timestamp не используется для расчёта
`duration_ms`. В `human` выводятся те же обязательные и применимые поля, но
пустые идентификаторы можно опускать.

- REQ-001: Корневой неизменяемый `Config` должен включать принадлежащую системе
  логирования типизированную конфигурацию. Только `load_config` читает
  `LOG_LEVEL` (`DEBUG`, `INFO`, `WARNING`, `ERROR`) и `LOG_FORMAT` (`human`,
  `json`) из переданного mapping либо process environment. Defaults — `INFO`
  и `human`. Недопустимые значения приводят к контролируемой ошибке
  конфигурации до создания приложения; регистр допустимых значений и формат
  ошибки документируются.
- REQ-002: Production bootstrap применяет готовую конфигурацию логирования
  один раз без чтения environment внутренними компонентами. Выбранный уровень
  реально фильтрует события приложения; повторная сборка приложения в тестах
  не добавляет дублирующие обработчики. Настройка учитывает уже созданные
  обработчики ASGI-сервера и не зависит от того, успел ли он настроить root
  logger.
- REQ-003: Оба формата пишутся в stdout/stderr контейнера по одной записи на
  строку и следуют общей схеме выше. `json` даёт валидный JSON-объект с
  типизированными числами; `human` показывает те же доступные поля в читаемом
  виде, без повторения контекста в тексте события. Имена полей и событий
  стабильны для обработки журналов.
- REQ-004: Backend генерирует непрогнозируемый `request_id` для каждого
  входящего HTTP-запроса к API и возвращает его в `X-Request-ID`, в том числе
  для `201`, `202`, ожидаемых `4xx` и `5xx`. В журнале безопасно отмечаются
  начало и завершение HTTP-запроса: метод, шаблон маршрута (не исходный URL),
  статус, `started_at`, `duration_ms` и `outcome`; тело, query string и
  заголовки не записываются.
  Идентификатор от клиента не принимается как доверенный без отдельного
  решения об аутентификации и прокси.
- REQ-005: При успешном принятии сообщения `request_id` передаётся в его
  фоновую задачу и сохраняется для событий сервиса, агента, LLM и инструментов
  до терминального результата, включая отмену и ошибку. Параллельные диалоги
  и последовательные сообщения одного диалога не смешивают контекст. Для
  событий, не связанных с HTTP-запросом, отсутствующий `request_id` остаётся
  пустым/`null`, а не наследуется от другого запроса.
- REQ-006: События жизненного цикла диалога и подписки содержат `dialog_id`.
  События agent loop и провайдера, относящиеся к принятому сообщению,
  наследуют его `dialog_id`; агент сохраняет номера итераций. Каждый вызов
  модели получает отдельный `call_id`, общий для его start/completed/failed
  записей. Выполнение инструмента содержит `tool_call_id`, имя инструмента и
  безопасный статус; `call_id` LLM не подменяет `tool_call_id`. Терминальные
  события обработки сообщения и выполнения инструмента содержат `started_at`,
  `duration_ms` и `outcome`, включая неуспех и отмену.
- REQ-007: Для каждого вызова LLM записываются модель, число сообщений и
  доступных инструментов, исход (`completed`, `failed`, `cancelled`),
  `started_at`, `duration_ms` и, если измеримо, `time_to_first_token_ms`.
  В записи завершения присутствуют `input_tokens`, `output_tokens`, `total_tokens`, когда
  провайдер сообщил соответствующие значения; при отсутствии метаданных
  фиксируется `usage_available=false`, а токены не выдумываются. Терминальная
  запись создаётся также при исключении во время чтения потока, а отмена
  asyncio-задачи не превращается в обычную ошибку.
- REQ-008: Если потоковый ответ LiteLLM содержит статистику использования,
  адаптер извлекает её без потери текстовых фрагментов и tool calls и без
  изменения внешнего HTTP/SSE-контракта. Провайдер, который не отдаёт usage,
  остаётся работоспособным. Некорректные либо отрицательные значения usage не
  выводятся как достоверные метрики и обрабатываются безопасно.
- REQ-009: Переполнение очереди подписчика SSE и её принудительное закрытие
  наблюдаемы через безопасное событие с `dialog_id` и причиной. Отключение
  клиента не отменяет фоновую обработку диалога и не раскрывает содержимое
  отправленных фрагментов.
- REQ-010: Политика уровней едина: штатные этапы и итог LLM — `INFO`,
  подробные диагностические этапы без payload — `DEBUG`, ожидаемые
  восстановимые отклонения (например, переполнение SSE) — `WARNING`,
  неуспех задачи, LLM или инструмента — `ERROR`. Ошибки содержат безопасный
  `error_type` и контекст этапа, но не текст внешнего исключения или traceback,
  пока для них не определена отдельная безопасная схема.
- REQ-011: Конфигурация приложения не повышает глобально подробность журналов
  сторонних библиотек. Вывод LiteLLM, Uvicorn и других зависимостей не должен
  обходить принятую политику скрытия payload и секретов; штатный access log
  сервера не должен включать query string либо дублировать события HTTP API.
- REQ-012: В журнал не попадают текст system prompt, запросов, истории и
  ответов, аргументы и результаты инструментов, API keys, полные URL с query,
  тела ответов провайдера и текст исключений, способный содержать эти данные.
  Это выполняется для обоих форматов, всех уровней и ошибок фоновой задачи.
- REQ-013: Настройки `LOG_LEVEL` и `LOG_FORMAT` доступны в
  `docker/.env.example` и Compose. Тематическая страница в `docs/` описывает
  поля, формат, уровни, границы метрик и поиск одной операции по `request_id`;
  `docs/README.md` отражает новую границу конфигурации и наблюдаемости.

## Сценарии

### Успешное сообщение

- Given запущен backend с `LOG_FORMAT=json` и `LOG_LEVEL=INFO` и создан диалог
- When клиент отправляет сообщение, агент делает два последовательных вызова
  LLM и один вызов инструмента, а второй вызов завершает ответ
- Then `202` содержит `X-Request-ID`, все события фоновой операции имеют тот
  же `request_id` и `dialog_id`, каждый вызов LLM имеет свой `call_id`, а
  событие инструмента содержит свой `tool_call_id`
- And терминальные записи HTTP, обработки сообщения, LLM и инструмента
  содержат `started_at`, `timestamp`, `duration_ms` и `outcome`
- And записи `llm.request.completed` содержат измеренную длительность и
  реальные токены, если провайдер их вернул
- And каждая строка журнала является отдельным JSON-объектом без payload.

### Читаемый журнал и изменение уровня

- Given `LOG_FORMAT=human` и `LOG_LEVEL=WARNING`
- When приложение обрабатывает успешный запрос и затем обнаруживает
  переполнение очереди SSE
- Then штатные `INFO`-события приложения подавлены, а предупреждение содержит
  безопасные идентификаторы и причину; строки остаются читаемыми.

### Отсутствующие метрики и сбой модели

- Given потоковый LLM-провайдер не присылает usage либо завершает поток ошибкой
- When завершается вызов модели
- Then имеется ровно одно терминальное событие для данного `call_id` с
  `duration_ms`, корректным исходом и `usage_available=false` при отсутствии
  подтверждённой статистики; текст ошибки и секреты в журнал не попадают
- And клиентский SSE-контракт и сохранение истории следуют прежним правилам.

### Параллельные сообщения и подписки

- Given два диалога обрабатываются одновременно, а в одном диалоге есть
  несколько последовательных сообщений и отдельное SSE-подключение
- When события этих операций перемежаются
- Then каждая запись относится к правильным `request_id`/`dialog_id`, а
  переполненная подписка создаёт предупреждение без остановки агента.

## Технологии и структура

Используются стандартный Python `logging`, типизированная Pydantic-конфигурация
и существующий `LiteLLMProvider`. Для переноса контекста через asyncio-задачи
предполагается `contextvars` либо эквивалентное явно передаваемое значение.
Форматирование и фильтрация составляют внутреннюю подсистему backend;
отдельный сервис логов, сборщик метрик и новый публичный API не создаются.
Конкретное расположение модулей и способ получения streaming usage уточняются
на этапе `plan` по возможностям зафиксированной версии LiteLLM.

- Запуск: `make run`
- Тесты: `make test`
- Линтинг: `make lint`

## Проверка требований

| Требования | Способ проверки |
| --- | --- |
| REQ-001–REQ-003, REQ-010–REQ-011 | Модульные тесты конфигурации, фильтрации, повторной инициализации и парсинга обоих форматов; проверка запуска через Compose с двумя наборами настроек |
| REQ-004–REQ-006 | HTTP/async-интеграционные тесты заголовка, времени начала, исхода и длительности HTTP/фоновой/tool операции, фонового контекста, двух сообщений одного диалога и параллельных диалогов |
| REQ-007–REQ-008 | Детерминированные потоки LiteLLM с usage, без usage, с некорректным usage, ошибкой и отменой; проверка ровно одного терминального события, чисел и неизменности SSE |
| REQ-009 | Тест переполнения ограниченной SSE-очереди с проверкой предупреждения и завершения агентной задачи |
| REQ-012 | Захват логов обоих форматов на `DEBUG` с маркерами секретов, payload и внешних исключений; интеграционная проверка безопасного server/access вывода |
| REQ-013 | Ревью Compose, шаблона окружения и архитектурной документации; автоматические тесты наличия файлов не добавляются |

## Границы

- Всегда: связывать события без записи содержимого диалога; сохранять
  асинхронность, действующие HTTP/SSE-ответы и модульный монолит.
- Сначала спросить: одобрение этой спецификации до этапа `plan` по правилу
  SDD; изменение публичного SSE payload, добавление внешней системы сбора
  журналов или платёжной метрики стоимости токенов.
- Никогда: хранить секреты или пользовательский текст в логах, подменять
  отсутствующий usage оценкой, трактовать `dialog_id`/`request_id` как
  аутентификацию, добавлять отдельное приложение логирования.

## Критерии приёмки

- [ ] `LOG_LEVEL` и `LOG_FORMAT` меняют реальный вывод backend; невалидные
  значения отклоняются при запуске.
- [ ] Для обоих форматов проверены обязательные поля, типы и отсутствие
  дублирующихся строк после повторной сборки приложения.
- [ ] У каждой записи есть UTC `timestamp`; для каждого завершённого HTTP,
  dialog, LLM и tool вызова есть `started_at`, числовой `duration_ms` и `outcome`.
- [ ] Принятое сообщение прослеживается от HTTP до терминального события
  фоновой задачи по `request_id` и `dialog_id`, каждый LLM/tool call различим.
- [ ] У каждого LLM-вызова есть длительность и один терминальный исход;
  подтверждённый usage отражён точно, отсутствующий обозначен явно.
- [ ] Переполнение SSE видно в журнале и не прерывает выполнение агента.
- [ ] Логи на `DEBUG` в обоих форматах не содержат секретов и payload.
- [ ] Обновлены Compose-шаблон и архитектурная документация.
- [ ] `make test` и `make lint` проходят успешно после реализации.

## Открытые вопросы

- Нет блокирующих вопросов. Способ получения usage из потокового ответа
  уточняется при планировании; при несовместимости части LLM-адаптеров
  отсутствие usage остаётся допустимым и явно наблюдаемым результатом.
