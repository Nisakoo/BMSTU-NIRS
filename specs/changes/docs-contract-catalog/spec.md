# Каталог архитектуры и контрактов проекта

## Цель

Создать в корневом каталоге `docs/` компактную точку входа для разработчика:
где находится каждая часть проекта, в каком состоянии она находится, какие
внутренние и HTTP-контракты уже согласованы и в какой SDD-спецификации искать
полные требования, сценарии и критерии приёмки.

Каталог не заменяет спецификации и не повторяет их целиком. Он предоставляет
быстрый обзор фактического состояния проекта и точные краткие контракты, а
спецификации остаются источником подробностей.

Эта спецификация документирует контракты изменений `agent-runtime` и
`agent-dialog-api` и реализуется после них, чтобы каталог отражал проверенное, а
не предполагаемое состояние кода.

## Допущения

- Основная обзорная страница располагается в `docs/README.md` и ведётся на
  русском языке.
- Корневой `README.md` содержит заметную ссылку на каталог.
- Статус SDD-изменения читается из `specs/status.yaml` и сверяется с текущими
  SDD-артефактами; наличие одной спецификации не означает завершённую
  реализацию.
- Подробные требования, сценарии, Mermaid-диаграммы и доказательства проверки
  остаются в `specs/changes/<change-id>/`.
- Каталог описывает только существующие либо уже согласованные части проекта и
  явно отличает их от будущих возможностей.

## Требования

- REQ-001: В корне репозитория должен существовать каталог `docs/` с файлом
  `docs/README.md`, который служит основной краткой навигацией по архитектуре,
  контрактам и SDD-изменениям проекта.
- REQ-002: Корневой `README.md` должен содержать ссылку на `docs/README.md` и
  объяснять, что там находится краткий каталог компонентов и контрактов.
- REQ-003: В начале каталога должна быть краткая карта верхнеуровневых частей
  `frontend/`, `backend/`, `docker/`, `docs/` и `specs/` с их назначением и
  ссылками на соответствующие пути.
- REQ-004: Каталог должен содержать таблицу компонентов с колонками «Компонент»,
  «Назначение», «Состояние», «Где реализация» и «Где конкретика». Для
  нереализованного компонента путь реализации помечается как планируемый, а не
  существующий.
- REQ-005: Каталог должен использовать состояния «Специфицировано»,
  «Запланировано», «Реализуется» и «Проверено» и кратко объяснять их. Компонент
  сопоставляет их со статусами `draft`, `in-queue`, `in-progress` и `done` из
  `specs/status.yaml`; его нельзя помечать как «Проверено» без статуса `done` и
  успешного `verification.md`.
- REQ-006: Для agent runtime каталог должен кратко и явно зафиксировать
  следующие внутренние контракты:
  - создание `Agent` с `LLMProvider`, `ToolRegistry` и `AgentConfig`;
  - `async Agent.run(history, request) -> AgentResponse`;
  - `async LLMProvider.generate(messages, tools) -> LLMResponse`;
  - наследование каждого инструмента от `Tool`, его Pydantic-схему аргументов и
    асинхронное выполнение;
  - создание `ToolRegistry` из последовательности экземпляров `Tool` и
    выполнение tool call только через реестр;
  - максимум один tool call за итерацию и максимум четыре итерации;
  - успешный пустой финальный ответ `FakeLLMProvider`.
- REQ-007: Для диалогового слоя каталог должен кратко и явно зафиксировать
  следующие внутренние контракты:
  - `async AgentService.start_dialog() -> dialog_id`;
  - `async AgentService.submit(dialog_id, request) -> None`, где возврат означает
    постановку запуска в in-memory очередь, а не завершение агента;
  - `HistoryStore` с операциями создания диалога, чтения истории и добавления
    сообщений;
  - последовательное выполнение запросов одного диалога и независимое
    выполнение разных диалогов;
  - сохранение пользовательского и финального сообщений только после успешного
    фонового запуска.
- REQ-008: Каталог должен содержать компактную таблицу HTTP-контрактов как
  минимум со следующими строками:
  - `POST /api/v1/dialogs` → `201 Created`, заголовок `Location`, тело
    `{"dialog_id": "<uuid>"}`;
  - `POST /api/v1/dialogs/{dialog_id}/messages` с телом
    `{"request": "<непустой текст>"}` → немедленный `202 Accepted` с пустым
    телом после постановки agent loop в очередь;
  - `404 Not Found` для неизвестного `dialog_id`;
  - `422 Unprocessable Entity` для некорректного UUID или пустого запроса;
  - `503 Service Unavailable`, если запрос невозможно поставить в очередь.
- REQ-009: Рядом с HTTP-контрактом должно быть явно указано, что первая версия
  не возвращает результат agent loop, историю, прогресс или фоновую ошибку через
  HTTP и не использует cookie, CORS либо SSE.
- REQ-010: Каталог должен содержать краткий контракт наблюдаемости: создание
  диалога, постановка запроса, каждая итерация loop, имя и статус инструмента,
  завершение, отмена и ошибка фиксируются серверным журналом; тексты запросов,
  история, tool payload и секреты не журналируются.
- REQ-011: Для каждого набора контрактов каталог должен ссылаться на
  соответствующую спецификацию, а для проверенного изменения — также на план и
  `verification.md`. Относительные ссылки должны открываться из
  `docs/README.md`.
- REQ-012: Каталог должен ссылаться на `specs/status.yaml` как на краткий
  источник текущего состояния SDD-изменений и не копировать из спецификаций
  прогресс отдельных задач.
- REQ-013: Каталог должен явно сообщать, что при расхождении краткого описания со
  спецификацией источником истины является последняя согласованная спецификация
  вместе с результатом её проверки.
- REQ-014: `AGENTS.md` должен закреплять `docs/README.md` как обязательный
  краткий каталог. Любое SDD-изменение, добавляющее, удаляющее или меняющее
  компонент либо контракт, должно обновлять каталог в рамках того же изменения.
- REQ-015: Каталог не должен объявлять RAG, реального LLM-провайдера, frontend,
  CORS, SSE, постоянную базу истории или авторизацию реализованными до появления
  и успешной проверки соответствующих изменений.
- REQ-016: Для проверки каталога не должны добавляться автоматические тесты,
  которые проверяют только наличие `docs/README.md`, заголовков, таблиц, ссылок
  или служебных файлов.

## Сценарии

### Поиск реализации и подробной спецификации

- Given разработчик впервые открыл репозиторий
- When он переходит из корневого README в каталог
- Then он видит назначение agent runtime и диалогового API
- And видит их фактическое состояние
- And может перейти к пути реализации и авторитетной SDD-спецификации

### Быстрый просмотр внутреннего контракта

- Given разработчику нужно вызвать агента или добавить инструмент
- When он открывает раздел внутренних контрактов
- Then он видит сигнатуры `Agent`, `LLMProvider`, `ToolRegistry` и `Tool`
- And понимает async-семантику, ограничения loop и результат fake-провайдера
- And по ссылке может открыть полные требования `agent-runtime`

### Быстрый просмотр HTTP-контракта

- Given разработчик frontend хочет отправить сообщение
- When он открывает таблицу HTTP-контрактов
- Then он видит порядок создания `dialog_id`, тело запроса и коды ответа
- And понимает, что `202 Accepted` имеет пустое тело и не означает завершение
  agent loop
- And понимает, что результат первой версии доступен только в серверных логах и
  внутренней истории

### Изменение контракта

- Given новое SDD-изменение меняет HTTP-маршрут или внутреннюю сигнатуру
- When изменение проходит стадии plan, implement и verify
- Then `docs/README.md` обновляется в том же изменении
- And состояние компонента и ссылки соответствуют фактическим артефактам

### Защита от преждевременного обещания

- Given для SSE или реального LLM ещё нет проверенной реализации
- When разработчик читает каталог
- Then возможность не помечена как реализованная
- And при упоминании обозначена как будущая и не смешивается с действующим
  контрактом

## Технологии и структура

- Создаётся один основной документ `docs/README.md` в Markdown.
- Корневой `README.md` получает ссылку на каталог без дублирования контрактов.
- В каталоге используются компактные Markdown-таблицы, относительные ссылки и
  короткие сигнатуры в code blocks.
- Состояния компонентов берутся из управляемого скриптом
  `specs/status.yaml`; каталог не вводит отдельный реестр статусов.
- Полные сценарии и диаграммы не копируются: каталог ссылается на
  `specs/changes/agent-runtime/` и `specs/changes/agent-dialog-api/`.
- `AGENTS.md` получает правило обязательного обновления каталога при изменении
  архитектуры или контрактов.

Новые runtime-зависимости, генераторы документации и отдельный сайт документации
не добавляются.

## Команды

- Запуск: `make run` не изменяется документационным изменением.
- Тесты: `make test` не используется как проверка структуры документации; если
  продуктовые тесты уже настроены, их запуск остаётся общей регрессионной
  проверкой, но не доказывает корректность каталога.

## Тестирование

| Требования | Способ проверки |
| --- | --- |
| REQ-001–REQ-005 | Ревью навигации, карты проекта, таблицы компонентов и корректности состояний |
| REQ-006–REQ-010 | Ручное сопоставление кратких контрактов с утверждёнными спецификациями и реализованными интерфейсами |
| REQ-011–REQ-013 | Переход по каждой относительной ссылке и сверка со `specs/status.yaml` и источниками истины |
| REQ-014 | Ревью изменения `AGENTS.md` и правила синхронного обновления каталога |
| REQ-015 | Ревью формулировок и статусов без автоматического теста структуры |
| REQ-016 | Проверка отсутствия новых тестов, проверяющих только документационные файлы |

Это документационное изменение не добавляет поведение Python-кода. Новые
автоматические тесты не создаются; приёмка выполняется ревью содержимого и
ссылок.

## Границы

- Всегда: указывать фактический статус; давать ссылку на источник конкретики;
  обновлять каталог вместе с контрактом; отличать внутренний контракт от HTTP.
- Сначала спросить: добавить генератор документации, отдельный документационный
  сайт, англоязычную версию, ADR или автоматически вычисляемые статусы.
- Никогда: выдавать запланированное за проверенное; заменять каталогом SDD-
  спецификации; дублировать в каталоге полные требования и сценарии; добавлять
  структурные тесты документации.

## Критерии приёмки

- [ ] Из корневого `README.md` можно одним переходом открыть `docs/README.md`.
- [ ] По каталогу можно определить назначение, статус, путь реализации и
  спецификацию agent runtime и диалогового API.
- [ ] Состояния каталога согласованы со `specs/status.yaml`, а task progress в
  каталоге не дублируется.
- [ ] В каталоге приведены внутренние контракты `Agent`, `LLMProvider`, `Tool`,
  `ToolRegistry`, `AgentService` и `HistoryStore`.
- [ ] HTTP-таблица однозначно описывает создание диалога и немедленный
  `202 Accepted` с пустым телом при постановке сообщения в очередь.
- [ ] Ограничения fake-провайдера, in-memory хранения, фонового запуска и
  серверного логирования видны без чтения полных спецификаций.
- [ ] Все ссылки ведут на существующие пути либо явно помечены как планируемые.
- [ ] Нереализованные RAG, реальный LLM, frontend, CORS, SSE, постоянное
  хранилище и авторизация не обозначены как готовые.
- [ ] `AGENTS.md` требует обновлять каталог в одном изменении с контрактом.
- [ ] Новые автоматические тесты структуры документации не добавлены; приёмка
  выполнена ревью.
