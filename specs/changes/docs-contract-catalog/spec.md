# Каталог архитектуры и контрактов проекта

## Цель

Создать в корневом каталоге `docs/` компактную многостраничную точку входа для разработчика: где находится каждая часть проекта, в каком состоянии она
находится, какие внутренние и HTTP-контракты уже согласованы и в какой SDD- спецификации искать полные требования, сценарии и критерии приёмки. Каталог не
заменяет спецификации и не повторяет их целиком. В него входят только архитектурные решения, необходимые пояснения по реализации и точные краткие контракты.
Требования, сценарии, критерии приёмки и прочие подробности остаются в соответствующих спецификациях и доступны по ссылкам. Эта спецификация документирует
контракты изменений `agent-runtime` и `agent-dialog-api` и реализуется после них, чтобы каталог отражал проверенное, а не предполагаемое состояние кода.

## Требования

- REQ-001: В корне репозитория должен существовать каталог `docs/` с файлом `docs/README.md`, который служит основной краткой навигацией по архитектуре, тематическим страницам компонентов и SDD-изменениям проекта.
- REQ-002: Корневой `README.md` должен содержать ссылку на `docs/README.md` и объяснять, что там находится краткий каталог компонентов и контрактов.
- REQ-003: В начале каталога должна быть краткая карта верхнеуровневых частей `frontend/`, `backend/`, `docker/`, `docs/` и `specs/` с их назначением и ссылками на соответствующие пути.
- REQ-004: Каталог должен содержать таблицу компонентов с колонками «Компонент», «Назначение», «Состояние», «Где реализация» и «Где конкретика». Для нереализованного компонента путь реализации помечается как планируемый, а не существующий.
- REQ-005: Каталог должен использовать состояния «Специфицировано», «Запланировано», «Реализуется» и «Проверено» и кратко объяснять их. Компонент сопоставляет их со статусами `draft`, `in-queue`, `in-progress` и `done` из
  `specs/status.yaml`; его нельзя помечать как «Проверено» без статуса `done` и успешного `verification.md`.
- REQ-006: Для agent runtime каталог должен кратко и явно зафиксировать в `docs/agent.md` следующие внутренние контракты: - создание `Agent` с `LLMProvider`, `ToolRegistry` и `AgentConfig`; - `async Agent.run(history, request) ->
  AgentResponse`; - `async LLMProvider.generate(messages, tools) -> LLMResponse`; - наследование каждого инструмента от `Tool`, его Pydantic-схему аргументов и асинхронное выполнение; - создание `ToolRegistry` из последовательности
  экземпляров `Tool` и выполнение tool call только через реестр; - максимум один tool call за итерацию и максимум четыре итерации; - успешный пустой финальный ответ `FakeLLMProvider`.
- REQ-007: Для диалогового слоя каталог должен кратко и явно зафиксировать в `docs/dialogs.md` следующие внутренние контракты: - `async AgentService.start_dialog() -> dialog_id`; - `async AgentService.submit(dialog_id, request) -> None`,
  где возврат означает постановку запуска в in-memory очередь, а не завершение агента; - `HistoryStore` с операциями создания диалога, чтения истории и добавления сообщений; - последовательное выполнение запросов одного диалога и
  независимое выполнение разных диалогов; - сохранение пользовательского и финального сообщений только после успешного фонового запуска.
- REQ-008: `docs/dialogs.md` должен содержать компактную таблицу HTTP-контрактов как минимум со следующими строками: - `POST /api/v1/dialogs` → `201 Created`, заголовок `Location`, тело `{"dialog_id": "<uuid>"}`; - `POST
  /api/v1/dialogs/{dialog_id}/messages` с телом `{"request": "<непустой текст>"}` → немедленный `202 Accepted` с пустым телом после постановки agent loop в очередь; - `404 Not Found` для неизвестного `dialog_id`; - `422 Unprocessable
  Entity` для некорректного UUID или пустого запроса; - `503 Service Unavailable`, если запрос невозможно поставить в очередь.
- REQ-009: Рядом с HTTP-контрактом в `docs/dialogs.md` должно быть явно указано, что первая версия не возвращает результат agent loop, историю, прогресс или фоновую ошибку через HTTP и не использует cookie, CORS либо SSE.
- REQ-010: Тематические страницы должны содержать краткий контракт наблюдаемости в относящемся к ним контексте: создание диалога, постановка запроса, каждая итерация loop, имя и статус инструмента, завершение, отмена и ошибка фиксируются
  серверным журналом; тексты запросов, история, tool payload и секреты не журналируются.
- REQ-011: Для каждого набора контрактов каталог должен ссылаться на соответствующую спецификацию, а для проверенного изменения — также на план и `verification.md`. Относительные ссылки должны открываться из содержащего их документа в
  `docs/`.
- REQ-012: Каталог должен ссылаться на `specs/status.yaml` как на краткий источник текущего состояния SDD-изменений и не копировать из спецификаций прогресс отдельных задач.
- REQ-013: Каталог должен явно сообщать, что при расхождении краткого описания со спецификацией источником истины является последняя согласованная спецификация вместе с результатом её проверки.
- REQ-014: `AGENTS.md` должен закреплять `docs/README.md` и тематические страницы `docs/` как обязательный краткий каталог. Любое SDD-изменение, добавляющее, удаляющее или меняющее компонент либо контракт, должно обновлять относящиеся к
  нему страницы каталога в рамках того же изменения.
- REQ-015: Каталог не должен объявлять RAG, реального LLM-провайдера, frontend, CORS, SSE, постоянную базу истории или авторизацию реализованными до появления и успешной проверки соответствующих изменений.
- REQ-016: Для проверки каталога не должны добавляться автоматические тесты, которые проверяют только наличие `docs/README.md`, заголовков, таблиц, ссылок или служебных файлов.
- REQ-017: Содержание каталога должно ограничиваться архитектурными решениями, пояснениями по фактической реализации и краткими внутренними и внешними контрактами. Нельзя механически переносить в него полные требования, сценарии, критерии
  приёмки, планы задач или результаты проверки из SDD- артефактов.
- REQ-018: В каталоге можно и нужно использовать Mermaid-диаграммы, когда они делают архитектуру, связи компонентов или последовательность взаимодействий понятнее текста. Неуместные или дублирующие текст диаграммы добавляться не должны.
- REQ-019: `docs/README.md` должен ссылаться на каждую тематическую страницу, а тематические страницы — возвращать к глобальному каталогу и не смешивать контракты несвязанных компонентов. Для запуска и контейнерной конфигурации каталог
  должен ссылаться на существующий `docker/README.md`, а не дублировать его инструкции.

Действующий контракт и архитектурные границы описаны в [каталоге](../../../docs/README.md).
