# План: каталог архитектуры и контрактов

## Основание

План реализует спецификацию `specs/changes/docs-contract-catalog/spec.md`.
Изменение создаёт компактную многостраничную точку входа в архитектуру,
фактическую реализацию и действующие контракты проекта. Каталог не заменяет
SDD-артефакты и не переносит из них полные требования, сценарии, планы или
verification-отчёты.

## Решения и зависимости

Каталог оформляется набором русскоязычных Markdown-документов без генератора,
отдельного сайта и новых зависимостей. Он опирается только на проверенные
изменения `agent-runtime` и `agent-dialog-api`, статус которых подтверждён
`specs/status.yaml` и соответствующими `verification.md`.

Основная структура каталога:

1. `docs/README.md` — глобальная карта верхнеуровневых каталогов, легенда
   состояний, таблица компонентов и общая архитектура;
2. `docs/agent.md` — реализация и внутренние контракты runtime агента,
   LLM-провайдера, инструментов и реестра;
3. `docs/dialogs.md` — реализация и контракты `AgentService`, истории, HTTP и
   наблюдаемости;
4. `docker/README.md` — существующий источник команд запуска и контейнерной
   конфигурации, на который каталог только ссылается.

Mermaid используется только для общей архитектуры и потока принятого сообщения,
где схема делает границы слоёв и фоновое выполнение понятнее линейного текста.
Диаграммы из спецификаций не копируются целиком.

## Порядок реализации

1. Создать глобальную карту и навигацию каталога.
2. Создать отдельные страницы агента и диалогового слоя.
3. Добавить навигацию из корневого README и правило сопровождения в
   `AGENTS.md`.
4. Выполнить ручную сверку содержания, статусов, относительных ссылок и границ
   текущей реализации.
5. Записать результат Verify и обновить статус спецификации.

## Задача 1. Создать глобальную карту каталога

**Связанные требования:** REQ-001, REQ-003–REQ-005, REQ-012, REQ-013,
REQ-015, REQ-017–REQ-019.

**Критерии приёмки:** разработчик видит назначение частей проекта, состояния
компонентов, общие архитектурные границы и ссылки на тематические страницы и
SDD-артефакты; подробные контракты не перегружают глобальную страницу.

**Зависимости:** проверенные `agent-runtime` и `agent-dialog-api`.

**Файлы:**

- `docs/README.md`.

**Действия:**

1. Добавить карту `frontend/`, `backend/`, `docker/`, `docs/` и `specs/` с
   относительными ссылками и честным описанием состояния.
2. Объяснить сопоставление `draft`, `in-queue`, `in-progress`, `done` с
   пользовательскими состояниями каталога и сослаться на `specs/status.yaml`.
3. Добавить таблицу компонентов с назначением, состоянием, реализацией и
   источником конкретики.
4. Нарисовать небольшую Mermaid-схему архитектурных границ без копирования
   полной sequence diagram из спецификации.
5. Дать навигацию к `agent.md`, `dialogs.md`, `docker/README.md` и
   спецификациям проверенных изменений.
6. Явно перечислить нереализованные возможности, не выдавая их за компоненты
   текущей версии.

**Проверка:** ручное сопоставление карты с `specs/status.yaml`, структурой
репозитория и SDD-артефактами. Автоматический тест структуры документации не
создаётся.

## Задача 2. Создать тематические страницы компонентов

**Связанные требования:** REQ-006–REQ-011, REQ-013, REQ-015, REQ-017–REQ-019.

**Критерии приёмки:** `agent.md` содержит только реализацию и контракты runtime
и инструментов; `dialogs.md` содержит только реализацию и контракты сервиса,
истории, HTTP и логирования; обе страницы ссылаются на глобальный каталог и
полные SDD-артефакты.

**Зависимости:** задача 1.

**Файлы:**

- `docs/agent.md`;
- `docs/dialogs.md`.

**Действия:**

1. В `agent.md` кратко описать архитектурную роль и сигнатуры `Agent`,
   `LLMProvider`, `Tool`, `ToolRegistry`, ограничения loop, fake-провайдер и
   безопасное логирование runtime.
2. В `dialogs.md` кратко описать роль `AgentService`, `HistoryStore`,
   последовательность одного диалога, независимость диалогов и семантику
   успешного сохранения истории.
3. Добавить в `dialogs.md` таблицу HTTP-контрактов, ограничения `202 Accepted`
   и компактную Mermaid-схему фонового пути сообщения.
4. На каждой странице дать ссылки на глобальный каталог, реализацию, spec, plan
   и verification соответствующего изменения.
5. Не копировать полные сценарии, критерии приёмки и диаграммы спецификаций.

**Проверка:** ручное сопоставление с публичными Python-интерфейсами, маршрутами
FastAPI и завершёнными SDD-артефактами. Автоматический тест структуры
документации не создаётся.

## Задача 3. Подключить каталог к процессу разработки

**Связанные требования:** REQ-002, REQ-014, REQ-017–REQ-019.

**Критерии приёмки:** каталог открывается одним переходом из корневого README;
`AGENTS.md` требует обновлять его вместе с изменением компонента или контракта и
ограничивает содержание архитектурой, пояснениями реализации и контрактами;
Mermaid рекомендуется только при смысловой пользе.

**Зависимости:** задачи 1 и 2.

**Файлы:**

- `README.md`;
- `AGENTS.md`.

**Действия:**

1. Добавить в корневой README заметную ссылку на `docs/README.md` с кратким
   назначением каталога без дублирования его содержания.
2. Дополнить `AGENTS.md` обязательным правилом синхронного обновления каталога
   и соответствующей тематической страницы при изменении архитектуры,
   реализации компонентов или контрактов.
3. Зафиксировать в `AGENTS.md`, что каталог не копирует SDD-спецификации, а
   Mermaid добавляется только для уместной визуализации.

**Проверка:** ручное ревью навигации и формулировок. Новые продуктовые или
структурные тесты не создаются.

## Задача 4. Проверить каталог и зафиксировать результат

**Связанные требования:** REQ-001–REQ-019.

**Критерии приёмки:** все критерии спецификации подтверждены; относительные
ссылки разрешаются в существующие файлы; состояния соответствуют
`specs/status.yaml`; будущие возможности не названы реализованными; diff не
содержит ошибок форматирования и новых тестов документации.

**Зависимости:** задачи 1–3.

**Файлы:**

- `specs/changes/docs-contract-catalog/verification.md`.

**Действия:**

1. Сопоставить каждый REQ с разделом итогового каталога и фактическим кодом.
2. Проверить двустороннюю навигацию и каждую относительную Markdown-ссылку
   переходом к целевому пути.
3. Сверить статусы и наличие verification для проверенных компонентов.
4. Проверить разделение глобальной и тематических страниц и отсутствие
   механического переноса требований, сценариев и планов.
5. Проверить уместность и корректность Mermaid-схем.
6. Выполнить `git diff --check` и общую регрессионную проверку `make test`, не
   считая тесты доказательством содержимого документации.
7. Записать доказательства в `verification.md`; после успешной проверки
   перевести изменение в `done` только через SDD-скрипт.

**Проверка:**

```sh
git diff --check
make test
```

## Риски и меры

- **Устаревший контракт:** каждое утверждение сверяется с фактическим Python API
  и завершёнными спецификациями, а `AGENTS.md` закрепляет дальнейшее обновление.
- **Дублирование SDD:** каталог содержит только краткие архитектурные сведения,
  пояснения реализации и контракты, а за подробностями направляет ссылками.
- **Ложный статус:** состояние «Проверено» используется только при `done` и
  наличии успешного `verification.md`.
- **Избыточные схемы:** Mermaid применяется только к отношениям и
  последовательностям, которые проще воспринимать визуально.

## Вне плана

- генератор или сайт документации;
- англоязычная версия;
- ADR;
- автоматически вычисляемый реестр состояний;
- документация ещё не реализованных RAG, реального LLM, frontend, SSE, CORS,
  постоянной истории и авторизации как действующих возможностей;
- автоматические тесты структуры Markdown-документов.
