# Тестовое окружение PostgreSQL и Redis одной командой

## Цель

Дать разработчикам одну команду для полного прогона backend-тестов на настоящих PostgreSQL и Redis. Сейчас интеграционные тесты пропускаются без
`TEST_DATABASE_URL` и `TEST_REDIS_URL`, и каждое изменение, которому они
нужны, вручную поднимает временные контейнеры с собственными портами и паролями (`backend-auth-jwt`, `admin-user-stats`, `auth-rate-limit`,
`knowledge-*`). Команда убирает ручную работу и делает полный прогон
воспроизводимым: одни версии образов, чистая БД, гарантированная уборка.

## Допущения

- Команда — `make test-integration`: она поднимает и PostgreSQL, и Redis, поэтому имя `test-postgres` из дорожной карты было бы неточным.
- `make test` не меняется: он остаётся быстрым и не требует Docker.
- pytest запускается на хосте через `uv`, как в `make test`; в контейнерах работают только PostgreSQL и Redis. Сборка образа backend не нужна.
- Версии образов совпадают с основным `docker/compose.yaml`:
  `postgres:17-alpine` и `redis:7-alpine`.
- Тесты сами сбрасывают схему `public` и применяют миграции; команда отдаёт им пустую БД и не выполняет миграции сама.
- Изменение не трогает тесты, код продукта и основной Compose-проект. Длительность прогона тестов других модулей с недоступной БД (см. «Открытые вопросы») не исправляется.

## Требования

### Запуск

- REQ-001: `make test-integration` поднимает временные PostgreSQL и Redis, дожидается их готовности по healthcheck и запускает полный backend-набор pytest с `TEST_DATABASE_URL` и `TEST_REDIS_URL`, указывающими на них.
- REQ-002: Окружение — отдельный Compose-проект `smeshariki-ai-test` из отдельного файла `docker/compose.test.yaml`. Он не использует `docker/.env`, тома и сеть основного проекта `smeshariki-ai` и может работать
  одновременно с `make run`.
- REQ-003: Порты PostgreSQL и Redis публикуются только на `127.0.0.1` и выбираются Docker динамически; команда узнаёт их у Compose. Занятые порты хоста не мешают запуску.
- REQ-004: Данные PostgreSQL хранятся в `tmpfs` ограниченного размера (512 МБ): каждый запуск начинается с пустой БД и не пишет данные на диск. Учётные данные — фиксированные тестовые значения, не секреты.
- REQ-005: `PYTEST_ARGS` передаёт аргументы pytest вместо полного набора, например `make test-integration PYTEST_ARGS=backend/tests/integration/rag`.

### Результат и уборка

- REQ-006: Скрипт `docker/test-integration.sh` возвращает код pytest, а
  `make test-integration` — `0` при успехе pytest и ненулевой код иначе (GNU
  Make сводит ненулевые коды к `2`, исходный код виден в его сообщении
  `Error <код>`). При ошибке запуска окружения код ненулевой, а pytest не
  запускается.
- REQ-007: Контейнеры, сеть и анонимные тома проекта `smeshariki-ai-test` удаляются после завершения — при успехе, падении тестов, ошибке запуска и прерывании `Ctrl+C`.
- REQ-008: Если остались ресурсы от прерванного ранее запуска, новый запуск удаляет их перед стартом и проходит.
- REQ-009: Без запущенного Docker команда завершается ненулевым кодом с понятным сообщением в stderr и не запускает pytest.

### Документация

- REQ-010: `make help`, `docker/README.md`, `docs/README.md` и раздел «Процесс разработки» `AGENTS.md` описывают команду (правка `AGENTS.md` согласована). Изменения общих файлов только аддитивные.

## Границы

- Всегда: удалять только ресурсы проекта `smeshariki-ai-test`; сохранять код возврата pytest; в общих файлах только добавлять.
- Сначала спросить: изменение `make test`, тестов или `docker/compose.yaml`; добавление сборки образа backend; правки `AGENTS.md` сверх строки о команде.
- Никогда: использовать `docker/.env` или реальные секреты; выполнять глобальные `docker system/volume/builder prune`; трогать ресурсы других Compose-проектов.
