# Аутентификация в backend: JWT, refresh-токены и пользователи в PostgreSQL

## Цель

Реализовать в Python backend серверную часть [контракта аутентификации](../../../docs/auth.md), которой уже пользуется страница `/login/`. Backend регистрирует
пользователей, выдаёт короткоживущий access JWT и долгоживущий refresh-токен, отзывает access-токены через blacklist в Redis и хранит пользователей в
PostgreSQL. Схема базы данных проектируется сразу с учётом будущего постоянного хранения истории диалогов и описывается на отдельной странице
`docs/database.md`. Аутентификация становится ещё одним модулем модульного монолита `smeshariki_ai`; отдельный сервис не создаётся. PostgreSQL и Redis — новые
инфраструктурные контейнеры, orchestration и обращение к ним остаются ответственностью backend. Существующий frontend-контракт не меняется: оба токена
передаются только `HttpOnly` cookie, поэтому `fetch` и `EventSource` продолжают работать без заголовка `Authorization`, а `auth-api.js` и `/login/` не требуют
правок.

## Требования

- REQ-001: Пакет `smeshariki_ai.auth` содержит доменный `AuthService` и контракты `UserStore`, `RefreshSessionStore`, `TokenBlacklist`. Сервис не зависит от FastAPI, SQLAlchemy и redis-py и не читает environment.
- REQ-002: Регистрация создаёт пользователя с ролью `user` и хешем argon2id и отвечает по контракту, включая `409` для логина, отличающегося только регистром.
- REQ-003: Вход проверяет пароль, создаёт refresh-сессию и выставляет обе cookie; неизвестный логин и неверный пароль неотличимы по статусу и телу.
- REQ-004: `GET /users/me` принимает только действительный access JWT не из blacklist и возвращает актуальные `login` и `role` из БД.
- REQ-005: `refresh` ротирует refresh-токен, выдаёт новый access и при повторном использовании отозванного токена отзывает всё семейство.
- REQ-006: `logout` идемпотентен, заносит `jti` в Redis с TTL до `exp`, отзывает refresh-сессию и сбрасывает обе cookie.
- REQ-007: Недоступность PostgreSQL или Redis даёт `503` и никогда не даёт успешную аутентификацию.
- REQ-008: `load_config` дополнительно загружает подконфиги `auth`, `database` и `redis` из `AUTH_JWT_SECRET` (обязателен, не короче 32 байт), `AUTH_ACCESS_TTL_SECONDS`, `AUTH_REFRESH_TTL_SECONDS`, `AUTH_COOKIE_SECURE`, `DATABASE_URL`,
  `REDIS_URL`. Компоненты получают только свой подконфиг. `docker/.env.example` содержит только плейсхолдеры.
- REQ-009: Bootstrap создаёт async engine и Redis-клиент, передаёт адаптеры в `AuthService` и закрывает подключения в lifespan. Существующие ручки диалогов работают как раньше и аутентификации не требуют.
- REQ-010: Журнал содержит события регистрации, входа, refresh, logout и обнаружения повторного refresh с `user_id` и исходом, но не содержит логинов, паролей, хешей, токенов, `jti`, cookie и тел запросов.
- REQ-011: Alembic-миграция создаёт `users` и `refresh_sessions` по схеме выше; `docs/database.md` описывает всю схему, включая запланированные `dialogs` и `messages`.
- REQ-012: Compose запускает `postgres` и `redis` с healthcheck и volume для PostgreSQL, сервис `migrate` применяет миграции, `backend` стартует после их успешного завершения.

Действующий контракт и архитектурные границы описаны в [каталоге](../../../docs/README.md).
