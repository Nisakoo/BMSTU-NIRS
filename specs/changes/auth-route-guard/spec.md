# Защита ручек диалогов и редирект неавторизованных пользователей

## Цель

Backend уже реализует контракт аутентификации из
[`docs/auth.md`](../../../docs/auth.md), но ручки диалогов доступны всем, а
frontend не проверяет сессию на страницах чата и панели администратора. Это
изменение закрывает ручки диалогов для гостей и делает так, чтобы пользователь
без действительной сессии попадал на страницу входа `/login/`, а пользователь
с истёкшим access-токеном незаметно продлевал сессию через
`POST /api/v1/auth/refresh`. Панель администратора `/admin/` становится
доступной только пользователям с ролью `admin`. Администратор создаётся
отдельной консольной командой backend, которая переиспользует механизм
аутентификации: те же правила полей и то же хеширование пароля argon2id.
Прямая запись пользователя в базу SQL-запросом невозможна, так как пароль
хранится только как хеш.

## Требования

### Backend

- REQ-001: `POST /api/v1/dialogs`, `POST /api/v1/dialogs/{dialog_id}/messages`
  и `GET /api/v1/dialogs/{dialog_id}/events` без действительного access-токена
  отвечают `401` с телом `{"error":"unauthorized"}` и не создают диалог, не
  ставят запрос в очередь и не открывают SSE-поток.
- REQ-002: Если PostgreSQL или Redis недоступны при проверке токена, эти ручки
  отвечают `503` `{"error":"unavailable"}` (fail closed).
- REQ-003: С действительным access-токеном ручки диалогов ведут себя как
  раньше: прежние коды ответов, тела и формат ошибок FastAPI для `404`, `422`
  и `503` сервиса агента.
- REQ-004: Проверка токена выполняется до валидации тела и поиска диалога:
  гость получает `401`, а не `404` или `422`.
- REQ-005: Ручки аутентификации (`/users`, `/auth/*`, `/users/me`) и HTML
  страница `/agent_test` остаются доступными без сессии.

### Frontend: клиент контракта

- REQ-006: `AuthApi.refresh()` отправляет `POST /api/v1/auth/refresh` без тела
  с `credentials: "same-origin"`, при `200` возвращает пользователя, при `401`
  выбрасывает `unauthorized`, при остальных исходах — `unavailable` или
  `invalid_response` по существующим правилам `AuthApi`.
- REQ-007: Общая проверка сессии вызывает `GET /api/v1/users/me`; при
  `unauthorized` один раз вызывает `refresh()` и при успехе использует
  пользователя из его ответа (по контракту — актуальные данные из БД).
  Результат — один из исходов: «пользователь», «нет сессии» или «сервис
  недоступен».

### Frontend: чат `/`

- REQ-008: При открытии чат сначала проверяет сессию и только после
  результата «пользователь» создаёт диалог и открывает `EventSource`. До этого
  форма заблокирована.
- REQ-009: При результате «нет сессии» страница выполняет переход на
  `/login/` через `location.replace`, не создавая диалог.
- REQ-010: При результате «сервис недоступен» страница не переходит на
  `/login/`, показывает состояние недоступности, держит форму заблокированной
  и повторяет проверку через три секунды.
- REQ-011: Если создание диалога или отправка сообщения получили `401`,
  frontend один раз выполняет `refresh()` и повторяет ту же операцию; при
  повторном отказе по сессии выполняется переход на `/login/`. Пользовательский
  запрос не дублируется: повтор отправки выполняется только после `401`,
  когда backend гарантированно не принял запрос.
- REQ-012: При ошибке SSE-соединения frontend проверяет сессию по REQ-007:
  «нет сессии» — переход на `/login/`; «пользователь» — если `EventSource`
  закрыт браузером, открывается новое соединение к тому же `dialog_id`; если
  браузер переподключается сам, новое соединение не создаётся.

### Frontend: панель администратора `/admin/`

- REQ-013: Перед отображением demo-данных `/admin/` выполняет ту же проверку
  сессии: «нет сессии» — переход на `/login/`; пользователь с ролью `user` —
  переход в чат `/`; роль `admin` — показ панели; «сервис недоступен» —
  сообщение о недоступности без demo-данных. До результата проверки demo-данные
  не отображаются. Проверка на frontend не является защитой данных: панель
  по-прежнему работает только на локальных demo-данных, а будущий
  административный API должен проверять роль на backend.

### Frontend: страница входа `/login/`

- REQ-014: При открытии `/login/` используется проверка сессии из REQ-007:
  если пользователь получен (в том числе после `refresh()`), выполняется
  переход по роли, иначе форма остаётся доступной.
- REQ-015: После успешного входа или регистрации и при переходе из REQ-014
  страница `/login/` открывает `/admin/` для роли `admin` и `/` для роли
  `user`. Адрес перехода не берётся из URL или другого пользовательского ввода.

### Создание администратора

- REQ-016: Консольная команда backend создаёт пользователя с ролью `admin`
  по логину и паролю. Запуск из корня репозитория:
  `make create-admin LOGIN=<login>`; Make-цель выполняет команду в Docker
  Compose после применения миграций.
- REQ-017: Пароль запрашивается интерактивно без отображения ввода и
  подтверждается повторным вводом. Пароль не передаётся аргументом командной
  строки или переменной окружения и не выводится в консоль или журнал.
- REQ-018: Логин и пароль проверяются по тем же правилам, что и при
  регистрации (`Credentials`), а пароль хешируется тем же
  `Argon2PasswordHasher`. Созданный администратор входит через обычный
  `POST /api/v1/auth/login`.
- REQ-019: Если логин занят (без учёта регистра), поля нарушают правила,
  пароли не совпадают или база недоступна, команда завершается с ненулевым
  кодом и понятным сообщением без введённого пароля и ничего не записывает.
- REQ-020: Роль `admin` по-прежнему нельзя получить через HTTP API:
  регистрация создаёт только `user`.

### Документация

- REQ-021: [`docs/auth.md`](../../../docs/auth.md),
  [`docs/dialogs.md`](../../../docs/dialogs.md), `frontend/README.md` и
  раздел «Реализованный frontend»/«Реализованные диалоги» в `AGENTS.md`,

## Сценарии

### Гость открывает чат

- Given в браузере нет cookie `access_token` и `refresh_token`
- When пользователь открывает `/`
- Then frontend получает `401` от `/users/me` и от `/auth/refresh`
- And выполняется переход на `/login/`, `POST /api/v1/dialogs` не отправляется

### Access-токен истёк, refresh действителен

- Given пользователь входил ранее, access-токен истёк, refresh-токен действителен
- When пользователь открывает `/`
- Then `/users/me` отвечает `401`, `/auth/refresh` — `200` с новыми cookie
- And повторный `/users/me` отвечает `200`, чат создаёт диалог как обычно

### Сессия истекла во время работы

- Given открыт чат, access-токен истёк, refresh-токен отозван
- When пользователь отправляет сообщение
- Then `POST .../messages` отвечает `401`, `refresh` отвечает `401`
- And выполняется переход на `/login/`, реплика пользователя в чат не добавлена

### Обычный пользователь открывает админку

- Given пользователь с ролью `user` вошёл в систему
- When он открывает `/admin/`
- Then `/users/me` отвечает `200` с `"role":"user"`
- And выполняется переход в чат `/`, demo-данные не показываются

### Назначение первого администратора

- Given приложение запущено, логин `ksenia` свободен
- When выполняется `make create-admin LOGIN=ksenia` и дважды вводится пароль
- Then команда сообщает о создании администратора
- And вход `ksenia` через `/login/` возвращает `"role":"admin"`
- And после входа `/login/` открывает `/admin/`, и панель отображается

### Логин администратора уже занят

- Given пользователь `Ksenia` уже существует
- When выполняется `make create-admin LOGIN=ksenia`
- Then команда завершается с ошибкой «логин уже занят», база не меняется

### Backend недоступен

- Given PostgreSQL или Redis недоступны
- When пользователь открывает `/`
- Then `/users/me` отвечает `503`
- And страница остаётся на `/`, форма заблокирована, проверка повторяется

### Гость обращается к API напрямую

- Given запрос без cookie
- When клиент вызывает `POST /api/v1/dialogs/<несуществующий id>/messages`
- Then ответ `401` `{"error":"unauthorized"}`, а не `404`

## Технологии и структура

- Backend: FastAPI-зависимость `current_user` из `api/auth.py` подключается к
  роутеру диалогов. `create_app` без `auth_service` используется только
  тестами; в этом случае ручки диалогов должны fail closed (`503`), а не
  оставаться открытыми — детали фиксируются в плане.
- Frontend: vanilla JavaScript без новых зависимостей. Проверка сессии
  выносится в отдельный модуль без зависимости от DOM (предварительно
  `src/auth-session.js`), который используют чат, `/admin/` и `/login/`.
  `AgentApi` различает `401` (код `unauthorized`) и прочие ошибки.
- Создание администратора: модуль backend с запуском
  `python -m smeshariki_ai.<модуль>` по аналогии с `smeshariki_ai.db.migrate`;
  использует `Credentials`, `Argon2PasswordHasher` и `UserStore`
  (`PostgresUserStore` в production). Чтение пароля и вывод отделены от
  логики создания, чтобы её можно было тестировать без терминала. Точное имя
  модуля и способ вызова через Compose фиксируются в плане.
- Привязка диалогов к пользователю, кнопка выхода, снятие роли `admin`,
  повышение роли существующего пользователя и
  административный backend API в объём не входят.

## Команды

- Запуск: `make run`
- Тесты: `make test`
- Линтер: `make lint`

## Тестирование

- Backend Pytest (integration, in-memory реализации `auth/memory.py`): `401`
  для каждой ручки диалогов без cookie, с некорректным токеном и токеном в
  blacklist; `401` раньше `404`/`422`; `503` при недоступности хранилищ;
  прежнее поведение с действительным токеном. Существующие тесты диалогов и
  SSE обновляются, чтобы выполнять вход перед вызовами.
- Frontend Node-тесты с fake `fetch` и fake `EventSource`: `AuthApi.refresh`;
  три исхода проверки сессии, включая единственную попытку refresh; редирект
  и отсутствие `POST /dialogs` у гостя; повтор после `401` у создания диалога
  и отправки без дублирования реплики; поведение при ошибке SSE; guard для
  `/admin/` с ролями `user` и `admin`; переход по роли на `/login/`.
- Backend Pytest для создания администратора на in-memory `UserStore`:
  успешное создание с ролью `admin` и хешем, проверяемым
  `Argon2PasswordHasher`; занятый логин в другом регистре; нарушение правил
  полей; несовпадение паролей; недоступность хранилища; отсутствие пароля в
  выводе и журнале.
- Ручная проверка в `make run`: гость с `/` и `/admin/` попадает на `/login/`;
  после входа чат работает; обычный пользователь с `/admin/` попадает в чат;
  после `make create-admin` вход администратора открывает `/admin/`; после удаления cookie `access_token` страница
  восстанавливает сессию через refresh.

## Границы

- Всегда: токены остаются только в `HttpOnly` cookie; JavaScript не читает
  cookie и не хранит токены; пользовательский текст не логируется.
- Сначала спросить: привязка диалогов к владельцу, изменения контракта
  backend-ручек аутентификации, новые способы выдачи роли `admin`.
- Никогда: пароль в аргументах команды, environment или журнале; заголовок
  `Authorization`, хранение токенов в `localStorage`,
  открытый редирект на произвольный URL, выдача роли `admin` через HTTP.

## Критерии приёмки

- [ ] Без сессии все три ручки диалогов отвечают `401`
  `{"error":"unauthorized"}`, в том числе для несуществующего диалога.
- [ ] С действительной сессией существующие сценарии диалогов и SSE проходят.
- [ ] Гость на `/` и `/admin/` попадает на `/login/` без создания диалога.
- [ ] Пользователь с ролью `user` на `/admin/` попадает в `/` и не видит
  demo-данные; администратор видит панель.
- [ ] После входа администратор попадает в `/admin/`, пользователь — в `/`.
- [ ] `make create-admin LOGIN=<login>` создаёт администратора, который
  входит через `/login/` и видит панель; пароль нигде не отображается.
- [ ] Занятый логин, неверные поля и несовпадение паролей дают ошибку без
  записи в базу.
- [ ] Истёкший access-токен при действительном refresh не приводит к
  переходу на `/login/`.
- [ ] Недоступность backend не приводит к переходу на `/login/`.
- [ ] `/login/` с действительной сессией переходит на страницу по роли.
- [ ] Документация обновлена по REQ-021.
- [ ] `make test` и `make lint` проходят успешно.

## Открытые вопросы

- Ручки для защиты не перечислены в задаче явно; предполагаются три ручки
  диалогов (REQ-001). Ответ команды подтверждается до начала реализации.
