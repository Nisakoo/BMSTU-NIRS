# BM25-поиск по лору: ядро, PostgreSQL-индекс и загрузка

## Цель

Добавить в RAG собственный поиск BM25 по неструктурированному лору
(сценарии, описания эпизодов, фрагменты сюжетов), чтобы агент мог получать
нарративный контекст, а не только структурированные карточки канона.
Индекс реализуется самостоятельно, без готовых поисковых движков.
Production-индекс хранится и считается в PostgreSQL и не требует загрузки
всего корпуса в память backend. In-memory реализация нужна только для
детерминированных тестов и benchmark.

Изменение создаёт ядро BM25, формат YAML-пакета лора, таблицы `rag_lore_*`,
загрузку и поиск через CLI. Интеграция с агентом (`search_lore`) и
benchmark-метрики оформляются следующими изменениями.

## Допущения

- Размер корпуса заранее не считается малым. Production-поиск не держит
  корпус и postings в памяти процесса и не делает запрос на каждый документ.
  In-memory индекс допустим только для тестов и benchmark.
- Лор — отдельный слой от структурированного канона. BM25 ищет нарративные
  фрагменты; `lookup_knowledge` продолжает отвечать за точные факты.
- Реальные данные лежат вне Git в `data/` и распространяются зашифрованными;
  тесты и benchmark используют синтетический корпус.
- Формат пакета — YAML, совместимый по стилю с существующим RAG.
- Лемматизация разрешена. Используется `pymorphy3`; выбор обосновывается
  benchmark-сравнением с простым анализатором.
- Изменение не трогает `agent`, `application`, `api`, `dialogs`, `auth`,
  `admin`, frontend и `bootstrap.py`. Инструмент агента появится отдельно.

## Требования

### Домен и BM25

- REQ-001: Должны существовать неизменяемые модели `LoreDocument`,
  `LoreChunk`, `LoreQuery`, `LoreHit` и `LoreSearchResult`. Документ содержит
  `id`, `title`, `text`, необязательные `source`, `continuity`, `characters`,
  `tags`; чанк — `document_id`, `position`, `text`, `term_count`.
- REQ-002: Чистый модуль BM25 реализует IDF
  `ln(1 + (N - df + 0.5) / (df + 0.5))`, вклад терма
  `tf*(k1+1)/(tf + k1*(1-b+b*L/avgdl))` и сумму по уникальным термам запроса.
  Параметры по умолчанию — `k1=1.2`, `b=0.75`.
- REQ-003: BM25 корректно обрабатывает пустой корпус, `avgdl=0`, терм с
  `df=0`, `tf=0`, пустой запрос и отсутствие совпадений. Документы с нулевым
  баллом не возвращаются. Сортировка — по убыванию балла, затем по
  `(document_id, position)`.
- REQ-004: `TextAnalyzer` — порт с методом `terms(text) -> tuple[str, ...]`.
  `SimpleAnalyzer` выполняет NFC, нижний регистр, `ё → е`, разбиение по
  Unicode-словам и сохраняет дефисные имена; `MorphAnalyzer` дополнительно
  приводит русские слова к начальной форме через `pymorphy3`, а неизвестные
  слова и имена оставляет как есть. Запрос и документы проходят один и тот же
  анализатор.
- REQ-005: `pymorphy3` добавляется в backend-зависимости. Отказ от
  лемматизации или замена библиотеки возможны только по результатам
  benchmark и с обоснованием.

### Порты и адаптеры

- REQ-006: `LoreDocumentSource` — порт чтения документов и версии корпуса;
  `LoreIndex` — порт перестроения и поиска; `LoreStore` — порт загрузки и
  замены корпуса. Use case `SearchLore` зависит только от портов и не знает
  о PostgreSQL, CLI и агенте.
- REQ-007: `InMemoryBm25Index` реализует `LoreIndex` для тестов и benchmark:
  хранит postings `term -> {chunk_key: tf}`, длины чанков, `N` и `avgdl`,
  считает баллы чистым Python-модулем BM25.
- REQ-008: `PostgresBm25Index` реализует `LoreIndex` для production: поиск
  выполняется одним set-based SQL-запросом по таблицам postings, термов,
  чанков и статистики. Число SQL-запросов не зависит от числа документов;
  корпус не загружается в память целиком.
- REQ-009: `InMemoryBm25Index` и `PostgresBm25Index` проходят один
  контрактный набор тестов и дают одинаковый порядок результатов на одном
  наборе документов и запросов.

### Хранение и масштаб

- REQ-010: Миграция `0013_lore_bm25` создаёт таблицы `rag_lore_documents`,
  `rag_lore_chunks`, `rag_lore_terms`, `rag_lore_postings`, `rag_lore_stats`
  и `rag_lore_loads`. Внешние ключи существуют только внутри `rag_lore_*`;
  связей с другими модулями нет.
- REQ-011: `rag_lore_postings` имеет первичный ключ `(term, chunk_id)` и
  индекс по `term`; `rag_lore_chunks` — уникальность
  `(document_id, position)` и индекс по `document_id`;
  `rag_lore_terms.df` хранит число чанков с термом; `rag_lore_stats` хранит
  `n_chunks`, `avgdl` и версию корпуса.
- REQ-012: `lore-load` заменяет корпус целиком в одной транзакции: удаляет
  прежние документы, чанки, postings, термы и статистику, пишет новые данные
  пакетами и обновляет версию. Читатель видит либо старый, либо новый корпус,
  но не частичную загрузку. При ошибке БД не меняется.
- REQ-013: Загрузка не обязана держать весь корпус в памяти: документы
  читаются по одному, чанки и postings пишутся пакетами, словарь термов и
  счётчики `df` накапливаются отдельно от текстов. Размер пакета фиксирован
  константой.
- REQ-014: `lore-search` не перестраивает индекс на каждый запрос, не читает
  все чанки и не делает запрос на документ. Поиск использует индексы
  `rag_lore_terms` и `rag_lore_postings`; статистика читается один раз.

### Пакет лора

- REQ-015: Пакет — каталог с обязательным `package.yaml`
  (`format_version: 1`) и `documents/<id>.yaml`. Пакет может содержать любое
  непустое подмножество документов. Один файл — один документ; `id` совпадает
  с именем файла.
- REQ-016: `check` проверяет пакет без БД и environment: обязательные поля,
  типы, непустой текст, уникальность `id`, отсутствие лишних файлов,
  символьных ссылок, тегов и якорей YAML. Ошибки адресуются файлом и полем;
  код возврата `0` — валиден, `1` — невалиден или не найден, `2` — неверные
  аргументы.
- REQ-017: Чанкование детерминировано: целевой размер 150–250 слов,
  перекрытие 30–50 слов, границы документа не пересекаются, слишком короткие
  чанки сливаются с соседним. Позиция чанка стабильна и используется в
  tie-break.

### CLI и наблюдаемость

- REQ-018: `python -m smeshariki_ai.rag lore-check <path> [--format text|json]`
  не читает environment. `lore-load <path>` читает конфиг только при
  выполнении, пишет журнал `rag_lore_loads` и возвращает `0/1/2`.
  `lore-search "<query>" [--top-k N] [--format text|json]` читает конфиг,
  возвращает `0` при успехе, `1` при недоступной БД или схеме, `2` при
  неверных аргументах.
- REQ-019: `make lore-check DIR=<path>`, `make lore-load DIR=<path>` и
  `make lore-search QUERY="..." [TOPK=N]` запускают команды из корня. Цели
  аддитивны и не меняют существующие команды знаний.
- REQ-020: События `lore.load.completed` и `lore.search.completed` содержат
  `outcome`, длительность, число документов/чанков, число совпадений и
  версию корпуса. Текст запроса, документов, чанков и термов в журнал не
  попадает.

### Документация и проверка

- REQ-021: `docs/lore.md` описывает назначение, формулу BM25, формат пакета,
  чанкование, таблицы, команды, масштабирование и ограничения;
  `docs/rag.md`, `docs/database.md`, `docs/README.md` получают ссылки и
  строки о новых таблицах и командах. `AGENTS.md` и `bootstrap.py` не
  меняются в этом изменении.
- REQ-022: Unit-тесты покрывают формулу, анализатор, пакет, чанкование и
  use case; интеграционные тесты — миграцию, загрузку, PostgreSQL-поиск,
  контракт in-memory/PostgreSQL и CLI. `make lint`, `make test` и
  `make test-integration` проходят. Тесты проверяют поведение продукта, а не
  структуру каталогов.

## Сценарии

### Загрузка и поиск

- Given синтетический пакет из трёх документов про возврат оплаты
- When выполняется `lore-load`, затем `lore-search "возврат оплаты"`
- Then в выдаче первым идёт документ, где встречаются оба терма, и его текст
  возвращается вместе с `document_id`, `title` и позицией чанка.

### Лемматизация

- Given документ содержит «возвращают билеты», а запрос — «возврат билета»
- When используется `MorphAnalyzer`
- Then документ находится по общей лемме; `SimpleAnalyzer` на этом примере
  может не найти совпадение, что фиксируется benchmark-различием.

### Пустой корпус

- Given таблицы `rag_lore_*` пусты
- When выполняется `lore-search`
- Then возвращается пустая выдача без ошибки, а не `500`.

### Схема не готова

- Given миграция `0013` не применена
- When выполняется `lore-load` или `lore-search`
- Then команда возвращает безопасную ошибку `schema_not_ready` и код `1`,
  PostgreSQL не изменяется.

### Большой корпус

- Given в БД десятки тысяч чанков
- When выполняется поиск по двум-трём термам
- Then поиск не загружает все чанки в память и не выполняет запрос на каждый
  документ; число SQL-запросов фиксировано.

### Ошибка в пакете

- Given документ без `title` или с `id`, не совпадающим с именем файла
- When выполняется `lore-check`
- Then Возвращается `1`, ошибка указывает файл и поле, загрузка не
  выполняется.

## Технологии и структура

- Python 3.12, Pydantic, SQLAlchemy async Core, asyncpg, Alembic, PyYAML —
  существующий стек.
- Новая зависимость: `pymorphy3` для русской лемматизации.
- Новый пакет `smeshariki_ai.rag.lore`:
  - `models.py` — доменные модели;
  - `bm25.py` — чистый расчёт;
  - `analyzer.py` — `TextAnalyzer`, `SimpleAnalyzer`, `MorphAnalyzer`;
  - `index.py` — `InMemoryBm25Index`;
  - `ports.py` — `LoreDocumentSource`, `LoreIndex`, `LoreStore`;
  - `services.py` — `SearchLore`, `LoadLore`;
  - `package.py` — чтение и проверка YAML-пакета;
  - `chunking.py` — детерминированное чанкование;
  - `postgres.py` — `PostgresLoreDocumentStore`, `PostgresLoreStore`,
    `PostgresBm25Index`;
  - `tables.py` — метаданные `rag_lore_*`.
- Миграция `backend/src/smeshariki_ai/db/migrations/versions/0013_lore_bm25.py`
  — аддитивная, только таблицы `rag_lore_*`.
- CLI добавляется в существующий `smeshariki_ai.rag.cli`; Makefile получает
  аддитивные RAG-цели.
- `bootstrap.py`, `config.py`, `agent`, `application`, `api` и frontend не
  меняются.

## Границы

- Всегда: только `backend/src/smeshariki_ai/rag/`, RAG-тесты, RAG-документация,
  аддитивная миграция `rag_lore_*` и аддитивные Make-цели.
- Сначала спросить: изменения `bootstrap.py`, `config.py`, `agent`,
  `application`, `api`, frontend, системного промпта, а также любые правки
  чужих файлов, кроме аддитивных RAG-строк.
- Никогда: готовый поисковый индекс, PostgreSQL FTS/`ts_rank` как замена
  BM25, embeddings/vector DB, отдельный сервис, реальные данные в Git,
  текст запросов и документов в журнале.

## Критерии приёмки

- [ ] BM25 реализован самостоятельно и совпадает с формулой методички.
- [ ] Production-поиск работает через PostgreSQL и не загружает корпус в
      память; in-memory адаптер проходит тот же контракт.
- [ ] YAML-пакет лора проверяется, загружается и заменяет корпус атомарно.
- [ ] `lore-check`, `lore-load`, `lore-search` и Make-цели работают с
      кодами `0/1/2`.
- [ ] Схема `rag_lore_*` создаётся миграцией `0013` и не связана с другими
      модулями.
- [ ] Логи не содержат текста запросов, документов и термов.
- [ ] `make lint`, `make test` и `make test-integration` проходят.
- [ ] Документация обновлена; `bootstrap.py`, `config.py` и чужие модули не
      изменены.
