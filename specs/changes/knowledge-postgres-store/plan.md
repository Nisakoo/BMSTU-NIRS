# План: хранилище структурированных знаний в PostgreSQL

## Основание

План реализует согласованную спецификацию
`specs/changes/knowledge-postgres-store/spec.md`: таблицы `rag_*`, миграцию
`0003`, порт `KnowledgeStore` с in-memory и PostgreSQL-реализациями, журнал
загрузок и ревизий, use case и команду загрузки. Выгрузка, удаление и
инструмент агента остаются следующим изменениям.

## Решения и зависимости

- Новых зависимостей нет: SQLAlchemy Core (async), asyncpg, Alembic,
  PostgreSQL 17.
- Описание таблиц выносится в `rag/tables.py` с собственным `MetaData`, а
  адаптер — в `rag/postgres.py`: так файлы не смешивают схему и логику
  сохранения. Миграция `0003` описывает те же таблицы явно, как миграции
  `0001` и `0002`; совпадение проверяет тест сравнения схемы через
  `alembic.autogenerate.compare_metadata`.
- Ссылки между агрегатами указывают только на корневые таблицы
  (`ON DELETE RESTRICT`), поэтому сохранение может удалять и вставлять
  дочерние строки агрегата, не трогая чужие агрегаты. Внутри агрегата все
  внешние ключи — `ON DELETE CASCADE`.
- Два правила целостности дополнительно закрепляются составными внешними
  ключами внутри агрегата, без триггеров: участники взаимодействия ссылаются
  на `(episode_id, character_id)` участников эпизода, а варианты канона
  отношения — на `(character_id, continuity_id)` версий владельца.
- Таблицы списков имеют ключ «владелец — `position`» и уникальность значения в
  пределах владельца; таблица вариантов канона версий — ключ
  «персонаж — вариант канона». Нормализованное имя вычисляет приложение
  функцией `normalize_name`: это осознанная денормализация ради индекса.
- Транзакция порта: `read_all`, `start_load(started_at)`, `save(changes,
  load_id)` и `finish_load(load_id, finished_at, report)`. Номер ревизии
  назначает хранилище: следующий после максимального номера сущности.
  Время даёт подменяемая функция `clock` use case, как в `create_admin`.
- Сохранение сначала удаляет дочерние строки всех изменённых агрегатов, затем
  обновляет корни (`INSERT … ON CONFLICT (id) DO UPDATE`) в порядке
  «варианты канона → произведения → персонажи → локации → артефакты →
  эпизоды» и вставляет дочерние строки. Так перенос алиаса между персонажами
  одного пакета не нарушает уникальность. Каждая таблица пишется одним
  пакетным запросом.
- Адаптер переводит `SQLAlchemyError`, `PostgresError`, `OSError` и
  `TimeoutError` в `KnowledgeStoreUnavailableError`, а отсутствующую таблицу
  (`UndefinedTableError`) — в `KnowledgeSchemaNotReadyError`, по образцу
  `_unavailable_on_failure` в `db/history.py`.
- `load` получает фабрику хранилища через параметр `cli.main`: по умолчанию
  она создаёт engine из `load_config().database`, а тесты передают
  in-memory хранилище. `check` и `schema` конфиг не загружают.
- PostgreSQL-тесты лежат в `tests/integration/rag/`; их `conftest.py`
  пересоздаёт схему `public` и применяет миграции, как тесты других модулей.
  Для проверки используется временный контейнер `postgres:17-alpine`.

## Порядок реализации

1. Таблицы и миграция — самый рискованный шаг: схема, ограничения и
   совместимость с тестами других модулей.
2. Порт, in-memory хранилище и контрактный набор.
3. PostgreSQL-адаптер.
4. Use case загрузки.
5. Команда `load` и цель `Makefile`.
6. Документация и общие файлы.
7. Итоговая проверка.

## Задача 1. Таблицы `rag_*` и миграция `0003`

**Связанные требования:** REQ-001–REQ-009, REQ-025.

**Критерии приёмки:** миграция создаёт 23 таблицы и удаляет их при
`downgrade`; схема после `upgrade` совпадает с `rag/tables.py`; ограничения
отвергают недопустимые строки; двойной цикл «удалить `public` → `upgrade`»
проходит.

**Зависимости:** нет.

**Файлы:**

- `backend/src/smeshariki_ai/rag/tables.py`;
- `backend/src/smeshariki_ai/db/migrations/versions/0003_rag_knowledge.py`;
- `backend/tests/integration/rag/conftest.py`;
- `backend/tests/integration/rag/test_schema.py`.

**Действия (RED → GREEN → REFACTOR):**

1. Написать падающие тесты: сравнение схемы с `MetaData`, `downgrade` до
   `0002` и повторный `upgrade`, двойной сброс схемы `public`, по тесту на
   каждый вид ограничения (формат `id`, словари, номера, уникальность номера
   эпизода, уникальность имён персонажей, одна версия на вариант канона,
   участник взаимодействия вне эпизода, `RESTRICT` между агрегатами, `jsonb`
   не массив).
2. Описать таблицы по группам: корни с `created_at`/`updated_at`, имена,
   версии, связи, списки, журнал. Имена ограничений — в стиле проекта
   (`rag_episodes_number_positive`).
3. Написать миграцию `0003` с `down_revision = "0002"`.

**Тест:**

```sh
TEST_DATABASE_URL=… uv run --project backend --locked pytest backend/tests/integration/rag/test_schema.py
```

## Задача 4. Use case загрузки

**Связанные требования:** REQ-017–REQ-022.

**Критерии приёмки:** невалидный пакет не открывает хранилище; пакет
объединяется с БД; нарушение по данным БД откатывает транзакцию и адресуется
`db:<тип>/<id>`; неизменные сущности не сохраняются; отчёт содержит
идентификатор загрузки, счётчики по типам, общее число и длительность;
недоступная БД и неготовая схема дают коды `database_unavailable` и
`schema_not_ready`.

**Зависимости:** задача 2.

**Файлы:**

- `backend/src/smeshariki_ai/rag/services.py`;
- `backend/tests/unit/rag/test_load.py`.

**Действия (RED → GREEN → REFACTOR):**

1. Написать падающие тесты на in-memory хранилище для каждого критерия.
2. Реализовать `load_package(root, store, clock)`: проверка пакета,
   транзакция, объединение, `check_integrity(complete=True)`, расчёт
   изменений, сохранение и отчёт `LoadReport`.

**Тест:**

```sh
uv run --project backend --locked pytest backend/tests/unit/rag/test_load.py
```
