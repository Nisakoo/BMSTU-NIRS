# Несколько вызовов инструментов в одном ответе LLM

## Цель

Агент должен отвечать на запросы, для которых модель в одном ответе просит
вызвать несколько инструментов. Сейчас runtime допускает ровно один tool call
на ответ LLM, а `deepseek/deepseek-flash` на запрос «Придумай мне сказку про
Кроша и Ежика с их любимыми предметами» стабильно возвращает два параллельных
вызова `lookup_knowledge` (иногда и третий — `get_context`).
`LiteLLMProvider` отвергает такой поток с `TypeError`, пользователь видит
«Ошибка ответа». Флаг `parallel_tool_calls=False` эта модель игнорирует
(проверено тремя запросами), поэтому исправление нужно в runtime и
провайдере.

При реализации выяснилось второе препятствие: `deepseek-flash` работает в
режиме рассуждений и отвечает `400` («The `reasoning_content` in the thinking
mode must be passed back to the API»), если сообщение ассистента с tool calls
возвращается в историю без его `reasoning_content`. Это касается и одного
вызова. Провайдер сейчас рассуждения отбрасывает, поэтому продолжение после
вызова инструмента может падать. С `reasoning_content` та же история
принимается (проверено реальным запросом).

## Допущения

- Вызовы одного ответа выполняются последовательно в порядке, заданном
  моделью (по `index` потока). Конкурентное выполнение — отдельное изменение,
  если понадобится.
- Лимит вызовов в одном ответе нужен, чтобы ошибочный ответ модели не запустил
  неограниченную работу. Значение по умолчанию — 4, задаётся в `AgentConfig`;
  переменная окружения не добавляется.
- Вызовы сверх лимита не выполняются, но получают безопасный `ToolResult` с
  ошибкой: Chat Completions требует ответ на каждый `tool_call_id`, а модель
  сможет продолжить с полученными данными.
- Лимит итераций (`max_iterations`, по умолчанию 4) не меняется: одна
  итерация — один ответ LLM вместе со всеми его вызовами.
- Смешение текста и tool calls в одном ответе по-прежнему некорректно.
- История диалога, HTTP API, SSE-события и инструменты не меняются: tool calls
  в историю не сохраняются.
- Рассуждения модели — внутренние данные одного запуска агента: они не
  показываются пользователю, не сохраняются в историю диалога и не
  журналируются. Возвращаются они только в сообщении ассистента с tool calls
  внутри того же запуска. Если провайдер рассуждений не прислал, поле не
  передаётся, и поведение для других моделей не меняется.

## Требования

- REQ-001: `LiteLLMProvider` собирает из потока все tool calls ответа по их
  `index` и возвращает их в `LLMResponse.tool_calls` в порядке возрастания
  `index`. Индекс — неотрицательное целое; фрагменты одного индекса
  склеиваются, как сейчас.
- REQ-002: Ответ с tool calls некорректен (`LLMProviderError`), если у
  какого-либо вызова пустые `id` или имя, аргументы не являются JSON-объектом,
  `id` повторяются или ответ смешивает текст и tool calls.
- REQ-003: `Agent` считает ответ без текста с одним или несколькими tool calls
  ответом типа `tool_call`. Ответ без текста и без вызовов, а также с текстом
  и вызовами одновременно остаётся некорректным.
- REQ-004: Для ответа с tool calls `Agent` добавляет в рабочий контекст одно
  сообщение ассистента со всеми вызовами ответа, затем по одному сообщению с
  результатом на каждый вызов в том же порядке, и снова обращается к LLM.
- REQ-005: Первые `AgentConfig.max_tool_calls_per_response` вызовов (по
  умолчанию 4, целое больше нуля) выполняются через `ToolRegistry`
  последовательно. Остальные не выполняются и получают `ToolResult` с ошибкой
  `tool_call_limit_exceeded`.
- REQ-006: `LiteLLMProvider` переводит сообщение ассистента с несколькими
  вызовами в одно Chat Completions сообщение с массивом `tool_calls` и
  `content: null`.
- REQ-007: Журнал: `agent.llm.completed` дополнительно содержит
  `tool_call_count`; каждый вызов, выполненный или отклонённый по лимиту,
  журналируется событиями `agent.tool.*` со своим `tool_call_id`, отклонённый —
  с `tool_status="error"`. Аргументы и результаты в журнал по-прежнему не
  попадают.
- REQ-008: Отмена asyncio-задачи во время выполнения любого из вызовов
  распространяется без преобразования, как сейчас.
- REQ-009: `docs/agent.md` и раздел «Реализованный runtime агента» в
  `AGENTS.md` описывают несколько вызовов в одном ответе, лимит и возврат
  рассуждений.
- REQ-010: `LiteLLMProvider` собирает текстовые фрагменты
  `delta.reasoning_content` ответа и для ответа с tool calls возвращает их в
  `LLMResponse.reasoning_content`; пользователю они не передаются как
  `LLMTextDelta`. Нестроковое значение — некорректный ответ.
- REQ-011: `Agent` переносит `reasoning_content` в сообщение ассистента с
  вызовами, а `LiteLLMProvider` передаёт его в Chat Completions сообщении
  ассистента полем `reasoning_content` только если оно непустое. Финальные
  ответы, история диалога и журнал рассуждений не содержат.

## Сценарии

### Сказка про двух героев

- Given модель отвечает двумя вызовами `lookup_knowledge` («Крош», «Ёжик»), а
  затем финальным текстом
- When пользователь отправляет запрос
- Then оба инструмента выполняются, модель получает обе карточки, пользователь
  получает финальный ответ, история сохраняет только запрос и ответ

### Слишком много вызовов

- Given `max_tool_calls_per_response = 2`, модель возвращает три вызова
- When агент обрабатывает ответ
- Then выполняются первые два, третий получает `tool_call_limit_exceeded`, а
  агент обращается к LLM со всеми тремя результатами

### Некорректный поток

- Given поток содержит два вызова с одинаковым `id` или текст вместе с вызовами
- When провайдер собирает ответ
- Then `LLMProviderError`, запуск завершается контролируемой ошибкой, история не
  меняется

### Модель с рассуждениями

- Given поток ответа с tool call содержит фрагменты `reasoning_content`
- When агент выполняет вызов и снова обращается к LLM
- Then сообщение ассистента в запросе содержит те же рассуждения, пользователь
  их не видит, в историю и журнал они не попадают

### Прежнее поведение

- Given модель возвращает один вызов или сразу финальный текст
- When агент обрабатывает ответ
- Then поведение и журнал совпадают с текущими, кроме нового поля
  `tool_call_count`

## Технологии и структура

- `agent/models.py`: `Message.tool_call: ToolCall | None` заменяется на
  `Message.tool_calls: tuple[ToolCall, ...]`; `Message` и `LLMResponse`
  получают `reasoning_content: str | None = None`; `AgentConfig` получает
  `max_tool_calls_per_response: int = 4` (`gt=0`).
- `agent/runtime.py`: `_result_type` и цикл обработки вызовов.
- `agent/providers/litellm.py`: сборка нескольких вызовов из потока и
  отображение сообщения ассистента.
- Новых зависимостей, переменных окружения, таблиц и HTTP-контрактов нет.

## Границы

- Всегда: последовательное выполнение; ответ на каждый `tool_call_id`;
  безопасный журнал.
- Сначала спросить: конкурентное выполнение вызовов; переменная окружения для
  лимита; изменение `max_iterations` или системного промпта.
- Никогда: сохранять tool calls или рассуждения в историю диалога; показывать
  рассуждения пользователю; включать auto-execution LiteLLM; журналировать
  аргументы и результаты инструментов и рассуждения.

## Критерии приёмки

- [ ] Ответ модели с несколькими tool calls выполняется, и агент возвращает
      финальный ответ.
- [ ] Вызовы сверх лимита не выполняются и получают `tool_call_limit_exceeded`.
- [ ] Некорректные потоки (повторный `id`, текст с вызовами, не-JSON
      аргументы) дают `LLMProviderError`.
- [ ] Одиночный вызов и финальный ответ работают как раньше.
- [ ] Журнал содержит `tool_call_count` и события по каждому вызову без payload.
- [ ] Рассуждения модели возвращаются в сообщении ассистента с вызовами и не
      попадают к пользователю, в историю и в журнал.
- [ ] `docs/agent.md` и `AGENTS.md` обновлены.
- [ ] `make lint` и `make test` проходят; запрос из раздела «Цель» в запущенном
      приложении получает ответ.
