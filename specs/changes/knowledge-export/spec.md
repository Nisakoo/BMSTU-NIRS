# Выгрузка знаний из PostgreSQL в пакет

## Цель

Дать автору контента и его агенту способ получить текущее состояние структурированных знаний из PostgreSQL в виде обычного пакета YAML: для просмотра, редактирования вне репозитория и резервной копии перед изменениями. Выгрузка не меняет базу и не требует остановки backend. Это первое изменение серии `knowledge-maintenance`. За ним следуют `knowledge-delete` и `knowledge-optimistic-lock`.

## Требования

### Снимок хранилища
- REQ-001: Порт `KnowledgeStore` получает операцию `snapshot()`, возвращающую `KnowledgeSnapshot` с неизменяемым `KnowledgeSet` и индексом текущих ревизий сущностей. `PostgresKnowledgeStore` читает снимок в одной транзакции `REPEATABLE READ
  READ ONLY` без advisory lock загрузки; `InMemoryKnowledgeStore` возвращает согласованное состояние процесса. Оба адаптера проходят общий контрактный набор.
- REQ-002: `PostgresKnowledgeStore.snapshot()` выполняет фиксированное число запросов, не зависящее от числа сущностей, и видит состояние БД до или после параллельной загрузки целиком, а не её середину.
- REQ-003: Ошибки снимка переводятся в существующие `KnowledgeStoreUnavailableError`, `KnowledgeSchemaNotReadyError` и `KnowledgeDataInvalidError` без текста SQL, параметров и содержимого строк. ### Use case выгрузки
- REQ-004: Use case `export_package(path, store, types=None)` читает снимок один раз, при необходимости оставляет только выбранные типы и возвращает `ExportReport`. Если в БД нет ни одной сущности — ошибка `empty_store`; если фильтр не
  выбрал ни одной сущности — ошибка `empty_selection`; в обоих случаях файлы не создаются.
- REQ-005: Каталог назначения проверяется до чтения БД: он должен отсутствовать или быть пустым. Существующий непустой каталог или файл — ошибка `destination_not_empty`; существующие файлы не удаляются и не перезаписываются.
- REQ-006: Запись пакета атомарна с точки зрения наблюдаемого результата: при ошибке чтения, проверки или записи каталог назначения не содержит частичного пакета. Временные файлы и каталоги не остаются после завершения команды.
- REQ-007: Выгрузка создаёт `package.yaml` с `format_version: 1` и по одному файлу `<id>.yaml` в каталоге каждого типа. Поля сериализуются с алиасами (`from`, `register`), без `null` и без необязательных значений по умолчанию; порядок
  файлов и ключей детерминирован.
- REQ-008: Пакет, созданный выгрузкой, читается `read_package` в `KnowledgeSet`, равный выгруженному снимку (с учётом фильтра), и проходит `check`. Полная выгрузка, загруженная в ту же БД, не меняет строки сущностей; обычная запись
  `rag_loads` при этом остаётся.
- REQ-009: Выгрузка только выбранных типов создаёт валидный неполный пакет: отсутствующие сущности других типов выводятся `check` как внешние ссылки, а не как ошибки. ### Отчёт и CLI
- REQ-010: `ExportReport` содержит `exported`, `path`, `entity_count`, счётчики по типам и `issues`. Текстовый вывод печатает итог и счётчики по-русски; `--format json` печатает один JSON-документ. Коды возврата: `0` — выгружено, `1` —
  ошибка выгрузки, `2` — неверные аргументы.
- REQ-011: CLI: `python -m smeshariki_ai.rag export <path> [--type TYPE]... [--format text|json]`. `--type` принимает имена каталогов пакета (`continuities`, `works`, `episodes`, `characters`, `locations`, `artifacts`) и может повторяться;
  без `--type` выгружаются все сущности. Команда не задаёт вопросов; `check` и `schema` по-прежнему не читают environment.
- REQ-012: Конфигурация backend читается только при выполнении `export`. Ошибка конфигурации даёт `configuration_error`, недоступная БД — `database_unavailable`, отсутствующие таблицы — `schema_not_ready`, повреждённые строки —
  `stored_data_invalid`, ошибка записи — `export_failed`. Текст ошибок не содержит SQL, URL, параметров и содержимого знаний.
- REQ-013: `make knowledge-export DIR=<path> [FORMAT=json] [TYPE=<type>]` запускает выгрузку в Compose-сервисе `migrate`, монтируя `DIR` writable. `DIR` должен существовать и быть пустым; отсутствие или неверный путь — подсказка и код `2`.
  Цель не применяет миграции автоматически. stdout содержит только отчёт `export`, вывод сборки и служебных сообщений идёт в stderr.
- REQ-014: После `make knowledge-export` созданные файлы доступны пользователю хоста без `sudo`: контейнер запускается с UID/GID пользователя или иным способом, не оставляющим root-owned файлы. Проверка ручная, в Compose и на хосте. ###
  Наблюдаемость и документация
- REQ-015: Каждый вызов пишет событие `rag.export.completed` с `outcome` (`exported`, `rejected`, `failed`), `entity_count`, `duration_ms` и при необходимости `reason` или `error_type`. Путь, `id` сущностей и содержимое знаний в журнал не
  попадают. Числовые безопасные поля добавляются в `observability._SAFE_FIELDS` аддитивно.
- REQ-016: `docs/rag.md` описывает команду, снимок и отчёт; `docs/knowledge.md` — запись пакета и round-trip; `docs/logging.md` — событие `rag.export.completed`; `docs/README.md` и раздел «Реализованный каталог знаний» `AGENTS.md` получают
  строки о выгрузке. Изменения общих файлов аддитивные и согласуются с их владельцами.
- REQ-017: Тесты покрывают use case, оба хранилища, CLI и PostgreSQL; новые тесты проверяют поведение продукта, а не структуру каталогов. `make lint`, `make test` и `make test-integration` проходят.

Действующий контракт и архитектурные границы описаны в [каталоге](../../../docs/README.md).
