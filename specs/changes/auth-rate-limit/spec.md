# Ограничение частоты входа и одновременный refresh

## Цель

Сейчас вход и регистрация не ограничены по частоте: возможен перебор паролей, а параллельные argon2-хеши (64 МБ каждый) могут исчерпать память backend.
Кроме того, одновременный `refresh` из двух вкладок воспринимается backend как повторное использование refresh-токена и разлогинивает пользователя.
Изменение добавляет ограничение частоты с хранением в Redis, ограничивает параллельные операции argon2 и сериализует refresh во frontend.

Третья из трёх связанных спецификаций после [`auth-hardening`](../auth-hardening/spec.md) и [`dialog-ownership`](../dialog-ownership/spec.md).

## Требования

### Ограничение частоты

- REQ-001: Неудачные попытки входа считаются по паре «логин без учёта регистра + IP клиента». После 5 неудачных попыток за 15 минут следующие попытки этой пары, включая с верным паролем, отвечают `429`
  `{"error":"too_many_attempts"}` с заголовком `Retry-After` в секундах до
  конца окна и не проверяют пароль. Успешный вход сбрасывает счётчик пары.
- REQ-002: С одного IP допускается не более 30 запросов `POST /auth/login` в минуту и не более 10 запросов `POST /users` в час; превышение — `429`
  `{"error":"too_many_attempts"}` с `Retry-After`, без проверки или хеширования
  пароля.
- REQ-003: Порядок проверок у `POST /users` и `POST /auth/login`: `403` по
  `Sec-Fetch-Site`, `415` по media type (из `auth-hardening`), `429` по
  REQ-001–002, затем `422` и остальные ответы контракта.
- REQ-004: Счётчики хранятся в Redis с TTL окна; при недоступности Redis ручки отвечают `503` `{"error":"unavailable"}` и не проверяют пароль (fail closed). Пороги и окна задаются конфигурацией через `load_config` с
  указанными значениями по умолчанию.
- REQ-005: IP клиента определяется по соединению; заголовок
  `X-Forwarded-For` учитывается только от доверенного reverse proxy (Caddy в
  Compose). Подставленный клиентом `X-Forwarded-For` при прямом обращении к backend не меняет определённый IP.
- REQ-006: Одновременно выполняется не более 4 операций хеширования или проверки пароля argon2 на процесс backend; остальные ожидают очереди.

### Frontend

- REQ-007: Frontend выполняет `POST /api/v1/auth/refresh` под общей для всех вкладок origin блокировкой (Web Locks API), так что одновременные проверки
  сессии в разных вкладках не предъявляют один refresh-токен дважды. Вкладка, дождавшаяся блокировки, сначала повторяет `GET /users/me` и вызывает
  `refresh` только при `401`. Без поддержки Web Locks поведение остаётся
  прежним.
- REQ-008: `AuthApi` переводит `429` у входа и регистрации в код
  `too_many_attempts`; страница `/login/` показывает по нему «Слишком много
  попыток. Попробуйте позже», сохраняет логин и очищает пароль.

### Журналирование и документация

- REQ-009: Отказ `429` журналируется стабильным событием с исходом и видом лимита без логина, пароля и IP.
- REQ-010: [`docs/auth.md`](../../../docs/auth.md) описывает лимиты, `429`, порядок проверок, доверие `X-Forwarded-For`, ограничение argon2 и блокировку refresh во frontend; из «Что пока не реализовано» удаляется rate
  limiting. [`docs/configuration.md`](../../../docs/configuration.md), [`docker/README.md`](../../../docker/README.md) и `docker/.env.example` описывают новые переменные. `AGENTS.md` («Реализованная аутентификация
  backend», «Реализованный frontend») и [`docs/README.md`](../../../docs/README.md) обновлены и ссылаются на артефакты.

## Границы

- Всегда: fail closed при недоступности Redis; в журнал не попадают логин, пароль, IP и токены.
- Сначала спросить: изменение порогов по умолчанию, блокировка аккаунта независимо от IP, исключения для роли `admin`.
- Никогда: доверие `X-Forwarded-For` от произвольного клиента; проверка пароля после срабатывания лимита; ослабление обнаружения повторного использования refresh-токена на backend.
