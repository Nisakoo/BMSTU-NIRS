# Ограничение частоты входа и одновременный refresh

## Цель

Сейчас вход и регистрация не ограничены по частоте: возможен перебор паролей,
а параллельные argon2-хеши (64 МБ каждый) могут исчерпать память backend.
Кроме того, одновременный `refresh` из двух вкладок воспринимается backend как
повторное использование refresh-токена и разлогинивает пользователя.
Изменение добавляет ограничение частоты с хранением в Redis, ограничивает
параллельные операции argon2 и сериализует refresh во frontend.

Третья из трёх связанных спецификаций после
[`auth-hardening`](../auth-hardening/spec.md) и
[`dialog-ownership`](../dialog-ownership/spec.md).

## Требования

### Ограничение частоты

- REQ-001: Неудачные попытки входа считаются по паре «логин без учёта
  регистра + IP клиента». После 5 неудачных попыток за 15 минут следующие
  попытки этой пары, включая с верным паролем, отвечают `429`
  `{"error":"too_many_attempts"}` с заголовком `Retry-After` в секундах до
  конца окна и не проверяют пароль. Успешный вход сбрасывает счётчик пары.
- REQ-002: С одного IP допускается не более 30 запросов `POST /auth/login` в
  минуту и не более 10 запросов `POST /users` в час; превышение — `429`
  `{"error":"too_many_attempts"}` с `Retry-After`, без проверки или хеширования
  пароля.
- REQ-003: Порядок проверок у `POST /users` и `POST /auth/login`: `403` по
  `Sec-Fetch-Site`, `415` по media type (из `auth-hardening`), `429` по
  REQ-001–002, затем `422` и остальные ответы контракта.
- REQ-004: Счётчики хранятся в Redis с TTL окна; при недоступности Redis
  ручки отвечают `503` `{"error":"unavailable"}` и не проверяют пароль (fail
  closed). Пороги и окна задаются конфигурацией через `load_config` с
  указанными значениями по умолчанию.
- REQ-005: IP клиента определяется по соединению; заголовок
  `X-Forwarded-For` учитывается только от доверенного reverse proxy (Caddy в
  Compose). Подставленный клиентом `X-Forwarded-For` при прямом обращении к
  backend не меняет определённый IP.
- REQ-006: Одновременно выполняется не более 4 операций хеширования или
  проверки пароля argon2 на процесс backend; остальные ожидают очереди.

### Frontend

- REQ-007: Frontend выполняет `POST /api/v1/auth/refresh` под общей для всех
  вкладок origin блокировкой (Web Locks API), так что одновременные проверки
  сессии в разных вкладках не предъявляют один refresh-токен дважды. Вкладка,
  дождавшаяся блокировки, сначала повторяет `GET /users/me` и вызывает
  `refresh` только при `401`. Без поддержки Web Locks поведение остаётся
  прежним.
- REQ-008: `AuthApi` переводит `429` у входа и регистрации в код
  `too_many_attempts`; страница `/login/` показывает по нему «Слишком много
  попыток. Попробуйте позже», сохраняет логин и очищает пароль.

### Журналирование и документация

- REQ-009: Отказ `429` журналируется стабильным событием с исходом и видом
  лимита без логина, пароля и IP.
- REQ-010: [`docs/auth.md`](../../../docs/auth.md) описывает лимиты, `429`,
  порядок проверок, доверие `X-Forwarded-For`, ограничение argon2 и
  блокировку refresh во frontend; из «Что пока не реализовано» удаляется rate
  limiting. [`docs/configuration.md`](../../../docs/configuration.md),
  [`docker/README.md`](../../../docker/README.md) и `docker/.env.example`
  описывают новые переменные. `AGENTS.md` («Реализованная аутентификация
  backend», «Реализованный frontend») и
  [`docs/README.md`](../../../docs/README.md) обновлены и ссылаются на
  артефакты.

## Сценарии

### Перебор пароля

- Given пользователь `Krosh` существует
- When с одного IP пять раз подряд вводится неверный пароль
- Then шестая попытка, даже с верным паролем, отвечает `429` с `Retry-After`
- And вход с другого IP по-прежнему возможен; после окна вход снова доступен

### Сброс после успеха

- Given четыре неудачные попытки пары логин+IP
- When пятая попытка успешна
- Then счётчик пары сброшен, следующие пять неудачных попыток снова допустимы

### Redis недоступен при входе

- Given Redis недоступен
- When пользователь отправляет `POST /api/v1/auth/login`
- Then ответ `503` `{"error":"unavailable"}`, пароль не проверяется

### Подмена IP

- Given клиент обращается к backend напрямую, минуя Caddy
- When он отправляет `X-Forwarded-For` с произвольными адресами
- Then лимиты считаются по адресу соединения

### Две вкладки одновременно продлевают сессию

- Given access-токен истёк, refresh действителен, открыты две вкладки
- When обе одновременно проверяют сессию
- Then `refresh` выполняется один раз, вторая вкладка получает пользователя
  повторным `/users/me`, семейство сессий не отзывается

## Технологии и структура

- Без новых зависимостей. Redis (redis-py) — счётчики фиксированного окна
  (`INCR` + `EXPIRE`) с отдельным префиксом ключей.
- `smeshariki_ai.auth`: транспортно-независимый контракт ограничителя
  попыток с in-memory реализацией для тестов; конфигурация лимитов в
  `AuthConfig` или отдельной модели; семафор в `Argon2PasswordHasher`.
- `smeshariki_ai.cache`: Redis-реализация ограничителя.
- `api/auth.py`: вызов ограничителя в ручках регистрации и входа, `429` и
  `Retry-After`.
- Доверие к `X-Forwarded-For`: параметры Uvicorn (`--forwarded-allow-ips`)
  в `docker/Dockerfile` или Compose; способ фиксируется в плане.
- Frontend: `navigator.locks.request` вокруг refresh в `auth-session.js`;
  код `too_many_attempts` в `auth-api.js` и текст на `/login/`.
- CAPTCHA и блокировка аккаунта без учёта IP в объём не входят.

## Команды

- Запуск: `make run`
- Тесты: `make test`
- Линтер: `make lint`

## Тестирование

- Backend Pytest (unit): ограничитель на in-memory реализации с управляемыми
  часами — пороги, окна, сброс при успехе, `Retry-After`; семафор не
  допускает больше 4 одновременных операций; загрузка конфигурации лимитов.
- Backend Pytest (integration, `httpx.ASGITransport`): `429` и `Retry-After`
  у входа и регистрации; пароль не проверяется после срабатывания; порядок
  `403`→`415`→`429`→`422`; `503` при недоступном хранилище лимитов; журнал
  без логина, пароля и IP.
- Backend Pytest (integration с Redis, `TEST_REDIS_URL`): Redis-реализация
  счётчиков с TTL.
- Проверка `X-Forwarded-For`: тест определения IP или ручная проверка прямого
  обращения к backend в Compose — фиксируется в плане.
- Frontend Node-тесты с fake `fetch` и fake `navigator.locks`: refresh под
  блокировкой, повтор `/users/me` после ожидания, прежнее поведение без Web
  Locks; `too_many_attempts` в `AuthApi` и текст на `/login/`.
- Ручная проверка в `make run`: шестая неверная попытка получает понятную
  ошибку на `/login/`; две вкладки после истечения access остаются в системе.

## Границы

- Всегда: fail closed при недоступности Redis; в журнал не попадают логин,
  пароль, IP и токены.
- Сначала спросить: изменение порогов по умолчанию, блокировка аккаунта
  независимо от IP, исключения для роли `admin`.
- Никогда: доверие `X-Forwarded-For` от произвольного клиента; проверка
  пароля после срабатывания лимита; ослабление обнаружения повторного
  использования refresh-токена на backend.

## Критерии приёмки

- [ ] Шестая неудачная попытка входа пары логин+IP за 15 минут и превышение
  лимитов по IP дают `429` с `Retry-After` без проверки пароля.
- [ ] Недоступный Redis даёт `503` у входа и регистрации.
- [ ] Подставленный `X-Forwarded-For` при прямом обращении не обходит лимиты.
- [ ] Не более 4 параллельных операций argon2.
- [ ] Две вкладки, одновременно продлевающие сессию, остаются в системе.
- [ ] `/login/` показывает понятную ошибку при `429`.
- [ ] Документация обновлена по REQ-010.
- [ ] `make test` и `make lint` проходят успешно.
