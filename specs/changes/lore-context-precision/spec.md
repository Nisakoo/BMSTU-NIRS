# Точность контекста RAG для сказки

## Цель

Убрать из контекста сказки слабые совпадения BM25 и предметы, которые просочились через свободные трейты `get_story_canon`. Живой прогон показал две
проблемы: запрос `Крош Ёжик дружба` оставлял только один документ и отбрасывал «Скамейку» из-за относительного порога, а профиль Ёжика содержал трейт «коллекционирует фантики», из-за чего фантик попадал в каждую сказку.

## Требования

- REQ-001: `LoreContextBuilder` отбрасывает фрагменты ниже абсолютного
  `min_score` (по умолчанию `2.0`); относительный порог `0.5` не используется.
- REQ-002: второй и третий релевантные документы с меньшим, но ненулевым баллом сохраняются, если проходят `min_score`.
- REQ-003: запрос, состоящий только из имён персонажей и служебных слов (`Крош`, `Крош и Ёжик`), даёт `status=empty` даже при найденных чанках.
- REQ-004: запрос с содержательным термом (`Крош строит скамейку`) не отбрасывается правилом содержательных термов.
- REQ-005: `SearchLore` отдаёт проанализированные термы запроса инструменту, чтобы анализ выполнялся один раз.
- REQ-006: `StoryCanonLookup` отбрасывает трейты, в которых назван артефакт или локация, по каноническим именам; трейты без предметов сохраняются.
- REQ-007: `KnowledgeReader` получает необязательный `prop_names()`; без поддержки он возвращает пустой кортеж, PostgreSQL и in-memory реализации отдают канонические имена артефактов и локаций.
- REQ-008: описание `get_story_canon` предлагает вызвать `search_lore` для сцены, предмета или места, не превращая профиль в сюжет.
- REQ-009: схема БД, миграции и формат пакетов не меняются.

## Границы

- Всегда: профиль героя — ограничение на характер, а не список предметов.
- Сначала спросить: изменение схемы БД, формата пакетов, системного промпта.
- Никогда: не отдавать в сказку свободные описания отношений и предметы; не удалять артефакты и локации из полного канона.
