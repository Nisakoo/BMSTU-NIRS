# Интеграция frontend с агентом через Vite proxy и SSE

## Цель

Подключить существующий статический интерфейс в `frontend/` к реализованным
dialog API и SSE-потоку backend. Пользователь должен создавать диалог при
открытии страницы, отправлять сообщения агенту и видеть его потоковый ответ в
текущем дизайне. Для локальной разработки frontend запускается отдельным Vite-
процессом, который проксирует `/api` в backend и тем самым сохраняет same-origin
модель браузера без добавления CORS в FastAPI.

Изменение опирается на рабочий протокол и защиту от гонки из
`backend/src/smeshariki_ai/api/agent_test.html`, но не заменяет и не удаляет
backend-страницу `/agent_test`.

## Допущения

- Backend локально доступен по умолчанию на `http://127.0.0.1:8000`.
- Vite используется только для frontend-разработки и сборки; frontend не
  добавляется в `docker/compose.yaml`.
- Прокси-адрес backend можно переопределить environment-переменной процесса
  Vite `BACKEND_URL`; это несекретная локальная настройка.
- Диалог остаётся in-memory и создаётся заново при каждой полной загрузке
  страницы. `dialog_id` не сохраняется в cookie или `localStorage`.
- Backend API, event schema и тестовая страница `/agent_test` уже реализованы и
  не меняются в рамках интеграции.
- Production reverse proxy и deployment frontend не входят в это изменение;
  Vite proxy обеспечивает локальный development contract.

## Требования

- REQ-001: `frontend/` должен получить минимальную Vite-конфигурацию с корнем
  приложения `frontend/src/`, dev-командой, production build-командой и
  зафиксированными npm-зависимостями.
- REQ-002: Vite dev server должен проксировать все запросы пути `/api` на
  `BACKEND_URL`, а при отсутствии переменной — на
  `http://127.0.0.1:8000`. Браузерный код должен использовать только
  относительные same-origin URL `/api/v1/...`.
- REQ-003: FastAPI не должен получать CORS middleware ради локальной
  интеграции. Frontend должен оставаться отдельным от backend Docker Compose.
- REQ-004: При загрузке страницы frontend должен вызвать
  `POST /api/v1/dialogs`, извлечь `dialog_id` из успешного `201` JSON-ответа и
  открыть один `EventSource` по адресу
  `/api/v1/dialogs/{dialog_id}/events`.
- REQ-005: До SSE-события `ready` поле и кнопка отправки должны быть
  недоступны. После `ready` интерфейс показывает готовность и разрешает ввод,
  если другой запрос не отправляется и агент не формирует ответ.
- REQ-006: Отправка непустого текста должна вызвать
  `POST /api/v1/dialogs/{dialog_id}/messages` с JSON
  `{"request":"<текст>"}`. Сообщение пользователя добавляется в чат только
  после успешного `202 Accepted`, затем поле очищается.
- REQ-007: Пока POST находится в полёте, SSE-события ответа должны временно
  буферизоваться и применяться после подтверждения `202`, чтобы
  `message_start` или `message_delta` не появились раньше сообщения
  пользователя.
- REQ-008: `message_start` должен создать ровно одно сообщение ассистента,
  каждый `message_delta` — безопасно дописать `data.delta` как текст, а
  `message_end` — завершить текущий ответ и снова разрешить отправку.
- REQ-009: `message_error` должен завершить состояние обработки, показать
  безопасное сообщение ошибки в чате или статусе и снова разрешить работу,
  если SSE-соединение остаётся готовым. Текст запросов и SSE payload не должен
  вставляться через `innerHTML`.
- REQ-010: В один момент времени frontend должен принимать не более одного
  пользовательского запроса. Повторная отправка Enter, кнопкой или иным
  способом во время POST либо ответа агента игнорируется, а элементы формы
  остаются disabled.
- REQ-011: Ошибка создания диалога должна оставить форму disabled и показать
  понятный статус. Ошибка отправки должна сохранить введённый текст для
  повторной попытки и не добавлять ложное пользовательское сообщение. Ошибка
  EventSource должна показать переподключение и временно заблокировать форму;
  встроенное переподключение `EventSource` не отключается.
- REQ-012: При закрытии или перезагрузке страницы активный `EventSource`
  должен закрываться. Новый диалог при этом будет создан следующей загрузкой,
  без client-side persistence и replay.
- REQ-013: Быстрые тематические кнопки должны продолжать заполнять textarea,
  автоподбор высоты и отправка по Enter без Shift должны сохраниться после
  интеграции.
- REQ-014: Сетевой контракт frontend должен быть вынесен из DOM-логики в
  небольшой ES-модуль с явными зависимостями `fetch` и `EventSource`, чтобы
  формирование запросов и разбор SSE можно было детерминированно тестировать в
  Node без браузера и сети.
- REQ-015: Frontend-тесты должны проверять создание диалога, URL и тело
  отправки, обработку именованных SSE-событий, некорректный JSON и закрытие
  соединения. `make test` должен запускать как backend Pytest, так и frontend
  Node-тесты.
- REQ-016: Сборка Vite должна успешно создавать production bundle без
  изменения backend и без включения `node_modules/` или `frontend/dist/` в
  Git.
- REQ-017: Документация должна описывать раздельный запуск backend и frontend,
  Vite proxy, `BACKEND_URL`, отсутствие CORS и текущие in-memory/SSE
  ограничения. `AGENTS.md` и архитектурный каталог должны отражать фактическую
  интеграцию.

## Сценарии

### Создание диалога при загрузке

- Given backend запущен, а пользователь открывает Vite frontend
- When модуль страницы инициализируется
- Then форма блокируется и показывается состояние подключения
- And frontend через proxy вызывает `POST /api/v1/dialogs`
- And открывает `EventSource` созданного диалога
- When приходит `ready`
- Then статус меняется на готовность и форма разблокируется

### Потоковый ответ агента

- Given диалог готов и пользователь ввёл непустой запрос
- When backend принимает POST и возвращает `202`
- Then сообщение пользователя появляется в чате, поле очищается и форма
  остаётся заблокированной
- When приходят `message_start` и несколько `message_delta`
- Then frontend создаёт одну реплику ассистента и последовательно дописывает
  фрагменты текста
- When приходит `message_end`
- Then ответ считается завершённым и форма снова доступна

### Быстрый SSE до завершения POST

- Given frontend отправляет сообщение, а backend начинает публиковать SSE до
  завершения браузерного обработчика POST
- When `message_start` и `message_delta` приходят при активном `submitting`
- Then события буферизуются
- When подтверждён `202`
- Then сначала отображается сообщение пользователя, а затем по порядку
  применяются накопленные события агента

### Ошибка отправки

- Given пользователь ввёл сообщение и диалог готов
- When POST завершается сетевой ошибкой или статусом, отличным от `202`
- Then пользовательское сообщение не добавляется в чат
- And исходный текст остаётся в textarea
- And статус сообщает о невозможности отправки
- And форма снова доступна, если SSE-соединение готово

### Ошибка агента или SSE

- Given сообщение принято backend
- When приходит `message_error`
- Then частичный ответ не сохраняется backend, а frontend помечает текущий
  ответ ошибкой и завершает processing-состояние
- When браузер сообщает об ошибке EventSource
- Then форма блокируется, статус сообщает о переподключении и браузер может
  автоматически переподключить тот же EventSource

### Backend недоступен

- Given Vite frontend запущен, но backend недоступен по proxy target
- When страница пытается создать диалог
- Then форма остаётся заблокированной и пользователь видит понятный статус без
  демонстрационного или выдуманного ответа

## Технологии и структура

- Vanilla JavaScript остаётся UI-технологией; React и другие UI-фреймворки не
  добавляются.
- Vite добавляется как dev dependency и запускает приложение с root
  `frontend/src/`.
- npm используется для frontend dependency/lock management; коммитятся
  `frontend/package.json` и `frontend/package-lock.json`.
- `frontend/vite.config.js` настраивает proxy `/api` и build output
  `frontend/dist/`.
- Сетевой адаптер размещается в отдельном ES-модуле внутри `frontend/src/`, а
  `script.js` отвечает за DOM и UI state.
- Детерминированные frontend-тесты используют встроенный `node:test` и fake
  `fetch`/`EventSource`, не требуют реального backend или браузера.
- FastAPI, agent runtime, application service и SSE broker не изменяются.

## Команды

- Backend: `make run`.
- Frontend: `make frontend` в отдельном терминале.
- Frontend напрямую: `npm --prefix frontend run dev`.
- Frontend с другим backend:
  `BACKEND_URL=http://127.0.0.1:9000 npm --prefix frontend run dev`.
- Тесты: `make test`.
- Сборка frontend: `npm --prefix frontend run build`.
- Python lint: `make lint`.

## Границы

- Всегда: использовать действующие dialog/SSE API; проксировать `/api` через
  Vite; безопасно выводить пользовательский и потоковый текст; блокировать
  конкурентные отправки; сохранять frontend отдельным от Docker backend.
- Сначала спросить: менять backend API или SSE schema; добавлять CORS;
  сохранять `dialog_id` или историю в браузере; добавлять новый диалог-контрол,
  replay, авторизацию, frontend-фреймворк или production reverse proxy.
- Никогда: возвращать демонстрационный hardcoded ответ; обращаться из браузера
  к захардкоженному cross-origin backend URL; помещать frontend в Compose;
  вставлять текст пользователя, LLM или ошибок через `innerHTML`; коммитить
  `node_modules`, `dist` или секреты.

## Критерии приёмки

- [ ] `make frontend` запускает Vite отдельно от Docker и открывает приложение
  из `frontend/src/`; `/api` проксируется в backend target.
- [ ] При загрузке создаётся новый диалог, открывается один EventSource, а форма
  становится доступна только после `ready`.
- [ ] Отправленный текст попадает в API как `{"request": ...}`, появляется в
  чате после `202`, а потоковые delta образуют один ответ ассистента.
- [ ] Гонка между POST и быстрыми SSE-событиями не меняет порядок сообщений.
- [ ] Ошибки создания, отправки, SSE JSON, agent response и разрыва соединения
  переводят UI в определённое безопасное состояние без hardcoded ответа.
- [ ] Тематические кнопки, autosize и Enter/Shift+Enter продолжают работать.
- [ ] Backend не содержит нового CORS middleware, а Compose не содержит
  frontend service.
- [ ] Frontend Node-тесты, полный `make test`, `make lint` и Vite build проходят
  успешно.
- [ ] `frontend/README.md`, `docs/README.md`, `docs/dialogs.md` и `AGENTS.md`
  соответствуют реализованной интеграции и ограничениям.
