# Интеграция frontend с агентом через Vite proxy и SSE

> Действующий клиент реализован на Svelte и TypeScript. Сетевой контракт ниже сохраняется, а актуальное размещение модулей и запуск описаны в [структуре frontend](../frontend-src-layout/spec.md) и [руководстве](../../../frontend/README.md).

## Цель

Подключить существующий статический интерфейс в `frontend/` к реализованным dialog API и SSE-потоку backend. Пользователь должен открывать диалог при
загрузке страницы, отправлять сообщения агенту и видеть его потоковый ответ в текущем дизайне. Для локальной разработки frontend запускается отдельным Vite-
процессом, который проксирует `/api` в backend и тем самым сохраняет same-origin модель браузера без добавления CORS в FastAPI.

Изменение опирается на рабочий протокол и защиту от гонки из
`backend/src/smeshariki_ai/api/agent_test.html`, но не заменяет и не удаляет
backend-страницу `/agent_test`.

## Допущения

- Backend локально доступен по умолчанию на `http://127.0.0.1:8000`.
- Vite используется только для frontend-разработки и сборки; frontend не добавляется в `docker/compose.yaml`.
- Прокси-адрес backend можно переопределить environment-переменной процесса Vite `BACKEND_URL`; это несекретная локальная настройка.
- Черновики живут в памяти сервера, завершённые истории хранятся в PostgreSQL. После F5 вкладка открывает диалог текущего пользователя по UUID из `sessionStorage`.
- Backend API, event schema и тестовая страница `/agent_test` уже реализованы и не меняются в рамках интеграции.
- Production reverse proxy и deployment frontend не входят в это изменение; Vite proxy обеспечивает локальный development contract.

## Требования

- REQ-001: `frontend/` должен получить минимальную Vite-конфигурацию с корнем приложения `frontend/src/`, dev-командой, production build-командой и зафиксированными npm-зависимостями.
- REQ-002: Vite dev server должен проксировать все запросы пути `/api` на
  `BACKEND_URL`, а при отсутствии переменной — на
  `http://127.0.0.1:8000`. Браузерный код должен использовать только
  относительные same-origin URL `/api/v1/...`.
- REQ-003: FastAPI не должен получать CORS middleware ради локальной интеграции. Frontend должен оставаться отдельным от backend Docker Compose.
- REQ-004: При отсутствии доступного диалога frontend должен вызвать
  `POST /api/v1/dialogs`, извлечь `dialog_id` из успешного `201` JSON-ответа и
  открыть один `EventSource` по адресу
  `/api/v1/dialogs/{dialog_id}/events`.
- REQ-005: До SSE-события `ready` поле и кнопка отправки недоступны. В готовом диалоге пользователь может набирать текст во время POST и ответа агента.
- REQ-006: Отправка непустого текста должна вызвать
  `POST /api/v1/dialogs/{dialog_id}/messages` с JSON
  `{"request":"<текст>"}`. Сообщение пользователя добавляется в чат только
  после успешного `202 Accepted`. При отправке кнопкой или клавишей Enter поле сразу очищается и получает фокус для следующего черновика.
- REQ-007: Пока POST находится в полёте, SSE-события ответа должны временно буферизоваться и применяться после подтверждения `202`, чтобы
  `message_start` или `message_delta` не появились раньше сообщения
  пользователя.
- REQ-008: При отправке лента показывает индикатор ожидания до первого видимого текста. `message_start` сохраняет индикатор, `message_delta` дописывает текст в одну реплику ассистента, `message_end` завершает ответ.
  Положение прокрутки при обновлениях выбирает читатель. При уменьшении движения индикатор статичен.
- REQ-009: `message_error` должен завершить состояние обработки, показать безопасное сообщение ошибки в чате или уведомлении над полем ввода и снова разрешить работу,
  если SSE-соединение остаётся готовым. Текст запросов и SSE payload не должен вставляться через `innerHTML`.
- REQ-010: В один момент времени frontend принимает не более одного запроса. Кнопка отправки заблокирована, а отправка через Enter или программный submit игнорируется до завершения ответа. При завершении ответа фокус остаётся на выбранном пользователем элементе.
- REQ-011: Ошибка создания диалога должна оставить форму disabled и показать понятный статус. При ошибке отправки исходный текст возвращается, если пользователь ещё не редактировал новый черновик.
  Сообщение в ленту попадает только при успешной отправке. Ошибка EventSource должна показать переподключение и временно заблокировать форму; встроенное переподключение `EventSource` не отключается.
- REQ-012: При закрытии или перезагрузке страницы активный `EventSource` должен закрываться. При следующей загрузке та же вкладка восстанавливает выбранный диалог текущего пользователя согласно [контракту боковой панели](../chat-sidebar-layout/spec.md). После `ready` и окончания ранее начатой генерации полные сообщения читаются через HTTP.
- REQ-013: Тематические кнопки заполняют поле. Пустой и короткий черновик располагаются в одной строке с кнопками. При ручном или автоматическом переносе поле занимает всю ширину над кнопками, растёт до меньшего из 176 px и 24% высоты окна, затем прокручивается внутри. Удаление текста или изменение ширины возвращает компактный вид, когда черновик помещается в одну строку. Enter отправляет текст, Shift+Enter переносит строку, подтверждение ввода через IME сохраняет черновик.
- REQ-014: Сетевой контракт frontend должен быть вынесен из DOM-логики в небольшой ES-модуль с явными зависимостями `fetch` и `EventSource`, чтобы
  формирование запросов и разбор SSE можно было детерминированно тестировать в Node без браузера и сети.
- REQ-015: Frontend-тесты должны проверять создание диалога, URL и тело отправки, обработку именованных SSE-событий, некорректный JSON и закрытие
  соединения. `make test` должен запускать как backend Pytest, так и frontend Node-тесты.
- REQ-016: Сборка Vite должна успешно создавать production bundle без изменения backend и без включения `node_modules/` или `frontend/dist/` в Git.
- REQ-017: Документация должна описывать раздельный запуск backend и frontend, Vite proxy, `BACKEND_URL`, отсутствие CORS и текущие in-memory/SSE
  ограничения. `AGENTS.md` и архитектурный каталог должны отражать фактическую интеграцию.

## Границы

- Всегда: использовать действующие dialog/SSE API; проксировать `/api` через Vite; безопасно выводить пользовательский и потоковый текст; блокировать конкурентные отправки; сохранять frontend отдельным от Docker backend.
- Сначала спросить: менять backend API или SSE schema; добавлять CORS; сохранять тексты истории в браузерном хранилище; добавлять новый диалог-контрол, replay, авторизацию, frontend-фреймворк или production reverse proxy.
- Никогда: возвращать демонстрационный hardcoded ответ; обращаться из браузера к захардкоженному cross-origin backend URL; помещать frontend в Compose;
  вставлять текст пользователя, LLM или ошибок через `innerHTML`; коммитить
  `node_modules`, `dist` или секреты.
