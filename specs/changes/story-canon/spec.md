# Компактный `story-canon` для генерации сказок

## Цель

Отделить полный структурированный канон от компактного профиля, который нужен агенту для написания сказки. Сейчас `lookup_knowledge(\"Крош\")` возвращает
черты, речь и отношения с свободными описаниями. Одно из них содержит «скамейку», и модель переносит её в каждую сказку. `story-canon` должен отдавать только то, что ограничивает персонажа в повествовании: возраст,
характер, манеру речи, коронные фразы и тип отношений. Без артефактов, локаций, источников и свободных описаний.

Полная структура БД при этом не меняется: `lookup_knowledge` продолжает отвечать на фактические вопросы, а `story-canon` — это узкая проекция тех же данных.

## Требования

### Доменные модели

- REQ-001: `StoryCharacter` содержит `id`, `name`, `species`,
  `continuity`, `age_group`, `traits`, `speech_style`, `catchphrases` и
  `relationships`. `StorySpeechStyle` содержит `register`, `markers`,
  `constraints`. `StoryRelationship` содержит только `to` и `type`.
- REQ-002: `StoryCanon` содержит статус `found`/`not_found`/`unavailable`, кортеж персонажей и безопасное сообщение. В моделях нет `description` отношений, `sources`, `aliases`, локаций и артефактов.
- REQ-003: `StoryCharacter` не содержит свободного текста об отношениях, эпизодах или предметах. Даже если в исходном `Character.relationship` описание упоминает скамейку, зонтик или эпизод, в `story-canon` это не
  попадает.

### Use case

- REQ-004: `StoryCanonLookup` получает `KnowledgeReader` и параметры
  `default_continuity=\"classic\"`. Метод `lookup(names, continuity=None)`
  нормализует имена, читает персонажей через `find` и возвращает не более трёх уникальных персонажей.
- REQ-005: Для каждого персонажа выбирается версия, в `continuities` которой есть запрошенный вариант канона. Если версии нет, персонаж не попадает в
  результат, а общий статус остаётся `not_found` с нейтральным сообщением. Версия другого канона молча не подставляется.
- REQ-006: Отношения фильтруются по выбранному варианту канона и преобразуются в `to` (имя персонажа, если оно известно, иначе slug) и
  `type`. Описания, источники и варианты канона отношений наружу не выходят.
- REQ-007: Если знаний нет или `rag_*` недоступны, результат —
  `not_found`/`unavailable` с безопасным сообщением, без исключения и без
  текста запроса. Частичные данные не выдаются.
- REQ-008: Пустой список имён, больше трёх имён, пустое имя или имя длиннее 200 символов отклоняются до чтения хранилища.

### Инструмент

- REQ-009: `GetStoryCanonTool` наследуется от `Tool`, имя —
  `get_story_canon`. Аргументы: `names` (1–3 строки по 1–200 символов) и
  необязательный `continuity` (slug). Лишние поля запрещены.
- REQ-010: Инструмент возвращает JSON `{status, characters, message}`. Каждый персонаж содержит только поля `StoryCharacter`; в JSON нет
  `description`, `sources`, локаций, артефактов и внутренних postings.
- REQ-011: Описание инструмента требует использовать его для сказки, когда названы конкретные герои, не более одного раза; профиль — ограничение на характер и речь, а не сюжет; нельзя перечислять отношения, предметы и
  места; при `not_found`/`unavailable` нужно продолжать по идее пользователя.
- REQ-012: `lookup_knowledge` остаётся инструментом фактических вопросов. Его ответ не меняется. `search_lore` остаётся источником нарративных фрагментов. Системный промпт различает три инструмента.

### Composition root и наблюдаемость

- REQ-013: Production bootstrap регистрирует `get_story_canon` рядом с
  `lookup_knowledge` и `search_lore` на том же `PostgresKnowledgeStore`.
  `build_agent_service` получает общий `KnowledgeReader`; тесты без БД
  используют `InMemoryKnowledgeStore`.
- REQ-014: Событие `rag.story_canon.completed` содержит `outcome`,
  `entity_count`, длительность и тип ошибки. Имена героев, описания и
  пользовательский текст в журнал не попадают.
- REQ-015: Схема БД, миграции и порт `KnowledgeReader` не меняются.
  `StoryCanonLookup` — read model поверх существующего канона.

### Данные, документация, проверка

- REQ-016: `docs/knowledge.md` фиксирует правило: описание отношения описывает отношение, а не предмет или эпизод; `story-canon` всё равно отбрасывает свободные описания. `docs/rag.md`, `docs/agent.md`,
  `docs/README.md` и `AGENTS.md` описывают новый инструмент и границу с
  `lookup_knowledge`.
- REQ-017: Тесты покрывают выбор версии, отсутствие версии, отношения без описаний, отсутствие артефактов/локаций/источников, `not_found`,
  `unavailable`, валидацию аргументов, JSON инструмента и bootstrap.
  `make lint`, `make test` и `make test-integration` проходят.
- REQ-018: Исправление конкретного отношения Кроша в `data/knowledge` — отдельная правка данных; код `story-canon` не зависит от того, упоминает ли описание скамейку, и обязан отбрасывать такое описание в любом случае.

## Границы

- Всегда: `StoryCanon` — проекция существующего канона; полный
  `lookup_knowledge` сохраняется; свободные описания отношений не выходят в
  story-режим.
- Сначала спросить: изменение схемы БД, `KnowledgeReader`, формата пакетов, поведения `lookup_knowledge`, системного промпта и `bootstrap.py`.
- Никогда: дублировать канон в отдельном YAML/таблице; удалять артефакты, локации и эпизоды из полной БД; отдавать `description` отношений и
  `sources` в story-режим.
