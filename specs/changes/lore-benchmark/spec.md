# Benchmark BM25-поиска по лору

## Цель

Дать воспроизводимую проверку качества BM25 и ответов по найденным фрагментам: 30 документов, 10 обычных вопросов с эталонами и 5 вопросов-ловушек. Benchmark
работает офлайн через in-memory индекс и не требует PostgreSQL; ответы можно передать готовым JSON или получить через LLM.

## Требования

### Набор

- REQ-001: В репозитории есть синтетический набор
  `backend/tests/fixtures/lore_benchmark/`: 30 YAML-документов, 10 обычных
  вопросов и 5 ловушек. У каждого обычного вопроса не менее трёх
  `relevant_documents`; у ловушки — ноль. Реальные данные не используются.
- REQ-002: `questions.yaml` содержит `id`, `text`, `kind` (`normal`/`trap`), `relevant_documents`, `reference_answer` и
  `required_facts`. Модели строгие: лишние поля, дубли `id`, обычный вопрос с
  менее чем тремя документами или без фактов, ловушка с документами или фактами — ошибка.
- REQ-003: `read_benchmark_questions` читает YAML-1.2-safe способом, не выполняет код и возвращает безопасную `BenchmarkError` без текста вопросов при ошибке.

### Поиск и метрики

- REQ-004: `BenchmarkRunner` строит `InMemoryBm25Index` из пакета лора, выполняет `SearchLore` для каждого вопроса с заданным `k` и не обращается к PostgreSQL.
- REQ-005: `Recall@k` — средняя доля релевантных документов в первых `k` уникальных документах; `MRR@k` — средний обратный ранг первого релевантного документа (0, если его нет). Обе метрики считаются только по обычным
  вопросам; для ловушек они `null`.
- REQ-006: `Accuracy` — доля обычных вопросов, в ответе которых присутствуют все `required_facts` после нормализации. `Correct Rejection Rate` — доля
  ловушек, в ответе которых есть маркер отказа (например, «В документах нет этой информации»). Пустые наборы дают `null`, а не деление на ноль.

### Ответы и CLI

- REQ-007: `Answerer` — порт. `StaticAnswerer` берёт ответы из JSON
  `{question_id: answer}`; `LiteLLMAnswerer` формирует сообщения
  «только по фрагментам» и получает ответ через `LLMProvider`. LLM-адаптер используется только benchmark-ом, не runtime-агентом.
- REQ-008: `lore-benchmark <path> --questions <yaml> [--k 5] [--answers <json>] [--format text|json]` не требует БД. Без `--answers` читает конфиг LLM; с `--answers` не читает environment. Коды: `0` — успех,
  `1` — ошибка набора/загрузки/ответов, `2` — неверные аргументы.
- REQ-009: Make-цель `make lore-benchmark DIR=<path> QUESTIONS=<yaml> [K=5] [ANSWERS=<json>]` запускает команду в Compose-сервисе `migrate`; каталог лора, вопросы и ответы монтируются только для чтения.
- REQ-010: Текстовый вывод содержит число документов, вопросов, обычных и ловушек, `k`, четыре метрики и строку на каждый вопрос. JSON-вывод содержит те же данные и `results` с `retrieved_documents`, `recall`,
  `reciprocal_rank`, `answer`, `correct`.

### Наблюдаемость, документация, проверка

- REQ-011: Benchmark не логирует текст вопросов, ответов, документов и
  `required_facts`. `SearchLore` использует существующие безопасные события.
- REQ-012: `docs/lore.md` и `docs/rag.md` описывают набор, метрики, команды и ограничения; `AGENTS.md` получает строку о benchmark. `docs/README.md` обновляет состояние компонента.
- REQ-013: Тесты покрывают форму набора, метрики, ошибки валидации, готовые ответы, LLM-адаптер и CLI; `make lint`, `make test` и
  `make test-integration` проходят. Тесты проверяют поведение, а не структуру
  каталогов.

## Границы

- Всегда: синтетические данные; benchmark без БД; ответы только по найденным фрагментам; фиксированный `k` в отчёте.
- Сначала спросить: изменение production-поиска, `SearchLore`, агента, системного промпта, LLM-провайдера.
- Никогда: коммитить реальные данные; логировать вопросы/ответы/документы; использовать benchmark как runtime-путь.
