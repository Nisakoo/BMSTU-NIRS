# Жалобы на ответы агента и их разбор администратором

## Цель

Сервис детский, и ответ модели может оказаться страшным, грубым или
неподходящим. Пользователь должен иметь возможность пожаловаться на конкретный
ответ ассистента, а администратор — увидеть жалобу с текстом ответа в панели
`/admin/` и отметить её как рассмотренную или отклонённую. Оценки-мордашки
остаются без изменений: жалоба — отдельный сигнал, требующий разбора.

## Требования

### Хранение

- REQ-001: Миграция `0006` создаёт таблицу `message_reports`: `id`
  (`bigint` identity, PK), `message_id` (`bigint`, `UNIQUE`, FK
  `messages(id) ON DELETE SET NULL`, nullable), `user_id` (FK `users(id) ON
  DELETE CASCADE`), `reason` (`scary | rude | wrong | other`, `CHECK`),
  `comment` (текст до 500 символов, nullable), `request_text` (запрос
  пользователя перед ответом, nullable), `answer_text` (текст ответа),
  `status` (`new | resolved | dismissed`, `CHECK`, default `new`),
  `created_at`, `resolved_at` (nullable), `resolved_by` (FK `users(id)`,
  nullable). Индекс по `(status, created_at)`.
- REQ-002: При подаче жалобы в неё копируются текст ответа и ближайшего
  предшествующего сообщения пользователя. Удаление истории пользователем
  обнуляет `message_id`, но жалоба и копия текста остаются у администратора.

### API пользователя

- REQ-003: `POST /api/v1/dialogs/{dialog_id}/messages/{message_id}/report` с
  телом `{"reason": "scary"|"rude"|"wrong"|"other", "comment": "..."?}`
  создаёт жалобу и отвечает `201`. `comment` необязателен, обрезается по краям,
  пустой считается отсутствующим, длиннее 500 символов — `422`.
- REQ-004: На один ответ можно подать одну жалобу; повторная подача —
  `409 {"detail":"Already reported."}`, первая жалоба не меняется.
- REQ-005: Пожаловаться можно только на ответ ассистента в собственном
  диалоге. Чужой или несуществующий диалог, несуществующее сообщение,
  сообщение другого диалога и сообщение пользователя дают `404`
  `{"detail":"Message not found."}`. Некорректное тело или `message_id` —
  `422`; гость — `401` раньше `404`/`422`; сбой PostgreSQL — `503`.
- REQ-006: `GET /api/v1/dialogs/{dialog_id}/messages` возвращает у каждого
  сообщения поле `reported` (`true`, если на него есть жалоба; у сообщений
  пользователя всегда `false`).

### Frontend чата

- REQ-007: Рядом с мордашками под каждым завершённым ответом ассистента есть
  кнопка-флажок «Пожаловаться» (`aria-label`). Под ответом с ошибкой и пока
  ответ генерируется её нет.
- REQ-008: Нажатие открывает небольшое окно «Что не так с историей?» с
  вариантами «Страшно», «Грубо или обидно», «Неправильно или непонятно»,
  «Другое», необязательным полем комментария (до 500 символов) и кнопками
  «Отправить» и «Отмена». «Отправить» недоступна, пока причина не выбрана.
  Окно закрывается по «Отмена» и `Escape`.
- REQ-009: После `201` (или `409`) кнопка становится неактивной с подписью
  «Жалоба отправлена», в строке состояния — «Спасибо! Взрослые посмотрят».
  При ошибке окно остаётся открытым с сохранённым выбором, строка состояния —
  «Не удалось отправить жалобу». При `401` действует прежнее правило сессии.
- REQ-010: При открытии сохранённой истории у ответов с `reported: true`
  кнопка сразу в состоянии «Жалоба отправлена».

### API и панель администратора

- REQ-011: `GET /api/v1/admin/reports?status=new|resolved|dismissed|all`
  (default `new`) возвращает до 50 жалоб от новых к старым:
  `{"reports":[{"id","reason","comment","request_text","answer_text","status","created_at","resolved_at","dialog_deleted"}]}`.
  `dialog_deleted` — `true`, если `message_id` обнулён. Логин и
  идентификатор пользователя, подавшего жалобу, не возвращаются.
- REQ-012: `PATCH /api/v1/admin/reports/{id}` с `{"status": "resolved"|"dismissed"|"new"}`
  меняет статус, записывает `resolved_at`/`resolved_by` (для `new` обнуляет
  их) и отвечает `204`; неизвестный `id` — `404`.
- REQ-013: `GET /api/v1/admin/stats` дополнительно возвращает
  `"reports_new"` — число жалоб в статусе `new` (без учёта периода).
- REQ-014: Обе новые ручки защищены `current_admin`: `401`/`403`/`503` до
  валидации параметров, как у `admin/stats`.
- REQ-015: В навигации `/admin/` появляется раздел «Жалобы» (`#reports`) со
  счётчиком новых жалоб. Раздел показывает список с причиной, датой,
  комментарием, запросом и ответом (как текст), фильтр по статусу и кнопки
  «Рассмотрено» и «Отклонить» (для закрытых — «Вернуть в новые»). После
  действия жалоба обновляется в списке и меняется счётчик. Пустой список —
  «Жалоб нет».

### Безопасность и журнал

- REQ-016: Тексты жалоб, комментариев, запросов и ответов не попадают в
  журнал; события журналируются с `dialog_id`, `message_id`, `report_id`,
  причиной и статусом. Во frontend динамический текст вставляется только через
  `textContent`.

## Сценарии

### Жалоба на новый ответ

- Given агент завершил ответ, пришёл `message_end` с `message_id`
- When пользователь нажимает «Пожаловаться», выбирает «Страшно» и «Отправить»
- Then `POST …/report` отвечает `201`, кнопка показывает «Жалоба отправлена»

### Повторная жалоба

- Given на ответ уже есть жалоба
- When запрос `POST …/report` отправлен ещё раз
- Then `409`, первая жалоба не изменилась

### Чужой ответ

- Given ответ принадлежит диалогу другого пользователя
- When отправляется `POST …/report`
- Then `404`, жалоба не создаётся

### Разбор администратором

- Given есть новая жалоба «Грубо или обидно»
- When администратор открывает «Жалобы» и нажимает «Рассмотрено»
- Then жалоба переходит в `resolved`, счётчик новых уменьшается

### Пользователь удалил историю

- Given на ответ подана жалоба
- When пользователь удаляет историю
- Then администратор видит жалобу с текстом ответа и пометкой «история удалена»

## Технологии и структура

- Backend: миграция `0006` и таблица в `db/tables.py`; операция
  `report` в контракте `HistoryStore` (`InMemoryHistoryStore`,
  `PostgresHistoryStore`) и поле `reported` в сообщениях; метод жалобы в
  `AgentService`; ручка в `api/app.py`, схемы в `api/schemas.py`; в пакете
  `admin` — контракт и сервис списка и смены статуса жалоб,
  `PostgresAdminStatsStore` или отдельное хранилище в `db/`; ручки в
  `api/admin.py`; `reports_new` в статистике.
- Frontend: `agent-api.js` (`reportMessage`, разбор `reported`),
  `script.js`, `styles.css`, `index.html`; `admin/admin-api.js`,
  `admin/admin.js`, `admin/index.html`, `admin/admin.css`.
- Документация: `docs/dialogs.md`, `docs/database.md`, `docs/admin.md`
  (снять запрет на показ текстов ответов для жалоб), `docs/README.md`,
  `frontend/README.md`, `AGENTS.md`.

## Тестирование

- Модульные тесты `InMemoryHistoryStore` и `AgentService`: создание жалобы с
  копией текстов, `409` при повторе, отказ для сообщения пользователя и
  чужого диалога, `reported` в истории; сервиса жалоб администратора.
- Интеграционные API-тесты: коды `201/401/404/409/422/503` для жалобы;
  `reported` в истории; `GET`/`PATCH` `admin/reports` c `401/403/404/422`,
  фильтром статуса и отсутствием данных пользователя; `reports_new`.
- Интеграционные тесты PostgreSQL (`TEST_DATABASE_URL`): миграция `0006`,
  уникальность, сохранение жалобы при удалении диалога (`message_id` → `NULL`).
- Node-тесты: `AgentApi.reportMessage`; UI чата (кнопка, окно, выбор
  причины, состояние после `201`/`409`, ошибка, восстановление из истории,
  отсутствие у ошибочного ответа); UI админки (список, фильтр, смена статуса,
  счётчик, пустое состояние, вывод текста через `textContent`).
- Ручная проверка в `make run`: жалоба в чате и её разбор в `/admin/`.

## Границы

- Всегда: проверять владельца на backend; копировать тексты в жалобу в момент
  подачи; не возвращать администратору логин автора жалобы.
- Сначала спросить: показ логина автора, уведомление пользователя о
  результате разбора, автоматическую модерацию ответов, жалобы на сообщения
  пользователя, удаление жалоб.
- Никогда: не менять миграции `0001`–`0005`; не логировать тексты.

## Критерии приёмки

- [ ] Под завершёнными ответами есть «Пожаловаться» с выбором причины;
  жалоба сохраняется, повтор невозможен, состояние восстанавливается из истории.
- [ ] API жалобы отвечает по REQ-003–REQ-005; чужой ответ — `404`.
- [ ] Раздел «Жалобы» в `/admin/` показывает жалобы с текстами, фильтр и смену
  статуса; счётчик новых жалоб корректен.
- [ ] Жалоба остаётся у администратора после удаления истории пользователем.
- [ ] `make migrate` применяет `0006` без потери данных.
- [ ] `make test` и `make lint` проходят успешно.

## Открытые вопросы

- Нет. Допущения (предложены ранее, можно поменять до одобрения):
  администратор видит текст ответа и предшествующий запрос, но не логин
  автора; жалоба переживает удаление истории; пользователь не получает
  уведомления о результате разбора.
