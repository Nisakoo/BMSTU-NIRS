# Оптимистичная блокировка изменений знаний по ревизиям

## Цель

Не терять изменения, когда несколько авторов или агентов выгружают знания,
редактируют пакеты вне репозитория и загружают их обратно. Пакет, созданный
выгрузкой, несёт текущую ревизию каждой сущности; `load` применяет изменения
только если в БД всё ещё та же ревизия. Иначе загрузка отменяется целиком и
показывает конфликты.

Это третье изменение серии `knowledge-maintenance`, после `knowledge-export` и
`knowledge-delete`.

## Допущения

- Ревизии уже append-only и хранятся в `rag_revisions`; текущая ревизия
  сущности — максимальный номер её ревизии.
- `KnowledgeStore.snapshot()` из `knowledge-export` возвращает
  `KnowledgeSnapshot` с сущностями и индексом ревизий; отдельный порт для
  ревизий не вводится.
- Метаданные блокировки необязательны. Пакет без них загружается по прежним
  правилам (последняя запись побеждает), поэтому старые пакеты и сценарии
  остаются рабочими.
- Ожидаемые ревизии хранятся в `package.yaml` в поле `revisions`.
  `format_version` остаётся `1`: формат файлов сущностей не меняется, а поле
  необязательное. Пакеты без поля загружаются по старым правилам.
- `export` всегда пишет `revisions` для сущностей с ревизией больше `0`;
  отдельных флагов `--no-revisions` и `load --no-lock` нет. Для обхода
  блокировки автор удаляет поле из manifest осознанно.
- Конфликт блокирует весь пакет, а не отдельные сущности. В сообщении
  показываются ожидаемая и текущая ревизии либо отсутствие сущности.
- Устаревшие строки о RAG в `backend/README.md` и `docker/README.md`
  актуализируются в этом же изменении.
- Новых миграций и зависимостей нет. Схема `rag_*` не меняется.
- Блокировка защищает только от потери изменений при `load`. Она не заменяет
  проверку целостности и не блокирует параллельные загрузки: их по-прежнему
  сериализует advisory lock.

## Требования

### Ревизии в снимке

- REQ-001: `KnowledgeSnapshot` содержит `knowledge: KnowledgeSet` и
  `revisions: dict[EntityRef, int]` — текущую ревизию каждой сущности.
  `PostgresKnowledgeStore.snapshot()` читает сущности и максимальные ревизии в
  одной транзакции `REPEATABLE READ READ ONLY` фиксированным числом запросов;
  `InMemoryKnowledgeStore` отдаёт согласованный индекс процесса.
- REQ-002: Для сущности без строк в `rag_revisions` ревизия считается `0` и в
  пакет не записывается: такая сущность не блокируется. Для сущности с
  ревизиями индекс содержит максимальный номер.

### Экспорт метаданных

- REQ-003: `export` записывает в `package.yaml` необязательное поле `revisions`
  — отображение «каталог типа → `id` → текущая ревизия» только для выгруженных
  сущностей с ревизией больше `0`. Порядок ключей детерминирован; при отсутствии
  ревизий поле не пишется.
- REQ-004: Поле `revisions` не дублирует данные в файлах сущностей и не меняет
  `KNOWLEDGE_FORMAT_VERSION`. Пакет без поля остаётся валидным и загружается без
  блокировки.
- REQ-005: `package_schema` выводит схему manifest с необязательным `revisions`;
  схема сущностей не меняется.

### Проверка пакета

- REQ-006: `PackageManifest` принимает необязательное `revisions`; ключи верхнего
  уровня — только известные каталоги типов, `id` — slug, значения — целые числа
  `>= 1`. Неизвестный каталог или отсутствующая в пакете сущность дают
  `unknown_revision_entity`; неверный `id` или неположительная ревизия —
  `invalid_revision`; неверный YAML-тип значения сохраняет общий код
  `invalid_type`.
- REQ-007: `check` проверяет, что каждая запись `revisions` указывает на
  сущность, файл которой есть в пакете и прошёл проверку. Если файл сущности уже
  невалиден, отдельная ошибка ревизии не добавляется, чтобы не плодить каскад.
- REQ-008: Пакет с `revisions`, но без соответствующей сущности, невалиден;
  `load` до БД не доходит. Пакет без `revisions` валиден и не требует изменений
  в существующих файлах.

### Загрузка с блокировкой

- REQ-009: `load` читает ожидаемые ревизии из manifest и внутри той же
  транзакции, что и загрузка, получает текущий индекс ревизий. Для каждой
  сущности пакета с ожидаемой ревизией текущая ревизия должна совпадать.
- REQ-010: Конфликт — это несовпадение номера, отсутствие сущности в БД или
  отсутствие у неё ревизии. Конфликты собираются по всем затронутым сущностям;
  загрузка отменяется целиком, БД, `rag_loads` и `rag_revisions` не меняются.
- REQ-011: Отчёт конфликта содержит `file` сущности, `path="revisions"`, код
  `revision_mismatch` и номера ожидаемой и текущей ревизии либо пометку об
  отсутствии сущности. Номера ревизий не являются содержимым знаний и могут
  попадать в отчёт и журнал.
- REQ-012: Сущность пакета без ожидаемой ревизии обрабатывается как раньше:
  новая создаётся, существующая заменяется без проверки. Это сохраняет
  обратную совместимость и позволяет добавлять новые сущности.
- REQ-013: Успешная загрузка с метаданными не меняет формат ревизий: для
  изменённых сущностей пишется очередная ревизия, для неизменных — нет.
  Повторная загрузка неизменного пакета по-прежнему не меняет строки.

### Отчёт, CLI и наблюдаемость

- REQ-014: `LoadReport` получает конфликты в общем списке `issues`; текстовый и
  JSON-вывод сохраняют текущие поля и коды возврата (`1` при конфликте).
  Отдельный флаг подтверждения конфликтов не вводится.
- REQ-015: Каждый `load` пишет событие `rag.load.completed` с `outcome`
  (`loaded`, `rejected`, `failed`), `conflict_count`, `duration_ms` и при
  необходимости `reason` или `error_type`. `id`, ожидаемые ревизии и содержимое
  знаний в журнал не попадают; `conflict_count` добавляется в безопасные поля
  аддитивно.
- REQ-016: `docs/knowledge.md` описывает `revisions` в `package.yaml` и правило
  сравнения; `docs/rag.md` — экспорт метаданных и поведение `load` при
  конфликте; `docs/logging.md` — событие `rag.load.completed`;
  `docs/README.md` и раздел «Реализованный каталог знаний» `AGENTS.md`
  получают строки о блокировке. Изменения общих файлов аддитивные.
- REQ-017: Тесты покрывают manifest и `check`, экспорт ревизий, загрузку без
  метаданных и с конфликтами, оба хранилища, CLI и PostgreSQL. `make lint`,
  `make test` и `make test-integration` проходят.

## Сценарии

### Успешная загрузка после редактирования

- Given пакет выгружен с ревизиями и с тех пор никто не менял эти сущности
- When автор загружает изменённый пакет
- Then изменения применяются, для изменённых сущностей появляются новые
  ревизии, конфликтов нет

### Конкурентное изменение

- Given пакет выгружен с ревизией `3`, а другая загрузка изменила сущность до
  ревизии `4`
- When загружается старый пакет
- Then `load` отменяется, в отчёте `revision_mismatch` с ожидаемой `3` и текущей
  `4`, БД и журналы не изменены

### Конкурентное удаление

- Given сущность выгружена с ревизией, а затем удалена другой командой
- When загружается старый пакет
- Then `load` отменяется, конфликт сообщает об отсутствии сущности, БД не
  изменена

### Несколько конфликтов

- Given в пакете две сущности, обе изменены после выгрузки
- When выполняется `load`
- Then отчёт содержит оба конфликта, ни одна сущность не записана

### Пакет без метаданных

- Given пакет создан вручную и не содержит `revisions`
- When выполняется `load`
- Then поведение прежнее: существующие сущности заменяются, новые создаются

### Новая сущность без ревизии

- Given в пакете есть новая сущность без записи в `revisions`
- When выполняется `load`
- Then она создаётся, остальные проверки выполняются по общим правилам

### Неизвестная запись ревизии

- Given `package.yaml` содержит ревизию для `characters/ghost`, которого нет в
  пакете
- When выполняется `check`
- Then пакет невалиден с `unknown_revision_entity`, `load` не обращается к БД

## Технологии и структура

- `rag/ports.py` — `KnowledgeSnapshot.revisions` и индекс ревизий в транзакции.
- `rag/postgres.py`, `rag/memory.py` — чтение индекса ревизий.
- `rag/package.py` — `PackageManifest.revisions`, `PackageContents.revisions`,
  проверки и `package_schema`.
- `rag/maintenance.py` — запись `revisions` при экспорте.
- `rag/services.py` — сравнение ожидаемых и текущих ревизий в `load_package`.
- `rag/cli.py` — отчёт о конфликтах и коды возврата.
- `docs/knowledge.md`, `docs/rag.md`, `docs/README.md`, `AGENTS.md`.
- Новых миграций, зависимостей и изменений схемы нет.

## Команды

- `make knowledge-export DIR=<path>` — пакет с `revisions`
- `make knowledge-check DIR=<path>` — проверка manifest и сущностей
- `make knowledge-load DIR=<path>` — загрузка с проверкой ревизий
- Тесты: `make test`, `make lint`, `make test-integration`

## Границы

- Всегда: проверять ревизии до записи; отменять загрузку целиком при конфликте;
  сохранять обратную совместимость пакетов без метаданных; использовать
  синтетические данные; не логировать содержимое знаний.
- Сначала спросить: повышение `format_version` и поддержку нескольких версий;
  sidecar вместо поля manifest; новые зависимости; изменения других модулей;
  правки `AGENTS.md`, `observability.py` сверх аддитивных строк.
- Никогда: менять схему `rag_*`; перезаписывать конфликтную сущность; вводить
  блокировку для пакетов без метаданных; добавлять HTTP API или инструмент
  агента; удалять и переименовывать сущности в этом изменении.

## Критерии приёмки

- [ ] `export` пишет текущие ревизии выгруженных сущностей в `package.yaml`.
- [ ] `check` принимает пакеты с метаданными и без них и отвергает неизвестные
      или неположительные записи.
- [ ] `load` отменяется при любом конфликте и не оставляет изменений в БД,
      `rag_loads` и `rag_revisions`.
- [ ] Отчёт перечисляет все конфликты с номерами ревизий или отсутствием
      сущности.
- [ ] Пакеты без `revisions` загружаются по прежним правилам.
- [ ] Событие `rag.load.completed` содержит `conflict_count` и не содержит
      содержимого знаний.
- [ ] Документация обновлена, diff общих файлов аддитивный.
- [ ] `make lint`, `make test` и `make test-integration` проходят.

## Открытые вопросы

- Нет. Решения зафиксированы в допущениях и требованиях: `format_version: 1`
  и `revisions` в `package.yaml`, без sidecar и `--no-revisions`; конфликты
  блокируют весь пакет; номера ревизий показываются; ревизия `0` не пишется;
  `load --no-lock` отсутствует; устаревшие README обновляются здесь же.
