# Оптимистичная блокировка изменений знаний по ревизиям

## Цель

Не терять изменения, когда несколько авторов или агентов выгружают знания, редактируют пакеты вне репозитория и загружают их обратно. Пакет, созданный
выгрузкой, несёт текущую ревизию каждой сущности; `load` применяет изменения только если в БД всё ещё та же ревизия. Иначе загрузка отменяется целиком и
показывает конфликты. Это третье изменение серии `knowledge-maintenance`, после `knowledge-export` и `knowledge-delete`.

## Требования

### Ревизии в снимке
- REQ-001: `KnowledgeSnapshot` содержит `knowledge: KnowledgeSet` и `revisions: dict[EntityRef, int]` — текущую ревизию каждой сущности. `PostgresKnowledgeStore.snapshot()` читает сущности и максимальные ревизии в одной транзакции
  `REPEATABLE READ READ ONLY` фиксированным числом запросов; `InMemoryKnowledgeStore` отдаёт согласованный индекс процесса.
- REQ-002: Для сущности без строк в `rag_revisions` ревизия считается `0` и в пакет не записывается: такая сущность не блокируется. Для сущности с ревизиями индекс содержит максимальный номер. ### Экспорт метаданных
- REQ-003: `export` записывает в `package.yaml` необязательное поле `revisions` — отображение «каталог типа → `id` → текущая ревизия» только для выгруженных сущностей с ревизией больше `0`. Порядок ключей детерминирован; при отсутствии
  ревизий поле не пишется.
- REQ-004: Поле `revisions` не дублирует данные в файлах сущностей и не меняет `KNOWLEDGE_FORMAT_VERSION`. Пакет без поля остаётся валидным и загружается без блокировки.
- REQ-005: `package_schema` выводит схему manifest с необязательным `revisions`; схема сущностей не меняется. ### Проверка пакета
- REQ-006: `PackageManifest` принимает необязательное `revisions`; ключи верхнего уровня — только известные каталоги типов, `id` — slug, значения — целые числа `>= 1`. Неизвестный каталог или отсутствующая в пакете сущность дают
  `unknown_revision_entity`; неверный `id` или неположительная ревизия — `invalid_revision`; неверный YAML-тип значения сохраняет общий код `invalid_type`.
- REQ-007: `check` проверяет, что каждая запись `revisions` указывает на сущность, файл которой есть в пакете и прошёл проверку. Если файл сущности уже невалиден, отдельная ошибка ревизии не добавляется, чтобы не плодить каскад.
- REQ-008: Пакет с `revisions`, но без соответствующей сущности, невалиден; `load` до БД не доходит. Пакет без `revisions` валиден и не требует изменений в существующих файлах. ### Загрузка с блокировкой
- REQ-009: `load` читает ожидаемые ревизии из manifest и внутри той же транзакции, что и загрузка, получает текущий индекс ревизий. Для каждой сущности пакета с ожидаемой ревизией текущая ревизия должна совпадать.
- REQ-010: Конфликт — это несовпадение номера, отсутствие сущности в БД или отсутствие у неё ревизии. Конфликты собираются по всем затронутым сущностям; загрузка отменяется целиком, БД, `rag_loads` и `rag_revisions` не меняются.
- REQ-011: Отчёт конфликта содержит `file` сущности, `path="revisions"`, код `revision_mismatch` и номера ожидаемой и текущей ревизии либо пометку об отсутствии сущности. Номера ревизий не являются содержимым знаний и могут попадать в отчёт
  и журнал.
- REQ-012: Сущность пакета без ожидаемой ревизии обрабатывается как раньше: новая создаётся, существующая заменяется без проверки. Это сохраняет обратную совместимость и позволяет добавлять новые сущности.
- REQ-013: Успешная загрузка с метаданными не меняет формат ревизий: для изменённых сущностей пишется очередная ревизия, для неизменных — нет. Повторная загрузка неизменного пакета по-прежнему не меняет строки. ### Отчёт, CLI и
  наблюдаемость
- REQ-014: `LoadReport` получает конфликты в общем списке `issues`; текстовый и JSON-вывод сохраняют текущие поля и коды возврата (`1` при конфликте). Отдельный флаг подтверждения конфликтов не вводится.
- REQ-015: Каждый `load` пишет событие `rag.load.completed` с `outcome` (`loaded`, `rejected`, `failed`), `conflict_count`, `duration_ms` и при необходимости `reason` или `error_type`. `id`, ожидаемые ревизии и содержимое знаний в журнал не
  попадают; `conflict_count` добавляется в безопасные поля аддитивно.
- REQ-016: `docs/knowledge.md` описывает `revisions` в `package.yaml` и правило сравнения; `docs/rag.md` — экспорт метаданных и поведение `load` при конфликте; `docs/logging.md` — событие `rag.load.completed`; `docs/README.md` и раздел
  «Реализованный каталог знаний» `AGENTS.md` получают строки о блокировке. Изменения общих файлов аддитивные.
- REQ-017: Тесты покрывают manifest и `check`, экспорт ревизий, загрузку без метаданных и с конфликтами, оба хранилища, CLI и PostgreSQL. `make lint`, `make test` и `make test-integration` проходят.

Действующий контракт и архитектурные границы описаны в [каталоге](../../../docs/README.md).
