# Формат и проверка структурированных знаний

## Цель

Дать автору контента и его ИИ-агенту строгий формат структурированных знаний и
проверку подготовленного пакета до загрузки в БД: доменные модели всех
сущностей ER-модели из [`rag-architecture`](../rag-architecture/spec.md),
чтение YAML-пакета, правила целостности на уровне приложения и команды
`check` и `schema`. Изменение пересматривает два решения `rag-architecture`:
данные закрыты и не хранятся в репозитории, а ER-модель дополняется
ситуативными взаимодействиями персонажей в эпизодах.

## Допущения

- Источник истины — PostgreSQL. Загрузка пакета в БД, проверка правил с учётом
  уже загруженных данных и ограничения целостности PostgreSQL — изменение
  `knowledge-postgres-store`. Здесь БД не используется.
- Пакет — набор YAML-файлов, который автор или его агент готовит вне
  публичного репозитория. Пакет может содержать любое подмножество сущностей.
  Закрытое хранилище пакетов (например, приватный репозиторий) — возможное
  будущее изменение.
- Реальные данные никогда не попадают в репозиторий: тесты и примеры
  документации используют синтетические данные.
- Команды проверки на время выполнения загружают весь пакет: правила
  проверяют связи между файлами, а размер пакета (сотни записей) это
  позволяет.
- Ссылка на источник прикрепляется к записи (персонаж, версия, отношение,
  взаимодействие, локация, артефакт), а не к отдельному значению.
  Необязательное поле `note` уточняет, какой факт она подтверждает.
- Как агент применяет отношения и взаимодействия при генерации — изменение
  `knowledge-lookup-tool`; здесь фиксируется только их структура.
- PyYAML уже входит в `uv.lock` транзитивно через LiteLLM. Прямая зависимость
  не добавляет новых пакетов.
- Ориентир для `knowledge-postgres-store` и `knowledge-lookup-tool`: число
  запросов к БД не зависит от размера пакета или карточки (пакетные запросы
  по множеству `id`, `JOIN`), без N+1.
- Загрузка в `knowledge-postgres-store` читает знания из БД целиком
  фиксированным числом пакетных запросов и применяет к объединению с пакетом
  те же правила домена. Чтение только затронутой окрестности вводится, если
  этого потребуют метрики производительности. Правила целостности не
  дублируются в SQL.

## Требования

### Пересмотр решений `rag-architecture`

- REQ-001: Источник истины структурированных знаний — PostgreSQL (схема
  `rag`). Знания поступают пакетами YAML-файлов, подготовленными вне
  публичного репозитория; репозиторий содержит только код и синтетические
  тестовые данные. Заменяет REQ-006 и REQ-007 `rag-architecture`. REQ-008
  сохраняется: загрузка выполняется отдельной командой, backend стартует без
  загруженных знаний.
- REQ-002: ER-модель дополняется сущностью «взаимодействие в эпизоде»:
  ситуативная связь двух персонажей внутри одного эпизода. Отношение остаётся
  устойчивой связью в вариантах канона. Дополняет REQ-013 `rag-architecture`.

### Формат пакета

- REQ-003: Пакет — каталог с подкаталогами `continuities`, `works`,
  `episodes`, `characters`, `locations`, `artifacts`; любой из них может
  отсутствовать. Каждый файл `<id>.yaml` описывает одну сущность, имя файла
  без расширения совпадает с её `id`. Файлы и каталоги, имя которых
  начинается с точки (`.git`, `.DS_Store`), пропускаются. Другие файлы и
  подкаталоги, а также пакет без сущностей — ошибка.
- REQ-004: Файл — YAML-отображение. Скаляры разбираются по правилам YAML 1.2
  core: `true`/`false` — логические значения, десятичные числа — целые, `null`
  и пустое значение — отсутствие значения, остальное (включая `12:05`, `yes`,
  `no`, даты) — строки. Повторяющийся ключ, теги и якоря — ошибка.
- REQ-005: Файл содержит сущность целиком: отношения — в файле персонажа, от
  которого они направлены (для симметричного типа — в файле любого из двух);
  жители — в файле локации; создатели — в файле артефакта; участники и
  взаимодействия — в файле эпизода. Ссылки задаются `id` сущностей.

### Модели

- REQ-006: Доменные модели — неизменяемые Pydantic-модели без лишних полей и
  без неявных преобразований типов. Строковые поля обрезаются по краям и не
  пусты; списки не содержат повторов. Списки, не названные непустыми,
  необязательны и по умолчанию пусты; поля, названные необязательными,
  по умолчанию отсутствуют. Явное `null` вместо списка — ошибка типа.
- REQ-007: Вариант канона: `id`, `name`. Произведение: `id`, `title`, `kind`
  (`series` | `film`), `continuity`. Эпизод: `id`, `work`, необязательный
  `season` ≥ 1, `number` ≥ 1, `title`, списки `characters`, `locations`,
  `artifacts`, `interactions`.
- REQ-008: Персонаж: `id`, `name`, `aliases`, `species`, непустой список
  `versions`, список `relationships`, `sources`. Версия: непустой список
  `continuities`, `age_group` (`child` | `teen` | `adult` | `elderly`),
  непустой список `traits`, `speech_style` (`register`, `markers`,
  `constraints`), `catchphrases`, `sources`.
- REQ-009: Отношение: `to`, `type`, непустой список `continuities`,
  необязательное `description`, `sources`. Типы: `friendship` (дружба) и
  `neighborhood` (соседство) — симметричные; `affection` (симпатия), `mentor`
  (наставник → ученик) и `guardian` (опекун → подопечный) — направленные.
- REQ-010: Взаимодействие: `from`, `to`, `type`, обязательное `description`
  (суть ситуации), `sources`. Типы: `conflict` (конфликт или недопонимание) —
  симметричный; `support` (поддержка) и `empathy` (эмпатия) — направленные.
- REQ-011: Типы отношений и взаимодействий — два реестра домена с признаком
  симметричности. Добавление типа меняет только реестр; порядок разбиения
  типа на несколько описан в документации.
- REQ-012: Локация: `id`, `name`, `aliases`, `description`, непустой список
  `continuities`, `residents`, `sources`. Артефакт: `id`, `name`, `aliases`,
  `artifact_type`, `description`, `capabilities`, `limitations`, непустой
  список `continuities`, `creators`, `sources`.
- REQ-013: Ссылка на источник содержит ровно одно из двух: `episode` с
  необязательным `timecode` вида `MM:SS` или `HH:MM:SS`, либо `document` с
  необязательным `locator`; в обоих случаях — необязательное `note`.
- REQ-014: `id` соответствует `^[a-z0-9]+(_[a-z0-9]+)*$`. Нормализация имён и
  алиасов — одна функция домена: `strip → схлопнуть пробелы → lower → ё→е`.

### Целостность

- REQ-015: Правила целостности — функции домена над набором сущностей, не
  зависящие от его источника. Те же правила применяет загрузка в
  `knowledge-postgres-store` к объединению пакета и уже загруженных данных.
- REQ-016: Ссылка (`continuity`, `work`, участники, `residents`, `creators`,
  `to`, `from`, `continuities`, `episode` в источнике) указывает на сущность
  нужного типа.
- REQ-017: Множества `continuities` версий одного персонажа не пересекаются.
- REQ-018: Отношение не направлено на самого персонажа; его варианты канона
  входят в варианты канона версий обоих персонажей. Тройка «персонаж —
  персонаж — тип» с пересекающимися вариантами канона не повторяется; для
  симметричного типа это относится и к обратной паре.
- REQ-019: Участник эпизода существует в варианте канона эпизода: у персонажа
  есть версия с этим вариантом, у локации и артефакта он входит в
  `continuities`. Житель и создатель имеют версию хотя бы в одном варианте
  канона локации или артефакта.
- REQ-020: Оба персонажа взаимодействия входят в `characters` эпизода и
  различны. Тройка «персонаж — персонаж — тип» в эпизоде не повторяется; для
  симметричного типа это относится и к обратной паре.
- REQ-021: Нормализованные имена и алиасы уникальны среди всех персонажей; у
  локаций и артефактов — среди сущностей того же типа с пересекающимися
  `continuities`.
- REQ-022: Номер эпизода уникален в пределах произведения и сезона. У
  произведения вида `film` не больше одного эпизода; через него задаются
  участники и взаимодействия фильма.
- REQ-023: При проверке пакета ссылка на сущность, которой нет в пакете, не
  является ошибкой: она выводится как внешняя и проверяется при загрузке.
  Правила, которым нужны данные отсутствующей сущности, для неё откладываются
  до загрузки.
- REQ-024: Проверка линейна по размеру набора (число сущностей, ссылок и
  элементов списков), кроме сортировки вывода ошибок. Правила используют
  индексы по `id`, нормализованным именам и ключу «произведение — сезон —
  номер», построенные один раз, и не сравнивают сущности попарно.

### Команды

- REQ-025: Проверка собирает все ошибки формата, моделей и целостности. Ошибка
  содержит путь файла относительно корня пакета, путь поля (например,
  `versions[1].continuities[0]`), стабильный машинный код (например,
  `unknown_reference`) и сообщение на русском языке. Частые ошибки схемы (нет
  поля, лишнее поле, неверный тип, пустое или недопустимое значение) и все
  нарушения целостности имеют русские сообщения.
- REQ-026: `python -m smeshariki_ai.rag check <path> [--format text|json]` не
  требует environment, БД и сети и не задаёт вопросов. Код `0` — пакет
  валиден, `1` — пакет невалиден или не найден, `2` — неверные аргументы.
  Текстовый вывод содержит ошибки в порядке «файл, поле», число сущностей по
  типам и внешние ссылки; JSON-вывод — те же данные в документированной
  структуре.
- REQ-027: `python -m smeshariki_ai.rag schema` печатает JSON Schema формата
  сущностей каждого типа, построенную из доменных моделей.
- REQ-028: `make knowledge-check DIR=<path>` запускает `check` через `uv`.

### Документация

- REQ-029: `docs/knowledge.md` содержит ER-модель с взаимодействиями, формат
  пакета с синтетическими примерами каждого типа, словари типов с
  направленностью, коды ошибок, JSON-вывод, команду `schema` и порядок
  разбиения типа. `docs/rag.md` описывает PostgreSQL как источник истины и
  путь «пакет → check → загрузка → PostgreSQL».
- REQ-030: Добавленный в `rag-architecture` текст о каталоге `knowledge/` в
  `AGENTS.md` и `docs/README.md` заменяется описанием пакетов знаний вне
  репозитория. `AGENTS.md` дополняется разделом «Реализованный каталог
  знаний» по образцу разделов других компонентов; строка компонента в
  `docs/README.md` отражает реализацию. Чужой текст не меняется.

## Сценарии

### Валидный пакет

- Given пакет с вариантом канона, произведением, эпизодом и персонажем,
  участвующим в эпизоде
- When выполняется `check`
- Then выводится число сущностей по типам, код `0`

### Несколько ошибок

- Given у версии персонажа нет `age_group`, а локация указана дважды в
  участниках эпизода
- When выполняется `check`
- Then обе ошибки выводятся с файлом, полем, кодом и русским сообщением, код
  `1`

### Взаимодействие вне эпизода

- Given в эпизоде записан конфликт с персонажем, которого нет в `characters`
  эпизода
- When выполняется `check`
- Then выводится ошибка взаимодействия с путём `interactions[0].to`

### Внешняя ссылка

- Given пакет содержит только эпизод, ссылающийся на персонажа `krosh`
- When выполняется `check`
- Then `krosh` выводится как внешняя ссылка, а не как ошибка, код `0`

### Агент проверяет пакет

- Given агент автора подготовил пакет
- When он выполняет `check --format json`
- Then получает структуру с ошибками и их кодами и исправляет файлы без
  разбора текстового вывода

### Неявный тип YAML и повторяющийся ключ

- Given `timecode: 12:05` без кавычек и дважды указанный `traits`
- When пакет читается
- Then `timecode` остаётся строкой, а повторяющийся ключ — ошибкой

## Технологии и структура

- Python 3.12, Pydantic, PyYAML (безопасная загрузка с собственными правилами
  разбора скаляров), `argparse`.
- Код в `backend/src/smeshariki_ai/rag/`: `models.py` (сущности и реестры
  типов), `integrity.py` (правила), `yaml_reader.py` (безопасный разбор
  YAML), `package.py` (обход пакета),
  `services.py` (use case проверки), `cli.py` и `__main__.py`.
- Тесты в `backend/tests/unit/rag/` на синтетических пакетах в `tmp_path`.
- Общие файлы, только добавления: `backend/pyproject.toml` и `backend/uv.lock`
  (PyYAML), `Makefile` (цель), `AGENTS.md` (раздел). В `AGENTS.md` и
  `docs/README.md` также заменяется собственный текст из `rag-architecture`.

## Команды

- Проверка пакета: `make knowledge-check DIR=<path>`.
- Тесты: `make test`, `make lint`.

## Границы

- Всегда: проверять пакет целиком; не терять данные молча; не требовать БД и
  environment для `check` и `schema`; в общих файлах только добавлять, кроме
  собственного текста из `rag-architecture`.
- Сначала спросить: изменение словарей типов, обязательности полей и раскладки
  пакета; новые зависимости; любое изменение чужого текста.
- Никогда: класть реальные данные в репозиторий; исполнять YAML-теги и
  небезопасную загрузку; менять агента, `db/` и другие модули; править
  закрытую спецификацию `rag-architecture`.

## Критерии приёмки

- [ ] Модели покрывают все сущности ER-модели, включая взаимодействия; правила
  REQ-016–REQ-023 выполняются.
- [ ] `check` выводит все ошибки с файлом, полем, кодом и русским сообщением в
  текстовом и JSON-виде.
- [ ] Неявные типы YAML 1.1 и повторяющиеся ключи не искажают данные.
- [ ] `schema` выдаёт JSON Schema всех типов сущностей.
- [ ] В репозитории нет реальных данных; в общих файлах изменён только
  собственный текст из `rag-architecture`, остальное — добавления.
- [ ] `make knowledge-check`, `make lint` и `make test` проходят.
