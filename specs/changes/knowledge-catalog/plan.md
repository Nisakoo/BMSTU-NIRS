# План: формат и проверка структурированных знаний

## Основание

План реализует согласованную спецификацию
`specs/changes/knowledge-catalog/spec.md`. Изменение создаёт доменные модели
знаний, чтение YAML-пакета, правила целостности и команды `check` и `schema`.
БД, загрузка и инструмент агента остаются за границами этой работы.

## Решения и зависимости

- PyYAML объявляется прямой зависимостью диапазоном `pyyaml>=6.0.3,<7` через
  `uv add`. Пакет уже зафиксирован в `uv.lock` транзитивно, поэтому новые
  пакеты не появляются; diff `pyproject.toml` — одна добавленная строка.
- YAML читается отдельным модулем `yaml_reader.py` (обход пакета — в
  `package.py`) через собственный подкласс `yaml.SafeLoader`: неявные правила
  разбора скаляров заменены правилами YAML 1.2 core (`true`/`false` в трёх
  регистрах, десятичные целые, `null`/`~`/пустое значение). Повторяющийся ключ
  обнаруживается при построении отображения. Теги и якоря обнаруживаются
  проходом по событиям парсера до построения данных.
- Модели наследуют общий `KnowledgeModel` (`strict=True`, `extra="forbid"`,
  `frozen=True`): строгость действует по умолчанию для каждого нового поля.
  Нестрогость разрешена только полям-кортежам и полям-перечислениям
  (`Field(strict=False)`): в YAML нет ни кортежей, ни перечислений, а строгий
  режим Pydantic отвергает YAML-списки и строки на их месте. Элементы кортежей
  и вложенные модели остаются строгими, перечисление принимает только
  допустимое значение. Кортежи делают вложенные данные неизменяемыми.
- Ограничения выражаются декларативно (`StringConstraints` с `pattern` и
  `min_length`, `Field(ge=...)`), чтобы они попадали в JSON Schema команды
  `schema`. Собственный валидатор используется только для правила, которое
  Pydantic не выражает, — отсутствия повторов в списке; он дополняет схему
  признаком `uniqueItems`. Коды ошибок вроде `invalid_id` получаются из таблицы
  перевода типов ошибок Pydantic, а не из собственных исключений.
- Поле `from` взаимодействия хранится как `from_` с alias `from`; JSON Schema
  и сообщения используют alias.
- Ошибка проверки — `Issue(file, path, code, message)`. Ошибки Pydantic
  переводятся в коды и русские сообщения одной таблицей соответствия по типу
  ошибки; неизвестный тип даёт код `schema_error` и исходное сообщение.
- Правила целостности работают с `KnowledgeSet` — неизменяемым набором
  сущностей с индексами по `id`, построенными один раз. Параметр полноты
  набора различает проверку пакета (отсутствующая сущность — внешняя ссылка,
  REQ-023) и будущую загрузку (отсутствующая сущность — ошибка).
- Сущности из файлов, не прошедших проверку моделей, считаются известными, но
  непроверенными: ссылки на них не дают ни ошибок, ни внешних ссылок, а
  зависящие от них правила откладываются. Так одна ошибка в файле не порождает
  каскад ложных ошибок в других файлах.
- В `Makefile` добавляется отдельная строка `.PHONY: knowledge-check`, новая
  цель и строка справки; существующие строки не меняются.

## Порядок реализации

1. Безопасное чтение YAML — самое рискованное техническое решение.
2. Доменные модели и реестры типов.
3. Чтение пакета в `KnowledgeSet` и перевод ошибок схемы.
4. Правила целостности.
5. Use case проверки, CLI и цель `Makefile`.
6. Документация и общие файлы.
7. Итоговая проверка.

Задачи 2 и 3 зависят от 1 и 2 соответственно, задача 4 — от 3, задача 5 — от
4. Документация пишется после кода, чтобы описывать фактический формат.

## Задача 1. Безопасное чтение YAML

**Связанные требования:** REQ-004.

**Критерии приёмки:** скаляры разбираются по YAML 1.2 core; `12:05`, `yes`,
`no` и даты остаются строками; повторяющийся ключ, тег и якорь дают ошибку с
номером строки; синтаксическая ошибка и файл не в UTF-8 не роняют процесс.

**Зависимости:** нет.

**Файлы:**

- `backend/pyproject.toml`;
- `backend/uv.lock`;
- `backend/src/smeshariki_ai/rag/yaml_reader.py`;
- `backend/tests/unit/rag/test_yaml.py`.

**Действия (RED → GREEN → REFACTOR):**

1. Добавить PyYAML командой `uv add --project backend "pyyaml>=6.0.3,<7"` и
   убедиться, что diff `pyproject.toml` — одна добавленная строка.
2. Написать падающие тесты: YAML 1.1-ловушки, три вида логических значений,
   `null`, повторяющийся ключ на разной вложенности, явный тег, якорь и
   ссылка, синтаксическая ошибка, корень не отображение, файл не в UTF-8.
3. Реализовать загрузчик и функцию чтения одного файла, возвращающую данные
   либо ошибку YAML с кодом и строкой.

**Тест:**

```sh
uv run --project backend --locked pytest backend/tests/unit/rag/test_yaml.py
```

## Задача 2. Доменные модели и реестры типов

**Связанные требования:** REQ-006–REQ-014.

**Критерии приёмки:** модели всех сущностей отвергают отсутствующие
обязательные, лишние, пустые и неверно типизированные поля и повторы в
списках; необязательные списки по умолчанию пусты, а явное `null` вместо
списка — ошибка; словари типов
отношений и взаимодействий содержат признак симметричности; `id`, `timecode`
и ссылка на источник проверяются по спецификации; нормализация — одна
функция.

**Зависимости:** нет.

**Файлы:**

- `backend/src/smeshariki_ai/rag/models.py`;
- `backend/tests/unit/rag/test_models.py`.

**Действия (RED → GREEN → REFACTOR):**

1. Написать падающие тесты валидных и невалидных примеров каждой сущности,
   минимальных записей без необязательных полей, `null` вместо списка,
   словарей, `SourceRef`, `id`, `timecode`, нормализации.
2. Определить `KnowledgeModel`, общие аннотированные типы (`Slug`,
   `NonEmptyText`, уникальный кортеж), перечисления и реестры типов с
   симметричностью.
3. Определить модели варианта канона, произведения, эпизода с
   взаимодействиями, персонажа с версиями и отношениями, локации, артефакта и

4. Выразить ограничения декларативно; собственный валидатор оставить только

5. Проверить тестом, что JSON Schema моделей содержит шаблоны `id` и

## Задача 4. Правила целостности

**Связанные требования:** REQ-015–REQ-024.

**Критерии приёмки:** каждое правило ловит своё нарушение и не срабатывает на
валидном наборе; при неполном наборе отсутствующие сущности выводятся как
внешние ссылки, а зависящие от них правила откладываются; индексы строятся
один раз, попарных сравнений нет.

**Зависимости:** задача 3.

**Файлы:**

- `backend/src/smeshariki_ai/rag/integrity.py`;
- `backend/tests/unit/rag/test_integrity.py`.

**Действия (RED → GREEN → REFACTOR):**

1. Подготовить в тесте построитель синтетического валидного набора и по
   тесту на каждое нарушение REQ-016–REQ-022.
2. Добавить тесты неполного набора: внешняя ссылка, отложенное правило,
   непроверенная сущность.
3. Реализовать правила как функции над `KnowledgeSet`, возвращающие `Issue`;
   имя файла выводится из типа и `id` сущности.
4. Ревью сложности: индексы по `id`, нормализованным именам и ключу

**Тест:**

