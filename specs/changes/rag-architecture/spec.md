# Архитектура RAG и модель предметной области

## Цель

Зафиксировать до написания кода, что такое RAG в `smeshariki-ai`: границы модуля, гексагональные слои, единственное хранилище, источник истины данных, правила
изоляции и концептуальную ER-модель структурированных знаний о вселенной «Смешариков». Последующие изменения `knowledge-*` реализуют эту архитектуру и не
пересматривают её без нового изменения. Изменение только документационное: код, каталог `knowledge/`, таблицы и зависимости не создаются.

## Требования

### Границы и слои
- REQ-001: `docs/rag.md` описывает RAG как часть backend-монолита в пакете `smeshariki_ai.rag`, без отдельного сервиса и публичного HTTP API. Агент получает RAG только через наследников `agent.tools.Tool`, которые регистрируются в
  composition root. Инструмент точного поиска называется `lookup_knowledge`.
- REQ-002: `docs/rag.md` фиксирует гексагональные слои и правило зависимостей: домен (модели, правила целостности, нормализация) не зависит ни от чего, кроме Pydantic; use cases зависят от домена и исходящих портов; входящие адаптеры
  (инструменты агента, CLI) вызывают только use cases; исходящие адаптеры (PostgreSQL, файлы каталога) реализуют порты.
- REQ-003: Порты называются по возможностям предметной области, а не по технологиям. Порт вводится только на границе с внешней системой, которую тесты заменяют fake-реализацией (БД, LLM/embeddings). Чтение файлов каталога — адаптер без
  отдельного порта. ### Технологии и данные
- REQ-004: Единственное хранилище RAG — PostgreSQL backend. Допустимый путь расширения: встроенный полнотекстовый поиск, `pg_trgm`, `pgvector` и embeddings через уже используемый LiteLLM. Каждое расширение подключается отдельным изменением
  с обоснованием.
- REQ-005: Явно не используются: Qdrant и другие отдельные хранилища, локальные файлы индексов, pickle, ML-модели в процессе backend без подтверждения бенчмарком.
- REQ-006: Источник истины структурированных знаний — YAML-файлы в каталоге `knowledge/` в корне репозитория, по одному файлу на сущность. PostgreSQL — проекция только для чтения во время работы backend. Единственный писатель — команда
  синхронизации backend. Данные не кладутся в Alembic-миграции.
- REQ-007: Каталог `knowledge/` содержит только данные. Формат, схему и правила валидации определяет backend; каталог зависит от backend, а не наоборот.
- REQ-008: Синхронизация выполняется отдельным шагом после миграций, а не при старте backend. Backend стартует без загруженных знаний; инструмент в этом случае возвращает безопасную ошибку «знания недоступны». ### Изоляция модуля
- REQ-009: Таблицы RAG находятся в отдельной схеме PostgreSQL `rag`, описаны собственным `MetaData` в пакете `rag` и не имеют внешних ключей, `JOIN` и других зависимостей от таблиц других модулей.
- REQ-010: Адаптер PostgreSQL RAG находится в пакете `rag`; пакет `db/` других модулей не меняется. Миграции RAG — отдельные файлы в общей цепочке Alembic, затрагивающие только схему `rag`.
- REQ-011: Из других модулей код RAG импортирует только `agent.tools.Tool` (в адаптере инструментов) и общие `DatabaseConfig` и `create_engine`.
- REQ-012: Инструмент агента зависит от интерфейса use case, а не от его реализации, а аргументы и результаты use cases — Pydantic-модели без ORM-объектов и типов адаптеров. Так при выделении RAG в сервис инструмент заменяется HTTP-клиентом
  без изменения агента и домена. ### Модель предметной области
- REQ-013: `docs/knowledge.md` содержит концептуальную ER-модель из раздела «Модель предметной области»: сущности, ключевые атрибуты, связи, кардинальности и Mermaid ER-диаграмму.
- REQ-014: Правила идентичности: каждая сущность имеет неизменяемый slug `^[a-z0-9]+(_[a-z0-9]+)*$`, уникальный в пределах типа. Имена и алиасы нормализуются как `strip → схлопнуть пробелы → lower → ё→е`. Нормализованные имя и алиасы
  персонажа уникальны среди персонажей; у локаций и артефактов — среди сущностей того же типа с пересекающимися вариантами канона.
- REQ-015: Вариант канона — самостоятельная сущность. Персонаж — неизменная идентичность (slug, имя, алиасы, вид) и одна или несколько версий с атрибутами, которые могут различаться между вариантами канона. Каждая версия действует в
  непустом множестве вариантов канона; множества версий одного персонажа не пересекаются.
- REQ-016: Локации, артефакты и отношения не имеют версий и действуют в непустом множестве вариантов канона. Отношение связывает идентичности персонажей и допустимо только в вариантах канона, где у обоих персонажей есть версия. Жители и
  создатели — идентичности персонажей.
- REQ-017: Участие персонажа, локации или артефакта в эпизоде допустимо, только если вариант канона эпизода входит в варианты канона участника (для персонажа — одной из его версий). Все ссылки между сущностями проверяются до записи в БД.
- REQ-018: Ссылка на источник необязательна. Её указывают для чувствительных фактов: оспоримых, различающихся между вариантами канона или способных повлиять на будущие сюжеты. `docs/knowledge.md` содержит критерии для автора контента.
  Валидатор проверяет только корректность указанной ссылки.
- REQ-019: В структурированную модель не входят правила мира и стиля сказок (ответственность system prompt агента) и повествовательные тексты (будущий поиск по лору). ### Согласованность и интеграция
- REQ-020: Версия персонажа покрывает поля, на которые уже опирается system prompt агента: возрастная группа `child | teen | adult | elderly`, характер и `speech_style`. Различие вариантов канона выражается данными, а не правилами RAG.
- REQ-021: `docs/rag.md` содержит таблицу точек интеграции: файлы, которые RAG создаёт сам, и общие файлы, которые он затрагивает минимально (`bootstrap.py`, `docker/compose.yaml`, `docker/Dockerfile`, `Makefile`, добавление файлов в
  каталог версий миграций, `docs/README.md`, `AGENTS.md`). Каждое изменение общего файла согласуется с его владельцем.
- REQ-022: `docs/rag.md` содержит цепочку следующих изменений с одной строкой ответственности на каждое.
- REQ-023: `docs/README.md` получает только дополнения: строки каталога со ссылками на `rag.md` и `knowledge.md`. Чужой текст не переписывается.
- REQ-024: Правки `AGENTS.md` из раздела «Согласованность с документацией» вносятся только после одобрения владельцем (Nisakoo). До одобрения изменение не переходит в `verify`.

Действующий контракт и архитектурные границы описаны в [каталоге](../../../docs/README.md).
