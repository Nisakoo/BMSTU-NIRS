# План: архитектура RAG и модель предметной области

## Основание

План реализует согласованную спецификацию
`specs/changes/rag-architecture/spec.md`. Изменение только документационное:
создаются страницы `docs/rag.md` и `docs/knowledge.md`, `docs/README.md`
дополняется ссылками, а `AGENTS.md` правится после одобрения владельцем. Код,
каталог `knowledge/`, таблицы и зависимости не создаются.

## Решения и зависимости

- Страницы оформляются как остальные тематические страницы `docs/`
  (`database.md`, `agent.md`): заголовок, ссылка «← Глобальный каталог»,
  краткие разделы со ссылками на SDD-артефакты вместо копирования требований.
- Mermaid используется дважды: гексагональная схема в `docs/rag.md` и
  ER-диаграмма в `docs/knowledge.md`. ER-диаграмма переносится из спецификации
  без изменений; гексагональная схема — новая и короче варианта из обсуждения.
- Правки чужих документов разделены. Задача 3 только добавляет строки в
  `docs/README.md` (REQ-023). Замена текста в `AGENTS.md` и строки «Что пока не
  реализовано» в `docs/README.md` (таблица «Согласованность с документацией»)
  выполняется только в задаче 4, после одобрения владельцем (REQ-024).
- Пока одобрения нет, `docs/rag.md` содержит короткую пометку о расхождении с
  `AGENTS.md` (`search_knowledge`, отдельное векторное хранилище, Qdrant). Так
  читатель ветки не примет наши решения за уже согласованные общие правила.
  Задача 4 удаляет пометку.
- Предложение правок `AGENTS.md` уже подготовлено в виде diff и передано
  пользователю для отправки владельцу. Ответ владельца пользователь передаёт в
  чат; задача 4 выполняется по одному из трёх исходов, описанных в ней.

## Порядок реализации

1. Создать `docs/rag.md` с пометкой о расхождении.
2. Создать `docs/knowledge.md`.
3. Дополнить `docs/README.md` ссылками.
4. После ответа владельца: внести правки `AGENTS.md` и `docs/README.md`, снять
   пометку.
5. Выполнить verify и записать результат.

Задачи 1–3 не зависят от владельца и выполняются сразу. Если до задачи 4
ответа нет, работа останавливается со статусом `in-queue`.

## Задача 1. Создать страницу архитектуры RAG

**Связанные требования:** REQ-001–REQ-012, REQ-021, REQ-022.

**Критерии приёмки:** по одной странице понятны границы RAG в монолите,
гексагональные слои и правило зависимостей, допустимые и запрещённые
технологии, источник истины и путь данных, правила изоляции, точки интеграции
с владельцами и цепочка следующих изменений. Требования не копируются, страница
ссылается на спецификацию. Пометка о расхождении с `AGENTS.md` присутствует.

**Зависимости:** нет.

**Файлы:**

- `docs/rag.md`.

**Действия:**

1. Раздел «Назначение и границы»: RAG внутри `smeshariki_ai.rag`, без сервиса
   и HTTP API; агент получает его через инструмент `lookup_knowledge`;
   структурированные знания — первая очередь, поиск по лору — позже.
2. Раздел «Слои»: Mermaid-схема входящих адаптеров, use cases, домена, портов
   и исходящих адаптеров; правило зависимостей и правило введения порта.
3. Раздел «Технологии»: PostgreSQL как единственное хранилище, путь
   расширения (FTS, `pg_trgm`, `pgvector`, embeddings через LiteLLM) и явный
   список того, что не используется.
4. Раздел «Данные»: `knowledge/` как источник истины, проверка, синхронизация
   отдельным шагом после миграций, проекция только для чтения, поведение
   backend без загруженных знаний.
5. Раздел «Изоляция»: схема `rag`, отсутствие зависимостей от чужих таблиц и
   `db/`, допустимые импорты, зависимость инструмента от интерфейса use case.
6. Таблица точек интеграции: файл, что меняется, владелец, нужно ли
   согласование. Раздел «Дальнейшие изменения» с одной строкой на каждое.
7. Пометка «Расхождение с `AGENTS.md` ожидает согласования» со ссылкой на
   таблицу согласованности в спецификации.

**Проверка:** ревью страницы по REQ-001–REQ-012, REQ-021, REQ-022; ссылки
открываются из `docs/`. Автоматический тест не создаётся.

## Задача 2. Создать страницу модели знаний

**Связанные требования:** REQ-013–REQ-020.

**Критерии приёмки:** автор контента и разработчик по одной странице понимают
сущности и связи, правила идентичности и нормализации, устройство версий
персонажа и вариантов канона, правила участия в эпизодах, соответствие
агрегатов и реляционного представления и критерии указания источника.

**Зависимости:** нет.

**Файлы:**

- `docs/knowledge.md`.

**Действия:**

1. Перенести ER-диаграмму и таблицу сущностей из спецификации.
2. Раздел «Идентичность»: формат slug, неизменяемость, нормализация имён и
   алиасов, области уникальности для персонажей и для локаций и артефактов.
3. Раздел «Варианты канона и версии»: идентичность и версии персонажа,
   непересекающиеся множества версий, наборы вариантов у остальных сущностей,
   правила для отношений и эпизодов. Короткий YAML-пример персонажа с двумя
   версиями, помеченный как иллюстрация, а не формат.
4. Раздел «Реляционное представление»: агрегат в YAML и модели против таблиц;
   алиасы, варианты канона и связи — таблицы, описательные списки — `text[]`,
   `speech_style` — колонки версии; детали — в `knowledge-postgres-store`.
5. Раздел «Источники»: ссылка необязательна; критерии чувствительного факта с
   примерами; формы ссылки (эпизод с таймкодом, документ с местом).
6. Раздел «Вне модели»: правила мира и стиля (system prompt агента) и
   повествовательные тексты (будущий поиск по лору).

**Проверка:** ревью страницы по REQ-013–REQ-020; ER-диаграмма совпадает со
спецификацией. Автоматический тест не создаётся.

## Задача 3. Дополнить глобальный каталог

**Связанные требования:** REQ-023.

**Критерии приёмки:** из `docs/README.md` открываются обе новые страницы;
diff файла содержит только добавленные строки.

**Зависимости:** задачи 1 и 2.

**Файлы:**

- `docs/README.md`.

**Действия:**

1. Добавить в «Тематические страницы» пункты «RAG» и «Модель знаний».
2. Добавить в таблицу компонентов строку «Архитектура RAG» с состоянием
   «Специфицировано» и ссылками на страницы и спецификацию.

**Проверка:**

```sh
git diff --numstat docs/README.md
```

Во втором столбце (удалённые строки) — `0`.

## Задача 4. Согласованные правки чужих документов

**Связанные требования:** REQ-024.

**Критерии приёмки:** `AGENTS.md` и строка «Что пока не реализовано» в
`docs/README.md` соответствуют согласованному с владельцем варианту; пометка
о расхождении удалена из `docs/rag.md`.

**Зависимости:** задачи 1–3; ответ владельца, переданный пользователем.

**Файлы:**

- `AGENTS.md`;
- `docs/README.md`;
- `docs/rag.md`.

**Действия по ответу владельца:**

1. Одобрен diff как есть — применить его, заменить в `docs/README.md`
   «RAG и инструмент `search_knowledge`» на «RAG и его инструменты», удалить
   пометку.
2. Предложена другая формулировка без смены решений — применить её вариант,
   далее как в п. 1. Спецификация не меняется.
3. Не согласен с решением — остановиться, предложить пользователю изменение
   спецификации, после её повторного одобрения обновить `docs/rag.md`,
   `docs/knowledge.md` и этот план, затем применить согласованный вариант.

Неоднозначный ответ уточняется у пользователя.

**Проверка:** ревью diff `AGENTS.md` и `docs/README.md` против согласованного
варианта; в `docs/rag.md` нет пометки.

## Задача 5. Verify

**Связанные требования:** все.

**Зависимости:** задачи 1–4.

**Файлы:**

- `specs/changes/rag-architecture/verification.md`.

**Действия:**

1. Сверить страницы с каждым требованием и критерием приёмки.
2. Проверить относительные ссылки и отсутствие изменений вне перечисленных
   файлов: `git diff --stat origin/main`.
3. Записать `verification.md` и установить статус `done` через CLI.

`make test` неприменим: Python-код не изменяется.
