# План: макет frontend-панели администратора

## Исходное состояние и решения

- Текущий frontend является vanilla JavaScript приложением с одной Vite
  HTML-entry `frontend/src/index.html`; production build раздаётся существующим
  Nginx-контейнером, а Caddy направляет все пути кроме `/api/*` во frontend.
- Админский макет остаётся второй HTML-entry того же Vite-проекта. Production
  build должен содержать `index.html` и `admin/index.html`, поэтому отдельный
  сервис, порт и frontend package не нужны.
- Макет не использует backend. Все наборы данных локальны, детерминированы и
  явно помечены как демонстрационные. Реальный API и авторизация не
  проектируются скрыто внутри этой задачи.
- Визуальная связь с пользовательским режимом создаётся цветами, свечением,
  скруглениями и типографикой. CSS пользовательского чата не импортируется,
  чтобы admin-страница не зависела от его декоративной сцены.
- График строится без библиотек. DOM создаётся безопасными методами с
  `textContent`; `innerHTML` для динамических данных не используется.
- Desktop использует компактную боковую навигацию и широкую аналитическую
  область; tablet — двухколоночную сетку; mobile — одну колонку и карточное
  представление записей пользователей без горизонтального overflow страницы.

## Задача 1. Зафиксировать две frontend-entry и маршрутизацию `/admin/`

**Требования:** REQ-001, REQ-002, REQ-014.

**Критерии приёмки:** Vite dev server открывает пользовательскую страницу по
`/` и admin-entry по `/admin/`; production build содержит обе страницы;
существующий proxy `/api` и пользовательский чат не регрессируют.

**Зависимости:** одобренная спецификация; текущая Vite-конфигурация.

**Файлы:**

- `frontend/vite.config.js`;
- `frontend/src/admin/index.html`;
- `frontend/tests/proxy-smoke.mjs`.

**Шаги:**

1. Сначала расширить Vite smoke-проверку ожиданием отдельной admin-страницы и
   сохранить проверки пользовательской страницы, POST proxy и SSE proxy.
2. Добавить минимальную семантическую admin HTML-entry без production-
   поведения и оформить Vite multi-page input для двух страниц.
3. Выполнить build и убедиться, что admin-entry сохраняется в
   `dist/admin/index.html` и не меняет URL пользовательских assets.

**Проверка:**

```sh
npm --prefix frontend run test:proxy
npm --prefix frontend run build
```

## Задача 2. Описать и проверить демонстрационные наборы данных

**Требования:** REQ-005–REQ-009.

**Критерии приёмки:** существуют согласованные наборы для `7`, `30` и `90`
дней; каждый содержит карточки, временной ряд и последние записи пользователей;
данные валидируются и не зависят от времени, сети или случайных значений.

**Зависимости:** задача 1.

**Файлы:**

- `frontend/src/admin/demo-data.js`;
- `frontend/tests/admin-data.test.js`.

**Шаги:**

1. Сначала добавить падающие unit-тесты обязательных периодов, полей,
   неотрицательных значений, согласованных totals и отказа для неизвестного
   периода.
2. Реализовать immutable-подобные локальные наборы и функцию безопасного
   получения/валидации выбранного периода.
3. Использовать нейтральные демонстрационные имена и идентификаторы без
   реальных персональных данных.

**Проверка:**

```sh
npm --prefix frontend test
```

## Задача 3. Реализовать поведение панели через тесты

**Требования:** REQ-004–REQ-010, REQ-013.

**Критерии приёмки:** при загрузке отображаются данные за `30 дней`;
переключатели `7/30/90` синхронно обновляют карточки, график и пользователей;
active-state доступен программно; отсутствующий набор показывает безопасную
ошибку; динамические значения вставляются только как текст.

**Зависимости:** задачи 1–2.

**Файлы:**

- `frontend/src/admin/index.html`;
- `frontend/src/admin/admin.js`;
- `frontend/tests/admin-ui.test.js`.

**Шаги:**

1. Подготовить минимальный fake DOM harness и сначала добавить падающие тесты
   начального рендера, переключения периода, согласованного обновления всех
   секций и error-state.
2. Разметить семантические области: навигацию, заголовок, demo-badge,
   period-switcher, metric cards, activity chart, agent quality и список
   пользователей.
3. Реализовать небольшие функции рендера через `createElement`/`textContent`,
   единое состояние периода и безопасное переключение loading/content/error.
4. Добавить `aria-current` для навигации, `aria-pressed` для периода, доступное
   текстовое описание графика и live-region для ошибок.

**Проверка:**

```sh
npm --prefix frontend test
```

## Задача 4. Создать визуальную систему и адаптивную геометрию

**Требования:** REQ-003–REQ-007, REQ-011–REQ-013.

**Критерии приёмки:** admin-страница узнаваемо связана с пользовательским
режимом, но не содержит персонажей; desktop, tablet и mobile композиции не
перекрываются; от `320px` нет горизонтального overflow; focus заметен;
табличные данные читаемы на mobile.

**Зависимости:** задача 3 предоставляет полную семантическую разметку.

**Файлы:**

- `frontend/src/admin/admin.css`;
- `frontend/src/admin/index.html`.

**Шаги:**

1. Оформить тёмный фон, холодные градиенты, акцентные цвета, скруглённые
   панели и спокойные светящиеся детали без изображений персонажей.
2. На desktop реализовать sidebar и main grid с максимальной читаемой шириной;
   карточки распределить в адаптивную сетку, графику дать собственную панель.
3. На tablet сократить sidebar и перевести аналитические панели в две колонки.
4. На mobile перевести навигацию в компактную верхнюю полосу, карточки — в
   одну колонку, а строки пользователей — в вертикальные карточки с подписями
   полей; локальный scroll допустим только внутри специально обозначенной
   области.
5. Добавить `prefers-reduced-motion`, hover/focus-visible и контрастные
   состояния без зависимости только от цвета.

**Проверка:**

```sh
npm --prefix frontend run build
```

Дополнительно в реальном браузере проверить `320x568`, `375x667`, `768x1024`,
`1366x768`, `1440x900` и `1920x1080`: `scrollWidth === clientWidth`, границы
интерактивных элементов, переключение периода, keyboard focus и снимки mobile,
laptop и wide desktop.

## Риски и контроль

- **Nginx не открывает `/admin/` после production build.** Контроль структурой
  `dist/admin/index.html`, Vite smoke и контейнерной проверкой итогового URL.
- **Demo UI воспринимается как реальные данные.** Контроль постоянным badge и
  пояснением источника данных рядом с заголовком.
- **Макет случайно вводит незащищённый admin API.** В рамках изменения нет
  `fetch`, credentials, форм входа и backend-маршрутов.
- **Admin CSS влияет на пользовательский чат.** Стили подключаются только из
  admin-entry и используют отдельный namespace.
- **Таблица расширяет mobile viewport.** Записи меняют presentation на
  карточное при узком breakpoint; overflow страницы измеряется в браузере.
- **График недоступен screen reader.** Рядом с визуальными столбцами хранится
  текстовое описание тех же значений.
