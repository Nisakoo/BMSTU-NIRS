# Макет frontend-панели администратора

## Цель

Создать в существующем frontend отдельную адаптивную страницу администратора
по адресу `/admin/`. Страница должна визуально принадлежать проекту
«Смешарики AI», но использовать более сдержанную аналитическую композицию без
персонажей и детской декоративной сцены. На первом этапе все показатели
берутся из локальных детерминированных демонстрационных данных и не требуют
изменений backend.

## Требования

- REQ-001: Пользовательский чат продолжает открываться по `/`, а макет панели
  администратора открывается по `/admin/` из того же Vite build и того же
  frontend-контейнера.
- REQ-002: Панель администратора реализуется внутри существующего
  `frontend/` как отдельная страница одного Vite-проекта; отдельный
  top-level frontend, dev server, Nginx-контейнер или Compose-сервис не
  создаётся.
- REQ-003: Страница использует узнаваемые цвета, типографический характер,
  мягкие тени, скругления и светящиеся акценты пользовательского frontend, но
  не отображает Кроша, Копатыча, других персонажей, пейзаж или изображения из
  `static/characters`.
- REQ-004: Desktop-композиция содержит шапку или боковую навигацию, заголовок
  панели, явную метку «Демонстрационные данные», выбор периода и основную
  аналитическую область.
- REQ-005: Обзор содержит как минимум показатели общего числа пользователей,
  активных пользователей, диалогов и сообщений, а также отдельные показатели
  качества работы агента: долю успешных ответов и среднее время ответа.
- REQ-006: Страница содержит визуализацию активности по времени без новой
  runtime-зависимости на библиотеку графиков. График строится средствами
  HTML/CSS/SVG и имеет доступное текстовое описание значений.
- REQ-007: Страница содержит список последних пользователей с
  демонстрационными именем или идентификатором, датой активности, количеством
  диалогов и состоянием. На мобильном viewport список не создаёт
  горизонтальную прокрутку страницы и остаётся читаемым.
- REQ-008: Переключатель периода между `7`, `30` и `90` днями обновляет
  карточки, график и список на основании заранее заданных локальных наборов
  данных; выбранный период имеет визуально и программно определимое активное
  состояние.
- REQ-009: Демонстрационные данные хранятся отдельно от DOM-логики, являются
  детерминированными и не выдаются за реальные. Страница не обращается к
  backend, не создаёт пользователей и не сохраняет административные данные.
- REQ-010: При JavaScript-ошибке или отсутствии корректного набора данных
  страница показывает понятное безопасное состояние ошибки или отсутствия
  данных, а не оставляет вводящие в заблуждение показатели.
- REQ-011: На viewport от `320px` страница не создаёт горизонтальную прокрутку
  документа, карточки и секции переходят в одну колонку, навигация остаётся
  доступной, а интерактивные элементы не обрезаются.
- REQ-012: На tablet и desktop полезная область плавно расширяется: карточки
  используют адаптивную сетку, график и список не перекрываются, а длина строк
  остаётся читаемой на ширине до `1920px`.
- REQ-013: Интерактивные элементы доступны с клавиатуры, имеют заметный focus,
  семантические подписи и достаточный контраст; текущий раздел и выбранный
  период не определяются только цветом.
- REQ-014: Существующие пользовательский чат, его JavaScript/CSS, HTTP/SSE-
  контракт и пути статических изображений не изменяют поведение из-за
  добавления админской страницы.
- REQ-015: `frontend/README.md` и `docs/README.md` описывают новую страницу,
  её место в общей сборке, демонстрационный источник данных и отсутствие
  авторизации и реального административного API.

## Сценарии

### Открытие панели администратора

- Given frontend собран или запущен через Vite
- When пользователь открывает `/admin/`
- Then отображается отдельная административная панель
- And на странице явно указано, что данные демонстрационные
- And изображения персонажей не загружаются и не отображаются

### Просмотр статистики

- Given выбран период `30 дней`
- When страница загружает соответствующий локальный набор данных
- Then карточки показывают согласованные итоговые значения
- And график показывает активность за тот же период
- And список последних пользователей соответствует выбранному набору

### Переключение периода

- Given панель отображает данные за `7 дней`
- When пользователь выбирает `90 дней`
- Then активное состояние переходит на `90 дней`
- And карточки, график и список обновляются без перезагрузки страницы

### Мобильный экран

- Given панель открыта на viewport `320x568` или `375x667`
- When пользователь прокручивает страницу и переключает период
- Then документ не имеет горизонтального overflow
- And навигация, карточки, график и записи пользователей остаются доступными
- And ни один интерактивный элемент не обрезан краями viewport

### Некорректные демонстрационные данные

- Given выбранный набор данных отсутствует или не проходит frontend-валидацию
- When панель пытается его отобразить
- Then вместо числовых показателей показывается явное состояние ошибки
- And в DOM не вставляется непроверенный HTML

## Технологии и структура

Изменение остаётся в существующем vanilla JavaScript frontend:

- `frontend/src/admin/index.html` — отдельная Vite HTML-entry страницы
  `/admin/`;
- `frontend/src/admin/admin.css` — изолированные стили панели;
- `frontend/src/admin/admin.js` — DOM-состояние, переключение периода и
  отрисовка;
- `frontend/src/admin/demo-data.js` — локальные детерминированные наборы
  данных;
- при необходимости `frontend/src/shared/` — только действительно общие
  визуальные токены без изменения поведения пользовательского чата;
- `frontend/vite.config.js` — multi-page build для пользовательской и
  административной HTML-entry;
- `frontend/tests/` — Node-тесты поведения панели и неизменности основных
  frontend-контрактов.

Nginx продолжает раздавать один каталог `frontend/dist/`, а Caddy сохраняет
существующее разделение `/api/*` и статических страниц. Будущий защищённый
административный API и его клиент оформляются отдельным SDD-изменением.

## Команды

- Основной запуск: `make run`
- Frontend dev server: `make frontend`
- Frontend-тесты: `npm --prefix frontend test`
- Production-сборка: `npm --prefix frontend run build`
- Полная проверка продукта: `make test`

## Тестирование

| Требования | Способ проверки |
| --- | --- |
| REQ-001–REQ-002, REQ-014 | Vite multi-page build, smoke-проверка `/` и `/admin/`, существующие тесты пользовательского чата |
| REQ-003–REQ-007 | Browser render и визуальное ревью административной страницы; DOM-проверка показателей, графика и записей пользователей |
| REQ-008–REQ-010 | Node DOM-тесты переключения периода, согласованного обновления секций и безопасного состояния ошибки |
| REQ-011–REQ-013 | Browser-проверка viewport `320x568`, `375x667`, `768x1024`, `1366x768`, `1440x900` и `1920x1080`: overflow, границы элементов, keyboard/focus и доступные подписи |
| REQ-015 | Ревью документации без искусственных тестов структуры файлов |

Новые тесты на этапе `specify` не реализуются.

## Границы

- Всегда: явно помечать данные как демонстрационные; сохранять единый Vite и
  контейнерный frontend; проверять mobile, tablet, laptop и wide desktop;
  не допускать регрессии пользовательского чата.
- Сначала спросить: добавлять новые разделы админки, зависимости, реальные
  HTTP-запросы, форму входа, персональные данные, экспорт или изменять
  пользовательский frontend ради общего дизайна.
- Никогда: выдавать demo-значения за реальные; использовать `dialog_id` как
  авторизацию; добавлять незашищённый административный API; хранить секреты во
  frontend; создавать отдельный публичный admin-сервис без новой спецификации.

## Критерии приёмки

- [ ] `/` продолжает открывать пользовательский чат, `/admin/` открывает
  административный макет из одного production build.
- [ ] Макет визуально связан с пользовательским режимом, но не содержит
  персонажей или декоративного пейзажа.
- [ ] Карточки, график, список пользователей и показатели агента используют
  согласованный набор демонстрационных данных.
- [ ] Переключение `7/30/90 дней` обновляет все зависимые секции без
  перезагрузки страницы.
- [ ] На всех контрольных viewport отсутствуют горизонтальный overflow,
  обрезание интерактивных элементов и перекрытие секций.
- [ ] Состояния loading/empty/error визуально понятны и не вставляют данные
  через `innerHTML`.
- [ ] Существующие сценарии пользовательского frontend проходят без
  регрессий.
- [ ] `npm --prefix frontend test`, production build и `make test` проходят
  успешно.
- [ ] Frontend-документация и архитектурный каталог соответствуют реализации
  и ссылаются на SDD-артефакты.

## Открытые вопросы

- Нет. Для первого этапа согласован автономный визуальный макет с локальными
  демонстрационными данными; авторизация, реальные пользователи, постоянное
  хранение и административный API остаются отдельными будущими изменениями.
