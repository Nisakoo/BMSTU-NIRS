# Усиление аутентификации: CSRF, секрет подписи и отзыв сессии

## Цель

Проверка текущей авторизации показала, что ручки защищены, а базовые механизмы (JWT, ротация refresh, blacklist, argon2id, fail closed) сделаны правильно, но есть пробелы:

1. `POST /api/v1/auth/login` и `POST /api/v1/users` принимают JSON с любым
   `Content-Type`. HTML-форма `enctype="text/plain"` с чужого сайта может
   незаметно залогинить жертву в аккаунт атакующего (login CSRF); это подтверждено запросом с `Content-Type: text/plain`, который получил `200` и cookie.
2. Значение `AUTH_JWT_SECRET` из `docker/.env.example` проходит валидацию: при копировании шаблона секрет подписи становится публичным.
3. После выхода или обнаружения повторного использования refresh-токена другие access-токены той же сессии остаются действительными до `exp`.
4. SSE-поток проверяет сессию только при подключении и продолжает работать после выхода.

Изменение закрывает эти пробелы, не меняя транспорт токенов (`HttpOnly` cookie) и успешные ответы существующего контракта. Это первая из трёх связанных спецификаций; владение диалогами —
[`dialog-ownership`](../dialog-ownership/spec.md), ограничение частоты — [`auth-rate-limit`](../auth-rate-limit/spec.md).

## Требования

### Защита от межсайтовых запросов

- REQ-001: `POST /api/v1/users` и `POST /api/v1/auth/login` принимают тело только с media type `application/json` (параметры вроде `charset` допускаются, регистр не важен). Иначе — `415`
  `{"error":"unsupported_media_type"}` без создания пользователя, проверки
  пароля и выставления cookie.
- REQ-002: `POST /api/v1/dialogs/{dialog_id}/messages` после успешной проверки токена и с media type, отличным от `application/json`, отвечает `415` в
  формате ошибок FastAPI (`{"detail": ...}`) и не ставит запрос в очередь. Гость по-прежнему получает `401` раньше `415`.
- REQ-003: Любой запрос к `/api/*` с небезопасным методом (`POST`, `PUT`,
  `PATCH`, `DELETE`) и заголовком `Sec-Fetch-Site` со значением `cross-site`
  или `same-site` отвечает `403` `{"error":"forbidden_origin"}` до аутентификации и обработки тела. Запросы без этого заголовка и со значениями
  `same-origin` или `none` проходят дальше. `GET`-запросы, включая SSE, не
  затрагиваются.
- REQ-004: Порядок проверок у `POST /users` и `POST /auth/login`: `403` по REQ-003, `415` по REQ-001, затем `422` и остальные ответы контракта.

### Секрет подписи

- REQ-005: Загрузка конфигурации завершается ошибкой без вывода значения, если
  `AUTH_JWT_SECRET` начинается с `replace-with-` (соглашение шаблона
  `docker/.env.example`), как и при слишком коротком секрете.
- REQ-006: В `docker/.env.example` значение `AUTH_JWT_SECRET` пустое с комментарием о генерации; `make run` без заданного секрета останавливается сообщением Compose `Set AUTH_JWT_SECRET in docker/.env`.

### Отзыв сессии целиком

- REQ-007: Access-токен содержит claim `fid` — идентификатор семейства refresh-сессий, к которому он выпущен. Токен без `fid` отклоняется как некорректный (`401`); frontend восстанавливает сессию обычным `refresh`.
- REQ-008: `POST /api/v1/auth/logout` отзывает всё семейство refresh-сессий предъявленных токенов, а не одну сессию, и помечает семейство отозванным в Redis с TTL не меньше времени жизни access-токена.
- REQ-009: Обнаружение повторного использования refresh-токена также помечает семейство отозванным в Redis по REQ-008.
- REQ-010: Проверка access-токена отклоняет (`401`) токен, у которого `jti` или `fid` отозваны. Подпись, `iss` и `exp` по-прежнему проверяются до обращения к Redis; при недоступности Redis — `503` (fail closed).

### SSE

- REQ-011: Открытый поток `GET /api/v1/dialogs/{dialog_id}/events` перепроверяет сессию при каждом heartbeat (по умолчанию раз в 15 секунд): отзыв `jti` или `fid` и существование пользователя. Истечение `exp` после
  подключения поток не закрывает. При отрицательном результате или недоступности хранилищ поток завершается без отправки дальнейших событий; agent loop не отменяется.
- REQ-012: После выхода в другой вкладке поток закрывается не позже чем через один интервал heartbeat; frontend при ошибке SSE по существующей логике проверяет сессию и переходит на `/login/`.

### Журналирование

- REQ-013: Отказы `403` по REQ-003, `415` и закрытие SSE по отзыву сессии журналируются стабильными событиями без логина, пароля, токенов и текста запросов; допускаются `user_id`, `dialog_id` и исход.

## Границы

- Всегда: токены только в `HttpOnly` cookie; fail closed при недоступности PostgreSQL и Redis; в журнал не попадают логин, пароль, токены и пользовательский текст.
- Сначала спросить: изменение схемы БД, изменение успешных ответов контракта.
- Никогда: заголовок `Authorization` или токены в теле ответа; ослабление обнаружения повторного использования refresh-токена.
