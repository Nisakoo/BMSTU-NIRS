# Локальная озвучка сказок голосом рассказчика на Silero v5

## Цель

Дать пользователю возможность прослушать готовую сказку, не покидая чат.
Озвучка выполняется локально в backend на CPU встроенным русским голосом
Silero TTS v5. В одной сказке используется один голос — голос рассказчика;
роли персонажей и клонирование голосов в это изменение не входят.

Изменение добавляет кнопку «Озвучить» у завершённого ответа ассистента,
фоновую локальную генерацию, хранение готового аудио, воспроизведение во
frontend и скачивание готовой записи. После успешной генерации кнопка
«Озвучить» заменяется на «Скачать».

## Допущения

- Используется официальная русская модель Silero TTS v5 (`v5_ru`), версия и
  набор встроенных голосов фиксируются в образе/конфигурации; во время
  работы backend не скачивает модели из сети.
- Активный голос рассказчика выбирается конфигурацией из встроенных голосов
  Silero. По умолчанию используется `baya`; смена голоса через UI в это
  изменение не входит.
- Рассказчик читает весь текст ответа, включая реплики героев. Разметка
  «кто говорит» не требуется, дополнительный вызов LLM не выполняется.
- Озвучка запускается по явному действию пользователя, а не автоматически
  после каждого ответа. Это защищает CPU от постоянной фоновой нагрузки.
- Готовое аудио хранится в PostgreSQL вместе с метаданными сообщения. Формат
  — MP3 (`audio/mpeg`), моно, чтобы 10-минутная сказка не занимала десятки
  мегабайт.
- Существующие диалоги можно озвучивать по требованию: аудио создаётся для
  любого сохранённого ответа ассистента, а не только для последнего.
- После готовности рядом с плеером остаётся действие «Скачать»; скачивание
  не запускает повторный синтез и использует уже сохранённый MP3. Для
  сохранённой истории наличие готового аудио приходит вместе с сообщениями.

## Требования

### Backend

- REQ-001: Локальный провайдер синтеза использует Silero TTS v5 и работает
  на CPU. Во время выполнения запроса он не обращается к внешним TTS-сервисам
  и не скачивает модель из сети.
- REQ-002: Голос рассказчика берётся из фиксированного набора встроенных
  голосов Silero v5. Допустимый набор и значение по умолчанию задаются
  конфигурацией; неизвестное имя голоса останавливает запуск конфигурации до
  создания приложения.
- REQ-003: Модель Silero загружается один раз при старте приложения. Если
  модель отсутствует, повреждена или не может быть загружена, backend
  завершает запуск контролируемой ошибкой и не начинает обслуживать запросы
  с нерабочей озвучкой.
- REQ-004: Текст ответа нормализуется для синтеза: схлопываются лишние
  пробелы и переводы строк, нормализуются кавычки и тире, удаляются случайные
  Markdown-маркеры, если модель их всё же вернула. Смысл и порядок текста не
  меняются.
- REQ-005: Нормализованный текст разбивается на фрагменты не длиннее
  настроенного предела по границам предложений и абзацев. Между абзацами
  добавляется пауза. Ни один фрагмент не теряется и не дублируется.
- REQ-006: Синтез выполняется в отдельном потоке и не блокирует event loop
  FastAPI. Одновременно в процессе выполняется не более
  `SPEECH_MAX_CONCURRENCY` синтезов; по умолчанию — один. Остальные запросы
  ожидают в очереди.
- REQ-007: Для одного сообщения одновременно выполняется не более одной
  генерации. Повторный запрос во время генерации не создаёт вторую задачу и
  наблюдает тот же результат.
- REQ-008: Готовое аудио кэшируется. Повторный запрос для того же сообщения,
  того же текста и той же версии голоса возвращает сохранённое аудио без
  повторного синтеза.
- REQ-009: Кэш учитывает хэш исходного текста и версию голоса. Версия голоса
  включает идентификатор Silero-голоса, версию модели Silero v5, скорость
  речи и версию правил нормализации. При изменении любого из этих параметров
  аудио генерируется заново.
- REQ-010: Аудио и статус генерации хранятся в таблице `message_audio` с
  первичным ключом `message_id` и внешним ключом на `messages(id)` с
  `ON DELETE CASCADE`. Удаление диалога или сообщения удаляет связанное аудио.
- REQ-011: Статусы `message_audio` — `pending`, `ready` и `failed`. Строка
  `ready` содержит непустые `audio_data`, `mime_type` и `duration_ms`.
  Строка `failed` содержит безопасный `error_code` и не содержит аудио.
- REQ-012: Незавершённые генерации после рестарта не остаются вечно в
  `pending`: при старте приложения такие строки переводятся в `failed` с
  безопасным кодом прерывания, после чего повторный запрос может запустить
  генерацию заново.
- REQ-013: Фоновые задачи озвучки отслеживаются и отменяются при shutdown
  приложения. Отмена не оставляет новую строку `ready` и не логирует текст
  сказки.
- REQ-014: Ошибка Silero или кодирования аудио преобразуется в безопасную
  ошибку без текста сказки, аудиоданных, пути к модели и текста внешнего
  исключения. `asyncio.CancelledError` распространяется без преобразования.
- REQ-015: Результат сохраняется как MP3 (`audio/mpeg`), моно, с частотой
  дискретизации и битрейтом, достаточными для разборчивой русской речи.
  Конкретные параметры кодирования фиксируются в конфигурации или константах
  реализации. MP3 пригоден и для встроенного воспроизведения, и для
  скачивания файла; перекодирование при скачивании не выполняется.
- REQ-016: Логи содержат стабильные события начала, завершения и ошибки
  синтеза с `message_id`, числом символов, длительностью, исходом и
  безопасным типом ошибки. Текст сказки, аудио, путь к модели и содержимое
  исключения в лог не передаются.

### HTTP API

- REQ-017: `POST /api/v1/dialogs/{dialog_id}/messages/{message_id}/audio`
  запускает озвучку сохранённого ответа ассистента и не принимает тело
  запроса. При новой генерации или уже идущей генерации возвращается
  `202 Accepted` с JSON `{"status":"pending"}`. Если аудио уже готово и
  актуально, возвращается `200 OK` с JSON `{"status":"ready"}`.
- REQ-018: `GET /api/v1/dialogs/{dialog_id}/messages/{message_id}/audio`
  (и его вариант `?download=1`) возвращает:
  - `202 Accepted` и `{"status":"pending"}`, пока аудио генерируется;
  - `200 OK` и тело `audio/mpeg`, когда аудио готово;
  - `404 Not Found`, если сообщение не существует, принадлежит чужому
    диалогу, не является ответом ассистента или аудио ещё не запрашивалось;
  - `503 Service Unavailable` с безопасным JSON, если последняя генерация
    завершилась ошибкой или сервис озвучки недоступен.
- REQ-019: Обе ручки требуют действительный access-токен и проверяют
  владельца диалога. Для чужого диалога ответ такой же, как для
  несуществующего — `404`. Роль `admin` не даёт доступа к чужим диалогам.
- REQ-020: Озвучивать можно только сообщения с ролью `assistant`. Для
  пользовательского сообщения обе ручки отвечают `404`.
- REQ-021: Ответ с готовым аудио содержит `Content-Type: audio/mpeg`,
  корректный `Content-Length`, `ETag` по тексту и версии голоса и приватную
  политику кэширования. Без параметра `download` аудио отдаётся с
  `Content-Disposition: inline`; с `?download=1` — с
  `Content-Disposition: attachment; filename="smeshariki-<message_id>.mp3"`.
  Аудио не должно быть доступно без авторизации.
- REQ-022: Одновременные запросы к одной и той же озвучке не создают
  параллельных синтезов и не приводят к гонке при записи `message_audio`.

### Конфигурация и окружение

- REQ-023: Новый неизменяемый `SpeechConfig` принадлежит модулю озвучки.
  Корневой `Config` получает подконфиг `speech`; `load_config` читает его из
  process environment, а внутренние компоненты environment не читают.
- REQ-024: Поддерживаются как минимум настройки:
  - `SPEECH_ENABLED` — включает локальную озвучку, по умолчанию `true`;
  - `SPEECH_VOICE` — встроенный голос Silero, по умолчанию `baya`;
  - `SPEECH_SPEED` — скорость речи в допустимом диапазоне, по умолчанию `1.0`;
  - `SPEECH_MAX_CONCURRENCY` — целое положительное число, по умолчанию `1`;
  - `SPEECH_MAX_TEXT_CHARS` — максимальная длина озвучиваемого текста, по
    умолчанию `20000`;
  - `SPEECH_MODEL_PATH` — путь к локальному файлу Silero v5, по умолчанию
    `/models/silero/v5_ru.pt`.
  Невалидные значения останавливают загрузку конфигурации.
- REQ-025: `docker/.env.example` содержит безопасные значения новых
  переменных без секретов. `docker/compose.yaml` передаёт их backend.
- REQ-026: Используется официальная русская модель Silero v5 (`v5_ru`) из
  официального источника Silero Models. Модель и её файлы не коммитятся в
  публичный репозиторий. На этапе сборки скрипт в `docker/` скачивает
  зафиксированный файл по официальному URL, проверяет SHA-256 и кладёт его в
  образ или read-only volume; URL, версия, checksum и лицензия модели
  документируются. Для offline-сборки допускается заранее подготовленный
  `docker/models/silero/v5_ru.pt`. Во время работы приложения сеть для
  загрузки модели не используется.

### Frontend

- REQ-027: У каждого завершённого ответа ассистента — и в живой ленте после
  `message_end`, и в загруженной сохранённой истории — есть кнопка
  «Озвучить» с доступной подписью. Если для сохранённого ответа уже есть
  готовое актуальное аудио, кнопка сразу показывается как «Скачать».
- REQ-028: Нажатие кнопки запускает `POST`, затем опрашивает `GET` до
  получения аудио или безопасной ошибки. Во время ожидания кнопка показывает
  состояние «Готовим озвучку…» и не запускает повторную генерацию.
- REQ-029: После получения аудио в ленте появляется встроенный `<audio
  controls>` с готовым MP3, а кнопка «Озвучить» заменяется на «Скачать».
  Автовоспроизведение не используется: браузер может заблокировать его после
  асинхронной генерации.
- REQ-030: При переключении диалога, создании новой истории, выходе или
  повторной загрузке страницы текущее аудио останавливается, незавершённый
  polling прекращается, а состояние кнопки сбрасывается.
- REQ-031: Ошибки запуска, генерации и загрузки аудио показываются
  пользователю безопасным текстом; динамический текст вставляется только как
  текст, без `innerHTML`.
- REQ-032: Запросы озвучки используют существующую обработку сессии: при
  `401` выполняется один `refresh` и повтор, как у остальных операций чата.
- REQ-033: Кнопка озвучки не блокирует ввод, отправку сообщений и
  переключение истории. Озвучка одного сообщения не мешает озвучке другого,
  если backend принял оба запроса.

### Документация

- REQ-034: Добавляется тематическая страница `docs/audio.md` с описанием
  границ модуля, локального Silero-провайдера, API, хранения, кэша и
  ограничений CPU.
- REQ-035: Обновляются `docs/README.md`, `docs/dialogs.md`,
  `docs/database.md`, `docs/configuration.md`, `docker/README.md`,
  `frontend/README.md` и `AGENTS.md` в объёме нового компонента, контракта и

### Дополнительные контракты

- REQ-036: `GET /api/v1/dialogs/{dialog_id}/messages` для каждого сообщения
  возвращает `audio_available: bool`: `true` только для ответа ассистента с
  актуальной строкой `message_audio.status = ready`, иначе `false`. Поле не
  раскрывает текст, аудио или внутренние ошибки синтеза.
- REQ-037: Скачивание выполняется авторизованным запросом
  `GET .../audio?download=1` через существующий клиент с обработкой `401` и
  одним `refresh`. Frontend получает blob, создаёт object URL и инициирует
  скачивание с именем `smeshariki-<message_id>.mp3`, после чего освобождает
  URL. Скачивание не запускает повторный синтез.

## Сценарии

### Основной сценарий: первая озвучка

- Given пользователь получил и сохранил ответ ассистента
- When он нажимает «Озвучить»
- Then backend принимает запрос, возвращает `202`, запускает локальный синтез
  и frontend показывает состояние ожидания
- When генерация завершается
- Then `GET` возвращает `200 audio/mpeg`, в ленте появляется плеер, а кнопка
  «Озвучить» заменяется на «Скачать»

### Повторное открытие истории

- Given у сохранённого ответа уже есть готовое аудио
- When пользователь открывает историю
- Then сообщение сразу показывает плеер и кнопку «Скачать», а синтез не
  запускается

### Скачивание готовой записи

- Given озвучка завершена и кнопка показывает «Скачать»
- When пользователь нажимает «Скачать»
- Then браузер скачивает готовый MP3 с именем `smeshariki-<message_id>.mp3`
- Then повторный синтез не запускается, а плеер и аудио остаются доступны

### Повторный запрос во время генерации

- Given озвучка сообщения уже выполняется
- When приходит повторный `POST` для того же сообщения
- Then второй синтез не запускается, оба клиента видят `pending`, а после
  завершения получают один и тот же готовый файл

### Чужой диалог

- Given пользователь запрашивает озвучку сообщения из чужого диалога
- When вызывается `POST` или `GET`
- Then ответ `404`, как для несуществующего сообщения; существование диалога
  не раскрывается

### Пользовательское сообщение

- Given пользователь запрашивает озвучку собственного сообщения
- When вызывается `POST` или `GET`
- Then ответ `404`; синтез не запускается

### Ошибка Silero

- Given модель Silero недоступна или синтез завершился ошибкой
- When пользователь запрашивает озвучку
- Then строка получает статус `failed`, клиент получает безопасную ошибку, а
  текст сказки и детали исключения не попадают в HTTP-ответ или лог

### Рестарт во время генерации

- Given backend был остановлен во время синтеза
- When приложение запускается снова
- Then старая запись `pending` становится `failed`, а новый `POST` может
  запустить генерацию заново

### Превышение лимита текста

- Given текст ответа длиннее `SPEECH_MAX_TEXT_CHARS`
- When пользователь запрашивает озвучку
- Then синтез не запускается, возвращается безопасная ошибка, а приложение
  продолжает работать

## Технологии и структура

- Python 3.12, FastAPI, Pydantic, SQLAlchemy async Core, Alembic.
- Silero TTS v5 как локальный CPU-провайдер; версия модели и встроенные голоса
  фиксируются в образе/конфигурации.
- Новый пакет `smeshariki_ai.speech`:
  - `config.py` — `SpeechConfig`;
  - `models.py` — статусы и артефакт аудио;
  - `provider.py` — асинхронный контракт `SpeechProvider`;
  - `silero.py` — локальный CPU-адаптер Silero;
  - `normalize.py` — нормализация и нарезка текста;
  - `service.py` — `NarratorSpeechService`;
  - `store.py` — контракт `MessageAudioStore`;
  - `postgres.py` — реализация хранилища;
  - `memory.py` — in-memory реализация для тестов;
  - `fake.py` — детерминированный провайдер для тестов.
- `HistoryStore` получает способ получить конкретное сохранённое сообщение по
  `owner_id`, `dialog_id` и `message_id` либо сервис использует существующий
  `transcript`; окончательный выбор фиксируется на этапе plan.
- `bootstrap.py` создаёт локальный Silero-провайдер, хранилище аудио и
  `NarratorSpeechService`; тесты передают fake-провайдер и in-memory
  хранилище.
- Миграция Alembic добавляет `message_audio`; схема документируется в
  `docs/database.md`.
- Frontend: `frontend/src/agent-api.js` получает методы запуска, получения и
  скачивания аудио, `frontend/src/script.js` — кнопку, polling, плеер,
  замену «Озвучить» на «Скачать» и очистку состояния,
  `frontend/src/styles.css` — стили плеера и состояний.
- Docker: CPU-зависимости Silero v5 и файлы модели добавляются в backend-образ;
  крупные файлы модели не коммитятся. В `docker/` добавляется скрипт
  загрузки модели с pinned URL и проверкой SHA-256. При необходимости для
  кодирования MP3 добавляется локальный кодировщик или `ffmpeg`.
- Документация: `docs/audio.md` и перечисленные в REQ-035 страницы.

## Команды

- Запуск: `make run`
- Тесты: `make test`
- Интеграционные тесты: `make test-integration`
- Линтер: `make lint`

## Тестирование

- Модульные тесты нормализации и нарезки: пробелы, кавычки, тире, Markdown,
  длинные абзацы, отсутствие потерь и дублей.
- Модульные тесты `NarratorSpeechService` с fake-провайдером: кэш,
  идемпотентность, параллельные запросы, ошибки, отмена, лимит текста.
- Контрактные тесты `MessageAudioStore`: in-memory и PostgreSQL реализации
  проходят один набор операций; удаление сообщения/диалога удаляет аудио.
- Интеграционные API-тесты: `202`/`200`, `404` для чужого диалога,
  пользовательского сообщения и неизвестного id, `503` при ошибке синтеза,
  повторный `POST` без второй генерации, отсутствие аудио в ответе без
  авторизации, `audio_available` в истории и `Content-Disposition` для
  `?download=1`.
- Node-тесты frontend: кнопка у живого и сохранённого ответа, состояние
  ожидания, появление плеера, замена «Озвучить» на «Скачать», скачивание
  готового MP3, отображение «Скачать» после перезагрузки сохранённой
  истории, сброс при переключении истории, безопасный текст ошибок.
- Реальная модель Silero проверяется вручную на 2-, 5- и 10-минутном тексте:
  разборчивость, произношение имён, паузы, отсутствие обрывов, время
  генерации и размер MP3 на целевом CPU. Этот тест не входит в `make test`,
  чтобы набор тестов не зависел от модели и сети.
- Для изменения Python-кода продукта обязательны успешные `make test` и
  `make lint`.

## Границы

- Всегда: синтезировать локально на CPU; использовать один голос рассказчика
  для всей сказки; озвучивать только сохранённые ответы ассистента; проверять
  владельца; кэшировать результат; не логировать текст и аудио.
- Сначала спросить: смена модели Silero, добавление новых голосов, изменение
  формата аудио, автоматическая озвучка после каждого ответа, хранение аудио
  вне PostgreSQL.
- Никогда: не обращаться к внешним TTS-сервисам; не клонировать голоса; не
  добавлять голоса персонажей; не озвучивать произвольный текст от клиента;
  не отдавать аудио без авторизации; не коммитить модель и персональные
  аудиоданные в репозиторий.

## Критерии приёмки

- [ ] В `docker/.env.example` и конфигурации backend есть настройки Silero,
  модель загружается локально и не скачивается во время работы.
- [ ] `POST .../audio` запускает ровно одну фоновую генерацию для сообщения,
  повторный запрос использует кэш или текущую задачу.
- [ ] `GET .../audio` отдаёт `202` во время генерации и `200 audio/mpeg` после
  неё; чужой диалог и пользовательское сообщение дают `404`.
- [ ] `GET .../audio?download=1` отдаёт тот же MP3 с `Content-Disposition:
  attachment` и стабильным именем файла, не запуская синтез.
- [ ] Аудио сохраняется в `message_audio`, переживает рестарт и удаляется
  каскадом вместе с сообщением/диалогом.
- [ ] `GET .../messages` возвращает `audio_available`, и frontend сразу
  показывает «Скачать» для уже озвученного сохранённого ответа.
- [ ] Frontend показывает кнопку «Озвучить», состояние ожидания, плеер,
  замену кнопки на «Скачать» и безопасные ошибки; при переключении истории
  аудио останавливается.
- [ ] Текст сказки, аудио и детали исключений не попадают в логи.
- [ ] `make test` и `make lint` проходят успешно.
- [ ] Используется официальная Silero v5 (`v5_ru`), модель скачивается на
  этапе сборки по pinned URL, проверяется SHA-256 и не загружается в runtime
  из сети.
- [ ] Ручная проверка на целевом CPU подтверждает разборчивую русскую речь и
  приемлемое время генерации для 2-, 5- и 10-минутной сказки.
- [ ] `docs/audio.md` и перечисленные тематические страницы обновлены.

## Открытые вопросы

- Подтвердить после прослушивания дефолтный голос рассказчика: `baya`
  (женский) или один из мужских встроенных голосов Silero v5.
- Подтвердить параметры MP3: битрейт и частоту дискретизации.
- Выбрать способ поставки модели Silero v5: запекание в образ или read-only
  volume `docker/models/` с проверкой checksum.
- Нужно ли ограничивать озвучку только сообщениями, созданными после
  включения функции, или разрешать её для всей сохранённой истории. Текущее
  допущение — разрешать для всей истории.
