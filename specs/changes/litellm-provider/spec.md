# LiteLLM-провайдер и подмодуль LLM-провайдеров

## Цель

Добавить в backend реальный асинхронный адаптер `LiteLLMProvider`, который связывает существующий внутренний контракт `LLMProvider` с LiteLLM Python SDK и
позволяет выбирать поддерживаемую LiteLLM модель конфигурацией запуска. Настройки адаптера должны быть отделены от `AgentConfig`, собраны в неизменяемом
`LiteLLMProviderConfig` и переданы провайдеру извне через composition root. Одновременно связанный с LLM-провайдерами код переносится из одиночного модуля
`agent.llm` в отдельный внутренний подмодуль `agent.providers`. Эта граница содержит контракт провайдера, fake-реализацию, LiteLLM-адаптер, его конфигурацию и
ошибки адаптера, но не забирает доменные модели и оркестрацию agent loop. Изменение зависит от реализованных спецификаций
[`agent-runtime`](../agent-runtime/spec.md) и [`agent-dialog-api`](../agent-dialog-api/spec.md).

## Требования

- REQ-001: Внутри `smeshariki_ai.agent` должен существовать подмодуль `providers`, объединяющий `LLMProvider`, `FakeLLMProvider`, `LiteLLMProvider`, `LiteLLMProviderConfig` и ошибки провайдерного адаптера. После миграции модуль `agent.llm`
  не должен оставаться вторым источником тех же определений.
- REQ-002: Абстракция `LLMProvider` должна сохранить асинхронный метод `generate(messages, tools) -> LLMResponse` и использовать на границе только доменные типы проекта. `Agent` и `AgentService` не должны импортировать типы LiteLLM или
  знать формат его запросов и ответов.
- REQ-003: Доменные `Message`, `LLMResponse`, `ToolCall`, `ToolDefinition` и остальные модели agent loop должны остаться вне `agent.providers`, поскольку они принадлежат контракту агента, а не конкретному внешнему адаптеру.
- REQ-004: `LiteLLMProvider` должен получать готовый неизменяемый `LiteLLMProviderConfig` через конструктор. Провайдер не должен читать переменные окружения, загружать `.env` или самостоятельно выбирать настройки по умолчанию из глобальной
  конфигурации приложения.
- REQ-005: `LiteLLMProviderConfig` должен запрещать неизвестные поля и содержать ровно следующие настройки: обязательный непустой `model`; необязательные непустые `api_key` и HTTP(S) `base_url`; положительный `timeout_seconds` со значением
  по умолчанию 60; неотрицательный `num_retries` со значением по умолчанию 0. Секретный ключ не должен отображаться открытым текстом в `repr`, сообщениях валидации или логах.
- REQ-006: Загрузчик конфигурации приложения должен один раз собрать `LiteLLMProviderConfig` из `LLM_MODEL`, `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_TIMEOUT_SECONDS` и `LLM_NUM_RETRIES`, после чего bootstrap передаёт этот объект в
  `LiteLLMProvider`. `LLM_MODEL` обязателен; отсутствующие или пустые необязательные значения трактуются как `None`; некорректная конфигурация должна остановить запуск до создания FastAPI-приложения.
- REQ-007: Production-сборка backend должна использовать `LiteLLMProvider`. `FakeLLMProvider` сохраняется как детерминированная реализация без сети для модульных тестов и явной подмены зависимости, но не выбирается скрытым fallback при
  отсутствии или ошибке реальной конфигурации.
- REQ-008: `LiteLLMProvider.generate` должен напрямую ожидать `litellm.acompletion` и выполнять ровно один асинхронный непотоковый вызов LiteLLM на одну итерацию agent loop. Использование синхронного `litellm.completion`, его запуска через
  `asyncio.to_thread` или другого блокирующего сетевого пути не допускается. В вызов передаются модель, timeout, число повторов, заданные учётные данные, доменный контекст и определения инструментов. Пустой список инструментов не должен
  превращаться в фиктивное описание инструмента.
- REQ-009: Системные, пользовательские и обычные сообщения ассистента должны переводиться в Chat Completions-сообщения без изменения их текста, включая пустую строку ответа ассистента.
- REQ-010: Доменное сообщение ассистента с `ToolCall` должно переводиться в стандартный function tool call с сохранением `id`, имени и аргументов, а следующее доменное сообщение роли `tool` — в связанный по `tool_call_id` результат.
  `ToolResult`, включая безопасную ошибку инструмента, сериализуется в JSON без потери структурированных полей.
- REQ-011: Каждый `ToolDefinition` должен передаваться LiteLLM как function tool с тем же именем, описанием и JSON Schema параметров. LiteLLM не должен автоматически выполнять инструменты: исполнение остаётся исключительной ответственностью
  `Agent` и `ToolRegistry`.
- REQ-012: Из первого choice непотокового ответа LiteLLM адаптер должен создать доменный `LLMResponse`, сохранив различие между `content=None` и `content=""`. Каждый внешний function tool call переводится в доменный `ToolCall` с теми же
  `id` и именем; строка аргументов должна разбираться как JSON-объект.
- REQ-013: Адаптер не должен скрывать от `Agent` ответы, одновременно содержащие текст и tool call, несколько tool calls или ни одного допустимого результата. Он переводит доступные данные в `LLMResponse`, после чего действующие правила
  `Agent` классифицируют такой ответ как некорректный.
- REQ-014: Отсутствующий choice, несовместимая структура ответа, невалидный JSON аргументов, аргументы не в форме JSON-объекта и несериализуемый результат инструмента должны приводить к контролируемой ошибке провайдерного адаптера, а не к
  утечке SDK-исключения или частично сформированному доменному ответу.
- REQ-015: Ошибки сети, timeout, аутентификации, rate limit и другие исключения LiteLLM должны преобразовываться в стабильную внутреннюю `LLMProviderError`. Её публичное сообщение не содержит prompt, историю, tool payload, URL с
  параметрами, API key, тело ответа внешнего сервиса или текст исходного исключения; отмена asyncio-задачи должна распространяться без преобразования.
- REQ-016: Провайдер может журналировать только стабильные события начала, успешного завершения и ошибки запроса, идентификатор модели, число сообщений и инструментов и безопасный тип ошибки. Логи провайдера и включённые им настройки
  LiteLLM не должны записывать содержимое сообщений, аргументы и результаты инструментов, ответы модели, секреты или текст внешнего исключения. Интеграция не должна подключать callbacks наблюдаемости LiteLLM.
- REQ-017: Ошибка реального провайдера в фоновом запуске должна проходить через существующий контракт `AgentService`: уже отправленный HTTP-ответ остаётся `202 Accepted`, пара пользователь/ассистент не добавляется в историю, а сбой
  наблюдаем в безопасном серверном журнале.
- REQ-018: LiteLLM должен быть добавлен как зафиксированная `uv`-зависимость backend, совместимая с Python 3.12. В runtime не должны появиться LangChain, LangGraph или отдельный LiteLLM Proxy.
- REQ-019: `docker/.env.example`, Compose и документация запуска должны перечислять новые настройки без реальных секретов. Frontend не добавляется в Compose, а LiteLLM не оформляется отдельным сервисом.
- REQ-020: Тематическая документация агента и глобальная карта архитектуры должны отражать новый подмодуль, production-адаптер, границу конфигурации и замену fake-провайдера в composition root. Корневой `AGENTS.md` обновляется только по
  подтверждённому результату реализации.
- REQ-021: Публичные импорты `LLMProvider` и `FakeLLMProvider` из `smeshariki_ai.agent` должны сохраниться; там же должны экспортироваться `LiteLLMProvider`, `LiteLLMProviderConfig` и `LLMProviderError`. Внутренний путь
  `smeshariki_ai.agent.llm` не считается публичным контрактом и после миграции не поддерживается.
- REQ-022: `make test` должен проверять конфигурацию, преобразования запросов и ответов, ошибки и bootstrap без сетевых обращений, реального API key и внешней модели.
- REQ-023: Один экземпляр `LiteLLMProvider` должен безопасно обслуживать несколько одновременных `generate` из независимых диалогов без глобальной блокировки и без общего изменяемого состояния конкретного запроса. Ожидание ответа одного
  внешнего вызова не должно мешать началу и завершению другого; правило последовательного выполнения сообщений одного `dialog_id` остаётся ответственностью `AgentService`.

Действующий контракт и архитектурные границы описаны в [каталоге](../../../docs/README.md).
