# LiteLLM-провайдер и подмодуль LLM-провайдеров

## Цель

Добавить в backend реальный асинхронный адаптер `LiteLLMProvider`, который
связывает существующий внутренний контракт `LLMProvider` с LiteLLM Python SDK и
позволяет выбирать поддерживаемую LiteLLM модель конфигурацией запуска.
Настройки адаптера должны быть отделены от `AgentConfig`, собраны в неизменяемом
`LiteLLMProviderConfig` и переданы провайдеру извне через composition root.

Одновременно связанный с LLM-провайдерами код переносится из одиночного модуля
`agent.llm` в отдельный внутренний подмодуль `agent.providers`. Эта граница
содержит контракт провайдера, fake-реализацию, LiteLLM-адаптер, его конфигурацию
и ошибки адаптера, но не забирает доменные модели и оркестрацию agent loop.

Изменение зависит от реализованных спецификаций
[`agent-runtime`](../agent-runtime/spec.md) и
[`agent-dialog-api`](../agent-dialog-api/spec.md).

## Допущения

- Интеграция использует LiteLLM Python SDK внутри процесса backend и его
  асинхронный Chat Completions-интерфейс. Отдельный LiteLLM Proxy, новый
  контейнер и публичный endpoint не создаются.
- В одной конфигурации запуска используется одна модель. Маршрутизация между
  моделями, балансировка, fallback-модели и budget management не входят в
  изменение.
- Первая версия выполняет только непотоковые запросы. SSE и передача токенов
  клиенту остаются отдельным изменением.
- Непотоковый режим не означает синхронное выполнение: весь путь от
  `Agent.run` до сетевого клиента LiteLLM остаётся асинхронным и освобождает
  event loop на время ожидания внешнего ответа.
- `LiteLLMProviderConfig` содержит только настройки LLM-провайдера: модель,
  учётные данные и сетевые параметры. Системная инструкция и лимит agent loop
  остаются в `AgentConfig`; параметры генерации наподобие `temperature` и
  `max_tokens` пока не настраиваются.
- `api_key` и `base_url` являются необязательными: некоторые поддерживаемые
  LiteLLM способы аутентификации используют локальный endpoint или стандартную
  цепочку учётных данных конкретного облачного провайдера. Сам адаптер при этом
  не читает environment.
- Поддержка tool calling зависит от выбранной модели и внешнего сервиса.
  Адаптер переводит общий контракт инструментов, но не подменяет выбор модели и
  не выполняет инструменты средствами LiteLLM.
- Существующее ограничение agent loop остаётся прежним: один ответ модели может
  содержать не более одного tool call. Если внешняя модель вернула несколько
  вызовов, адаптер сохраняет их в доменном ответе, а `Agent` отклоняет ответ по
  действующему контракту.

## Требования

- REQ-001: Внутри `smeshariki_ai.agent` должен существовать подмодуль
  `providers`, объединяющий `LLMProvider`, `FakeLLMProvider`,
  `LiteLLMProvider`, `LiteLLMProviderConfig` и ошибки провайдерного адаптера.
  После миграции модуль `agent.llm` не должен оставаться вторым источником тех
  же определений.
- REQ-002: Абстракция `LLMProvider` должна сохранить асинхронный метод
  `generate(messages, tools) -> LLMResponse` и использовать на границе только
  доменные типы проекта. `Agent` и `AgentService` не должны импортировать типы
  LiteLLM или знать формат его запросов и ответов.
- REQ-003: Доменные `Message`, `LLMResponse`, `ToolCall`, `ToolDefinition` и
  остальные модели agent loop должны остаться вне `agent.providers`, поскольку
  они принадлежат контракту агента, а не конкретному внешнему адаптеру.
- REQ-004: `LiteLLMProvider` должен получать готовый неизменяемый
  `LiteLLMProviderConfig` через конструктор. Провайдер не должен читать
  переменные окружения, загружать `.env` или самостоятельно выбирать настройки
  по умолчанию из глобальной конфигурации приложения.
- REQ-005: `LiteLLMProviderConfig` должен запрещать неизвестные поля и содержать
  ровно следующие настройки: обязательный непустой `model`; необязательные
  непустые `api_key` и HTTP(S) `base_url`; положительный `timeout_seconds` со
  значением по умолчанию 60; неотрицательный `num_retries` со значением по
  умолчанию 0. Секретный ключ не должен отображаться открытым текстом в `repr`,
  сообщениях валидации или логах.
- REQ-006: Загрузчик конфигурации приложения должен один раз собрать
  `LiteLLMProviderConfig` из `LLM_MODEL`, `LLM_API_KEY`, `LLM_BASE_URL`,
  `LLM_TIMEOUT_SECONDS` и `LLM_NUM_RETRIES`, после чего bootstrap передаёт этот
  объект в `LiteLLMProvider`. `LLM_MODEL` обязателен; отсутствующие или пустые
  необязательные значения трактуются как `None`; некорректная конфигурация
  должна остановить запуск до создания FastAPI-приложения.
- REQ-007: Production-сборка backend должна использовать
  `LiteLLMProvider`. `FakeLLMProvider` сохраняется как детерминированная
  реализация без сети для модульных тестов и явной подмены зависимости, но не
  выбирается скрытым fallback при отсутствии или ошибке реальной конфигурации.
- REQ-008: `LiteLLMProvider.generate` должен напрямую ожидать
  `litellm.acompletion` и выполнять ровно один асинхронный непотоковый вызов
  LiteLLM на одну итерацию agent loop. Использование синхронного
  `litellm.completion`, его запуска через `asyncio.to_thread` или другого
  блокирующего сетевого пути не допускается. В вызов передаются модель, timeout,
  число повторов, заданные учётные данные, доменный контекст и определения
  инструментов. Пустой список инструментов не должен превращаться в фиктивное
  описание инструмента.
- REQ-009: Системные, пользовательские и обычные сообщения ассистента должны
  переводиться в Chat Completions-сообщения без изменения их текста, включая
  пустую строку ответа ассистента.
- REQ-010: Доменное сообщение ассистента с `ToolCall` должно переводиться в
  стандартный function tool call с сохранением `id`, имени и аргументов, а
  следующее доменное сообщение роли `tool` — в связанный по `tool_call_id`
  результат. `ToolResult`, включая безопасную ошибку инструмента, сериализуется
  в JSON без потери структурированных полей.
- REQ-011: Каждый `ToolDefinition` должен передаваться LiteLLM как function
  tool с тем же именем, описанием и JSON Schema параметров. LiteLLM не должен
  автоматически выполнять инструменты: исполнение остаётся исключительной
  ответственностью `Agent` и `ToolRegistry`.
- REQ-012: Из первого choice непотокового ответа LiteLLM адаптер должен создать
  доменный `LLMResponse`, сохранив различие между `content=None` и
  `content=""`. Каждый внешний function tool call переводится в доменный
  `ToolCall` с теми же `id` и именем; строка аргументов должна разбираться как
  JSON-объект.
- REQ-013: Адаптер не должен скрывать от `Agent` ответы, одновременно содержащие
  текст и tool call, несколько tool calls или ни одного допустимого результата.
  Он переводит доступные данные в `LLMResponse`, после чего действующие правила
  `Agent` классифицируют такой ответ как некорректный.
- REQ-014: Отсутствующий choice, несовместимая структура ответа, невалидный JSON
  аргументов, аргументы не в форме JSON-объекта и несериализуемый результат
  инструмента должны приводить к контролируемой ошибке провайдерного адаптера,
  а не к утечке SDK-исключения или частично сформированному доменному ответу.
- REQ-015: Ошибки сети, timeout, аутентификации, rate limit и другие исключения
  LiteLLM должны преобразовываться в стабильную внутреннюю
  `LLMProviderError`. Её публичное сообщение не содержит prompt, историю,
  tool payload, URL с параметрами, API key, тело ответа внешнего сервиса или
  текст исходного исключения; отмена asyncio-задачи должна распространяться без
  преобразования.
- REQ-016: Провайдер может журналировать только стабильные события начала,
  успешного завершения и ошибки запроса, идентификатор модели, число сообщений
  и инструментов и безопасный тип ошибки. Логи провайдера и включённые им
  настройки LiteLLM не должны записывать содержимое сообщений, аргументы и
  результаты инструментов, ответы модели, секреты или текст внешнего
  исключения. Интеграция не должна подключать callbacks наблюдаемости LiteLLM.
- REQ-017: Ошибка реального провайдера в фоновом запуске должна проходить через
  существующий контракт `AgentService`: уже отправленный HTTP-ответ остаётся
  `202 Accepted`, пара пользователь/ассистент не добавляется в историю, а сбой
  наблюдаем в безопасном серверном журнале.
- REQ-018: LiteLLM должен быть добавлен как зафиксированная `uv`-зависимость
  backend, совместимая с Python 3.12. В runtime не должны появиться LangChain,
  LangGraph или отдельный LiteLLM Proxy.
- REQ-019: `docker/.env.example`, Compose и документация запуска должны
  перечислять новые настройки без реальных секретов. Frontend не добавляется в
  Compose, а LiteLLM не оформляется отдельным сервисом.
- REQ-020: Тематическая документация агента и глобальная карта архитектуры
  должны отражать новый подмодуль, production-адаптер, границу конфигурации и
  замену fake-провайдера в composition root. Корневой `AGENTS.md` обновляется
  только по подтверждённому результату реализации.
- REQ-021: Публичные импорты `LLMProvider` и `FakeLLMProvider` из
  `smeshariki_ai.agent` должны сохраниться; там же должны экспортироваться
  `LiteLLMProvider`, `LiteLLMProviderConfig` и `LLMProviderError`. Внутренний
  путь `smeshariki_ai.agent.llm` не считается публичным контрактом и после
  миграции не поддерживается.
- REQ-022: `make test` должен проверять конфигурацию, преобразования запросов и
  ответов, ошибки и bootstrap без сетевых обращений, реального API key и
  внешней модели.
- REQ-023: Один экземпляр `LiteLLMProvider` должен безопасно обслуживать
  несколько одновременных `generate` из независимых диалогов без глобальной
  блокировки и без общего изменяемого состояния конкретного запроса. Ожидание
  ответа одного внешнего вызова не должно мешать началу и завершению другого;
  правило последовательного выполнения сообщений одного `dialog_id` остаётся
  ответственностью `AgentService`.

## Сценарии

### Прямой ответ реальной модели

- Given backend запущен с валидным `LiteLLMProviderConfig`
- And выбранная через LiteLLM модель доступна
- And рабочий контекст не требует вызова инструмента
- When `Agent` вызывает `LLMProvider.generate`
- Then провайдер выполняет один асинхронный непотоковый запрос
- And текст первого choice преобразуется в доменный `LLMResponse`
- And `Agent` завершает цикл этим текстом

### Вызов инструмента через LiteLLM

- Given в `ToolRegistry` зарегистрирован инструмент
- And модель сначала возвращает один function tool call с JSON-объектом
  аргументов
- When agent loop обрабатывает ответ и снова обращается к провайдеру
- Then первый ответ преобразуется в доменный `ToolCall`
- And инструмент выполняется только через `ToolRegistry`
- And второй LiteLLM-запрос содержит связанное сообщение ассистента и JSON-
  результат инструмента
- And финальный текст второго ответа завершает agent loop

### Одновременные вызовы из разных диалогов

- Given два разных диалога используют один экземпляр `LiteLLMProvider`
- And первый вызов LiteLLM ожидает управляемый внешний сигнал
- When второй диалог вызывает `generate`
- Then второй асинхронный вызов начинается до разблокировки первого
- And каждый вызов получает только собственные сообщения, tools и ответ
- And завершение вызовов не требует глобальной блокировки провайдера

### Пустой финальный ответ

- Given LiteLLM возвращает `content=""` без tool calls
- When адаптер преобразует ответ
- Then в `LLMResponse` сохраняется пустая строка, а не `None`
- And `Agent` считает ответ успешным финальным результатом

### Некорректные аргументы tool call

- Given LiteLLM вернул function tool call с невалидным JSON либо JSON-значением,
  которое не является объектом
- When адаптер разбирает ответ
- Then он поднимает безопасную `LLMProviderError`
- And инструмент не выполняется
- And логи не содержат исходную строку аргументов

### Недоступный внешний провайдер в фоновом запросе

- Given существующий диалог принял сообщение и HTTP API уже вернул пустой
  `202 Accepted`
- And LiteLLM завершил вызов ошибкой сети, timeout, аутентификации или rate limit
- When фоновая задача обрабатывает сбой
- Then история диалога не изменяется
- And журнал содержит `dialog_id`, безопасный тип ошибки и событие неуспеха без
  пользовательского текста, секрета и внешнего тела ответа

### Ошибка конфигурации при запуске

- Given `LLM_MODEL` отсутствует либо числовые сетевые настройки невалидны
- When composition root загружает конфигурацию
- Then создание приложения завершается ошибкой валидации до первого сетевого
  запроса
- And backend не переключается на `FakeLLMProvider`

## Технологии и структура

- Python 3.12, Pydantic, Pytest и `uv` остаются базовыми технологиями backend.
- LiteLLM Python SDK используется как инфраструктурный адаптер к Chat
  Completions API разных поставщиков. Конкретная совместимая версия выбирается
  в плане и фиксируется в `backend/uv.lock`.
- Целевая граница — пакет `smeshariki_ai.agent.providers`. Точная разбивка на
  файлы определяется на этапе `plan`, но пакет должен разделять общий контракт,
  fake-реализацию и LiteLLM-адаптер так, чтобы тесты не требовали импорта SDK в
  agent loop.
- `agent.models` остаётся владельцем сообщений и результатов agent loop;
  `agent.runtime` зависит только от `LLMProvider`; bootstrap является
  composition root и единственным местом штатной сборки
  `LiteLLMProviderConfig -> LiteLLMProvider -> Agent`.
- `ApplicationConfig` может содержать `LiteLLMProviderConfig` как отдельное
  вложенное значение, но поля агента и провайдера не объединяются в одну
  модель. Это обеспечивает внешнюю передачу конфигурации и не даёт адаптеру
  обращаться к environment.
- Для вызова используется официальный асинхронный Chat Completions-интерфейс
  LiteLLM и стандартный формат function tools. Responses API, LiteLLM Router и
  Proxy в эту версию не входят.
- Архитектурное решение по выносу подмодуля: контракт и адаптеры провайдеров
  группируются вместе, а доменные модели не переносятся. Так новый поставщик
  можно добавить рядом с LiteLLM без изменения `Agent`, не создавая обратной
  зависимости домена от SDK.

## Команды

- Запуск: `make run` запускает backend через Compose и требует настроенный
  `LLM_MODEL`; секрет при необходимости задаётся только в локальном
  `docker/.env` или внешнем environment.
- Тесты: `make test` запускает полный набор продуктовых Python-тестов через
  `uv` без сети и внешнего LLM.
- Линтинг: `make lint` проверяет backend через Ruff.
- Форматирование: `make format` исправляет и форматирует Python-код через Ruff.

Тестовая замена LiteLLM должна фиксировать переданные параметры и возвращать
контролируемые SDK-подобные ответы, но не открывать socket. Интеграция с
реальным внешним сервисом может проверяться вручную с локальным секретом и не
входит в обязательный `make test`.

## Границы

- Всегда: передавать провайдер и его отдельную конфигурацию извне; сохранять
  асинхронный доменный контракт `LLMProvider`; выполнять инструменты только в
  agent loop; фиксировать LiteLLM через `uv`; скрывать credentials и
  пользовательское содержимое в ошибках и логах; обновлять архитектурную
  документацию вместе с реализацией.
- Сначала спросить: добавить LiteLLM Proxy или Router; несколько моделей,
  fallback и балансировку; произвольные provider-specific параметры;
  настраиваемые параметры генерации; streaming/SSE; callbacks или внешнюю
  телеметрию; автоматические retries с ненулевым значением по умолчанию;
  изменить ограничение одного tool call.
- Никогда: читать environment внутри `LiteLLMProvider`; передавать типы LiteLLM
  в `Agent`; вызывать синхронный `litellm.completion`, в том числе запускать его
  в отдельном системном потоке через `asyncio.to_thread`; выполнять tools

  LiteLLM Proxy в Compose.

## Критерии приёмки

- [ ] Production composition root создаёт `LiteLLMProvider` из отдельно
  провалидированного `LiteLLMProviderConfig`, не смешанного с `AgentConfig`.
- [ ] `Agent` работает через прежний доменный `LLMProvider` и не зависит от
  LiteLLM SDK; публичные импорты существующего контракта сохраняются.
- [ ] Подмодуль `agent.providers` содержит контракт и обе реализации без
  дублирующего `agent.llm`, а доменные модели остаются в `agent.models`.
- [ ] Прямой ответ, пустой ответ и один tool call корректно проходят
  преобразование между доменной моделью и LiteLLM Chat Completions.
- [ ] Провайдер использует `litellm.acompletion`; два независимых вызова могут
  ожидаться и завершаться конкурентно без блокировки event loop и смешивания
  состояния запросов.
- [ ] Tool definitions и tool results передаются без автоматического исполнения
  LiteLLM; несколько или смешанные tool calls по-прежнему отклоняются `Agent`.
- [ ] Невалидные ответы и внешние сбои дают безопасную `LLMProviderError`, а
  отмена задачи не перехватывается.
- [ ] При фоновом сбое HTTP-контракт остаётся `202 Accepted`, история не
  изменяется, и в логах отсутствуют секреты и пользовательское содержимое.
- [ ] Запуск с отсутствующим `LLM_MODEL` или невалидными сетевыми настройками
  завершается ошибкой конфигурации и не использует fake-fallback.
- [ ] LiteLLM добавлен и зафиксирован через `uv`, без LangChain, LangGraph,
  Proxy-контейнера и frontend в Compose.
- [ ] `.env.example`, Compose, `docs/README.md`, `docs/agent.md` и `AGENTS.md`
  отражают реализованную конфигурацию и архитектурную границу без секретов.
- [ ] `make test` и `make lint` проходят успешно без сети, реального API key и
  внешней модели.
