# Оценка семантического поиска (отрицательный результат)

## Цель

Проверить гипотезу: embeddings и гибридный поиск с `pgvector` поднимут
`Recall@5` на лоре за счёт закрытия лексического разрыва. Решение о внедрении
pgvector зависит от замера, а не от ожиданий: в `docs/rag.md` записано правило
«ML-модели в процессе backend без подтверждения бенчмарком не используются».

Кода в продукте это изменение не добавляет: только протокол эксперимента,
числа и вывод.

## Требования

- REQ-001: сравнить на golden set (`data/lore-golden/`, 84 документа, 20
  обычных вопросов) чистый BM25, dense-поиск и гибрид.
- REQ-002: проверить не менее двух embedding-моделей разного класса
  (компактная многоязычная и крупная русская).
- REQ-003: измерить `Recall@5` и `MRR@5` на уровне документов, а также
  эффект на вопросы с нулевым попаданием.
- REQ-004: зафиксировать вывод и решение в `verification.md`; вопрос об
  изменении метрик не поднимать.
- REQ-005: не менять корпус, вопросы и продовый код.

## Сценарии

- Given golden set и три варианта поиска; When выполняется замер; Then таблица
  метрик и разбор по вопросам попадают в `verification.md`.
- Given гибрид не лучше BM25 на значимую величину; Then pgvector не внедряется,
  а причина записывается.

## Технологии и структура

Локальный запуск `transformers` + `torch` во временном окружении
(`uv run --with transformers`), модели Hugging Face; продуктовые файлы не
меняются.

## Команды

```text
uv run --project backend --with transformers python <временный скрипт>
```

## Тестирование

Ревью: числа, модели и порядок замера зафиксированы; продуктовый код не
изменён, `make test` на итоговом состоянии проходит.

## Границы

- Всегда: честный замер на held-out наборе, раскрытие всех вариантов.
- Сначала спросить: любое внедрение embeddings в продукт.
- Никогда: не менять вопросы golden set, не коммитить 400 МБ моделей.
