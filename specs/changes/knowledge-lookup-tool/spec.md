# Инструмент агента `lookup_knowledge`

## Цель

Дать агенту канонические знания из PostgreSQL: по имени, алиасу или slug
персонажа, локации или артефакта, а также по названию или slug эпизода
инструмент `lookup_knowledge` возвращает компактную карточку сущности. После изменения агент, сочиняя историю, может
опираться на характер, `speech_style`, отношения и описания из загруженного
пакета знаний, а не на собственную память модели. Это первый инструмент RAG
из [`docs/rag.md`](../../../docs/rag.md) и последний шаг перед ручным
испытанием агента с RAG.

## Допущения

- Поиск точный: ключ запроса нормализуется `normalize_name` и сравнивается с
  нормализованными именами и алиасами (индекс таблиц `rag_*_names`),
  нормализованным названием эпизода и со slug. Нечёткий поиск (`pg_trgm`),
  BM25 и векторный поиск — позже.
- Ищутся персонажи, локации, артефакты и эпизоды. Произведения и варианты
  канона самостоятельно не ищутся и появляются в карточках как названия.
  Карточка персонажа не перечисляет его эпизоды: список может быть длинным.
- Эпизоды уже хранятся в `rag_episodes`, но у названия нет нормализованного
  ключа. Название не уникально (у разных произведений могут совпадать),
  поэтому ключ получает неуникальный индекс; миграция — `0004`.
- Карточка содержит все версии персонажа с названиями их вариантов канона:
  модель знает названия («классический сериал»), а не slug, поэтому фильтр по
  варианту канона не вводится.
- Ссылки на источники (`sources`) в карточку не входят: модели они не нужны
  для сочинения, а увеличивают ответ. Они остаются в БД и журнале ревизий.
- Системный промпт принадлежит модулю agent и не меняется; когда вызывать
  инструмент, модель узнаёт из его описания.
- Подключение инструмента в `bootstrap.py` меняет строку владельца agent
  (`ToolRegistry((GetContextTool(),))`) и сигнатуру `build_agent_service`; это
  изменение выполняется только после его согласия (см. «Открытые вопросы»).
  `GetContextTool` не удаляется.
- Отдельный кэш не вводится: поиск — фиксированное число индексных запросов.

## Требования

### Ключ поиска эпизода

- REQ-016: Миграция `0004` добавляет в `rag_episodes` колонку
  `normalized_title` (`NOT NULL`, непустая) с неуникальным индексом,
  заполняет её для существующих строк через `normalize_name` и снимается
  `downgrade`. Описание таблицы в `rag/tables.py` и маппер эпизода
  записывают ключ при загрузке; доменная модель и формат пакета не меняются,
  `KNOWLEDGE_FORMAT_VERSION` остаётся `1`.

### Порт чтения

- REQ-001: Порт `KnowledgeReader` в `rag/ports.py` с методами
  `find(key) -> FoundKnowledge` и `has_knowledge() -> bool`. `FoundKnowledge`
  содержит найденные агрегаты (`KnowledgeSet` из персонажей, локаций,
  артефактов и эпизодов) и названия сущностей, на которые они ссылаются:
  варианты канона, произведения, персонажи, локации и артефакты.
- REQ-002: `find` находит сущность, если нормализованный ключ совпадает с
  нормализованным именем, алиасом, названием эпизода или slug; разные типы и
  несколько эпизодов с одним названием возвращаются вместе. `has_knowledge` истинно, если есть хотя бы одна
  успешная загрузка.
- REQ-003: `PostgresKnowledgeStore` и `InMemoryKnowledgeStore` реализуют
  порт; оба проходят один контрактный набор тестов. PostgreSQL читает в одной
  транзакции `READ ONLY` с уровнем `REPEATABLE READ`, без advisory lock
  загрузки, фиксированным числом запросов, не зависящим от числа сущностей.
- REQ-004: Ошибки чтения переводятся в существующие
  `KnowledgeStoreUnavailableError`, `KnowledgeSchemaNotReadyError` и
  `KnowledgeDataInvalidError` без текста SQL и данных.

### Use case

- REQ-005: Use case `KnowledgeLookup.lookup(name) -> LookupResult` в
  `rag/lookup.py` возвращает `status`: `found` с непустым списком карточек,
  `not_found`, если совпадений нет, а знания загружены, и `unavailable`, если
  знания не загружены или хранилище недоступно, схема не готова либо данные
  БД невалидны. Ошибки хранилища наружу не выходят.
- REQ-006: Карточка персонажа: `type`, `id`, `name`, `aliases`, `species`;
  версии — названия вариантов канона, `age_group`, `traits`, `speech_style`
  (`register`, `markers`, `constraints`), `catchphrases`; отношения — имя
  второго персонажа, тип, названия вариантов канона, описание.
- REQ-007: Карточка локации: `type`, `id`, `name`, `aliases`, `description`,
  названия вариантов канона, имена жителей. Карточка артефакта: `type`, `id`,
  `name`, `aliases`, `artifact_type`, `description`, `capabilities`,
  `limitations`, названия вариантов канона, имена создателей.
- REQ-017: Карточка эпизода: `type`, `id`, `title`, название произведения и
  его варианта канона, `season`, `number`, имена участников, названия
  локаций и артефактов; взаимодействия — имена обоих персонажей, тип и
  описание.
- REQ-008: Карточки упорядочены по типу (персонаж, локация, артефакт,
  эпизод), затем по `id`; списки внутри карточки сохраняют порядок пакета.
  Возвращается не больше 10 карточек; `total` содержит число совпадений, а
  `truncated` показывает, что часть отброшена. Результат — неизменяемые
  Pydantic-модели, сериализуемые в JSON без типов адаптеров.
- REQ-009: Каждый вызов журналирует событие `rag.lookup.completed` через
  `log_event`: `started_at`, `duration_ms`, `outcome` (значение `status`),
  `match_count` и при `unavailable` — `error_type` ошибки хранилища (уровень
  `WARNING`) или `reason=not_loaded`, если знания не загружены. Поле
  `match_count` добавляется в список безопасных полей `observability.py`
  (аддитивно). Текст запроса и содержимое карточек в журнал не попадают.

### Инструмент

- REQ-010: `LookupKnowledgeTool` в `rag/tools.py` — наследник
  `agent.tools.Tool` с именем `lookup_knowledge`, получающий `KnowledgeLookup`
  в конструкторе. Отдельный абстрактный интерфейс use case не вводится, пока
  нет второй реализации (например, HTTP-клиента); это уточняет REQ-012
  `rag-architecture`. Аргументы — строгая модель с единственным полем `name` (строка
  1–200 символов после обрезки пробелов, лишние поля запрещены); неверные
  аргументы `ToolRegistry` превращает в `invalid_arguments`.
- REQ-011: Описание инструмента на английском, как у существующих: искать
  героя, место, предмет или эпизод «Смешариков» по имени, прозвищу или
  названию перед тем, как описывать его характер, речь, отношения, свойства
  или события; при `not_found` и
  `unavailable` не выдавать придуманные факты за канон. Описание и JSON
  Schema аргументов проверяются тестом через `ToolRegistry.definitions`.
- REQ-012: Выход инструмента — `LookupResult`, сериализованный `ToolRegistry`
  в JSON; при `not_found` и `unavailable` он содержит короткое пояснение для
  модели на русском.

### Подключение и документация

- REQ-013: После согласия владельца agent `bootstrap.py` регистрирует
  `lookup_knowledge` рядом с `get_context`: production-приложение использует
  `PostgresKnowledgeStore` на общем engine, а сборка без engine (переданный
  `auth_service`, `build_agent_service` по умолчанию) — пустой
  `InMemoryKnowledgeStore`, поэтому инструмент отвечает `unavailable`.
- REQ-014: Backend стартует без загруженных знаний и без таблиц `rag_*`;
  поиск в этом случае возвращает `unavailable`, а не ошибку запроса.
- REQ-015: `docs/rag.md` описывает инструмент, порт чтения, карточки и
  статусы; `docs/README.md` и раздел «Реализованный каталог знаний»
  `AGENTS.md` получают строки об инструменте. Изменения общих файлов только
  аддитивные.

## Сценарии

### Персонаж найден по алиасу

- Given загруженный синтетический пакет с персонажем `pin` (имя «Пин»,
  алиас «Пин-механик»), его версией и дружбой с `krosh`
- When агент вызывает `lookup_knowledge` с `name="  пин-МЕХАНИК "`
- Then `status="found"`, одна карточка персонажа `pin` со `speech_style`
  версии, названием варианта канона и отношением к «Крош»

### Одно имя у разных типов

- Given персонаж и артефакт с одинаковым нормализованным именем
- When вызывается поиск по этому имени
- Then возвращаются обе карточки: сначала персонаж, затем артефакт

### Эпизод по названию

- Given загруженный эпизод `s01e01` «Пинг-понг» с участниками `pin` и
  `krosh`, локацией и взаимодействием
- When агент ищет «пинг-понг»
- Then карточка эпизода с названием произведения, сезоном, номером, именами
  участников, названием локации и взаимодействием «Пин» — «Крош»

### Миграция на заполненной БД

- Given БД с эпизодами, загруженными до миграции `0004`
- When применяется `make migrate`
- Then у каждого эпизода заполнен `normalized_title`, поиск по названию
  находит его, повторная загрузка того же пакета ничего не меняет

### Ничего не найдено

- Given загруженные знания без сущности «Бармалей»
- When агент ищет «Бармалей»
- Then `status="not_found"`, карточек нет, есть пояснение для модели

### Знания недоступны

- Given БД без таблиц `rag_*`, пустая БД или недоступный PostgreSQL
- When агент вызывает инструмент
- Then `status="unavailable"`, событие журнала с `error_type`, запрос
  пользователя и агент продолжают работу

### Неверные аргументы

- Given модель передала пустое `name`, строку длиннее 200 символов или
  лишнее поле
- When `ToolRegistry` исполняет вызов
- Then результат — ошибка `invalid_arguments`, хранилище не вызывается

## Технологии и структура

- Без новых зависимостей. Индексы нормализованных имён — из миграции `0003`,
  ключ названия эпизода — из новой миграции
  `db/migrations/versions/0004_rag_episode_title_key.py`.
- `rag/tables.py`, `rag/postgres_mappers.py` — колонка `normalized_title`.
- `rag/ports.py` — `KnowledgeReader`, `FoundKnowledge`.
- `rag/postgres.py`, `rag/memory.py` — реализации порта; чтение агрегатов по
  списку `id` переиспользует `MAPPERS` из `postgres_mappers.py`.
- `rag/lookup.py` — `KnowledgeLookup`, модели `LookupResult` и карточек.
- `rag/tools.py` — `LookupKnowledgeTool`.
- `bootstrap.py` — регистрация (REQ-013, после согласия).
- Тесты: `backend/tests/unit/rag/test_lookup.py`, `test_tools.py`;
  контрактные тесты порта — рядом с `test_store_contract.py`; строка в
  `backend/tests/unit/test_bootstrap.py`.

## Команды

- Тесты без инфраструктуры: `make test`
- Тесты с PostgreSQL и Redis: `make test-integration`
- Проверка кода: `make lint`
- Ручное испытание: `make knowledge-load DIR=<пакет>`, затем `make run`

## Границы

- Всегда: только синтетические данные в тестах и документации; без текста
  запросов и знаний в журнале; общие файлы только дополнять.
- Сначала спросить: изменение `bootstrap.py`, системного промпта, `agent/`,
  `config.py`; миграции сверх `0004` и новые зависимости.
- Никогда: писать в БД из поиска; брать advisory lock загрузки; отдавать
  модели текст ошибок БД.

## Критерии приёмки

- [ ] `KnowledgeReader` реализован для PostgreSQL и in-memory и проходит
      общий контрактный набор.
- [ ] Миграция `0004` добавляет и заполняет ключ названия эпизода, обратима.
- [ ] `lookup_knowledge` возвращает карточки персонажей, локаций, артефактов
      и эпизодов по имени, алиасу, названию и slug и
      статусы `found`, `not_found`, `unavailable` по сценариям.
- [ ] Неверные аргументы дают `invalid_arguments`.
- [ ] Событие `rag.lookup.completed` без текста запроса и знаний.
- [ ] Инструмент зарегистрирован в `bootstrap.py` после согласия владельца
      agent; backend стартует без знаний.
- [ ] Документация обновлена, diff общих файлов аддитивный.
- [ ] `make lint`, `make test` и `make test-integration` проходят.

## Открытые вопросы

- Согласие владельца agent на изменение `bootstrap.py`: сигнатура
  `build_agent_service` получает необязательный `knowledge_reader`, строка
  реестра — `ToolRegistry((GetContextTool(), LookupKnowledgeTool(...)))`,
  `create_application` передаёт `PostgresKnowledgeStore(engine)`.
- Подсказки похожих имён при `not_found` и поиск по части названия —
  отдельным изменением вместе с `pg_trgm` или BM25.
