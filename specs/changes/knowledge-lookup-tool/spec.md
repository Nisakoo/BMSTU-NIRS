# Инструмент агента `lookup_knowledge`

## Цель

Дать агенту канонические знания из PostgreSQL: по имени, алиасу или slug персонажа, локации или артефакта, а также по названию или slug эпизода инструмент
`lookup_knowledge` возвращает компактную карточку сущности. После изменения агент, сочиняя историю, может опираться на характер, `speech_style`, отношения и
описания из загруженного пакета знаний, а не на собственную память модели. Это первый инструмент RAG из [`docs/rag.md`](../../../docs/rag.md) и последний шаг
перед ручным испытанием агента с RAG.

## Требования

### Ключ поиска эпизода
- REQ-016: Миграция `0004` добавляет в `rag_episodes` колонку `normalized_title` (`NOT NULL`, непустая) с неуникальным индексом, заполняет её для существующих строк через `normalize_name` и снимается `downgrade`. Описание таблицы в
  `rag/tables.py` и маппер эпизода записывают ключ при загрузке; доменная модель и формат пакета не меняются, `KNOWLEDGE_FORMAT_VERSION` остаётся `1`. ### Порт чтения
- REQ-001: Порт `KnowledgeReader` в `rag/ports.py` с методами `find(key) -> FoundKnowledge` и `has_knowledge() -> bool`. `FoundKnowledge` содержит найденные агрегаты (`KnowledgeSet` из персонажей, локаций, артефактов и эпизодов) и названия
  сущностей, на которые они ссылаются: варианты канона, произведения, персонажи, локации и артефакты.
- REQ-002: `find` находит сущность, если нормализованный ключ совпадает с нормализованным именем, алиасом, названием эпизода или slug; разные типы и несколько эпизодов с одним названием возвращаются вместе. `has_knowledge` истинно, если
  есть хотя бы одна успешная загрузка.
- REQ-003: `PostgresKnowledgeStore` и `InMemoryKnowledgeStore` реализуют порт; оба проходят один контрактный набор тестов. PostgreSQL читает в одной транзакции `READ ONLY` с уровнем `REPEATABLE READ`, без advisory lock загрузки,
  фиксированным числом запросов, не зависящим от числа сущностей.
- REQ-004: Ошибки чтения переводятся в существующие `KnowledgeStoreUnavailableError`, `KnowledgeSchemaNotReadyError` и `KnowledgeDataInvalidError` без текста SQL и данных. ### Use case
- REQ-005: Use case `KnowledgeLookup.lookup(name) -> LookupResult` в `rag/lookup.py` возвращает `status`: `found` с непустым списком карточек, `not_found`, если совпадений нет, а знания загружены, и `unavailable`, если знания не загружены
  или хранилище недоступно, схема не готова либо данные БД невалидны. Ошибки хранилища наружу не выходят.
- REQ-006: Карточка персонажа: `type`, `id`, `name`, `aliases`, `species`; версии — названия вариантов канона, `age_group`, `traits`, `speech_style` (`register`, `markers`, `constraints`), `catchphrases`; отношения — имя второго персонажа,
  тип, названия вариантов канона, описание.
- REQ-007: Карточка локации: `type`, `id`, `name`, `aliases`, `description`, названия вариантов канона, имена жителей. Карточка артефакта: `type`, `id`, `name`, `aliases`, `artifact_type`, `description`, `capabilities`, `limitations`,
  названия вариантов канона, имена создателей.
- REQ-017: Карточка эпизода: `type`, `id`, `title`, название произведения и его варианта канона, `season`, `number`, имена участников, названия локаций и артефактов; взаимодействия — имена обоих персонажей, тип и описание.
- REQ-008: Карточки упорядочены по типу (персонаж, локация, артефакт, эпизод), затем по `id`; списки внутри карточки сохраняют порядок пакета. Возвращается не больше 10 карточек; `total` содержит число совпадений, а `truncated` показывает,
  что часть отброшена. Результат — неизменяемые Pydantic-модели, сериализуемые в JSON без типов адаптеров.
- REQ-009: Каждый вызов журналирует событие `rag.lookup.completed` через `log_event`: `started_at`, `duration_ms`, `outcome` (значение `status`), `match_count` и при `unavailable` — `error_type` ошибки хранилища (уровень `WARNING`) или
  `reason=not_loaded`, если знания не загружены. Поле `match_count` добавляется в список безопасных полей `observability.py` (аддитивно). Текст запроса и содержимое карточек в журнал не попадают. ### Инструмент
- REQ-010: `LookupKnowledgeTool` в `rag/tools.py` — наследник `agent.tools.Tool` с именем `lookup_knowledge`, получающий `KnowledgeLookup` в конструкторе. Отдельный абстрактный интерфейс use case не вводится, пока нет второй реализации
  (например, HTTP-клиента); это уточняет REQ-012 `rag-architecture`. Аргументы — строгая модель с единственным полем `name` (строка 1–200 символов после обрезки пробелов, лишние поля запрещены); неверные аргументы `ToolRegistry` превращает
  в `invalid_arguments`.
- REQ-011: Описание инструмента на английском, как у существующих: искать героя, место, предмет или эпизод «Смешариков» по имени, прозвищу или названию перед тем, как описывать его характер, речь, отношения, свойства или события; при
  `not_found` и `unavailable` не выдавать придуманные факты за канон. Описание и JSON Schema аргументов проверяются тестом через `ToolRegistry.definitions`.
- REQ-012: Выход инструмента — `LookupResult`, сериализованный `ToolRegistry` в JSON; при `not_found` и `unavailable` он содержит короткое пояснение для модели на русском. ### Подключение и документация
- REQ-013: После согласия владельца agent `bootstrap.py` регистрирует `lookup_knowledge` рядом с `get_context`: production-приложение использует `PostgresKnowledgeStore` на общем engine, а сборка без engine (переданный `auth_service`,
  `build_agent_service` по умолчанию) — пустой `InMemoryKnowledgeStore`, поэтому инструмент отвечает `unavailable`.
- REQ-014: Backend стартует без загруженных знаний и без таблиц `rag_*`; поиск в этом случае возвращает `unavailable`, а не ошибку запроса.
- REQ-015: `docs/rag.md` описывает инструмент, порт чтения, карточки и статусы; `docs/README.md` и раздел «Реализованный каталог знаний» `AGENTS.md` получают строки об инструменте. Изменения общих файлов только аддитивные.

Действующий контракт и архитектурные границы описаны в [каталоге](../../../docs/README.md).
