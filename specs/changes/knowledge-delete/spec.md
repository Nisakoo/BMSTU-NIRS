# Удаление знаний с проверкой ссылок и архивом ревизий

## Цель

Дать автору контента и его агенту безопасный способ удалять устаревшие или
ошибочные сущности структурированных знаний. Удаление физическое, но не
безвозвратное: снимок агрегата остаётся в журнале ревизий, а операция
фиксируется в журнале с числом удалённых сущностей.

Это второе изменение серии `knowledge-maintenance`. Оно опирается на
`knowledge-export` и предшествует `knowledge-optimistic-lock`.

## Допущения

- Логическое удаление (`deleted_at`) не вводится: оно требует фильтра в каждом
  запросе и ослабляет внешние ключи.
- `rag_revisions.operation` уже допускает `delete`; расширять схему ревизий не
  нужно. `rag_revisions.load_id` остаётся обязательным, поэтому удаление
  записывает строку журнала операций.
- `rag_loads` остаётся таблицей журнала, но получает признак операции
  `load`/`delete`. Старые строки считаются загрузками. Переименование таблицы в
  `rag_operations` не делается: это отдельное крупное изменение.
- Восстановление удалённой сущности загрузкой снимка ревизии в этом изменении не
  реализуется; снимок только сохраняется в журнале.
- Удаление выполняется только явно перечисленными ссылками. Массового
  `--all`, удаления по шаблону и `--ignore-missing` нет: отсутствующая
  сущность всегда ошибка.
- Dry-run является поведением по умолчанию; реальное удаление требует
  `--apply`. Dry-run читает read-only снимок и не берёт advisory lock.
- Свежий `export` перед удалением рекомендуется, но не является обязательным:
  снимок удалённого агрегата уже пишется в ревизию.
- `make knowledge-delete` не применяет миграции автоматически, чтобы dry-run
  оставался read-only; миграции выполняются отдельной командой `make migrate`.
- Команда доступна только через CLI. HTTP API и инструмент агента не
  добавляются.
- Отчёт содержит счётчики и коды, но не перечисляет `id` удалённых сущностей;
  отдельный код `deletion_rejected` не вводится, используются
  `entity_not_found` и существующие нарушения целостности.
- Новых зависимостей нет.

## Требования

### Ссылки и dry-run

- REQ-001: CLI: `python -m smeshariki_ai.rag delete <type>/<id>...
  [--apply] [--format text|json]`. Тип — имя каталога пакета (`characters`,
  `locations`, `artifacts`, `episodes`, `works`, `continuities`), `id` — slug.
  Нужна хотя бы одна ссылка; неверный тип или формат ссылки — код `2`;
  повторяющиеся ссылки дедуплицируются.
- REQ-002: Без `--apply` команда выполняет dry-run: читает снимок, проверяет
  существование сущностей и целостность оставшегося набора, печатает план и не
  пишет ни в БД, ни в журналы. Код `0` — план допустим, `1` — удаление
  невозможно; `applied=false`, `operation_id=null`.
- REQ-003: В dry-run отсутствующая сущность даёт `entity_not_found`, а ссылка
  оставшейся сущности на удаляемую — соответствующее нарушение целостности;
  обе ситуации отменяют весь план и перечисляются в отчёте.
- REQ-004: Dry-run читает через `KnowledgeStore.snapshot()` без advisory lock.
  Между dry-run и `--apply` состояние может измениться; `--apply` обязан
  повторно проверить ссылки и целостность и не полагаться на план dry-run.

### Применение удаления

- REQ-005: `--apply` выполняется в одной транзакции под advisory lock загрузки:
  читает все знания, проверяет существование всех ссылок, удаляет выбранные
  сущности из набора, применяет `check_integrity(complete=True)` к оставшемуся
  набору и только затем меняет БД.
- REQ-006: При нарушении целостности или отсутствии хотя бы одной сущности
  транзакция откатывается, БД не меняется, отчёт содержит все нарушения с
  адресами `db:<каталог>/<id>` и существующими кодами (`unknown_reference`,
  `continuity_mismatch`, `duplicate_name` и т. п.).
- REQ-007: Удаление множества сущностей поддерживает взаимные ссылки: сначала
  удаляются дочерние строки всех выбранных агрегатов, затем корневые строки в
  порядке, обратном зависимостям (`episodes`, `artifacts`, `locations`,
  `characters`, `works`, `continuities`). Удаление двух персонажей с взаимными
  отношениями не должно упираться в `ON DELETE RESTRICT`.
- REQ-008: Удаление атомарно: при ошибке БД, отмене задачи или нарушении
  ограничения не остаётся ни удалённых строк, ни записи журнала, ни новых
  ревизий.

### Ревизии и журнал

- REQ-009: Для каждой удалённой сущности в `rag_revisions` добавляется ревизия
  `operation=delete` со следующим номером ревизии сущности, текущей
  `format_version` и снимком агрегата в формате файла пакета. Снимок позволяет
  восстановить сущность загрузкой и переживает физическое удаление строк.
- REQ-010: `rag_loads.operation` использует значения `load` и `delete`; для
  журнала `delete` добавляется миграцией `0010`. `rag_revisions.operation`
  по-прежнему использует `create`, `update` и `delete`; значение `delete` там
  уже существует и не меняется.
- REQ-011: Миграция `0010` добавляет в `rag_loads` колонку `operation` (`NOT
  NULL`, default `load`, check `load|delete`). Существующие строки получают
  `load`; `tables.py`, `LoadRecord` и `start_load` отражают операцию. Старые
  значения `counts` без поля `deleted` читаются с нулём.
- REQ-012: Успешное удаление записывает в `rag_loads` строку с
  `operation=delete`, временем начала и окончания, длительностью, числом
  сущностей в БД после удаления и счётчиками по типам, включая `deleted`.
  Dry-run и отменённое удаление строк журнала не создают.
- REQ-013: `ChangeCounts` получает поле `deleted` (по умолчанию `0`). Загрузка
  по-прежнему заполняет только `added`, `updated`, `unchanged`; отчёт загрузки
  не меняет текст, но JSON получает аддитивное поле `deleted: 0`.

### Порт и адаптеры

- REQ-014: `EntityChange.operation` допускает `create`, `update` и `delete`.
  `KnowledgeTransaction.save` применяет удаление для обоих хранилищ: в
  PostgreSQL удаляет дочерние строки и корень, в in-memory удаляет агрегат;
  для `create` и `update` поведение не меняется. Ревизия пишется тем же путём,
  что и для загрузки.
- REQ-015: `PostgresKnowledgeStore` выполняет удаление пакетными запросами,
  число которых не зависит от числа удаляемых сущностей, и не удаляет строки
  `rag_loads` и `rag_revisions`.
- REQ-016: Ошибки хранилища переводятся в существующие безопасные типы; текст
  SQL, параметров и содержимого сущностей наружу и в журнал не попадает.

### Отчёт, CLI и Make

- REQ-017: `DeleteReport` содержит `applied`, `operation_id`, `counts`,
  `entity_count`, `duration_ms` и `issues`. Текстовый вывод печатает план или
  итог и счётчики по-русски; `--format json` печатает один JSON-документ. Коды
  возврата: `0` — успех или допустимый dry-run, `1` — отказ или ошибка, `2` —
  неверные аргументы.
- REQ-018: Ошибки конфигурации, БД, схемы и повреждённых данных дают
  `configuration_error`, `database_unavailable`, `schema_not_ready` и
  `stored_data_invalid`; отсутствующая сущность — `entity_not_found`. Отчёт не
  содержит содержимого сущностей.
- REQ-019: `make knowledge-delete REFS="characters/pin locations/house"
  [APPLY=1] [FORMAT=json]` выполняет удаление в Compose-сервисе `migrate` и не
  применяет миграции автоматически: без схемы команда сообщает
  `schema_not_ready`. Без `REFS` — подсказка и код `2`; без `APPLY=1` —
  dry-run. stdout содержит только отчёт `delete`, вывод сборки идёт в stderr.
- REQ-020: Каждый вызов пишет событие `rag.delete.completed` с `outcome`
  (`dry_run`, `applied`, `rejected`, `failed`), `deleted_count`, `duration_ms`
  и при необходимости `reason` или `error_type`. `id` сущностей и содержимое
  знаний в журнал не попадают; `deleted_count` добавляется в безопасные поля
  аддитивно.

### Документация и тесты

- REQ-021: `docs/rag.md` описывает удаление, dry-run, проверку ссылок и журнал;
  `docs/knowledge.md` — физическое удаление, ревизию `delete` и снимок;
  `docs/database.md` — `rag_loads.operation`; `docs/logging.md` — событие
  `rag.delete.completed`; `docs/README.md` и раздел «Реализованный каталог
  знаний» `AGENTS.md` получают строки об удалении. Изменения общих файлов
  аддитивные и согласуются с владельцами.
- REQ-022: Тесты покрывают use case, CLI, оба хранилища и PostgreSQL; новые
  тесты проверяют поведение продукта. `make lint`, `make test` и
  `make test-integration` проходят.

## Сценарии

### Удаление свободной сущности

- Given в БД есть локация `house`, на которую никто не ссылается
- When выполняется `delete locations/house --apply`
- Then строка локации удалена, в `rag_revisions` появилась ревизия `delete` со
  снимком, в `rag_loads` — операция `delete` с одним удалённым объектом

### Ссылка из оставшейся сущности

- Given эпизод `s01e01` ссылается на персонажа `pin`
- When выполняется `delete characters/pin --apply`
- Then удаление отменено, в отчёте `unknown_reference` по адресу
  `db:episodes/s01e01`, БД не изменена

### Удаление связанной пары

- Given персонажи `pin` и `krosh` состоят в отношениях друг с другом
- When выполняется `delete characters/pin characters/krosh --apply`
- Then оба персонажа и их отношения удалены одной транзакцией, ревизии
  `delete` записаны для обоих

### Удаление сущности вместе с зависимой

- Given эпизод `s01e01` ссылается на персонажа `pin`
- When выполняется `delete episodes/s01e01 characters/pin --apply`
- Then обе сущности удалены, проверка целостности не находит ссылок

### Dry-run

- Given удаление допустимо
- When выполняется `delete characters/pin` без `--apply`
- Then отчёт показывает план, `applied=false`, БД и журналы не изменены

### Отсутствующая сущность

- Given сущности `characters/ghost` нет
- When выполняется `delete characters/ghost --apply`
- Then отчёт содержит `entity_not_found`, код `1`, БД не изменена

### Ошибка БД

- Given удаление прошло проверку, но запись в БД завершилась ошибкой
- When транзакция откатывается
- Then нет удалённых строк, ревизий и записи журнала, отчёт содержит
  `database_unavailable`

### Миграция старой БД

- Given в `rag_loads` есть строки, созданные до миграции `0010`
- When применяется `0010`
- Then у старых строк `operation='load'`, чтение журнала продолжает работать

## Границы

- Всегда: проверять ссылки до удаления; удалять в одной транзакции; сохранять
  снимок в ревизии; использовать синтетические данные в тестах; не логировать
  содержимое знаний.
- Сначала спросить: миграции сверх `0010`; переименование `rag_loads`; изменение
  формата пакета; правки `AGENTS.md`, `Makefile`, `observability.py` сверх
  аддитивных строк; изменения других модулей.
- Никогда: логическое удаление; удаление журналов и ревизий; удаление без
  проверки целостности; массовое `--all`; HTTP API или инструмент агента;
  восстановление ревизии в этом изменении.

## Критерии приёмки

- [ ] Dry-run по умолчанию и `--apply` работают по сценариям, коды возврата
      стабильны.
- [ ] Удаление с ссылками из оставшихся сущностей отменяется с понятными
      адресами `db:`.
- [ ] Удаление множества сущностей с взаимными ссылками проходит одной
      транзакцией.
- [ ] Для каждой удалённой сущности есть ревизия `delete` со снимком; журналы
      переживают удаление.
- [ ] Миграция `0010` добавляет `rag_loads.operation`, старые строки читаются
      как `load`.
- [ ] Отчёт и журнал не содержат содержимого знаний.
- [ ] Документация обновлена, diff общих файлов аддитивный.
- [ ] `make lint`, `make test` и `make test-integration` проходят.
