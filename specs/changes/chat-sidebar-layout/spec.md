# Чат с боковой панелью «Мои истории»

## Цель

Команде не нравится, что чат `/` выглядит как два вложенных слоя: крупный заголовок, скруглённая «сцена» с рамкой и уже внутри неё окно чата. По выбранному макету (вариант «Компактно по центру») чат становится
приложением во весь экран: слева боковая панель с новой историей, списком сохранённых историй пользователя и выходом, справа сам чат. Список и история берутся из API постоянных диалогов
[user-dialog-history](../user-dialog-history/spec.md), поэтому это изменение реализуется после него. Изменение заменяет визуальные требования `frontend-responsive-layout`,
`frontend-laptop-baseline-mobile-chat` и `frontend-krosh-hint-input-dismiss` для страницы `/`; сетевой протокол чата из
[frontend-agent-integration](../frontend-agent-integration/spec.md) и проверка сессии из [auth-route-guard](../auth-route-guard/spec.md) сохраняются.

## Требования

### Раскладка

- REQ-001: Страница занимает весь viewport без внешней рамки, крупного заголовка над чатом, пузырей с персонажами, луны и подсказки Кроша. На desktop страница не прокручивается целиком: прокручиваются только список
  историй и лента сообщений.
- REQ-002: Слева — боковая панель шириной около `280px`: логотип «✦ Смешарики AI», кнопка «+ Новая история», заголовок «Мои истории», список историй и внизу логин текущего пользователя с кнопкой «Выйти».
- REQ-003: Справа — шапка с названием текущей истории (для новой — «Новая история»), лента сообщений по центру колонки шириной до `780px`, ниже поле ввода с кнопкой отправки и чипами
  тем. У нижнего края — приглушённые ночные холмы как фон, не перекрывающие текст и элементы управления.
- REQ-004: На ширине до `820px` боковая панель скрыта; в шапке появляется кнопка «Истории», которая открывает панель поверх чата, а выбор истории,
  «Новая история» или нажатие вне панели её закрывают. На viewport от `320px` до `1920px` нет горизонтальной прокрутки и элементов за краем экрана.

### Поведение

- REQ-005: При открытии страницы после проверки сессии frontend восстанавливает выбранный диалог вкладки либо создаёт новый, открывает `EventSource` и параллельно загружает `GET /api/v1/dialogs`. В панели
  показывается логин пользователя из результата проверки сессии.
- REQ-006: Каждая история списка показывает `title`; список отсортирован так, как вернул backend. Текущая история выделена и помечена
  `aria-current="true"`. Пустой список показывает текст «Здесь появятся ваши
  истории».
- REQ-007: Нажатие на историю закрывает текущий `EventSource`, загружает
  `GET /api/v1/dialogs/{dialog_id}/messages`, показывает сообщения в порядке
  ответа (пользовательские справа, ответы ассистента слева), ставит название в шапку и открывает `EventSource` этого диалога. Форма разблокируется только после `ready`. Новые сообщения отправляются в выбранный диалог.
- REQ-008: «+ Новая история» создаёт новый диалог, очищает ленту, показывает приветствие и снимает выделение в списке.
- REQ-009: Пока отправляется запрос или агент отвечает, переключение историй и «Новая история» недоступны (кнопки `disabled`).
- REQ-010: После `message_end` frontend перезагружает список, чтобы новая история появилась наверху со своим названием, а текущая осталась выделенной.
- REQ-011: Ошибка загрузки списка показывает в панели «Не удалось загрузить истории» и кнопку «Повторить»; чат при этом продолжает работать. Ошибка загрузки выбранной истории оставляет пользователя в текущем диалоге с
  уведомлением об ошибке над полем ввода; `404` дополнительно перезагружает список.
- REQ-012: Для новых запросов действует прежнее правило сессии: при `401` один `refresh` и повтор, при повторном отказе — переход на `/login/`.
- REQ-013: Названия историй, сообщения и тексты ошибок вставляются только как текст, без `innerHTML`. Вкладка сохраняет UUID открытого диалога в `sessionStorage` по ключу текущего пользователя. F5 восстанавливает его через авторизованные SSE и HTTP. Чужой или пропавший диалог получает тот же `404`, клиент создаёт новый. Временная ошибка повторяет восстановление выбранного диалога.
  При незавершённой отправке вкладка сохраняет UUID, ID предыдущего ответа и срок ожидания. После F5 можно вводить следующий запрос. Отправка ждёт сохранения результата, ошибки или проверки истории после двух минут без событий.
- REQ-014: Существующее поведение чата сохраняется: блокировка формы до
  `ready`, буферизация быстрых событий до ответа POST, одна реплика
  ассистента на ответ, повтор создания диалога через три секунды, отправка по Enter, чипы тем, выход через «Выйти».

### Клиент API

- REQ-015: `AgentApi.listDialogs()` выполняет `GET /api/v1/dialogs` и возвращает массив `{dialogId, title, updatedAt}`; `AgentApi.getMessages(id)` выполняет `GET /api/v1/dialogs/{id}/messages` и возвращает
  `{title, messages:[{role, content}]}`. Ошибки — `AgentApiError` с кодами
  `unauthorized` (`401`), `not_found` (`404`), `load_failed` (сеть и прочие
  статусы) и `invalid_response` (некорректный JSON или схема).

## Границы

- Всегда: проверять сессию как раньше, вставлять пользовательский и модельный текст только как текст, блокировать параллельные запросы.
- Сначала спросить: удаление или переименование историй, светлую тему.
- Никогда: не менять backend в рамках этого изменения, не использовать
  `innerHTML` для динамического текста, не хранить тексты историй и учётные данные в браузерном хранилище.

Исторические документы доступны в [архиве SDD](../../README.md).
