# Постоянная история диалогов пользователя

## Цель

Сейчас диалоги хранятся в памяти процесса `InMemoryHistoryStore`, не привязаны к пользователю и теряются при рестарте backend. Для боковой панели чата со
списком «Мои истории» ([chat-sidebar-layout](../chat-sidebar-layout/spec.md)) нужно, чтобы диалоги принадлежали вошедшему пользователю, сохранялись в
PostgreSQL и были доступны по HTTP: список диалогов и история одного диалога. Схема таблиц `dialogs` и `messages` уже согласована в [`docs/database.md`](../../../docs/database.md) как запланированная; это
изменение её реализует.

## Требования

### Хранение

- REQ-001: Миграция Alembic `0002` создаёт таблицы `dialogs` и `messages` по схеме из `docs/database.md`: внешние ключи с `ON DELETE CASCADE`, индекс
  `(user_id, updated_at DESC)`, `UNIQUE (dialog_id, position)` и `CHECK` роли
  `user | assistant`. Миграция `0001` не меняется.
- REQ-002: Production bootstrap использует PostgreSQL-реализацию
  `HistoryStore`; `InMemoryHistoryStore` остаётся детерминированной реализацией
  для модульных тестов и поддерживает тот же контракт.
- REQ-003: Диалог создаётся с владельцем — пользователем, вызвавшим
  `POST /api/v1/dialogs`. Идентификатор остаётся UUIDv4 и возвращается в
  прежнем формате ответа.
- REQ-004: После успешного ответа агента пара сообщений «пользователь — ассистент» сохраняется атомарно, в порядке позиций, а `updated_at` диалога
  обновляется в той же транзакции. При ошибке агента история не меняется, как и раньше. Tool calls и tool results не сохраняются.
- REQ-005: Название диалога (`title`) задаётся при первом успешном сохранении: это первый запрос пользователя, у которого последовательности пробельных
  символов заменены одним пробелом, а края обрезаны. Если запрос длиннее 60 символов, сохраняются первые 60 символов и `…`. Позднее название не меняется. До первого ответа `title` равен `null`.
- REQ-006: История переживает рестарт backend: после перезапуска контейнера ранее сохранённые диалоги и сообщения возвращаются API.

### Владение и доступ

- REQ-007: Все ручки конкретного диалога (`messages` POST/GET и `events`) работают только для владельца. Для чужого или несуществующего `dialog_id`
  ответ одинаковый: `404` в прежнем формате FastAPI, без раскрытия того, что диалог существует. Роль `admin` не даёт доступа к чужим диалогам.
- REQ-008: Как и сейчас, проверка access-токена выполняется раньше проверки владения и валидации: гость получает `401`.

### HTTP API

- REQ-009: `GET /api/v1/dialogs` возвращает `200` и JSON
  `{"dialogs":[{"dialog_id","title","created_at","updated_at"}]}` только с
  диалогами текущего пользователя, в которых есть хотя бы одно сообщение, отсортированными по `updated_at` от новых к старым, не более 50 штук. Время — ISO 8601 в UTC. Пустой список — `{"dialogs":[]}`.
- REQ-010: `GET /api/v1/dialogs/{dialog_id}/messages` возвращает владельцу
  `200` и JSON `{"dialog_id","title","messages":[{"role","content","created_at"}]}`
  с сообщениями в порядке позиций; для нового диалога без сообщений — пустой массив `messages`.
- REQ-011: Существующие ручки `POST /api/v1/dialogs`,
  `POST /api/v1/dialogs/{dialog_id}/messages` и
  `GET /api/v1/dialogs/{dialog_id}/events` сохраняют прежние коды ответов, тела
  и SSE-события для владельца.
- REQ-012: Если PostgreSQL недоступен при работе с диалогами, ручки диалогов отвечают `503` в прежнем формате ошибки сервиса агента (`{"detail":"Agent service is unavailable."}`), а не `500`. Сбой сохранения
  после ответа агента публикует `message_error`, как любая ошибка фонового запуска.

### Наблюдаемость и безопасность

- REQ-013: Логи по-прежнему не содержат текст запросов, ответов, истории и названий диалогов; события диалогов журналируются с `dialog_id`, без
  `user_id` в тексте сообщений об ошибках. Ошибки SQL не раскрывают параметры
  (`hide_parameters=True`).

## Границы

- Всегда: проверять владение на backend; хранить только сообщения `user` и
  `assistant`; держать `tables.py` и миграцию согласованными.
- Сначала спросить: удаление и переименование диалогов, пагинацию больше 50, доступ администратора к чужим диалогам, перенос брокера событий из памяти.
- Никогда: не менять миграцию `0001`, не логировать текст сообщений и названия, не отдавать чужие диалоги.
