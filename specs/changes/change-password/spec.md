# Смена пароля в настройках аккаунта

## Цель

Вошедший пользователь сейчас не может поменять свой пароль: его можно задать
только при регистрации. Изменение добавляет в боковую панель чата кнопку
«Настройки» с шестерёнкой. Она открывает окно настроек, в котором есть раздел
«Сменить пароль». После смены пароля остальные устройства пользователя
выходят из аккаунта, а текущее остаётся в нём.

Изменение дополняет контракт аутентификации из
[auth-route-guard](../auth-route-guard/spec.md) и
[backend-auth-jwt](../backend-auth-jwt/spec.md). Восстановление забытого
пароля в этот объём не входит.

## Требования

### Backend и API

- REQ-001: `PUT /api/v1/users/me/password` с телом
  `{"current_password":"<пароль>","new_password":"<пароль>"}` меняет пароль
  текущего пользователя и отвечает `204` без тела. Новый пароль хешируется
  тем же argon2id, что и при регистрации, и сохраняется в
  `users.password_hash`. После этого вход со старым паролем даёт `401`
  `invalid_credentials`, а с новым — `200`.
- REQ-002: Тело проверяется по тем же правилам, что и пароль при
  регистрации: оба поля — строки длиной 8–128 символов. Лишние поля,
  отсутствие поля, невалидный JSON и пустое тело дают `422`
  `{"error":"invalid_fields"}`. Если новый пароль совпадает с текущим, ответ
  — `422` `{"error":"same_password"}`, пароль не меняется.
- REQ-003: Если `current_password` неверный, ответ — `400`
  `{"error":"wrong_password"}`, пароль и сессии не меняются. Для этого ответа
  не используется `401`: `401` означает отсутствие сессии, а frontend на него
  выполняет `refresh`.
- REQ-004: Без действительного access-токена ручка отвечает `401`
  `{"error":"unauthorized"}` раньше `422` и `400`. При сбое PostgreSQL или
  Redis — `503` `{"error":"unavailable"}`, пароль не считается изменённым.
- REQ-005: После успешной смены отзываются все активные refresh-сессии
  пользователя, кроме текущей: её `sid` берётся из access-токена запроса.
  На других устройствах следующий `POST /auth/refresh` даёт `401`; их уже
  выданные access-токены остаются действительными не дольше своего TTL
  (15 минут). Текущие cookie не меняются, и пользователь остаётся в аккаунте.
- REQ-006: Успешная смена журналируется событием `auth.password.changed` с
  `user_id`, отказ из-за неверного пароля — событием
  `auth.password.rejected` с `user_id` и `outcome=rejected`. Пароли и их
  хеши в журнал не попадают.
- REQ-007: Тело ошибок ручки — `{"error":"<code>"}` без введённых значений,
  как у остальных ручек аутентификации.

### Frontend

- REQ-008: В нижней строке боковой панели чата, между логином и кнопкой
  «Выйти», есть кнопка-шестерёнка с доступным именем «Настройки» и
  подсказкой `title="Настройки"`. Ссылка «Панель администратора» не
  меняется.
- REQ-009: Кнопка открывает модальное окно (`role="dialog"`,
  `aria-modal="true"`) с заголовком «Настройки» и разделом «Сменить пароль».
  В разделе три поля пароля — «Текущий пароль», «Новый пароль», «Повторите
  новый пароль» — и кнопка «Сохранить». Фокус переходит на первое поле.
  Окно закрывают кнопка «Закрыть», `Escape` и щелчок по затемнению; после
  закрытия фокус возвращается на шестерёнку, а поля очищаются.
- REQ-010: До отправки форма проверяет поля и показывает ошибку, не делая
  запроса:
  - пустое поле или новый пароль короче 8 либо длиннее 128 символов —
    «Пароль должен быть от 8 до 128 символов»;
  - повтор не совпадает с новым паролем — «Пароли не совпадают»;
  - новый пароль совпадает с текущим — «Новый пароль совпадает с текущим».
- REQ-011: «Сохранить» отправляет `PUT /api/v1/users/me/password`. На время
  запроса поля и кнопки окна заблокированы. Ответы:
  - `204` — поля очищаются, окно показывает «Пароль изменён. На других
    устройствах нужно войти заново»;
  - `400` `wrong_password` — «Неверный текущий пароль», поле текущего
    пароля очищается и получает фокус;
  - `422` `same_password` — «Новый пароль совпадает с текущим»;
  - `401` — один `POST /auth/refresh` и повтор запроса, как у остальных
    операций чата; если сессии нет, страница переходит на `/login/`;
  - сетевая ошибка, `503` и любой другой ответ — «Не удалось сменить
    пароль. Попробуйте ещё раз».
- REQ-012: Сообщения окна выводятся как текст в области с
  `aria-live="polite"`. Пароли не сохраняются в `localStorage`,
  `sessionStorage`, URL и cookie, доступных JavaScript.
- REQ-013: Окно доступно и на экранах до `820px`: шестерёнка находится в
  выдвижной панели историй, а окно помещается по ширине экрана без
  горизонтальной прокрутки.
- REQ-014: Открытие окна не прерывает генерацию ответа и не меняет текущую
  историю и `EventSource`.

## Сценарии

### Успешная смена пароля

- Given пользователь `krosh` вошёл в чат с паролем `old-password`
- When он открывает «Настройки», вводит `old-password`, дважды
  `new-password` и нажимает «Сохранить»
- Then backend отвечает `204`, окно показывает «Пароль изменён…», чат
  остаётся открытым; после выхода вход с `new-password` успешен, а с
  `old-password` — нет

### Другое устройство

- Given `krosh` вошёл на двух устройствах
- When он меняет пароль на первом
- Then на втором следующий `POST /auth/refresh` отвечает `401`, а первое
  продолжает работать

### Неверный текущий пароль

- Given открыто окно настроек
- When пользователь вводит неверный текущий пароль
- Then backend отвечает `400` `wrong_password`, окно показывает «Неверный
  текущий пароль», пароль не изменён

### Пароли не совпадают

- Given открыто окно настроек
- When новый пароль и повтор различаются
- Then окно показывает «Пароли не совпадают», запрос не отправляется

### Истёк access-токен

- Given access-токен истёк, refresh действителен
- When пользователь нажимает «Сохранить»
- Then frontend выполняет один `refresh`, повторяет запрос и получает `204`

### Гость

- Given запрос без access cookie
- When отправлен `PUT /api/v1/users/me/password` с некорректным телом
- Then ответ `401` `unauthorized`

## Технологии и структура

- Backend:
  - `auth/models.py` — модель тела `PasswordChange` и ошибки
    `WrongPasswordError`, `SamePasswordError`;
  - `UserStore.get_password_hash(user_id)`,
    `UserStore.set_password_hash(user_id, password_hash, updated_at)` и
    `RefreshSessionStore.revoke_user_sessions(user_id, keep_session_id, now)`
    в контракте, in-memory и PostgreSQL-адаптерах; новая миграция не нужна;
  - `AuthService.change_password(access_token, current_password,
    new_password)`;
  - маршрут в `api/auth.py`.
- Frontend:
  - `auth-api.js` — `changePassword({ currentPassword, newPassword })` с
    кодами `wrong_password`, `same_password`, `invalid_fields`,
    `unauthorized`, `unavailable`;
  - `index.html`, `script.js`, `styles.css` — шестерёнка и окно настроек.
- Документация: `docs/auth.md` (контракт и раздел «Настройки»),
  `docs/database.md` (если описаны операции над `users`), `docs/README.md`,
  `frontend/README.md`, `AGENTS.md`.

## Команды

- Запуск: `make run`
- Тесты: `make test`
- Линтер: `make lint`

## Тестирование

- Модульные тесты `AuthService` на in-memory хранилищах: успешная смена и
  вход с новым паролем, `wrong_password`, `same_password`, отзыв остальных
  refresh-сессий при сохранении текущей, журнал без паролей.
- Интеграционные API-тесты: `204` и вход с новым паролем; `400`; `422`
  `invalid_fields` и `same_password`; `401` раньше `422`; `503`; refresh
  другой сессии после смены даёт `401`.
- Интеграционный тест PostgreSQL-адаптеров: `set_password_hash` и
  `revoke_user_sessions`.
- Frontend Node-тесты: сетевой контракт `changePassword`; UI — открытие и
  закрытие окна, возврат фокуса, локальные ошибки без запроса, сообщения на
  `204`/`400`/`422`/`503`, refresh и повтор на `401`, блокировка на время
  запроса, вывод текста без `innerHTML`.

## Границы

- Всегда: проверять текущий пароль на backend; отвечать без введённых
  значений; не журналировать пароли и хеши.
- Сначала спросить: добавление смены пароля в `/admin/`; ограничение частоты
  попыток; изменение текущих cookie после смены.
- Никогда: возвращать хеш пароля клиенту; хранить пароль в браузерных
  хранилищах; сливать ветку с `main` или пушить в рамках этого изменения.

## Критерии приёмки

- [ ] `PUT /api/v1/users/me/password` меняет пароль, после чего вход работает
      только с новым паролем.
- [ ] Неверный текущий пароль даёт `400` `wrong_password`, совпадающий новый —
      `422` `same_password`, некорректное тело — `422` `invalid_fields`,
      гость — `401` раньше `422`, сбой хранилища — `503`.
- [ ] После смены другие refresh-сессии пользователя отозваны, текущая
      работает.
- [ ] В боковой панели чата есть шестерёнка «Настройки», окно открывается и
      закрывается кнопкой, `Escape` и щелчком по фону с возвратом фокуса.
- [ ] Окно проверяет поля локально и показывает сообщения для всех ответов
      из REQ-011.
- [ ] Документация обновлена.
- [ ] `make test` и `make lint` проходят успешно.

## Открытые вопросы

- В `main` уже есть `auth-hardening` и `auth-rate-limit` (проверка
  `Sec-Fetch-Site`, `415`, rate limiting). Ветка пока не слита с `main`,
  поэтому ручка реализуется по текущему контракту ветки; при будущем слиянии
  к ней нужно применить те же проверки.
