# План: пример инструмента `get_context`

## Основание

План реализует [согласованную спецификацию](./spec.md). Инструмент остаётся внутренней частью agent runtime и использует действующие `Tool`, `ToolRegistry` и bootstrap. Новые зависимости и HTTP-маршруты не требуются.

## Решения и порядок

1. Реализовать инструмент и проверить его точный результат через реестр.
2. Зарегистрировать инструмент в bootstrap и проверить передачу результата через agent loop.
3. Обновить архитектурную документацию и выполнить общую проверку.

Текст хранится единственным литералом в реализации инструмента. Модель аргументов запрещает лишние поля. Описание инструмента сообщает модели, что его стоит вызывать для запроса маркера или контрольной фразы, но не содержит сам ответ.

## Задача 1. Добавить детерминированный инструмент

**Требования:** REQ-002–REQ-004. **Критерии:** `get_context` принимает `{}`, возвращает точную строку, повторяет результат при следующем вызове и отклоняет лишние аргументы через `ToolRegistry`.

**Зависимости:** нет.

**Файлы:**

- `backend/src/smeshariki_ai/agent/get_context.py`;
- `backend/tests/unit/agent/test_get_context.py`.

**Действия:** сначала написать поведенческие тесты через `ToolRegistry`, затем создать `Tool` и Pydantic-модель без полей. Убедиться, что определение для LLM содержит пустую схему свойств и не раскрывает фиксированный текст.

**Тест:** `UV_CACHE_DIR=/private/tmp/smeshariki-uv-cache uv run --project backend --locked pytest backend/tests/unit/agent/test_get_context.py`.

## Задача 2. Подключить инструмент к агенту

**Требования:** REQ-001, REQ-005. **Критерии:** production bootstrap передаёт `get_context` в реестр; scripted LLM получает строку после tool call и может вернуть финальный ответ.

**Зависимости:** задача 1.

**Файлы:**

- `backend/src/smeshariki_ai/bootstrap.py`;
- `backend/tests/unit/test_bootstrap.py`;
- `backend/tests/unit/agent/test_get_context.py`.

**Действия:** дополнить тест сборки и тест agent loop, затем зарегистрировать экземпляр инструмента в bootstrap. Не менять общий контракт `Agent`, `ToolRegistry` и HTTP API.

**Тест:** `UV_CACHE_DIR=/private/tmp/smeshariki-uv-cache uv run --project backend --locked pytest backend/tests/unit/test_bootstrap.py backend/tests/unit/agent/test_get_context.py`.

## Задача 3. Обновить каталог и проверить изменение

**Требования:** REQ-006 и все критерии приёмки.

**Зависимости:** задачи 1–2.

**Файлы:**

- `docs/agent.md`;
- `docs/README.md`;
- `specs/changes/get-context-example/verification.md` после успешной проверки.

**Действия:** описать контракт и регистрацию инструмента на странице агента, обновить строку компонента в глобальном каталоге, проверить документацию ревью. Записать фактические результаты verify.

**Проверка:** `make test`, `make lint`, `git diff --check`; для документации — ревью ссылок и соответствия коду.

## Риски

Главный риск — модель может не решить вызвать инструмент даже при наличии его определения. Проверка agent loop доказывает корректную передачу результата при вызове, а не гарантирует решение конкретной внешней модели. Описание инструмента должно ясно указывать повод для вызова.
