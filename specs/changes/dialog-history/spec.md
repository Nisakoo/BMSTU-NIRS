# Постоянная история диалогов

## Цель

Сейчас история диалогов хранится в `InMemoryHistoryStore`: после рестарта
backend она теряется, а получить по HTTP список своих диалогов или сообщения
прошлого диалога нельзя. Изменение переносит диалоги и сообщения в PostgreSQL
по уже согласованной схеме из [`docs/database.md`](../../../docs/database.md)
и добавляет HTTP-контракт истории. Он нужен будущему frontend: список
диалогов с подгрузкой при прокрутке, открытие прошлого диалога и удаление.

Диалог появляется в базе только после того, как пользователь получил первый
ответ агента. До этого он остаётся черновиком: его знает клиент, а backend
держит в памяти процесса только то, что нужно для работы чата. В PostgreSQL
черновики не записываются.

Изменение затрагивает только БД и backend. Frontend и `/agent_test` не
меняются; интерфейс истории делается отдельной спецификацией по контракту
из `docs/dialogs.md`.

## Допущения

- `POST /api/v1/dialogs` по-прежнему возвращает `dialog_id`, но создаёт только
  черновик. Полностью клиентский черновик без участия сервера не подходит:
  SSE-подписку нужно открыть до первого запроса, а сервер должен знать
  владельца `dialog_id`, чтобы не отдавать события чужому пользователю. Кроме
  того, текущий frontend вызывает `POST /dialogs`, и его поведение должно
  остаться прежним.
- Черновик живёт только в памяти процесса. После рестарта backend он теряется,
  и клиент создаёт новый. Сохранённые диалоги рестарт переживают.
- Заголовок диалога — начало первого пользовательского запроса. Отдельный
  вызов LLM для заголовка не делается.
- Список сортируется по последней активности (`updated_at`). Для подгрузки
  при прокрутке используется keyset-курсор, а не `offset`.
- Сообщения диалога отдаются целиком, без пагинации: длина истории на
  практике ограничена контекстом LLM.
- Очередь запусков агента и брокер SSE-событий остаются in-memory, как и
  раньше.
- Владение диалогом не меняется: чужой диалог неотличим от несуществующего
  (`404`), в том числе для `admin`
  ([`dialog-ownership`](../dialog-ownership/spec.md)). Это касается и
  черновиков.

## Требования

### Черновик и сохранение диалога

- REQ-001: `POST /api/v1/dialogs` создаёт черновик: новый UUIDv4 и владельца в
  памяти процесса, без обращения к PostgreSQL. Ответ остаётся прежним:
  `201 Created`, `Location` и `{"dialog_id": "<uuid>"}`.
- REQ-002: Владелец черновика может отправлять в него сообщения
  (`POST messages`) и подписываться на события (`GET events`) так же, как
  сейчас. Агент получает пустую историю.
- REQ-003: Когда первый запуск агента в черновике завершается успешно, backend
  одной транзакцией вставляет строку `dialogs` (владелец, заголовок по
  REQ-006, `created_at` и `updated_at` равны времени сохранения) и пару
  сообщений «пользователь — ассистент». После этого черновик удаляется из
  памяти, и дальше диалог обслуживается из PostgreSQL. `message_end`
  публикуется после фиксации транзакции.
- REQ-004: Если первый запуск завершается ошибкой или отменой либо
  транзакция сохранения не проходит, в базе не остаётся ни диалога, ни
  сообщений. Подписчики получают `message_error`, черновик остаётся
  черновиком, и следующий запрос снова считается первым.
- REQ-005: Черновик удаляется из памяти, если у него нет активных подписок
  `events` и нет активных или ожидающих запусков в течение 30 минут.
  После удаления его `dialog_id` во всех ручках отвечает `404`. Короткий
  разрыв и переподключение `EventSource` черновик не теряют.

### Хранение

- REQ-006: Заголовок получается из первого пользовательского сообщения: пробелы
  по краям удаляются, последовательности пробельных символов заменяются одним
  пробелом. Если результат длиннее 60 символов (code points), берутся первые
  60 символов и добавляется `…`. Заголовок задаётся при сохранении диалога и
  потом не меняется.
- REQ-007: Миграция Alembic `0002` создаёт таблицы `dialogs` и `messages` со
  столбцами, ограничениями, каскадами и индексом `(user_id, updated_at DESC)`
  по схеме из `docs/database.md`. Миграция применяется `make migrate` поверх
  `0001` и откатывается.
- REQ-008: `PostgresHistoryStore` хранит сохранённые диалоги, и production
  bootstrap использует его с тем же engine, что у аутентификации. Сохранённый
  диалог вместе с владельцем и сообщениями переживает рестарт backend. После
  рестарта с ним можно продолжать работу: агент получает сохранённую историю
  как контекст.
- REQ-009: Каждый следующий успешный запуск атомарно добавляет пару
  «пользователь — ассистент» в одной транзакции. Сообщения получают
  последовательные `position` в порядке добавления, а `updated_at` диалога
  становится текущим временем. При ошибке не сохраняется ни одно сообщение и
  `updated_at` не меняется. Tool calls и tool results, как и сейчас, не
  сохраняются.
- REQ-010: Для модульных тестов `AgentService` и HTTP API без PostgreSQL есть
  in-memory реализация того же контракта хранения, которая ведёт себя так же,
  включая правило черновика.
- REQ-011: Ошибки подключения к PostgreSQL и SQL-ошибки адаптер превращает в
  `HistoryUnavailableError`, наследника `DialogError`. Текст запросов, сообщения
  и параметры SQL в текст исключения и в журнал не попадают.

### HTTP API

Все ручки находятся под существующим роутером `/api/v1` с `current_user`. Без
действительного access-токена они отвечают `401` раньше `404`/`422`, при
недоступности хранилищ аутентификации отвечают `503`.

- REQ-012: `GET /api/v1/dialogs?limit=<n>&cursor=<c>` возвращает `200` и JSON
  `{"items": [...], "next_cursor": "<строка>" | null}`. В `items` попадают
  только сохранённые диалоги текущего пользователя; черновиков там нет.
  Каждый элемент имеет вид
  `{"dialog_id": "<uuid>", "title": "<строка>", "created_at": "<ISO 8601 UTC>",
  "updated_at": "<ISO 8601 UTC>"}`. Порядок: `updated_at` по убыванию, при
  равенстве — `dialog_id` по убыванию.
- REQ-013: `limit` — целое от 1 до 50, по умолчанию 20. Если после страницы
  есть ещё элементы, `next_cursor` содержит непрозрачную строку, иначе он
  равен `null`. Запрос с этим `cursor` возвращает следующую страницу
  (keyset по `(updated_at, dialog_id)`), без повторов и пропусков, если
  диалоги между запросами не менялись. При некорректном `limit` или
  `cursor`, который не удаётся декодировать, ответ — `422`.
- REQ-014: `GET /api/v1/dialogs/{dialog_id}/messages` для своего сохранённого
  диалога возвращает `200` и JSON
  `{"dialog_id": "<uuid>", "title": "<строка>", "messages": [{"role":
  "user" | "assistant", "content": "<строка>", "created_at": "<ISO 8601
  UTC>"}]}`. Сообщения идут в порядке `position`. Для своего черновика ответ —
  `200` с `"title": null` и `"messages": []`.
- REQ-015: `DELETE /api/v1/dialogs/{dialog_id}` для своего диалога или
  черновика отвечает `204` с пустым телом. Сохранённый диалог удаляется из
  базы вместе с сообщениями, черновик удаляется из памяти. После этого
  `messages` (GET и POST), `events` и повторный `DELETE` отвечают `404`, а
  диалог пропадает из списка.
- REQ-016: Если при удалении у диалога или черновика есть активный или
  ожидающий в очереди запуск агента, запуски отменяются, ничего не
  сохраняется, а подписчики `events` получают `message_error`, после чего
  поток закрывается. Удалённый черновик не появляется в базе, даже если его
  первый запуск был почти завершён. Запуски других диалогов не затрагиваются.
- REQ-017: Для неизвестного или чужого `dialog_id` (черновика или
  сохранённого диалога, в том числе при запросе `admin`) все ручки диалога
  отвечают `404` `{"detail":"Dialog not found."}` и ничего не меняют. Попытка
  доступа журналируется существующим событием `dialog.access.denied`. При
  некорректном UUID ответ — `422`.
- REQ-018: `DELETE` подпадает под существующий `ForbiddenOriginMiddleware`:
  при `Sec-Fetch-Site: cross-site|same-site` ответ — `403`.
- REQ-019: Если PostgreSQL недоступен, ручки, которым нужна база, отвечают
  `503` `{"detail":"Dialog storage is unavailable."}`: `GET /dialogs`, а также
  `GET/POST messages`, `GET events` и `DELETE` для `dialog_id`, которого нет
  среди черновиков. Создание черновика и работа с ним до сохранения от базы
  не зависят. Если сбой хранения происходит в фоновом запуске, подписчики
  получают `message_error`, а история не меняется.
- REQ-020: Остальное поведение `POST /dialogs`, `POST messages` и `GET
  events` для владельца сохраняется: коды ответов, SSE-события и порядок
  проверок `401` → `415` → `404`/`422`.

### Наблюдаемость и документация

- REQ-021: Сохранение черновика журналируется событием `dialog.persisted`,
  удаление — событием `dialog.deleted` с признаком черновика, удаление
  черновика по истечении срока — `dialog.draft.expired`. Все события содержат
  `dialog_id`, а события по запросу пользователя — ещё и `user_id`. Ошибка
  хранилища журналируется с `error_type`. Заголовки, тексты сообщений,
  курсоры и SQL-параметры в журнал не попадают.
- REQ-022: В [`docs/dialogs.md`](../../../docs/dialogs.md) описаны:
  - жизненный цикл диалога: черновик на клиенте и в памяти процесса,
    сохранение после первого ответа агента, срок жизни черновика, потеря
    черновика при рестарте;
  - HTTP-контракт новых ручек: параметры, форматы ответа, коды ошибок,
    семантика курсора и сортировки, правило заголовка, удаление во время
    запуска;
  - расширенные внутренние контракты хранения и `AgentService`.

  Из страницы удалены утверждения о том, что история теряется при рестарте и
  что API чтения истории нет. В [`docs/database.md`](../../../docs/database.md)
  таблицы `dialogs` и `messages` отмечены реализованными миграцией `0002`,
  описан `PostgresHistoryStore` и сказано, что строка `dialogs` появляется
  только вместе с первыми сообщениями. [`docs/README.md`](../../../docs/README.md)
  и `AGENTS.md` («Реализованные диалоги и HTTP API», «Согласованные
  технологии» — PostgreSQL хранит историю) обновлены и ссылаются на артефакты
  изменения.

## Сценарии

### Диалог сохраняется после первого ответа

- Given пользователь A создал черновик D через `POST /api/v1/dialogs`
- When A отправляет первый запрос, и агент успешно отвечает
- Then после `message_end` диалог D есть в базе с заголовком по REQ-006 и
  парой сообщений и появляется в `GET /api/v1/dialogs`

### Черновик не попадает в базу

- Given A создал черновик D и подписался на события
- When первый запуск завершается ошибкой, или A так и не отправил запрос
- Then в таблицах `dialogs` и `messages` нет записей D, D нет в списке, а
  `GET .../D/messages` отвечает `200` с пустой историей и `"title": null`

### Черновик истекает

- Given A создал черновик D, закрыл вкладку, и подписок нет
- When проходит 30 минут без подписок и запусков
- Then все ручки для D отвечают `404`

### История переживает рестарт

- Given у A есть сохранённый диалог D
- When backend перезапускается, и A запрашивает `GET /api/v1/dialogs/D/messages`
- Then ответ `200` содержит сообщения в исходном порядке, а следующий запрос в
  D передаёт агенту эту историю

### Список с подгрузкой

- Given у A 25 сохранённых диалогов и 3 черновика
- When A запрашивает `GET /api/v1/dialogs?limit=20`, а затем тот же запрос с
  полученным `next_cursor`
- Then первая страница содержит 20 диалогов от новых к старым и непустой
  `next_cursor`, вторая — оставшиеся 5 и `next_cursor: null`. Черновиков и
  диалогов других пользователей в ответах нет

### Заголовок

- Given черновик D
- When первый запрос — 100-символьный текст с переводами строк, и агент
  успешно отвечает
- Then `title` диалога D равен первым 60 символам нормализованного текста с
  `…`, и после следующих сообщений не меняется

### Удаление во время ответа

- Given A подписан на события D, агент генерирует ответ, и ещё один запрос D
  ждёт в очереди
- When A вызывает `DELETE /api/v1/dialogs/D`
- Then ответ `204`, подписчик получает `message_error`, поток закрывается,
  ничего не сохраняется, и следующий `GET /api/v1/dialogs/D/messages` отвечает
  `404`. Если D был черновиком, в базе он так и не появляется

### Чужой диалог

- Given D (черновик или сохранённый) принадлежит A
- When B или администратор вызывает любую ручку диалога D
- Then ответ `404` `Dialog not found.`, и D у A не меняется

### PostgreSQL недоступен

- Given backend запущен, а PostgreSQL остановлен
- When вошедший пользователь создаёт черновик, подписывается и отправляет
  первый запрос
- Then черновик создаётся (`201`), запрос принимается (`202`), но сохранение не
  проходит: подписчик получает `message_error`, черновик остаётся черновиком.
  `GET /api/v1/dialogs` отвечает `503` без текста внутреннего исключения

## Технологии и структура

Новые технологии не добавляются: используются PostgreSQL 17, SQLAlchemy
async Core, asyncpg и Alembic из `backend-auth-jwt`.

- `db/migrations/versions/0002_dialogs_messages.py` — таблицы `dialogs` и
  `messages`; `db/tables.py` повторяет схему. Схема не меняется относительно
  `docs/database.md`; `title` остаётся `NULL`-able, хотя при сохранении по
  этому изменению всегда заполняется.
- `db/history.py` (или `db/stores.py`, решается в плане) —
  `PostgresHistoryStore`. Первое сохранение — одна транзакция `INSERT dialogs`
  и `INSERT messages`. Последующие — блокировка строки диалога
  (`SELECT ... FOR UPDATE`), расчёт следующей `position`, вставка сообщений и
  обновление `updated_at`.
- `dialogs/` — контракт хранения расширяется: создание диалога вместе с
  первыми сообщениями, получение метаданных (владелец, заголовок), страница
  списка владельца и удаление. Сюда же выносится чистая функция заголовка и
  `HistoryUnavailableError`. In-memory реализация выполняет тот же контракт.
- Реестр черновиков — process-local компонент с владельцем, временем
  последней активности и истечением по REQ-005. Он не зависит от FastAPI и
  PostgreSQL. Где он живёт (`dialogs` или `application`) и как сочетается с
  `HistoryStore` (отдельная зависимость `AgentService` или композитное
  хранилище), фиксируется в плане.
- `application/agent_service.py` — `start_dialog` создаёт черновик;
  добавляются `list_dialogs(user_id, limit, cursor)`,
  `get_dialog(dialog_id, user_id)` и `delete_dialog(dialog_id, user_id)` с
  проверкой владельца. Первый успешный запуск сохраняет черновик, а удаление
  отменяет задачи диалога и закрывает его подписки.
- `application/event_broker.py` — контракт `DialogEventBroker` получает
  операцию закрытия всех подписок одного диалога.
- `api/app.py`, `api/schemas.py` — новые ручки и схемы ответов;
  `HistoryUnavailableError` превращается в `503`. Кодирование курсора
  (base64url от `updated_at` и `dialog_id`) фиксируется в плане.
- `bootstrap.py` — production создаёт `PostgresHistoryStore(engine)`. Если в
  `create_application` передан готовый `auth_service` (тестовый режим),
  используется in-memory хранилище.

Вне объёма: frontend и `/agent_test`, переименование диалога, пагинация
сообщений, поиск, доступ администратора к чужим диалогам, настройка срока
жизни черновика через environment, перенос очереди, брокера событий и
черновиков из памяти процесса, `Last-Event-ID` replay.

## Тестирование

- Backend Pytest (unit):
  - функция заголовка: обрезка, нормализация пробелов, граница 60 символов,
    не-ASCII;
  - реестр черновиков: владелец, истечение через 30 минут без подписок и
    запусков, отсутствие истечения при активной подписке или запуске (время
    подменяется детерминированными часами);
  - in-memory хранилище: список только владельца, порядок, курсор без повторов
    и пропусков, удаление;
  - `AgentService`: черновик сохраняется только после успешного первого
    запуска; при ошибке не сохраняется и остаётся черновиком;
    `list_dialogs`/`get_dialog`/`delete_dialog` проверяют владельца; удаление
    отменяет активный и ожидающий запуск, публикует `message_error`, ничего
    не сохраняет и не трогает другой диалог; ошибка хранения не меняет
    историю;
  - `InMemoryDialogEventBroker`: закрытие подписок одного диалога.
- Backend Pytest (integration, `TEST_DATABASE_URL`, по образцу
  `tests/integration/db/test_postgres_stores.py`):
  - миграция `0002` применяется и откатывается;
  - `PostgresHistoryStore`: создание диалога вместе с первыми сообщениями,
    чтение после нового engine (эмуляция рестарта), атомарность при ошибке,
    `position`, каскадное удаление сообщений при удалении диалога и
    пользователя, keyset-страницы;
  - недоступная БД даёт `HistoryUnavailableError`.
- Backend Pytest (integration API, `httpx.ASGITransport`): черновик не виден в
  списке до ответа агента и появляется после него; коды и форматы ответов
  новых ручек; `401` раньше `404`/`422`; `422` на `limit`/`cursor`; `404` для
  чужого диалога и черновика, в том числе для администратора; `403` на
  межсайтовый `DELETE`; `503` при `HistoryUnavailableError`; события журнала
  без пользовательского текста. Существующие тесты диалогов и SSE проходят без
  изменения ожидаемого поведения.
- Ручная проверка в `make run`: открыть чат и убедиться, что строки в
  `dialogs` нет; отправить сообщение и увидеть её после ответа; перезапустить
  `backend` и через `curl` с cookie получить список и сообщения; удалить
  диалог.

## Границы

- Всегда: черновик не записывается в PostgreSQL; первое сохранение и каждое
  добавление сообщений атомарны; чужой диалог неотличим от несуществующего;
  пользовательский текст и заголовки не попадают в журнал; схема в
  `tables.py` совпадает с миграцией.
- Сначала спросить: изменение схемы `dialogs`/`messages` относительно
  `docs/database.md`, хранение tool calls, изменение срока жизни черновика,
  изменение формата ответа существующих ручек, любые правки frontend.
- Никогда: `offset`-пагинация списка, ответ `403` или иной ответ, раскрывающий
  существование чужого диалога, хранение истории или черновиков в Redis.

## Критерии приёмки

- [ ] `make migrate` создаёт `dialogs` и `messages`; откат `0002` их удаляет.
- [ ] `POST /api/v1/dialogs` не создаёт записей в базе; диалог появляется в
  базе и в списке только после первого успешного ответа агента, а при ошибке
  первого запуска остаётся черновиком.
- [ ] Черновик без подписок и запусков исчезает через 30 минут.
- [ ] Сохранённый диалог доступен после рестарта backend, и его продолжение
  передаёт агенту сохранённую историю.
- [ ] `GET /api/v1/dialogs` отдаёт только свои сохранённые диалоги от новых к
  старым, а курсор листает страницы без повторов и пропусков.
- [ ] `GET /api/v1/dialogs/{id}/messages` отдаёт сообщения в порядке и
  заголовок по REQ-006.
- [ ] `DELETE /api/v1/dialogs/{id}` удаляет диалог или черновик, отменяет его
  запуски и закрывает поток событий; затем ручки диалога отвечают `404`.
- [ ] Чужой и неизвестный диалог дают `404`, а ручки, которым нужна
  недоступная PostgreSQL, отвечают `503`.
- [ ] Жизненный цикл и контракт описаны в `docs/dialogs.md` и
  `docs/database.md`; `docs/README.md` и `AGENTS.md` обновлены по REQ-022.
- [ ] `make test` и `make lint` проходят успешно.

## Открытые вопросы

- Нет. Решения пользователя: только БД и backend; заголовок из первого
  запроса; удаление и курсорная пагинация списка входят в объём; диалог
  сохраняется только после первого ответа агента, а до этого существует как
  черновик.
