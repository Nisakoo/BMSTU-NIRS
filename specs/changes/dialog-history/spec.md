# Постоянная история диалогов

## Цель

Сейчас история диалогов хранится в `InMemoryHistoryStore`: после рестарта backend она теряется, а получить по HTTP список своих диалогов или сообщения прошлого
диалога нельзя. Изменение переносит диалоги и сообщения в PostgreSQL по уже согласованной схеме из [`docs/database.md`](../../../docs/database.md) и добавляет
HTTP-контракт истории. Он нужен будущему frontend: список диалогов с подгрузкой при прокрутке, открытие прошлого диалога и удаление. Диалог появляется в базе
только после того, как пользователь получил первый ответ агента. До этого он остаётся черновиком: его знает клиент, а backend держит в памяти процесса только
то, что нужно для работы чата. В PostgreSQL черновики не записываются. Изменение затрагивает только БД и backend. Frontend и `/agent_test` не меняются;
интерфейс истории делается отдельной спецификацией по контракту из `docs/dialogs.md`.

## Требования

### Черновик и сохранение диалога
- REQ-001: `POST /api/v1/dialogs` создаёт черновик: новый UUIDv4 и владельца в памяти процесса, без обращения к PostgreSQL. Ответ остаётся прежним: `201 Created`, `Location` и `{"dialog_id": "<uuid>"}`.
- REQ-002: Владелец черновика может отправлять в него сообщения (`POST messages`) и подписываться на события (`GET events`) так же, как сейчас. Агент получает пустую историю.
- REQ-003: Когда первый запуск агента в черновике завершается успешно, backend одной транзакцией вставляет строку `dialogs` (владелец, заголовок по REQ-006, `created_at` и `updated_at` равны времени сохранения) и пару сообщений
  «пользователь — ассистент». После этого черновик удаляется из памяти, и дальше диалог обслуживается из PostgreSQL. `message_end` публикуется после фиксации транзакции.
- REQ-004: Если первый запуск завершается ошибкой или отменой либо транзакция сохранения не проходит, в базе не остаётся ни диалога, ни сообщений. Подписчики получают `message_error`, черновик остаётся черновиком, и следующий запрос снова
  считается первым.
- REQ-005: Черновик удаляется из памяти, если у него нет активных подписок `events` и нет активных или ожидающих запусков в течение 30 минут. После удаления его `dialog_id` во всех ручках отвечает `404`. Короткий разрыв и переподключение
  `EventSource` черновик не теряют. ### Хранение
- REQ-006: Заголовок получается из первого пользовательского сообщения: пробелы по краям удаляются, последовательности пробельных символов заменяются одним пробелом. Если результат длиннее 60 символов (code points), берутся первые 60
  символов и добавляется `…`. Заголовок задаётся при сохранении диалога и потом не меняется.
- REQ-007: Миграция Alembic `0002` создаёт таблицы `dialogs` и `messages` со столбцами, ограничениями, каскадами и индексом `(user_id, updated_at DESC)` по схеме из `docs/database.md`. Миграция применяется `make migrate` поверх `0001` и
  откатывается.
- REQ-008: `PostgresHistoryStore` хранит сохранённые диалоги, и production bootstrap использует его с тем же engine, что у аутентификации. Сохранённый диалог вместе с владельцем и сообщениями переживает рестарт backend. После рестарта с ним
  можно продолжать работу: агент получает сохранённую историю как контекст.
- REQ-009: Каждый следующий успешный запуск атомарно добавляет пару «пользователь — ассистент» в одной транзакции. Сообщения получают последовательные `position` в порядке добавления, а `updated_at` диалога становится текущим временем. При
  ошибке не сохраняется ни одно сообщение и `updated_at` не меняется. Tool calls и tool results, как и сейчас, не сохраняются.
- REQ-010: Для модульных тестов `AgentService` и HTTP API без PostgreSQL есть in-memory реализация того же контракта хранения, которая ведёт себя так же, включая правило черновика.
- REQ-011: Ошибки подключения к PostgreSQL и SQL-ошибки адаптер превращает в `HistoryUnavailableError`, наследника `DialogError`. Текст запросов, сообщения и параметры SQL в текст исключения и в журнал не попадают. ### HTTP API Все ручки
  находятся под существующим роутером `/api/v1` с `current_user`. Без действительного access-токена они отвечают `401` раньше `404`/`422`, при недоступности хранилищ аутентификации отвечают `503`.
- REQ-012: `GET /api/v1/dialogs?limit=<n>&cursor=<c>` возвращает `200` и JSON `{"items": [...], "next_cursor": "<строка>" | null}`. В `items` попадают только сохранённые диалоги текущего пользователя; черновиков там нет. Каждый элемент
  имеет вид `{"dialog_id": "<uuid>", "title": "<строка>", "created_at": "<ISO 8601 UTC>", "updated_at": "<ISO 8601 UTC>"}`. Порядок: `updated_at` по убыванию, при равенстве — `dialog_id` по убыванию.
- REQ-013: `limit` — целое от 1 до 50, по умолчанию 20. Если после страницы есть ещё элементы, `next_cursor` содержит непрозрачную строку, иначе он равен `null`. Запрос с этим `cursor` возвращает следующую страницу (keyset по `(updated_at,
  dialog_id)`), без повторов и пропусков, если диалоги между запросами не менялись. При некорректном `limit` или `cursor`, который не удаётся декодировать, ответ — `422`.
- REQ-014: `GET /api/v1/dialogs/{dialog_id}/messages` для своего сохранённого диалога возвращает `200` и JSON `{"dialog_id": "<uuid>", "title": "<строка>", "messages": [{"role": "user" | "assistant", "content": "<строка>", "created_at":
  "<ISO 8601 UTC>"}]}`. Сообщения идут в порядке `position`. Для своего черновика ответ — `200` с `"title": null` и `"messages": []`.
- REQ-015: `DELETE /api/v1/dialogs/{dialog_id}` для своего диалога или черновика отвечает `204` с пустым телом. Сохранённый диалог удаляется из базы вместе с сообщениями, черновик удаляется из памяти. После этого `messages` (GET и POST),
  `events` и повторный `DELETE` отвечают `404`, а диалог пропадает из списка.
- REQ-016: Если при удалении у диалога или черновика есть активный или ожидающий в очереди запуск агента, запуски отменяются, ничего не сохраняется, а подписчики `events` получают `message_error`, после чего поток закрывается. Удалённый
  черновик не появляется в базе, даже если его первый запуск был почти завершён. Запуски других диалогов не затрагиваются.
- REQ-017: Для неизвестного или чужого `dialog_id` (черновика или сохранённого диалога, в том числе при запросе `admin`) все ручки диалога отвечают `404` `{"detail":"Dialog not found."}` и ничего не меняют. Попытка доступа журналируется
  существующим событием `dialog.access.denied`. При некорректном UUID ответ — `422`.
- REQ-018: `DELETE` подпадает под существующий `ForbiddenOriginMiddleware`: при `Sec-Fetch-Site: cross-site|same-site` ответ — `403`.
- REQ-019: Если PostgreSQL недоступен, ручки, которым нужна база, отвечают `503` `{"detail":"Dialog storage is unavailable."}`: `GET /dialogs`, а также `GET/POST messages`, `GET events` и `DELETE` для `dialog_id`, которого нет среди
  черновиков. Создание черновика и работа с ним до сохранения от базы не зависят. Если сбой хранения происходит в фоновом запуске, подписчики получают `message_error`, а история не меняется.
- REQ-020: Остальное поведение `POST /dialogs`, `POST messages` и `GET events` для владельца сохраняется: коды ответов, SSE-события и порядок проверок `401` → `415` → `404`/`422`. ### Наблюдаемость и документация
- REQ-021: Сохранение черновика журналируется событием `dialog.persisted`, удаление — событием `dialog.deleted` с признаком черновика, удаление черновика по истечении срока — `dialog.draft.expired`. Все события содержат `dialog_id`, а
  события по запросу пользователя — ещё и `user_id`. Ошибка хранилища журналируется с `error_type`. Заголовки, тексты сообщений, курсоры и SQL-параметры в журнал не попадают.
- REQ-022: В [`docs/dialogs.md`](../../../docs/dialogs.md) описаны: - жизненный цикл диалога: черновик на клиенте и в памяти процесса, сохранение после первого ответа агента, срок жизни черновика, потеря черновика при рестарте; -
  HTTP-контракт новых ручек: параметры, форматы ответа, коды ошибок, семантика курсора и сортировки, правило заголовка, удаление во время запуска; - расширенные внутренние контракты хранения и `AgentService`. Из страницы удалены утверждения
  о том, что история теряется при рестарте и что API чтения истории нет. В [`docs/database.md`](../../../docs/database.md) таблицы `dialogs` и `messages` отмечены реализованными миграцией `0002`, описан `PostgresHistoryStore` и сказано, что
  строка `dialogs` появляется только вместе с первыми сообщениями. [`docs/README.md`](../../../docs/README.md) и `AGENTS.md` («Реализованные диалоги и HTTP API», «Согласованные технологии» — PostgreSQL хранит историю) обновлены и ссылаются
  на артефакты изменения.

Действующий контракт и архитектурные границы описаны в [каталоге](../../../docs/README.md).
