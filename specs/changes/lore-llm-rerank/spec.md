# Реранкинг кандидатов лора через LLM

## Цель

Узкое место поиска — не порядок, а состав контекста: `Recall@20` документов
`0.700`, а до агента доходит `Context Recall 0.367`. Половина нужного уже есть
в двадцатке кандидатов, но в три пассажа не попадает. Реранкер переупорядочивает
кандидатов до сборки контекста, поэтому нужные фрагменты оказываются первыми.
Отдельно: это закладывает порт `Ranker`, чтобы позже заменить LLM на
cross-encoder или dense-кандидатов без переделки поиска.

## Требования

- REQ-001: порт `Ranker` в `rag/lore/rerank.py` с методом
  `rerank(query, hits, limit) -> tuple[LoreHit, ...]`; `NoopRanker` сохраняет
  порядок.
- REQ-002: `LLMReranker` использует существующую абстракцию `LLMProvider`,
  нумерует кандидатов (текст обрезается до 400 символов), просит вернуть номера
  по убыванию полезности и разбирает ответ защитно (числа в диапазоне,
  дедупликация, `0` игнорируется).
- REQ-003: реранкер никогда не сужает набор кандидатов: выбранные фрагменты
  идут первыми, остальные сохраняются после них до лимита. Сбой провайдера или
  неразборчивый ответ возвращают исходный порядок.
- REQ-004: `SearchLoreTool` принимает необязательный `ranker`; реранкинг
  выполняется после поиска и до `LoreContextBuilder`. Контракт инструмента не
  меняется.
- REQ-005: `BenchmarkRunner` принимает `ranker`; CLI `lore-benchmark --rerank`
  включает LLM-реранкер (нужен конфиг LLM). Без флага метрики прежние.
- REQ-006: конфигурация `RAG_LORE_RERANK_ENABLED` (по умолчанию `false`);
  bootstrap собирает `LLMReranker` только при включённом флаге.
- REQ-007: документация: `docs/lore.md`, `docs/rag.md`, `AGENTS.md`,
  `docker/.env.example`.
- REQ-008: изменение сохраняется, только если контекстные метрики не хуже, а
  `Context Recall` или `Document MRR` выше; измерение фиксируется в
  `verification.md`.

## Сценарии

- Given top-20 кандидатов и включённый реранкинг, When агент вызывает
  `search_lore`, Then в трёх пассажах оказываются фрагменты, выбранные
  реранкером, а остальные кандидаты не теряются.
- Given сбой LLM, When выполняется реранкинг, Then порядок остаётся исходным,
  событие `lore.rerank.completed` помечено `failed`, исключение не выходит.

## Тестирование

- `test_rerank.py`: разбор номеров, порядок, лимит, сохранение остальных
  кандидатов, сбой провайдера, неразборчивый ответ, единственный кандидат.
- `test_tool.py`: реранкер вызывается и меняет порядок пассажей.
- `test_benchmark.py`: реранкер применяется в бенчмарке.
- `test_backend_config.py`: флаг разбирается, по умолчанию выключен.

## Границы

- Всегда: исходный набор кандидатов сохраняется; сбой деградирует к исходному
  порядку; в журнал не попадают текст запроса и фрагменты.
- Сначала спросить: включение по умолчанию, замена LLM на cross-encoder,
  dense-кандидаты.
- Никогда: не подгонять промпт под отдельные вопросы golden set.
