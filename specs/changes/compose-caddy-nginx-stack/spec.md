# Единый контейнерный запуск с Caddy и Nginx

## Цель

Запускать готовое приложение одной командой из корня репозитория. Caddy
становится единой внешней точкой входа, frontend собирается из актуальных
исходников и отдаётся отдельным Nginx-контейнером, а backend остаётся
внутренним сервисом того же Docker Compose проекта.

## Требования

- REQ-001: `make run` собирает и запускает backend, frontend на Nginx и Caddy
  через один `docker/compose.yaml`; отдельный запуск Vite для основного
  сценария не требуется.
- REQ-002: Для контейнерного запуска frontend собирается командой Vite build из
  `frontend/src/` с зафиксированными npm-зависимостями. Nginx раздаёт
  полученные статические файлы; он и Caddy работают в разных контейнерах.
- REQ-003: Публичный адрес по умолчанию — `http://localhost:8080/`. Только
  Caddy публикует порт на хосте; путь `/` и статические файлы передаются
  frontend-контейнеру, `/api` и `/api/*` — backend без удаления префикса.
  Внешний порт можно переопределить через `docker/.env`.
- REQ-004: Через публичный адрес сохраняются действующие HTTP- и SSE-контракты:
  создание диалога возвращает `201`, отправка сообщения — `202`, подключение к
  потоку получает `ready`, а дальнейшие события доходят без накопления до
  закрытия соединения. Браузерный код продолжает использовать относительные
  `/api/v1/...`; CORS для этого сценария не нужен.
- REQ-005: При временной недоступности backend на старте stack становится
  доступен после его готовности без ручного перезапуска сервисов. Отказ
  backend не маскируется статическим frontend-ответом на `/api/*`.
- REQ-006: Настройки LLM и локальные секреты по-прежнему поступают в backend
  через Compose environment из `docker/.env`; файл не коммитится. Все новые
  файлы контейнерного запуска располагаются в `docker/`.
- REQ-007: Документация и правила проекта отражают новый основной запуск,
  адрес, маршрутизацию и границы сервисов. `make frontend` с Vite остаётся
  необязательным режимом разработки; Python API и бизнес-логика не меняются.

## Сценарии

### Основной запуск

- Given Docker доступен и в `docker/.env` задана рабочая конфигурация LLM
- When пользователь выполняет `make run` из корня репозитория
- Then один Compose проект собирает оба образа приложения, запускает три
  сервиса и открывает frontend на `http://localhost:8080/`

### Общий HTTP/SSE origin

- Given stack готов и клиент открыл публичный адрес Caddy
- When клиент создаёт диалог и подключается к `/api/v1/dialogs/{id}/events`
- Then backend отвечает через Caddy с прежними кодами и SSE-событием `ready`,
  а статические ресурсы страницы отдаются Nginx на том же origin

### Недоступный backend

- Given frontend и Caddy доступны, но backend временно не отвечает
- When клиент обращается к `/api/v1/dialogs`
- Then запрос не попадает в Nginx и не возвращает HTML страницы вместо API;
  после восстановления backend запрос снова проходит без пересборки frontend

## Технологии и структура

Один `docker/compose.yaml` содержит `backend`, `frontend` и `caddy`. Новый
Dockerfile в `docker/` использует Node.js 22 для Vite build и Nginx для
раздачи результата. Конфигурация Caddy хранится в `docker/`; `/api` маршрутизируется
внутри Compose сети к backend, остальные пути — к Nginx. Для локального
однокомандного запуска Caddy работает по HTTP; домен, публичный HTTPS и
сертификаты здесь не настраиваются.

Текущие `frontend/vite.config.js` и `make frontend` сохраняются как dev-режим.
Backend остаётся модульным монолитом с прежним API. Требуемые изменения
`.dockerignore`, `Makefile`, шаблона environment, README, архитектурного
каталога и `AGENTS.md` входят в то же изменение.

## Команды

- Запуск: `make run`
- Полные тесты продукта: `make test`
- Проверка Compose: `docker compose --env-file docker/.env -f docker/compose.yaml config`
- Проверка без браузера: HTTP- и SSE-запросы к публичному адресу через `curl`

## Тестирование

| Требования | Способ проверки |
| --- | --- |
| REQ-001–REQ-003 | Compose config, сборка и запуск из чистого локального Compose проекта; проверка трёх сервисов и единственного опубликованного порта; HTTP-запросы страницы и статических файлов |
| REQ-004 | HTTP `curl` для создания диалога и отправки сообщения, потоковый `curl -N` для SSE `ready` и событий ответа; frontend Node-тесты |
| REQ-005 | Поведенческая проверка API при остановленном backend и после его запуска через тот же Caddy origin |
| REQ-006–REQ-007 | Ревью Compose environment, Git ignore и документации; проверка, что содержимое локального `.env` не попало в diff |

Автоматические тесты только для наличия файлов или структуры каталогов не
добавляются. Для этого изменения Python-код продукта не меняется; `make test`
запускается как общая регрессия, но требование SDD об обязательном Pytest после
Python-изменения здесь не применяется.

## Границы

- Всегда: сохранять существующие пути `/api/v1`, поток SSE и отсутствие
  секретов в репозитории; не вмешиваться в чужие незакоммиченные изменения.
- Сначала спросить: нужен ли внешний домен, автоматический HTTPS или другой
  публичный порт вместо выбранного локального значения по умолчанию.
- Никогда: не запускать браузер, не добавлять CORS, отдельный LiteLLM Proxy,
  RAG-сервис или постоянное хранилище истории в рамках этого изменения.

## Критерии приёмки

- [ ] Одна команда `make run` собирает и запускает все три сервиса.
- [ ] На `http://localhost:8080/` отдаются frontend и его ресурсы, а `/api/*`
  достигает backend через Caddy с сохранением префикса.
- [ ] HTTP-коды создания/отправки и потоковый SSE `ready` подтверждены через
  публичный адрес без браузера; для ответа агента подтверждена доставка
  `message_*` событий при рабочем LLM.
- [ ] Отказ и восстановление backend не требуют пересборки frontend; API не
  подменяется HTML.
- [ ] Только Caddy публикует порт; Nginx не совмещён с Caddy.
- [ ] Документация и архитектурный каталог обновлены, секреты не затронуты.
- [ ] `make test`, frontend build и Compose config проходят; поскольку Python-
  код не меняется, дополнительный тестовый этап для Python-изменений неприменим.

## Открытые вопросы

- Подтвердить локальный HTTP-вход на порту `8080` как первый этап; домен и
  публичный HTTPS потребуют отдельной конфигурации и, возможно, следующей
  спецификации.
