# Страница авторизации и контракт API аутентификации

## Цель

Добавить во frontend отдельную страницу входа и регистрации пользователя,
подключённую к HTTP API аутентификации backend, и зафиксировать этот API как
контракт в `docs/`. Backend-реализация контракта (хранение пользователей,
сессии, защита существующих ручек) выполняется отдельным изменением другого
участника команды; данное изменение задаёт для неё согласованный контракт и не
меняет backend.

## Контракт API

Все пути находятся под существующим префиксом `/api/v1`. Тела запросов и
ответов — JSON. Аутентификация выполняется серверной сессией: backend хранит
сессию на своей стороне, а браузер получает только cookie с её
идентификатором. Токены в теле ответа, `localStorage` или заголовке
`Authorization` не используются, поэтому cookie автоматически сопровождает и
обычные `fetch`, и `EventSource`.

| Метод и путь | Тело запроса | Успешный ответ | Ошибки |
| --- | --- | --- | --- |
| `POST /api/v1/users` — регистрация | `{"login": "<login>", "password": "<password>"}` | `201 Created`, `{"id": "<uuid>", "login": "<login>", "role": "user"}` | `409 Conflict` — логин занят; `422 Unprocessable Entity` — нарушены правила полей или переданы лишние поля |
| `POST /api/v1/auth/login` — аутентификация | `{"login": "<login>", "password": "<password>"}` | `200 OK`, тело как у регистрации, `Set-Cookie` с сессией | `401 Unauthorized` — неверная пара логин/пароль, одинаково для неизвестного логина и неверного пароля; `422` — некорректные поля |
| `POST /api/v1/auth/logout` — деавторизация | нет | `204 No Content`, сессия удалена, cookie сброшена | Нет: при отсутствии или недействительности сессии ответ тоже `204` |
| `GET /api/v1/users/me` — текущий пользователь | нет | `200 OK`, `{"id": "<uuid>", "login": "<login>", "role": "user" \| "admin"}` | `401 Unauthorized` — сессии нет или она недействительна |

Правила полей:

- `login` — от 3 до 32 символов, только латинские буквы, цифры, `_`, `.`
  и `-`; сравнение без учёта регистра;
- `password` — от 8 до 128 символов;
- клиент не может передать `id`, `role`, даты и другие системные поля: backend
  отвечает `422` на любые поля, кроме `login` и `password`;
- регистрация всегда создаёт пользователя с ролью `user`.

Сессионная cookie: `HttpOnly`, `SameSite=Lax`, `Path=/`; флаг `Secure`
включается вместе с HTTPS. Тела ошибок, если есть, не содержат пароль,
хеш пароля и сведения о том, существует ли логин (кроме `409` при
регистрации).

## Требования

- REQ-001: Frontend предоставляет страницу `/login/` как ещё одну HTML-entry
  того же Vite build и Nginx-контейнера; отдельный frontend-сервис или порт не
  создаётся.
- REQ-002: Страница содержит два режима — «Вход» и «Регистрация» — с полями
  логина и пароля; в режиме регистрации дополнительно есть подтверждение
  пароля. Текущий режим определим визуально и программно.
- REQ-003: Перед отправкой frontend проверяет поля по правилам контракта и
  совпадение пароля с подтверждением; при нарушении запрос не отправляется,
  а у соответствующего поля отображается понятная ошибка.
- REQ-004: Отдельный DOM-независимый клиент `AuthApi` выполняет четыре
  запроса контракта с относительными адресами `/api/v1/...` на том же origin и
  переводит HTTP-статусы и сетевые сбои в стабильные коды ошибок.
- REQ-005: Успешный вход перенаправляет пользователя на `/`. Успешная
  регистрация сразу выполняет вход с теми же данными и затем перенаправляет на
  `/`.
- REQ-006: Ошибки отображаются понятным текстом: `409` — логин занят, `401` —
  неверный логин или пароль, `422` — проверьте поля, сетевой сбой или иной
  статус — сервис временно недоступен. Неуспешная попытка сохраняет введённый
  логин и очищает пароль.
- REQ-007: Во время запроса форма и переключатель режима заблокированы,
  повторная отправка невозможна; после ответа форма разблокируется.
- REQ-008: Если при открытии `/login/` запрос `GET /api/v1/users/me` вернул
  `200`, страница сразу перенаправляет на `/`. Любой другой исход, включая
  отсутствующий backend, оставляет форму доступной.
- REQ-009: Пароль не сохраняется в `localStorage`, `sessionStorage`, cookie,
  URL или журнале консоли; frontend не читает и не хранит идентификатор сессии.
  Динамический текст вставляется только как текст, без `innerHTML`.
- REQ-010: Страница выполнена в стилистике пользовательского чата: тёмная
  ночная тема и фон страницы, плашка-kicker и крупный заголовок с розовым
  акцентом, сцена со звёздами и ночной полянкой, карточка формы в стиле панели
  чата, поля в стиле поля ввода чата, розовая градиентная кнопка отправки,
  переключатель режимов в стиле chips, а также групповое изображение
  Смешариков `static/characters/smeshariki.png` с облачком-подсказкой
  «Привет! Заходи, будем сочинять истории!». На desktop изображение стоит на
  ночной полянке рядом с карточкой формы; на mobile оно уменьшается и
  располагается над формой. Изображение оптимизируется до ширины около
  `1200px` без видимой потери качества.
- REQ-013: Страница адаптивна от `320px` до `1920px` без горизонтальной
  прокрутки, доступна с клавиатуры, поля имеют подписи, ошибки озвучиваются
  через live region.
- REQ-011: Пользовательский чат по `/`, его HTTP/SSE-поведение и тесты не
  изменяются; ограничение доступа к чату для гостей не входит в это изменение.
- REQ-012: Контракт описан на новой странице `docs/auth.md`, а каталог
  `docs/README.md` и `frontend/README.md` ссылаются на неё и на `/login/`.

## Сценарии

### Регистрация

- Given гость открыл `/login/` и выбрал «Регистрация»
- When он вводит свободный корректный логин, пароль и совпадающее
  подтверждение и отправляет форму
- Then frontend отправляет `POST /api/v1/users`, затем `POST /api/v1/auth/login`
- And после `200` перенаправляет на `/`

### Логин занят

- Given логин уже зарегистрирован
- When гость отправляет форму регистрации
- Then backend отвечает `409`
- And страница показывает «Этот логин уже занят», логин сохранён, пароль очищен

### Вход с неверным паролем

- Given гость в режиме «Вход»
- When backend отвечает `401`
- Then показывается «Неверный логин или пароль» без уточнения, что именно
  неверно

### Некорректные поля

- Given логин из двух символов или пароль короче восьми символов
- When гость отправляет форму
- Then запрос не отправляется, а ошибка показывается у поля

### Уже вошедший пользователь

- Given у браузера есть действительная сессия
- When пользователь открывает `/login/`
- Then `GET /api/v1/users/me` возвращает `200` и страница перенаправляет на `/`

### Backend ещё не реализован или недоступен

- Given `/api/v1/users/me` отвечает `404` или запрос не проходит
- When гость открывает `/login/` и отправляет форму
- Then форма доступна, а при отправке показывается «Сервис временно
  недоступен», без зависания в состоянии загрузки

## Технологии и структура

Изменение остаётся в vanilla JavaScript frontend без новых зависимостей:

- `frontend/src/login/index.html`, `login.css`, `login.js` — страница `/login/`;
- `frontend/src/auth-api.js` — клиент контракта по образцу `agent-api.js`
  с внедряемым `fetch`;
- `frontend/vite.config.js` — multi-page build с entry `/login/`;
- `frontend/tests/auth-api.test.js`, `frontend/tests/login-ui.test.js` — Node-
  тесты с fake `fetch` и fake DOM;
- `frontend/tests/proxy-smoke.mjs` — проверка, что `/login/` отдаётся dev
  server;
- `docs/auth.md`, `docs/README.md`, `frontend/README.md` — контракт и описание.

Backend, Docker Compose, Caddy и Nginx не меняются: Caddy уже направляет
`/api/*` в backend, а остальные пути — в Nginx.

## Команды

- Запуск: `make run`
- Frontend dev server: `make frontend`
- Frontend-тесты: `npm --prefix frontend test`
- Production-сборка: `npm --prefix frontend run build`
- Полная проверка: `make test`

## Границы

- Всегда: следовать контракту из этой спецификации; держать пароль только в
  поле формы до отправки; использовать относительные адреса на том же origin;
  не ломать пользовательский чат.
- Сначала спросить: менять контракт (пути, поля, коды); закрывать чат для
  гостей; добавлять кнопку выхода или имя пользователя в чат; добавлять другие
  изображения; добавлять зависимости.
- Никогда: хранить пароль или сессию в JavaScript-хранилищах; использовать
  JWT в `localStorage`; добавлять CORS или cross-origin URL; реализовывать или
  изменять backend в рамках этого изменения; копировать во frontend или docs
  текст учебных заданий.

## Критерии приёмки

- [ ] `/login/` открывается из того же production build, `/` продолжает
  открывать чат.
- [ ] Вход и регистрация отправляют запросы строго по контракту и
  перенаправляют на `/` после успеха.
- [ ] Ошибки `401`, `409`, `422`, сетевой сбой и отсутствие backend дают
  понятные сообщения без зависания формы.
- [ ] Пароль и сессия не попадают в JavaScript-хранилища, URL и консоль.
- [ ] Страница визуально узнаётся как часть сайта рядом с чатом.
- [ ] На контрольных viewport нет горизонтального overflow, форма доступна с
  клавиатуры.
- [ ] `docs/auth.md` описывает контракт, каталог и frontend README ссылаются на
  него.
- [ ] `npm --prefix frontend test`, proxy smoke, production build и `make test`
  проходят успешно.

## Открытые вопросы

- Контракт должен подтвердить участник, реализующий backend. До его согласия
  пути, поля и коды ответов считаются предложением.
- Закрытие чата для гостей, кнопка выхода и защита `/admin/` по роли
  выполняются отдельными изменениями после появления backend.
