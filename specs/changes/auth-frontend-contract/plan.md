# План: страница авторизации и контракт API аутентификации

Спецификация: [spec.md](./spec.md).

## Порядок

Сначала фиксируется контракт и клиент без DOM, затем подключается отдельная
Vite-страница, после чего добавляются поведение формы, стилистика и
документация. Рискованное предположение — multi-page build не затрагивает
пользовательский чат — проверяется в первой задаче.

## Задача 1. Multi-page entry `/login/`

**Требования:** REQ-001, REQ-011.

**Критерии приёмки:** `npm --prefix frontend run build` создаёт
`dist/index.html` и `dist/login/index.html`; dev server отдаёт `/` и `/login/`;
тесты чата проходят без изменений.

**Зависимости:** нет.

**Файлы:**

- `frontend/vite.config.js`;
- `frontend/src/login/index.html` — минимальный каркас страницы;
- `frontend/tests/proxy-smoke.mjs`.

**Проверка:**

```sh
npm --prefix frontend run test:proxy
npm --prefix frontend run build
npm --prefix frontend test
```

## Задача 2. Клиент контракта `AuthApi`

**Требования:** REQ-004, REQ-009.

**Критерии приёмки:** `register`, `login`, `logout` и `me` отправляют метод,
путь, заголовки и тело строго по контракту; успешные ответы возвращают
проверенный объект пользователя; `401`, `409`, `422`, прочие статусы,
некорректный JSON и сетевой сбой дают стабильные коды `AuthApiError`; клиент не
обращается к storage.

**Зависимости:** нет.

**Файлы:**

- `frontend/src/auth-api.js`;
- `frontend/tests/auth-api.test.js`.

**Шаги:**

1. Сначала добавить падающие Node-тесты с fake `fetch`.
2. Реализовать клиент по образцу `agent-api.js` с внедряемым `fetchImpl`.

**Проверка:**

```sh
npm --prefix frontend test
```

## Задача 3. Поведение страницы входа и регистрации

**Требования:** REQ-002, REQ-003, REQ-005–REQ-009.

**Критерии приёмки:** переключение режимов меняет поля и `aria-selected`;
клиентская валидация блокирует запрос и показывает ошибку у поля; регистрация
вызывает `register`, затем `login`, затем redirect на `/`; ошибки дают
согласованные тексты, логин сохраняется, пароль очищается; во время запроса
форма заблокирована; `200` от `me` при загрузке перенаправляет на `/`;
динамический текст вставляется без `innerHTML`.

**Зависимости:** задачи 1 и 2.

**Файлы:**

- `frontend/src/login/index.html`;
- `frontend/src/login/login.js`;
- `frontend/tests/login-ui.test.js`.

**Шаги:**

1. Сначала добавить падающие DOM-тесты с fake DOM, fake `AuthApi` и
   внедряемой функцией redirect.
2. Реализовать `mountLogin(document, { api, navigate })` без глобального
   состояния, вызываемый из модуля страницы.

**Проверка:**

```sh
npm --prefix frontend test
```

## Задача 4. Стилистика сайта и адаптивность

**Требования:** REQ-010, REQ-013.

**Критерии приёмки:** страница использует тёмную ночную тему чата, kicker,
заголовок с розовым акцентом, сцену со звёздами и полянкой, карточку формы в
стиле панели чата, chips-переключатель, розовую кнопку и групповое
изображение Смешариков с облачком «Привет! Заходи, будем сочинять истории!»;
на desktop изображение рядом с формой, на mobile — уменьшено над формой; нет
горизонтальной прокрутки, focus заметен; `smeshariki.png` уменьшен примерно
до ширины `1200px`.

**Зависимости:** задача 3.

**Файлы:**

- `frontend/src/login/login.css`;
- `frontend/src/login/index.html`;
- `frontend/src/static/characters/smeshariki.png`.

**Проверка:** визуальное ревью рядом с `/` в браузере на viewport `320x568`,
`375x667`, `768x1024`, `1440x900`, `1920x1080`; production build.

## Задача 5. Документация контракта

**Требования:** REQ-012.

**Критерии приёмки:** `docs/auth.md` описывает четыре метода, правила полей,
сессионную cookie и границу ответственности frontend/backend; `docs/README.md`
ссылается на страницу и содержит строку компонента; `frontend/README.md`
описывает `/login/` и структуру файлов.

**Зависимости:** задачи 1–4.

**Файлы:**

- `docs/auth.md`;
- `docs/README.md`;
- `frontend/README.md`.

**Проверка:** ревью документации без автоматических тестов структуры; затем
полный `make test`.
