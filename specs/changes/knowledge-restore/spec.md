# Восстановление знаний из журнала ревизий

## Цель

Замкнуть цикл обслуживания знаний: после `delete` автор может восстановить
удалённую сущность или вернуть одну из её прошлых версий из append-only журнала
`rag_revisions`, не заглядывая в PostgreSQL вручную. Снимок ревизии уже
хранится в формате файла пакета, поэтому восстановление переиспользует доменные
модели, правила целостности и обычную запись новой ревизии.

## Допущения

- Ревизии append-only; `Revision.payload` — снимок агрегата в формате файла
  пакета, `format_version` — версия этого формата.
- Поддерживается только текущая `KNOWLEDGE_FORMAT_VERSION`. Снимок другой
  версии отвергается с `unsupported_revision_format`; конвертация старых
  версий — отдельное изменение.
- За одна команда восстанавливается одна сущность. Массовое восстановление не
  вводится: его можно собрать снаружи из нескольких вызовов.
- Без `--revision` берётся последняя ревизия сущности, включая снимок
  `delete`. `--revision N` выбирает точный номер.
- `restore` по умолчанию делает dry-run; запись требует `--apply`. Это
  согласуется с `delete` и защищает от случайного отката.
- Восстановление — это `create`, если сущности нет, `update`, если она есть.
  Если выбранный снимок равен текущей сущности, ничего не пишется, но операция
  журналируется как `restore` с `unchanged=1`.
- `rag_loads.operation` получает значение `restore` миграцией `0011`;
  `rag_revisions.operation` по-прежнему использует `create`/`update`/`delete`.
- Команда доступна только через CLI; HTTP API и инструмент агента не
  добавляются.
- Новых зависимостей нет.

## Требования

### CLI и выбор ревизии

- REQ-001: CLI: `python -m smeshariki_ai.rag restore <type>/<id>
  [--revision N] [--apply] [--format text|json]`. Тип — имя каталога пакета,
  `id` — slug; `--revision` — целое `>= 1`. Одна ссылка за вызов; неверные
  аргументы — код `2`.
- REQ-002: Без `--revision` выбирается последняя ревизия сущности, включая
  `delete`. Если ревизий нет или запрошенный номер отсутствует — ошибка
  `revision_not_found`, запись не выполняется.
- REQ-003: Без `--apply` выполняется dry-run: читается снимок текущих знаний и
  история ревизий через read-only операции, проверяется план, но БД и журналы
  не меняются. Код `0` — план допустим, `1` — восстановление невозможно;
  `restored=false`, `operation_id=null`.
- REQ-004: `--apply` повторяет выбор и проверки в одной транзакции под advisory
  lock загрузки; план dry-run не переиспользуется без повторной проверки.

### Разбор снимка

- REQ-005: Снимок разбирается моделью типа сущности из `ENTITY_KINDS`;
  `id` снимка должен совпадать с запрошенной ссылкой. Ошибка разбора или
  несовпадение `id` дают `revision_invalid` без текста payload.
- REQ-006: `format_version` ревизии должен совпадать с
  `KNOWLEDGE_FORMAT_VERSION`; иначе `unsupported_revision_format`. Снимок
  ошибочной или неподдерживаемой ревизии не применяется.

### Проверка и запись

- REQ-007: Восстановленная сущность заменяет текущую с тем же типом и `id` в
  полном наборе знаний; к объединению применяется
  `check_integrity(complete=True)`. Нарушения ссылок и правил домена отменяют
  восстановление с адресами `db:<каталог>/<id>`.
- REQ-008: Если сущности не было, изменение — `create`; если была и отличается
  — `update`; если равна снимку — `unchanged`. В журнал `rag_revisions`
  добавляется ревизия только для `create`/`update`, номер — следующий после
  максимального; снимок payload сохраняется в текущем формате.
- REQ-009: `rag_loads` получает строку `operation=restore` с временем начала и
  окончания, длительностью, числом сущностей после операции и счётчиками
  `added`/`updated`/`unchanged`. Dry-run и отказ строку не создают.
- REQ-010: Восстановление атомарно: при ошибке БД, нарушении целостности или
  отмене не остаётся изменённых строк, новых ревизий и записи журнала.

### Порт и хранилища

- REQ-011: Порт `KnowledgeStore` получает
  `revision_history(ref) -> tuple[Revision, ...]` — историю одной сущности без
  advisory lock загрузки. PostgreSQL читает её в read-only снимке одним
  запросом; in-memory возвращает состояние процесса. Оба адаптера проходят
  общий контрактный набор.
- REQ-012: `JournalOperation` и `LoadRecord.operation` допускают `restore`;
  `tables.py` и миграция `0011` обновляют check
  `rag_loads.operation IN ('load','delete','restore')`. `downgrade` переводит
  существующие `restore` в `load`, чтобы старый check снова применялся.
- REQ-013: Ошибки хранилища переводятся в существующие безопасные типы; текст
  SQL, параметров и содержимого снимков наружу и в журнал не попадает.

### Отчёт, Make и наблюдаемость

- REQ-014: `RestoreReport` содержит `restored`, `operation_id`, `revision`,
  `counts`, `entity_count`, `duration_ms`, `issues`. Текстовый вывод печатает
  план или итог по-русски; `--format json` печатает один JSON-документ. Коды
  возврата: `0` — успех или допустимый dry-run, `1` — отказ или ошибка,
  `2` — неверные аргументы.
- REQ-015: Ошибки конфигурации, БД, схемы и повреждённых данных дают
  `configuration_error`, `database_unavailable`, `schema_not_ready`,
  `stored_data_invalid`; отсутствующая ревизия — `revision_not_found`;
  невалидный или неподдерживаемый снимок — `revision_invalid` /
  `unsupported_revision_format`. Отчёт не содержит payload и содержимого
  сущностей.
- REQ-016: `make knowledge-restore REF=<type>/<id> [REVISION=N] [APPLY=1]
  [FORMAT=json]` выполняет команду в Compose-сервисе `migrate`, не применяет
  миграции автоматически и печатает в stdout только отчёт. Без `REF` —
  подсказка и код `2`; без `APPLY=1` — dry-run.
- REQ-017: Каждый вызов пишет событие `rag.restore.completed` с `outcome`
  (`restored`, `dry_run`, `rejected`, `failed`), `entity_count`, `duration_ms`
  и при необходимости `reason` или `error_type`. `id`, номер ревизии и
  содержимое знаний в журнал не попадают.
- REQ-018: `docs/rag.md` описывает команду и восстановление; `docs/knowledge.md`
  — снимок ревизии, операцию `restore` и `rag_loads.operation`;
  `docs/database.md` — миграцию `0011`; `docs/logging.md` — событие;
  `docs/README.md` и раздел «Реализованный каталог знаний» `AGENTS.md`
  получают строки о восстановлении. Изменения общих файлов аддитивные.
- REQ-019: Тесты покрывают выбор ревизии, разбор снимка, dry-run, применение,
  отказ по целостности, журнал и ревизии, CLI, Make и PostgreSQL. `make lint`,
  `make test` и `make test-integration` проходят.

## Сценарии

### Восстановление удалённого эпизода

- Given эпизод `e1` удалён, в `rag_revisions` остались ревизии `create` и
  `delete` со снимком
- When выполняется `restore episodes/e1 --apply`
- Then эпизод снова в БД, добавлена ревизия `create`, в `rag_loads` —
  операция `restore` с `added=1`

### Возврат прошлой версии

- Given у персонажа `pin` есть ревизии `1` и `2`
- When выполняется `restore characters/pin --revision 1 --apply`
- Then в БД версия из ревизии `1`, добавлена ревизия `update` с номером `3`

### Ревизия не найдена

- Given у сущности нет ревизии `7`
- When выполняется `restore characters/pin --revision 7 --apply`
- Then отчёт содержит `revision_not_found`, БД не изменена

### Невалидный снимок

- Given payload ревизии не проходит доменную модель
- When выполняется restore
- Then отчёт содержит `revision_invalid`, payload не показан, БД не изменена

### Неподдерживаемая версия

- Given ревизия записана в формате будущей версии
- When выполняется restore
- Then отчёт содержит `unsupported_revision_format`, БД не изменена

### Нарушение ссылок

- Given снимок ссылается на отсутствующую сущность
- When выполняется restore
- Then `check_integrity` возвращает `unknown_reference` по адресу `db:`,
  восстановление отменено

### Снимок совпадает с текущим

- Given сущность уже равна выбранной ревизии
- When выполняется `restore ... --apply`
- Then новых ревизий нет, в `rag_loads` — `restore` с `unchanged=1`

### Миграция операции

- Given в `rag_loads` есть строки `load` и `delete`
- When применяется `0011`
- Then допустима операция `restore`, старые строки читаются без изменений;
  `downgrade` переводит `restore` в `load`

- `python -m smeshariki_ai.rag restore <type>/<id> [--revision N] [--apply] [--format text|json]`

## Границы

- Всегда: проверять снимок и целостность до записи; выполнять применение в
  одной транзакции; сохранять новую ревизию только при изменении; использовать
  синтетические данные; не логировать содержимое знаний.
- Сначала спросить: поддержку старых версий формата; массовое восстановление;
  изменения других модулей; правки `AGENTS.md`, `Makefile`,
  `observability.py` сверх аддитивных строк.
- Никогда: применять payload без валидации; восстанавливать без проверки
  ссылок; удалять или переписывать журналы; добавлять HTTP API или инструмент
  агента.

## Критерии приёмки

- [ ] `restore` выбирает последнюю или указанную ревизию и работает в режиме
      dry-run и `--apply`.
- [ ] Восстановленная сущность проходит проверку целостности; при нарушении
      БД не меняется.
- [ ] Создаётся новая ревизия `create`/`update`, журнал получает
      `operation=restore`.
- [ ] Невалидный и неподдерживаемый снимок отвергаются без раскрытия payload.
- [ ] `revision_history` реализован для обоих хранилищ и не берёт advisory
      lock загрузки.
- [ ] Миграция `0011` допускает `restore`, `downgrade` безопасен.
- [ ] Отчёт и журнал не содержат содержимого знаний.
- [ ] Документация обновлена, diff общих файлов аддитивный.
- [ ] `make lint`, `make test` и `make test-integration` проходят.

## Открытые вопросы

- Нет. Решения зафиксированы в допущениях: одна сущность за вызов, dry-run по

  `restore` в журнале через миграцию `0011`, Make без автомиграций.
