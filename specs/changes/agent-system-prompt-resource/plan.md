# План: системный промпт агента как версионируемый ресурс

## Основание

План реализует одобренную [`spec.md`](./spec.md) поверх завершённых изменений
`agent-runtime` и `backend-config`. Существующий текст системного промпта
сохраняется без смыслового изменения; меняются его источник, упаковка и
environment-контракт.

Перед планированием выполнены `make test` и `make lint`: проходят 125 тестов,
Ruff не находит нарушений. Это базовая точка для реализации.

## Решения и зависимости

### Владение и формат resource

Production-промпт размещается в
`smeshariki_ai/agent/prompts/system.md`. Каталог `prompts` становится Python
subpackage с узким API `load_system_prompt()`, поэтому ресурс принадлежит
агенту, но сам `Agent` не знает о файловой системе.

Загрузчик использует `importlib.resources.files`, читает UTF-8 и удаляет только
краевые пробельные символы. Относительные пути и зависимость от текущей рабочей
директории не используются. Если ресурс отсутствует, не читается или после
нормализации пуст, загрузчик поднимает безопасную доменную ошибку без fallback
на встроенную строку или environment.

### Сборка конфигурации

`load_config` вызывает `load_system_prompt()` и передаёт результат в прежнее
поле `AgentConfig.system_prompt`. `AgentConfig` и конструктор `Agent` не
меняются. Значение `AGENT_SYSTEM_PROMPT` больше не читается даже при его
наличии во входном mapping; все остальные правила environment-загрузки
сохраняются.

Загрузка resource выполняется при каждой явной сборке `Config`, без
module-level singleton и кэширования. В штатном entrypoint это по-прежнему один
вызов при старте процесса.

### Упаковка и Docker

Markdown-файл хранится внутри импортируемого пакета. Hatchling должен включить
его в wheel без отдельного runtime-монтирования. Это будет проверено сборкой
wheel во временный каталог и просмотром архива.

Docker Compose больше не передаёт `AGENT_SYSTEM_PROMPT`, а `.env.example` не
предлагает его пользователю. Образ получает промпт вместе с установленным
Python-пакетом.

## Порядок реализации

1. Через TDD добавить безопасную загрузку package resource.
2. Подключить resource к корневому config и удалить env/Docker override.
3. Обновить архитектурную документацию и правила проекта.
4. Выполнить полную регрессионную проверку и проверить состав wheel.

Первые две задачи закрывают основные риски: независимость от CWD, fail-fast для
некорректного resource и невозможность незаметного production override.

## Задача 1. Добавить загрузчик системного промпта

**Связанные требования:** REQ-001–REQ-003, REQ-005.

**Критерии приёмки:** непустой Markdown-resource читается в UTF-8 через package
API независимо от CWD; внешние пробельные символы не входят в итоговый prompt;
пустой, отсутствующий или нечитаемый resource приводит к безопасной
контролируемой ошибке; `Agent` и `AgentConfig` не получают файловой логики.

**Зависимости:** нет.

**Файлы:**

- `backend/src/smeshariki_ai/agent/prompts/__init__.py`;
- `backend/src/smeshariki_ai/agent/prompts/system.md`;
- `backend/tests/unit/agent/test_prompts.py`.

**Действия (RED → GREEN → REFACTOR):**

1. Написать падающие поведенческие тесты успешной загрузки, независимости от
   CWD и отклонения пустого текста.
2. Определить безопасный тип ошибки resource и `load_system_prompt()` на базе
   `importlib.resources.files`.
3. Добавить Markdown-resource с текущим production-текстом
   `You are a helpful Smeshariki assistant.`.
4. Добавить ветви безопасной ошибки для отсутствующего или нечитаемого
   resource без включения содержимого промпта в сообщение.
5. Проверить, что изменения не затронули runtime и модели агента.

**Тест:**

```sh
uv run --project backend --locked pytest backend/tests/unit/agent/test_prompts.py
```

## Задача 2. Подключить resource к Config и удалить env override

**Связанные требования:** REQ-002–REQ-006.

**Критерии приёмки:** `load_config` всегда получает production-промпт через
package loader; `AGENT_SYSTEM_PROMPT` не влияет на результат и отсутствует в
Compose и `.env.example`; `AGENT_MAX_ITERATIONS` и LLM-параметры ведут себя как
раньше; ошибка resource возникает до создания приложения.

**Зависимости:** задача 1.

**Файлы:**

- `backend/src/smeshariki_ai/config.py`;
- `backend/tests/unit/test_backend_config.py`;
- `docker/compose.yaml`;
- `docker/.env.example`.

**Действия (RED → GREEN → REFACTOR):**

1. Изменить config-тесты так, чтобы default ожидался от prompt loader, а
   переданный `AGENT_SYSTEM_PROMPT` не мог заменить production-текст.
2. Добавить тест делегирования загрузчику и распространения контролируемой
   ошибки до bootstrap.
3. Заменить встроенную строку и чтение `AGENT_SYSTEM_PROMPT` вызовом
   `load_system_prompt`, сохранив сборку immutable `AgentConfig`.
4. Удалить переменную из environment-секции Compose и `.env.example`.
5. Поиском проверить отсутствие активных чтений `AGENT_SYSTEM_PROMPT` и
   файловой логики в `Agent`.

**Тест:**

```sh
uv run --project backend --locked pytest backend/tests/unit/test_backend_config.py backend/tests/unit/test_bootstrap.py
```

## Задача 3. Документировать новый источник промпта

**Связанные требования:** REQ-003, REQ-004, REQ-007.

**Критерии приёмки:** документация конфигурации показывает package resource
как источник системного промпта и больше не объявляет env override; документация
агента описывает границу загрузки; `AGENTS.md` фиксирует реализованное правило
для будущих изменений.

**Зависимости:** задачи 1–2, чтобы документация описывала фактический код.

**Файлы:**

- `docs/configuration.md`;
- `docs/agent.md`;
- `AGENTS.md`.

**Действия:**

1. Обновить схему потока конфигурации, таблицу environment и описание
   источников в `docs/configuration.md`.
2. Дополнить `docs/agent.md` расположением resource и границей ответственности:
   загрузчик собирает config, runtime использует готовый текст.
3. Закрепить реализованный контракт версионируемого production-промпта в
   `AGENTS.md`, не копируя полную спецификацию.
4. Проверить ссылки и соответствие документации фактическим именам вручную; не
   добавлять тесты структуры или текста документации.

**Проверка:** ревью изменённых страниц, `rg "AGENT_SYSTEM_PROMPT"` и
`git diff --check`.

## Задача 4. Полная проверка реализации и дистрибутива

**Связанные требования:** REQ-001–REQ-007.

**Критерии приёмки:** все продуктовые тесты проходят; Ruff не находит
нарушений; wheel содержит `smeshariki_ai/agent/prompts/system.md`; поиск не
обнаруживает поддерживаемого env override; diff соответствует спецификации.

**Зависимости:** задачи 1–3.

**Файлы:** изменения не планируются; исправления возвращаются в задачу,
нарушившую проверку. Wheel собирается только во временный каталог.

**Проверка:**

```sh
make test
make lint
git diff --check
uv build --project backend --wheel --out-dir <temporary-directory>
python -m zipfile -l <temporary-wheel>
```

Дополнительно ревью через `rg` подтверждает, что `Agent` не читает resource или
environment, `load_config` остаётся единственным environment reader, а
`backend/uv.lock` и зависимости не изменились.

## Риски и откат

- Главный packaging-риск — Markdown-файл доступен из checkout, но отсутствует
  в wheel. Поэтому состав собранного дистрибутива проверяется отдельно, а при
  необходимости include-правило Hatchling добавляется в задаче 1.
- Удаление `AGENT_SYSTEM_PROMPT` намеренно прекращает deployment override.
  Существующий локальный `docker/.env` может содержать устаревшую строку, но
  Compose больше не передаст её backend и миграция данных не требуется.
- Ошибка чтения resource станет fail-fast ошибкой импорта ASGI entrypoint, что
  соответствует спецификации и не требует fallback.
- Откат выполняется атомарным возвратом loader/config/Docker изменений; формат
  данных, HTTP-контракт и история диалогов не меняются.
