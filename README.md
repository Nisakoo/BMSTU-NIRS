# smeshariki-ai

НИРС-проект «Смешарики AI».

## О проекте

«Смешарики AI» — веб-приложение, которое сочиняет новые сказки во вселенной
мультсериала «Смешарики». Пользователь в чате описывает идею: кто из героев
участвует, что происходит, какое настроение у истории. Ассистент пишет
сказку и выводит её по мере сочинения.

Цель — не просто генерировать текст, а сохранять дух оригинала:

- **конфликт без злодеев** — сюжет строится на столкновении характеров,
  недопонимании или разных взглядах на жизнь, а не на борьбе с врагом;
- **узнаваемые герои** — сохраняются возраст, характер и манера речи
  каждого персонажа (Крош, Ёжик, Нюша, Бараш, Лосяш, Пин, Копатыч, Совунья,
  Кар-Карыч);
- **два слоя** — история понятна ребёнку, а взрослый замечает философский
  или ироничный подтекст;
- **тихий светлый финал** — история заканчивается пониманием или принятием,
  без произнесённой морали.


## Структура

- `frontend/` — пользовательский интерфейс;
- `backend/` — API, runtime агента, серверная бизнес-логика и RAG;
- `docker/` — единый контейнерный запуск Caddy, frontend и backend;
- `docs/` — краткий каталог архитектуры, реализации и контрактов;
- `specs/` — спецификации, планы и результаты проверки SDD-изменений.

Основной запуск собирает frontend и поднимает Caddy, Nginx и backend одним
Docker Compose проектом. Агент и RAG входят в состав backend-приложения.

## Команды

- `make run` — сборка и запуск всего приложения через Docker Compose;
- `make frontend` — отдельный Vite dev server при разработке frontend;
- `make test` — запуск frontend-тестов Vitest и backend Pytest;
- `make lint` — проверка Svelte и TypeScript через svelte-check и Python-кода через Ruff;
- `make format` — автоматическое исправление и форматирование Python-кода.

После настройки `docker/.env` приложение доступно на
[`http://localhost:8090/`](http://localhost:8090/), демо-макет панели
администратора — на [`http://localhost:8090/admin/`](http://localhost:8090/admin/), а
страница входа и регистрации — на [`http://localhost:8090/login/`](http://localhost:8090/login/).
Настройки и примеры HTTP-запросов описаны в
[`docker/README.md`](docker/README.md). Backend использует настраиваемый
LiteLLM-провайдер, PostgreSQL для пользователей, истории диалогов и знаний RAG,
а также Redis для аутентификации. RAG предоставляет агенту инструмент
`lookup_knowledge`, а знания загружаются, выгружаются и удаляются командами из
корня репозитория.

## Как повторить проверку (бенчмарк RAG)

Проверка поискового движка воспроизводится на закоммиченном наборе: ничего
расшифровывать и поднимать не нужно, БД и доступ к модели не требуются.

- **Корпус:** 30 документов с идентификаторами `d01…d30` —
  [`backend/tests/fixtures/lore_benchmark/lore/`](backend/tests/fixtures/lore_benchmark/lore/).
- **Вопросы:** 10 обычных (у каждого три релевантных документа и эталонный
  ответ) и 5 ловушек без ответа в корпусе —
  [`questions.yaml`](backend/tests/fixtures/lore_benchmark/questions.yaml).
- **Ответы для офлайн-проверки:**
  [`answers.json`](backend/tests/fixtures/lore_benchmark/answers.json).

```sh
make benchmark          # детерминированный прогон, k=5
make benchmark K=3      # другая глубина
```

Ожидаемый вывод на этом наборе (эталон, зафиксирован в
[`docs/benchmark.md`](docs/benchmark.md)):

```text
Документов: 30; вопросов: 15 (обычных 10, ловушек 5); k=5.
Recall@5: 0.867
MRR@5: 1.000
Accuracy: 0.900
Correct Rejection Rate: 1.000
```

Что важно понимать:

- `Recall@k` и `MRR` измеряют **поиск**; `Accuracy` и
  `Correct Rejection Rate` проверяют ответы (в офлайн-режиме — файл
  `answers.json`, а не живую модель);
- ловушки в метрики поиска не входят;
- вопросы сформулированы своими словами, а не копируют фрагменты документов;
- реальный корпус команды (84 эпизода) лежит в `data/` в репозитории:
  команда для него и полученные метрики — в [`docs/benchmark.md`](docs/benchmark.md).

Живая демонстрация RAG (вопрос → поиск → LLM → ответ) требует `LLM_API_KEY` в
`docker/.env`: без `--answers` бенчмарк получает ответы у модели. Подробности и
разбор ошибок — в [`docs/benchmark.md`](docs/benchmark.md).

## Озвучка сказок

Для локальной озвучки нужна модель Silero TTS v5 `v5_ru.pt`. Скачайте её с
официального URL и положите в `docker/models/silero/`:

```sh
mkdir -p docker/models/silero
curl -fL https://models.silero.ai/models/tts/ru/v5_ru.pt \
  -o docker/models/silero/v5_ru.pt
```

Файл модели не коммитится и уже исключён в `.gitignore`. Для проверки
SHA-256 можно использовать `docker/fetch-silero.sh`:

```sh
SILERO_MODEL_SHA256=<sha256> \
  ./docker/fetch-silero.sh docker/models/silero/v5_ru.pt
```

После этого установите `SPEECH_ENABLED=true` в `docker/.env` и запустите
`make run`. Если модель пока не нужна, оставьте `SPEECH_ENABLED=false`.
Подробности — в [`docs/audio.md`](docs/audio.md).
