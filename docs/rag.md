# RAG

[← Глобальный каталог](./README.md)

RAG даёт агенту канонические знания о вселенной «Смешариков». Первая очередь —
структурированные знания: сущности со строгой схемой и их точный поиск. Поиск
по неструктурированному лору (сюжеты, сценарии) — следующая очередь.

Состояние: реализованы формат и проверка пакетов, хранилище в PostgreSQL,
загрузка, выгрузка, удаление с проверкой ссылок, восстановление из ревизий,
оптимистичная блокировка загрузки по ревизиям, нечёткие подсказки имён через
`pg_trgm`, инструмент агента `lookup_knowledge`, компактный `get_story_canon`
без предметов в профиле и BM25-поиск по лору (ядро, PostgreSQL-индекс,
загрузка, CLI, precision-фильтр контекста и benchmark на реальном корпусе).

## Назначение и границы

- RAG — модуль backend-монолита в пакете `smeshariki_ai.rag`, а не отдельный
  сервис. Публичного HTTP API нет.
- Агент получает RAG только через инструменты — наследники `agent.tools.Tool`,
  которые регистрируются в composition root (`bootstrap.py`). Инструмент
  точного поиска — `lookup_knowledge`. Когда его вызывать, модель узнаёт из
  описания инструмента; system prompt агента RAG не меняет.
- Выделение RAG в микросервис возможно в будущем. Правила изоляции ниже
  делают его дешёвым, но HTTP API заранее не создаётся.

```mermaid
    end

    end
    Tool --> UC
    CLI --> UC
    UC --> Domain
    UC --> Port
    Port -.реализует.- PG
    UC --> Files
```

Правило зависимостей:

- домен зависит только от Pydantic;
- use cases зависят от домена и исходящих портов;
- входящие адаптеры вызывают только use cases;
- исходящие адаптеры реализуют порты.

Порт называется по возможности предметной области, а не по технологии, и
вводится только на границе с внешней системой, которую тесты заменяют
fake-реализацией: базой данных, позже LLM и embeddings. Пакет знаний читается
адаптером без отдельного порта: в тестах это временный каталог.

## Технологии

| Используется | Допустимое расширение (отдельным изменением) | Не используется |
| --- | --- | --- |
| PostgreSQL backend — единственное хранилище; PyYAML — разбор пакетов | Встроенный полнотекстовый поиск, `pg_trgm`, `pgvector`, embeddings через LiteLLM | Qdrant и другие отдельные хранилища, локальные файлы индексов, pickle, ML-модели в процессе backend без подтверждения бенчмарком |

## Данные

```mermaid
flowchart LR
    Author["Автор контента<br/>или его агент"] --> Package["Пакет YAML<br/>в data/, вне Git"]
    Package --> Check["check<br/>формат и целостность"]
    Check --> Load["загрузка<br/>правила по всей БД"]
    Load --> PG[("PostgreSQL<br/>таблицы rag_*")]
    PG --> Lookup[lookup_knowledge]
```

- Источник истины — PostgreSQL (таблицы `rag_*`). Знания закрыты: репозиторий
  публичный, поэтому реальные данные попадают в него только зашифрованными, а
  тесты и примеры документации синтетические.
- Рабочая копия закрытых данных (сценарии, пакеты знаний) лежит в
  игнорируемой Git папке `data/`, например пакет — в `data/knowledge/`. В
  репозитории хранится только архив `encrypted/data.enc` (scrypt +
  AES-256-GCM): `make data-encrypt` и `make data-decrypt [FORCE=1]` с общей
  кодовой фразой команды. Порядок работы и запрет агенту касаться фразы —
  skill [`data-crypt`](../.agents/skills/data-crypt/SKILL.md), спецификация —
  [`data-encryption`](../specs/changes/data-encryption/spec.md).
- Знания поступают пакетами YAML-файлов, по одному файлу на сущность. Пакет
  может содержать любое подмножество сущностей; формат описан на странице
  [Модель знаний](./knowledge.md#формат-пакета).
- `check` проверяет пакет без БД: сущность, которой нет в пакете, выводится
  как внешняя ссылка. Загрузка читает знания из БД целиком фиксированным
  числом запросов и применяет к объединению с пакетом те же правила домена.
  Чтение только затронутой окрестности вводится, если этого потребуют метрики.
- Сложные правила целостности проверяет приложение; PostgreSQL дополнительно
  держит ключи и ограничения. Правила в SQL не дублируются.
- Загрузка выполняется в одной транзакции под advisory lock: проверка пакета,
  чтение БД, проверка правил на объединении, запись только новых и изменённых
  сущностей и журнала. При любом нарушении БД не меняется; повторная загрузка
  того же пакета ничего не пишет, кроме записи журнала загрузок.
- Каждая успешная загрузка записывается в `rag_loads`, каждое добавление и
  изменение сущности — в `rag_revisions` со снимком агрегата: так сохраняются
  история и возможность вернуть прежнюю версию. Схема описана на странице
  [Модель знаний](./knowledge.md#физическая-схема).
- Загрузка выполняется отдельной командой, а не при старте backend. Без
  загруженных знаний backend стартует, а инструмент возвращает безопасную
  ошибку «знания недоступны».
- Выгрузка читает знания в `REPEATABLE READ READ ONLY` без advisory lock и
  пишет обычный пакет во временный каталог с последующей атомарной заменой
  назначения. Непустой каталог не перезаписывается, пустая БД — ошибка.
- Удаление сначала проверяет ссылки на полном наборе, затем в одной транзакции
  удаляет дочерние строки и корни и пишет ревизию `delete` со снимком агрегата.
  Журнал `rag_loads` хранит операцию `load` или `delete`; `ChangeCounts`
  содержит счётчик `deleted`. Восстановление — загрузка снимка ревизии,
  отдельной команды restore пока нет.
- Пакет, созданный выгрузкой, содержит необязательные `revisions` в
  `package.yaml`. `load` сравнивает их с текущими ревизиями в той же
  транзакции и при конфликте отменяет весь пакет. Пакеты без `revisions`
  загружаются по прежним правилам.

## Команды

| Команда | Назначение |
| --- | --- |
| `python -m smeshariki_ai.rag check <path> [--format text\|json]` | Проверить пакет без БД и environment. Код `0` — валиден, `1` — невалиден или не найден, `2` — неверные аргументы |
| `python -m smeshariki_ai.rag schema` | Версия формата, JSON Schema `package.yaml` и файлов каждого типа сущностей — подсказка агенту автора |
| `python -m smeshariki_ai.rag load <path> [--format text\|json]` | Проверить пакет и загрузить его в БД; конфиг БД берётся из `load_config`. Код `0` — загружено, `1` — пакет невалиден, нарушена целостность, конфликт ревизий, БД недоступна или схема не готова, `2` — неверные аргументы |
| `python -m smeshariki_ai.rag export <path> [--type TYPE]... [--format text\|json]` | Выгрузить знания в пакет; `--type` можно повторять. Код `0` — выгружено, `1` — ошибка чтения, пустая БД/выборка, непустой каталог или запись, `2` — неверные аргументы |
| `python -m smeshariki_ai.rag delete <type>/<id>... [--apply] [--format text\|json]` | Проверить план удаления; без `--apply` — dry-run. Код `0` — успех или допустимый dry-run, `1` — отказ или ошибка, `2` — неверные аргументы |
| `python -m smeshariki_ai.rag restore <type>/<id> [--revision N] [--apply] [--format text\|json]` | Восстановить сущность из журнала ревизий; без `--revision` берётся последняя, без `--apply` — dry-run. Код `0` — успех или допустимый dry-run, `1` — отказ или ошибка, `2` — неверные аргументы |
| `make knowledge-check DIR=<path>` | `check` из корня репозитория через `uv`; `make` при любой ошибке возвращает собственный код `2` |
| `make knowledge-load DIR=<path> [FORMAT=json]` | Применить миграции и выполнить `load` в Compose-контейнере с окружением из `docker/.env`; пакет монтируется только для чтения. stdout содержит только отчёт `load` (с `FORMAT=json` — один JSON-документ), вывод сборки образа и миграций идёт в stderr |
| `make knowledge-export DIR=<path> [FORMAT=json] [TYPE=<type>]` | Выгрузить знания в существующий пустой каталог; контейнер запускается с UID/GID хоста, миграции не применяются. stdout содержит только отчёт |
| `make knowledge-delete REFS="<type>/<id> ..." [APPLY=1] [FORMAT=json]` | Удалить сущности в Compose; без `APPLY=1` — dry-run. Миграции автоматически не применяются |
| `make knowledge-restore REF=<type>/<id> [REVISION=N] [APPLY=1] [FORMAT=json]` | Восстановить сущность в Compose; без `APPLY=1` — dry-run. Миграции автоматически не применяются |

Команды через Compose требуют заполненного локального `docker/.env`. Когда
появится общая БД, загрузка перейдёт на отдельный конфиг только БД: это
изменение `config.py` и правила `AGENTS.md` по согласованию с владельцем.

## Выгрузка, удаление, восстановление и блокировка

- **`export`** читает `KnowledgeSnapshot`: сущности и текущие ревизии в одном
  read-only снимке. Пакет пишется во временный каталог рядом с назначением и
  заменяет пустой каталог атомарно; непустой каталог и файл отвергаются.
  `--type` оставляет только выбранные каталоги, внешние ссылки допустимы.
- **`delete`** принимает ссылки `characters/pin`. Dry-run строит план на
  read-only снимке, `--apply` повторяет проверку в транзакции под advisory lock.
  Нарушение ссылок отменяет всё удаление; сообщения адресуются как
  `db:<каталог>/<id>`. Удаление множества сущностей сначала убирает дочерние
  строки, затем корни в обратном порядке зависимостей, поэтому взаимные
  отношения не мешают.
- **`restore`** читает историю ревизий через read-only операцию, выбирает
  последнюю или указанную `--revision`, проверяет снимок доменной моделью и
  целостность полного набора. `--apply` пишет `create`/`update` в одной
  транзакции и добавляет операцию `restore` в журнал. Если снимок совпадает с
  текущей сущностью, новая ревизия не пишется. Перед первым использованием
  после обновления выполните `make migrate`: Make-цель не применяет миграции
  автоматически.
- **Ревизии.** Каждое удаление добавляет в `rag_revisions` запись `delete` со
  снимком агрегата. `rag_loads` хранит операцию `load`/`delete`/`restore`; для
  удаления счётчики содержат `deleted`. Журналы не удаляются.
- **Блокировка.** `export` записывает в `package.yaml` поле `revisions`
  (`characters: {pin: 3}`). `load` читает ожидаемые ревизии и текущий индекс в
  одной транзакции; несовпадение, отсутствие сущности или ревизии даёт
  `revision_mismatch`, и пакет не применяется целиком. Пакет без `revisions`
  сохраняет прежнее поведение «последняя запись побеждает».

## Инструмент `lookup_knowledge`

```mermaid
flowchart LR
    Agent["Agent<br/>ToolRegistry"] --> Tool["LookupKnowledgeTool<br/>rag/tools.py"]
    Tool --> UC["KnowledgeLookup<br/>rag/lookup.py"]
    UC --> Port["KnowledgeReader<br/>rag/ports.py"]
    Port -.реализует.- PG["PostgresKnowledgeStore"]
    Port -.реализует.- Mem["InMemoryKnowledgeStore"]
```

- **Аргументы:** `{"name": "<строка 1–200 символов>", "fields": ["speech" | "traits" | "relationships", ...]}`; `fields` необязателен. Лишние поля
  запрещены. Неверные аргументы `ToolRegistry` превращает в
  `invalid_arguments`, хранилище не вызывается. Для персонажа `fields`
  оставляет только запрошенные части карточки: это нужно, чтобы сказка
  запрашивала факт под сцену, а не вываливала всего героя.
- **Поиск точный:** запрос нормализуется `normalize_name` и сравнивается с
  именами и алиасами персонажей, локаций и артефактов, названиями эпизодов
  (`rag_episodes.normalized_title`, миграция `0004`) и slug. Произведения и
  варианты канона не ищутся, а показываются в карточках названиями.
- **Нечёткий fallback:** если точных совпадений нет, а знания загружены,
  `suggest(key)` ищет похожие нормализованные имена, алиасы и названия
  эпизодов через `pg_trgm` (порог `0.3`, до 5 подсказок). In-memory хранилище
  считает триграммное сходство тем же правилом. Slug в fallback не участвует.
  Подсказка содержит только `type`, `id` и каноническое `name`; это не карточка
  и не факт.
- **Порт чтения** `KnowledgeReader`: `find(key)` возвращает найденные
  агрегаты, произведения их эпизодов и названия всех сущностей, на которые
  они ссылаются; `suggest(key, limit)` — компактные подсказки;
  `has_knowledge()` — есть ли завершённая загрузка. PostgreSQL читает в
  транзакции `REPEATABLE READ READ ONLY` без advisory lock загрузки, поэтому
  поиск не ждёт загрузку и видит состояние до неё или после. Число запросов не
  зависит от числа сущностей. Индексы `gin_trgm_ops` создаёт миграция `0012`
  вместе с расширением `pg_trgm`.
- **Ответ:** `status`, `total`, `truncated`, `matches`, `suggestions` и
  `message`.

| `status` | Когда | `message` |
| --- | --- | --- |
| `found` | Есть точные совпадения; в `matches` не больше 10 карточек, `total` — число совпадений | — |
| `not_found` | Точных совпадений нет, знания загружены; `suggestions` может быть непустым | Не выдавать придуманные факты за канон; при подсказках повторить поиск по точному имени |
| `unavailable` | Знаний нет, таблиц `rag_*` нет, БД недоступна или её данные невалидны | Не выдавать придуманные факты за канон |

- **Карточки** (`type` = `character`, `location`, `artifact`, `episode`)
  упорядочены по типу, затем по `id`. Ссылки показаны именами вместо slug,
  `sources` не входят. Персонаж — все версии с названиями вариантов канона,
  характер, `speech_style`, коронные фразы и отношения; локация — описание и
  жители; артефакт — тип, описание, возможности, ограничения и создатели;
  эпизод — произведение и его вариант канона, сезон и номер, участники,
  места, предметы и взаимодействия.
- **Журнал:** каждый вызов пишет `rag.lookup.completed` с `outcome`,
  `match_count`, `suggestion_count`, длительностью, а при `unavailable` —
  `error_type` (ошибка хранилища, уровень `WARNING`) или
  `reason=not_loaded`. Текст запроса, подсказки и содержимое карточек в журнал
  не попадают.
- **Подключение:** `build_agent_service` принимает необязательный
  `knowledge_reader` и регистрирует `lookup_knowledge` как единственный
  production-инструмент. `create_application` передаёт
  `PostgresKnowledgeStore` на общем engine;
  без него (явный `auth_service`, вызов по умолчанию) используется пустой
  `InMemoryKnowledgeStore`, и инструмент отвечает `unavailable`. Модули RAG
  импортируются напрямую: пакет `rag` ничего не реэкспортирует, чтобы CLI не
  загружал агент и LiteLLM.

## Компактный `story-canon`

`lookup_knowledge` — полный фактический канон. Для сказки он слишком широк:
возвращает свободные описания отношений, которые могут тянуть в сюжет
конкретные предметы и эпизоды. Поэтому добавлен отдельный read model
`StoryCanonLookup` и инструмент `get_story_canon`.

- вход: 1–3 имени и необязательный `continuity` (по умолчанию `classic`);
- выход: имя, вид, возрастная группа, черты характера, манера речи, коронные
  фразы, примеры реплик, «так не говорит», роль в сюжете, устойчивые динамики
  с другими героями и отношения `to` + `type`;
- **не выходят**: свободные описания отношений, `sources`, локации,
  артефакты, эпизоды и `interests`;
- трейты, в которых назван артефакт или локация, отбрасываются: профиль
  остаётся ограничением на голос и характер, а не списком предметов;
- если у героя нет версии в запрошенном варианте канона, версия другого
  канона не подставляется;
- `StoryCanonLookup` читает через тот же `KnowledgeReader`, схема БД и
  миграции расширены миграцией `0016`; для отсева предметов reader отдаёт
  канонические имена артефактов и локаций.

`get_story_canon` используется для персонажей сказки, `lookup_knowledge` — для
фактических вопросов, `search_lore` — для нарративного тона. Профиль героя —
ограничение на характер и речь, а не сюжетный список.

## Поиск по лору (BM25)

Лор — отдельный слой RAG для нарративных фрагментов: сценариев, описаний
эпизодов и сюжетных заготовок. Он не заменяет структурированный канон:
`lookup_knowledge` по-прежнему отвечает за точные факты, а BM25 даёт агенту
примеры тона и сюжетных ходов.

```mermaid
flowchart LR
    Package["YAML-пакет лора<br/>data/lore/"] --> Check["lore-check"]
    Check --> Load["lore-load"]
    Load --> PG[("PostgreSQL<br/>rag_lore_*")]
    PG --> Index["PostgresBm25Index"]
    Index --> Search["SearchLore"]
    Search --> CLI["lore-search / CLI"]
    Memory["InMemoryBm25Index"] -. тесты и benchmark .-> Search
```

- Реализация — пакет [`rag/lore/`](../backend/src/smeshariki_ai/rag/lore/);
  подробности формата, формулы, чанкования и таблиц — на странице
  [BM25-поиск по лору](./lore.md).
- Production-индекс хранится в PostgreSQL: postings, `df`, `n_chunks` и
  `avgdl` лежат в `rag_lore_*`, а BM25 считается одним set-based SQL-запросом.
  Корпус не загружается в память backend.
- In-memory индекс используется только для тестов и benchmark и проходит тот
  же контракт, что PostgreSQL-адаптер.
- Лемматизация — `pymorphy3`; `SimpleAnalyzer` остаётся для сравнения. Оба
  анализатора удаляют стоп-слова (`rag/lore/stopwords.py`), поэтому документ и
  запрос фильтруются одинаково; после изменения анализа индекс перезагружается
  `make lore-load`.
- Запрос перед поиском можно расширить ключевыми словами LLM
  (`QueryExpander` и `LiteLLMQueryExpander` в `rag/lore/expansion.py`); флаг
  `RAG_QUERY_EXPANSION_ENABLED`, по умолчанию выключен. Режим
  `RAG_QUERY_EXPANSION_MODE`: `replace` (по умолчанию) ищет только по
  ключевым словам, `append` добавляет их к вопросу. При сбое модели поиск идёт
  по исходному запросу; результат кэшируется. Параметры окна и бюджета
  контекста задаются `RAG_LORE_*`.
- Кандидатов можно переранжировать LLM перед сборкой контекста: порт `Ranker`
  и `LLMReranker` (`rag/lore/rerank.py`), флаг `RAG_LORE_RERANK_ENABLED`
  (по умолчанию выключен). Сырое ранжирование улучшается, контекст агента —
  нет (см. [страницу лора](./lore.md#реранкинг-кандидатов)).
- Команды: `lore-check`, `lore-clean`, `lore-load`, `lore-search`,
  `lore-benchmark`, `knowledge-benchmark` и соответствующие Make-цели.
  `knowledge-benchmark` измеряет точный поиск канона (имена, алиасы, названия
  эпизодов, опечатки, ловушки): `accuracy`, `exact_match_rate`,
  `suggestion_rate`, `false_positive_rate`. `lore-clean` удаляет из
  документов технический мусор экспорта (ссылки на видео) и не трогает
  стилистику. Инструмент агента `search_lore` отдаёт не более
  5 фрагментов, один на документ, до 4800 символов и без score/id. Слабые
  фрагменты отсекает абсолютный `min_score`, а запрос только из имён
  персонажей даёт пустой контекст. Режим `mode` (`any`, `style`, `plot`,
  `facts`) фильтрует документы по `tags`: `style` ищет диалоги и примеры
  голоса, `plot` — сюжетные ходы. Benchmark 30/10/5 считает `Recall@k`,
  `MRR`, `Accuracy` и `Correct Rejection Rate`; флаг `--context` добавляет
  метрики пути `search_lore` — контекстный Recall и долю ловушек, получивших
  пассажи. Отдельный прогон на реальном корпусе и честный golden set описаны
  на [странице лора](./lore.md#реальный-корпус).
- События `lore.search.completed` и `lore.tool.completed` содержат
  `query_term_count`, `hit_count`, `top_score`, `passage_count` и
  `context_chars` без текста запроса и фрагментов.

## Изоляция

- Таблицы RAG имеют префикс `rag_` в схеме `public`, описаны собственным
  `MetaData` в пакете `rag` и не ссылаются на таблицы других модулей: нет
  внешних ключей и `JOIN`. Отдельная схема не используется: тесты других
  модулей пересоздают схему `public` и миграции с нуля.
- Адаптер PostgreSQL находится в пакете `rag`; пакет `db/` других модулей не
  меняется. Миграции RAG — отдельные файлы в общей цепочке Alembic,
  затрагивающие только таблицы `rag_*`.
- Из других модулей RAG импортирует только `agent.tools.Tool` (в
  `rag/tools.py`), `log_event` и `utc_now` из `observability` и общие
  `DatabaseConfig` и `create_engine`.
- Инструмент получает use case `KnowledgeLookup` в конструкторе, аргументы и
  результаты — Pydantic-модели. Отдельный абстрактный интерфейс use case
  появится вместе со второй реализацией: при выделении RAG в сервис
  инструмент получит HTTP-клиент без изменения агента и домена.

## Точки интеграции

В общих файлах RAG только добавляет строки. Изменение существующего чужого
кода или текста решается отдельно с владельцем.

| Файл | Что добавляет RAG | Владелец |
| --- | --- | --- |
| `backend/src/smeshariki_ai/rag/` | Весь код модуля | RAG |
| `docs/rag.md`, `docs/knowledge.md` | Документация модуля | RAG |
| `backend/pyproject.toml`, `backend/uv.lock` | Зависимость PyYAML | Общий |
| `Makefile` | Цели команд знаний | Общий |
| `backend/src/smeshariki_ai/db/migrations/versions/` | Новые файлы миграций таблиц `rag_*`; `0010` — `rag_loads.operation`, `0011` — `restore`, `0012` — `pg_trgm`-индексы | Общий |
| `backend/src/smeshariki_ai/observability.py` | Аддитивные безопасные числовые поля `entity_count`, `deleted_count`, `conflict_count`, `suggestion_count` | Backend |
| `backend/src/smeshariki_ai/bootstrap.py` | Регистрация инструмента; список инструментов задан одной строкой, поэтому её изменение требует решения владельца агента | Агент |
| `backend/src/smeshariki_ai/config.py` | Подконфиг RAG, если понадобится; добавление поля в `Config` требует решения владельца | Backend |
| `docker/compose.yaml` | Не меняется: загрузка запускается в существующем сервисе `migrate` | Общий |
| `docs/README.md`, `AGENTS.md` | Строки каталога и разделы о реализованном RAG | Общий |

## Дальнейшие изменения

1. Поиск по лору: ядро BM25, YAML-пакет, PostgreSQL-индекс, CLI, инструмент
   `search_lore` и benchmark 30/10/5 реализованы. Следующие изменения —
   качество генерации сказок (декодирование, промпт, компактный story canon) и
   развитие поиска по реальному корпусу.
2. Переименование `id`/slug — отдельная спека, только при реальной
   необходимости: идентификаторы объявлены неизменяемыми, а переименование
   требует перезаписи всех ссылок и истории.

Серия `knowledge-maintenance` реализована изменениями `knowledge-export`,
`knowledge-delete`, `knowledge-optimistic-lock`, а цикл восстановления
закрывает `knowledge-restore`. Нечёткие подсказки имён реализует
`knowledge-fuzzy-lookup`.
